FedNAS: Federated Deep Learning via Neural Architecture Search

  2022-09-28 2022-09-28 Created

Paper

FedNAS is a good baseline to read before DFNAS. It takes a DARTS/MiLeNAS-style differentiable NAS method and puts it inside a federated loop: each client updates both network weights and architecture parameters , the server aggregates both, and the process repeats.

The interesting part is that the paper treats NAS as a personalization tool, not only as a way to find one global model. In a non-IID FL setting, two clients may need different local inductive biases even if they start from the same global architecture. FedNAS tries to use architecture search to close that gap.

Motivation

Most FL papers start with a fixed model: ResNet, DenseNet, MobileNet, or another manually selected architecture. That is convenient, but it assumes the model designer already knows a good architecture for all client distributions.

This assumption is weak in federated learning:

  1. The server cannot inspect every client’s local data.
  2. Non-IID clients may have very different label or feature distributions.
  3. Weight-only personalization can adapt the representation, but the network structure is still frozen.

FedNAS asks a simple question: can clients collaboratively search for the architecture itself while keeping data local?

The loop is close to FedAvg, except the communicated state has two parts: operation weights and architecture parameters . Clients search locally, the server merges the client updates, and the merged are synchronized back.

Contribution

The paper’s main contributions are:

  1. It formulates federated NAS as joint optimization over weights and architecture parameters.
  2. It adapts MiLeNAS local search to the FL setting.
  3. It supports both global architecture search and personalized local adaptation.
  4. It implements a distributed AutoFL system on top of FedML/MPI/PyTorch.
  5. It compares personalized FedNAS with local adaptation, Ditto, and perFedAvg under non-IID CIFAR-10 splits.

The method is not trying to invent a new search space. It is more about whether a differentiable NAS loop can survive the communication and heterogeneity constraints of FL.

One important detail: after the search stage, the paper still runs an additional evaluation/training stage with a traditional federated optimizer such as FedAvg. So FedNAS is still closer to a two-stage NAS pipeline than to a direct “search and deploy” method.

Personalized FedNAS

For personalization, the searched global model is not treated as the final model for every client. Each client fine-tunes the received model locally by alternating updates of and . That means personalization happens at both levels:

  • Weight adaptation changes the learned representation.
  • Architecture adaptation changes which operations are preferred locally.

This is the part that makes FedNAS different from many FL personalization baselines, which usually keep the architecture fixed.

Experiments

Setup

The main experiments use CIFAR-10 with non-IID client partitions.

For personalized model search, the paper uses 20 clients and selects 4 clients per round. In the label-skew setting, each client receives images from only five classes, with 3000 images split into 75% training and 25% validation. The paper also evaluates an LDA-style distribution.

The baselines use ResNet18 with 11M parameters. FedNAS uses an 8-layer DARTS cell structure with 4M parameters. This matters when reading the numbers: FedNAS is not only changing the optimizer, it is also changing the architecture and parameter count.

For global model search, the paper uses a cross-silo setup with 16 clients and one server, all on RTX 2080Ti GPUs. Global test accuracy is measured on the 10,000-image CIFAR-10 test set.

Personalized Results

The average local validation accuracy is:

Method Params Label skew acc. LDA acc.
FedNAS 4M 0.913 +/- 0.025 0.907 +/- 0.024
Local Adaptation 11M 0.864 +/- 0.028 0.861 +/- 0.0357
Ditto 11M 0.894 +/- 0.035 0.880 +/- 0.032
perFedAvg 11M 0.888 +/- 0.036 0.894 +/- 0.032

FedNAS is strongest in both reported non-IID settings. On label skew, it is about 4.9 percentage points above local adaptation and 1.9 points above Ditto. The paper also notes that FedNAS has the lowest standard deviation in this table, which is useful because personalized FL can look good on average while failing badly for a subset of clients.

The per-client plots show the same pattern: FedNAS is not better for every single client, but its accuracy distribution is shifted to the right and has fewer low-accuracy clients. The paper reports one client with up to 15 percentage points improvement over perFedAvg, while local adaptation is slightly better on two clients.

Global Results

For global model search, FedNAS is compared with FedAvg on DenseNet under the same fixed non-IID data distribution.

Method Rounds shown Marked test accuracy
FedAvg on DenseNet 100 77.78%
FedNAS 50 81.24%

The paper runs each method three times and tunes hyperparameters for both. The result is a roughly 4 percentage-point gain for the searched FedNAS architecture over the manually designed DenseNet baseline in this setting.

System Efficiency

The distributed efficiency comparison is:

Method Search time Params Hyperparameters
FedAvg distributed 12 hours 20.01M 100 rounds, 20 local epochs, batch size 64
FedNAS distributed < 5 hours 1.93M 50 rounds, 5 local epochs, batch size 64

This table is useful but should not be over-read. FedNAS is faster in this experiment because the searched model is smaller and the schedule uses fewer rounds/local epochs. It does show that the distributed implementation is practical, but it is not a universal proof that NAS is always cheaper than training a manually designed model.

Takeaway

FedNAS is convincing as an early federated NAS baseline because it keeps the algorithm close to FedAvg: local clients update , the server averages , and the process repeats. The personalized results are the most interesting part of the paper, since architecture search gives another axis of adaptation beyond local weight fine-tuning.

The limitations are also clear:

  • The search space is a DARTS/MiLeNAS cell space, not a hardware-aware mobile search space.
  • The method communicates architecture parameters in addition to weights, but does not add privacy protection by itself.
  • The comparison changes both optimization method and architecture size, so gains are not purely from personalization.
  • The final searched architecture still needs an additional evaluation/training stage.
  • The strongest reported evidence in the main text is on CIFAR-10 non-IID splits.

Compared with DFNAS, FedNAS is the more DARTS-like method: it searches a mixed-operation supernet and then evaluates the derived architecture. DFNAS later makes a different engineering tradeoff by using one-path sampling and avoiding the extra retraining stage. So I read FedNAS as the personalization-oriented starting point, and DFNAS as the systems-oriented response to its search cost.
