Paper: HAQ: Hardware-Aware Automated Quantization with Mixed Precision

HAQ is a hardware-aware quantization paper. The central point is simple but important: there is no universal best bit-width allocation for a neural network. The right precision for each layer depends on the accuracy sensitivity of that layer and on the hardware target that will run it.

This paper is from the CNN/mobile-accelerator era, but the lesson transfers directly to modern model deployment. A quantization format is only useful if it maps to the target hardware and kernels. FLOPs, parameter count, and average bit width are proxies. HAQ puts hardware feedback into the search loop.

Motivation

Figure cropped from the paper PDF: mixed precision can dominate fixed 8-bit quantization because different layers tolerate different bit widths.

Uniform quantization is attractive because it is easy to describe: make all weights 8-bit, or all weights 4-bit. But neural networks are not uniform. Some layers are sensitive and need more precision. Some layers are redundant and can tolerate fewer bits. Some layers dominate memory traffic, while others dominate compute.

The important part is the subscript in (C_{\text{hardware}}). The cost model is not generic FLOPs. It is feedback from the deployment hardware or a simulator calibrated to that hardware.

Hardware Dependence

The same MobileNet-V1 quantization policy has different latency on different hardware targets.

Table 1 is the paper’s simplest argument. A policy optimized for one hardware target is not optimal on another. This is exactly why hand-written rules like “use more bits in early layers” or “compress layers with many parameters” are insufficient.

The reason is that hardware cost is shaped by memory hierarchy, parallelism, supported arithmetic, batch size, dataflow, and kernel implementation. A layer that looks expensive in FLOPs can be efficient on one accelerator and awkward on another. A layer with fewer FLOPs can still bottleneck memory traffic.

This is the same conceptual issue behind hardware-aware NAS. Architecture search learned that FLOPs are a poor proxy for latency; HAQ makes the same argument for quantization policy.

HAQ Framework

HAQ overview: an RL agent proposes a quantization policy, the model is quantized, and hardware feedback is returned as part of the reward.

HAQ formulates mixed-precision quantization as a sequential decision problem. The controller visits layers one by one. At each step it observes layer information and emits a bit-width action. After a full policy is sampled, the network is quantized, briefly fine-tuned, evaluated, and scored with a hardware-aware reward.

The loop has four pieces:

  1. A policy generator chooses per-layer bit widths.
  2. The model is quantized according to that policy.
  3. A hardware simulator or feedback path reports latency, energy, or model size.
  4. Validation accuracy and hardware cost determine the reward.

The controller uses DDPG, an actor-critic reinforcement learning method for continuous actions. The continuous action is later mapped into valid integer bit widths. This is not the only possible optimizer, but it was a reasonable tool for searching a large mixed-precision design space at the time.

State, Action, And Reward

The state includes structural information about the current layer: layer index, input/output channels, kernel size, stride, feature-map size, parameter count, and previous action context. This gives the agent enough information to distinguish a depthwise convolution from a pointwise convolution, an early large-feature-map layer from a late compact layer, and a cheap layer from an expensive one.

The action is the precision choice for weights and activations. HAQ can search flexible bit widths instead of forcing a global value.

The reward depends on the deployment objective:

  • For latency-constrained search, the policy should maximize accuracy while meeting a latency budget.
  • For energy-constrained search, the hardware energy estimate enters the objective.
  • For model-size-constrained search, storage replaces latency/energy as the resource.

This is the paper’s main abstraction: quantization is not a single-objective compression problem. It is a constrained deployment optimization problem.

Hardware Configuration

The paper evaluates edge and cloud accelerator configurations with different parallelism and memory resources.

The edge and cloud accelerators differ in batch size, processing-element array size, AXI port width, and block RAM. These differences change the best policy. A small edge device may be memory constrained in places where a cloud accelerator is compute constrained, and vice versa.

This is why HAQ does not try to learn one “good” mixed-precision pattern for MobileNet. It learns a policy for a model-hardware-objective tuple.

Latency-Constrained Results

Latency-constrained quantization on BISMO: flexible per-layer precision beats fixed-bit baselines under similar latency budgets.

The latency table compares HAQ with fixed-bit PACT baselines on edge and cloud accelerator settings. The result is not just that flexible precision can save latency. The more important result is that it can preserve accuracy under a target latency constraint better than uniform precision.

The policy is also interpretable. Under latency optimization, the agent tends to assign different precision patterns to depthwise and pointwise convolutions because those layers stress the hardware differently.

Mobile-readable takeaway: under comparable latency budgets, HAQ’s flexible policy usually keeps higher top-1/top-5 accuracy than fixed-bit quantization. The reported latency reduction reaches roughly 1.4x to 1.95x compared with fixed 8-bit baselines in the BISMO experiments.

MobileNet-V1 policy under latency constraints: edge and cloud targets receive different bit allocations.

For MobileNet-V1, the paper explains the edge/cloud difference through operation intensity. On the edge accelerator, depthwise convolutions are more memory-bound, so activations in depthwise layers receive fewer bits. On the cloud accelerator, the policy changes because the bottleneck changes.

This is a useful result because it is not merely an accuracy table. It tells us what the controller learned about the hardware. The learned policy reflects memory/computation balance rather than parameter count alone.

MobileNet-V2 policy under latency constraints: the same hardware-aware pattern appears in a deeper MobileNet variant.

MobileNet-V2 shows the same qualitative lesson. The optimal policy changes across hardware targets, and the depthwise/pointwise distinction remains important. The policy is not a generic “give every depthwise layer fewer bits” rule. It depends on the target accelerator and constraint.

BitFusion Energy And Latency

BitFusion results: HAQ searches policies for latency and energy objectives instead of relying on one uniform precision.

The BitFusion experiments are useful because they separate two deployment metrics that are often conflated. A policy that is good for latency is not necessarily the best for energy. Both can be correlated, but hardware utilization, memory access, and arithmetic precision can make them diverge.

HAQ’s framework can swap the resource term in the reward. That means the same search machinery can target latency, energy, or model size. This is more flexible than designing one manual bit allocation heuristic and hoping it generalizes.

The headline result in these tables is that HAQ can roughly halve latency or energy relative to the 8-bit baseline while keeping accuracy close. More importantly, the best policy for latency and the best policy for energy are searched as separate objectives.

Model-Size-Constrained Results

Model-size-constrained quantization: HAQ can preserve accuracy at similar model sizes compared with earlier compression baselines.

The model-size objective produces a different policy from the latency objective. This is a key part of the paper. Under a size constraint, the cost of assigning bits is dominated by parameter count. Depthwise convolutions have fewer parameters than pointwise convolutions, so giving them more bits can be cheap while preserving accuracy.

The result table is small on mobile, so the main reading is: for MobileNet and ResNet settings, HAQ matches or improves accuracy at similar model sizes compared with the hand-designed compression baseline, especially under aggressive compression.

Under model-size constraints, the learned policy gives more bits to depthwise layers because they have fewer parameters.

Compare this with the latency policy. Under latency constraints, depthwise layers may receive fewer bits on some hardware because they are memory-bound. Under model-size constraints, they can receive more bits because they are small. Same model, different objective, different answer.

Why RL Is Not The Main Point

It is easy to read HAQ as an RL paper, but I do not think RL is the enduring contribution. The lasting idea is hardware feedback in the quantization loop.

The controller could be replaced by Bayesian optimization, evolutionary search, differentiable relaxation, integer programming, or a learned cost model plus greedy refinement. The paper’s contribution is the formulation:

  • policy = per-layer weight/activation bit widths;
  • objective = validation accuracy under a hardware constraint;
  • hardware feedback = latency/energy/size signal from the target platform;
  • result = device-specific mixed precision, not a universal bit schedule.

This framing is still relevant even when the search algorithm changes.

Relation To Modern LLM Quantization

HAQ is about CNNs on edge/cloud accelerators, but its deployment lesson maps well to LLM serving.

Consider common LLM quantization formats:

  • W4A16 weight-only quantization can be strong on GPUs with optimized INT4 kernels.
  • W8A8 can be better when hardware has fast INT8 tensor cores and activation quantization is stable.
  • FP8 can be attractive on recent accelerators with native support.
  • KV-cache quantization only helps when KV memory bandwidth or capacity is the bottleneck.

There is no globally best format. The best choice depends on hardware, batch size, sequence length, tensor parallelism, attention implementation, and kernel availability. That is the same problem HAQ identified for CNN quantization, just at a different scale.

Practical Reading Notes

The paper gives a good checklist for any mixed-precision result:

  • What exact hardware target was optimized?
  • Was latency measured, simulated, or approximated by FLOPs?
  • Are weights and activations both quantized?
  • Are first and last layers treated specially?
  • Is the reported model size only raw weights, or does it include scales and metadata?
  • Does the hardware actually support all searched bit widths efficiently?
  • Is the policy evaluated after fine-tuning or immediately after quantization?

These questions matter because mixed precision can look good on paper while failing in deployment if the hardware does not execute the searched formats efficiently.

Limitations

HAQ has real limitations:

  • RL search is expensive compared with a direct heuristic.
  • Hardware simulators must be accurate enough to guide policy search.
  • The paper focuses on CNNs and specialized accelerators, not transformers.
  • Quantization and fine-tuning details can change the final policy.
  • The search space assumes the hardware can benefit from flexible precision.

Those limitations do not weaken the main message. They define where the method needs engineering support.

Takeaway

HAQ should be remembered as a hardware-aware formulation of mixed-precision quantization. It moves the question from “Should this model be 8-bit or 4-bit?” to “Which layer should use which precision on this hardware under this objective?”

That is the right question for deployment. A bit-width policy is not an abstract compression artifact. It is a contract between the model, the quantizer, the kernels, and the device.
