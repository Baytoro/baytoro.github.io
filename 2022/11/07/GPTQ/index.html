GPTQ: One-Shot LLM Weight Quantization

H.J. Chen
  2022-11-07 2022-11-07 Created  
  • Paper Reading 
 
  • Quantization 
  • | LLM 
  • | Inference 

Paper: GPTQ: Accurate Post-Training Quantization for Generative Pre-trained Transformers

GPTQ is one of the papers that made low-bit LLM deployment feel practical. The target is not a small CNN and not a quantization-aware training recipe. The target is a pretrained decoder LLM with billions to hundreds of billions of parameters, and the constraint is harsh: compress the weights to 3 or 4 bits without full retraining.

The paper should be read as a scaling paper for second-order post-training quantization. The core mathematical idea comes from Optimal Brain Quantization (OBQ): when a weight is rounded, update the remaining weights so the layer output changes as little as possible on calibration activations. GPTQ keeps that idea, but changes the implementation enough that it can run on GPT-scale matrices.

The Problem

LLM inference is often dominated by moving weights through memory. In batch-1 decoding, each generated token touches a huge number of model weights while doing relatively small matrix-vector work. Weight-only quantization directly attacks this bottleneck: store weights in 3 or 4 bits, dequantize them inside the kernel, and keep activations in FP16/BF16.

This is different from full INT8 or W8A8 quantization. GPTQ is primarily a W3A16/W4A16 method:

  • weights are quantized;
  • activations stay high precision;
  • LayerNorm, attention softmax, residual paths, and KV cache are not the main quantization target;
  • the serving win depends on low-bit weight kernels and memory bandwidth.

Why Round-To-Nearest Is Not Enough

Figure cropped from the paper PDF: GPTQ avoids the collapse seen with naive round-to-nearest, especially at 3-bit precision.

The first figure is the paper’s main motivation. Round-to-nearest (RTN) can work at mild compression, but it breaks badly when bit width becomes aggressive. For large OPT and BLOOM models, GPTQ stays much closer to the FP16 perplexity curve, while RTN can produce huge perplexity spikes at 3 bits.

This is the important point: low-bit quantization error is not just independent noise. Rounding one weight changes the output, but the remaining unrounded weights can compensate for some of that change. Plain RTN throws away this degree of freedom.

From OBQ To GPTQ

OBQ quantizes one weight at a time. Suppose (w_q) is the next weight to quantize and (F) is the set of still-unquantized weights in that row. OBQ estimates the loss increase of quantizing (w_q), then applies a compensating update to the remaining weights:

$$
\delta_F =
-\frac{w_q - \operatorname{quant}(w_q)}
{[H_F^{-1}]{qq}}
(H_F^{-1}){:,q}.
$$

This is the right shape of update: the error introduced by quantizing one coordinate is pushed into the remaining coordinates according to inverse-Hessian geometry. The issue is cost. Doing this naively for every weight in a huge transformer matrix is far too expensive.

GPTQ keeps the row-wise reconstruction view but makes several implementation changes:

  1. It uses a fixed quantization order instead of an expensive greedy search.
  2. It quantizes the same column across all rows together.
  3. It batches updates inside column blocks.
  4. It uses a Cholesky-based reformulation of the inverse Hessian to improve numerical stability.

GPTQ’s blockwise procedure: columns are quantized recursively, and the remaining weights are updated with Hessian information.

The figure is easy to underestimate. It is not just an illustration of “do blocks.” It shows the core scaling trick. A block of columns is processed locally, while global updates are delayed and applied in larger chunks. This improves the compute-to-memory ratio and makes the algorithm usable on very large matrices.

Algorithm Details

A simplified reading of the algorithm:

The damping term (\lambda I) improves conditioning. The paper uses a small fraction of the average diagonal as damping.

  1. Compute the Cholesky form used for stable inverse-Hessian updates.

  2. Process columns in blocks. For each column (j), quantize all rows of (W_{:,j}), record the quantization error, and update later columns in the current block.

  3. After a block is done, apply the accumulated block error to the remaining unprocessed columns.

This is why GPTQ is not simply “RTN with a better scale.” The quantized value of a column changes the future unquantized columns. The method is sequential, and the error compensation is part of the quantizer.

The paper also reports that arbitrary fixed order works surprisingly well at scale. Later implementations often expose variants such as activation-order sorting, group-wise quantization, and different block sizes. Those options matter in practice, but the central idea remains second-order compensation under a layer reconstruction objective.

Why Weight-Only Works Here

GPTQ avoids the hardest parts of full-network quantization by keeping activations in high precision. That is not a weakness; it is the deployment tradeoff.

For decoder LLM serving, weights are static and huge. Reducing them from FP16 to 4 bits can cut model weight storage by roughly 4x before metadata overhead. At batch-1 decode, that can directly reduce memory traffic. Activations and KV cache still consume memory, but GPTQ is attacking the dominant static weight footprint.

This also explains what GPTQ does not solve:

  • it does not reduce KV-cache memory;
  • it does not make all activations INT8-safe;
  • it does not remove the need for specialized low-bit GEMM/GEMV kernels;
  • it does not guarantee speedup if dequantization overhead dominates.

In deployment language, GPTQ is a strong W4A16 or W3A16 model-compression method. It is not a complete quantized inference stack by itself.

Scaling And Runtime

Tables cropped from the paper PDF: GPTQ is competitive with prior PTQ on vision models and can quantize the largest OPT/BLOOM models in hours.

The runtime table is one of the paper’s most practical claims. GPTQ quantizes 13B/30B models in minutes to under an hour, and 66B/175B-scale models in hours. That is the difference between a method that is mathematically interesting and one that can actually be used on public LLM checkpoints.

The comparison with vision PTQ methods is also useful context. GPTQ is not introduced as a weaker LLM-only shortcut. It is positioned as a scalable variant of second-order PTQ that remains competitive on smaller benchmarks while being dramatically more relevant for large transformers.

Perplexity Results

OPT and BLOOM WikiText2 perplexity results: GPTQ is much more stable than RTN at 3-bit and 4-bit precision.

Tables 3 and 4 show the central empirical pattern:

  • At 4 bits, GPTQ is usually close to FP16 perplexity.
  • At 3 bits, RTN often collapses, while GPTQ remains usable for many models.
  • Larger models are often easier to quantize in perplexity terms, except for model-specific outliers.

This last point is important. A larger model can have more redundancy, so the same bit width may hurt it less than a smaller model. That is why low-bit compression became especially interesting for the largest LLMs: those are the models that most need memory reduction, and they can sometimes absorb quantization error better.

Mobile-readable takeaway: the key comparison is not the exact value in every cell, but the gap between RTN and GPTQ. For OPT, 3-bit RTN can jump to unusable perplexity values, while 3-bit GPTQ stays in a range where the model still behaves like a language model. For BLOOM, the same pattern appears: GPTQ tracks the FP16 baseline much more closely than direct rounding.

175B-Scale Summary

Summary for OPT-175B and BLOOM-176B: GPTQ keeps 3-bit and 4-bit results much closer to FP16 than RTN.

Table 5 is the deployment-facing result. OPT-175B and BLOOM-176B are compressed aggressively, and GPTQ retains reasonable perplexity and LAMBADA accuracy. The group-size rows are especially relevant because practical GPTQ implementations often use group-wise scales and zero points.

For the two 175B-class models, the practical reading is:

  • 4-bit GPTQ is close to the FP16 baseline on perplexity and LAMBADA.
  • 3-bit GPTQ is worse but still usable; 3-bit RTN collapses much more severely.
  • grouping with sizes such as 1024 or 128 recovers extra accuracy at the cost of metadata and kernel complexity.

Group size is a tradeoff:

  • smaller groups usually improve accuracy because each scale covers fewer weights;
  • smaller groups add metadata overhead;
  • smaller groups complicate kernels and memory layout;
  • the effective bits per weight can be higher than the nominal weight bit width.

So “3-bit GPTQ” is not a complete deployment specification. One should always ask about group size, scale/zero overhead, packing format, activation order, and kernel support.

Generation Latency

Per-token latency table from the paper: speedup comes from lower weight memory traffic and custom low-bit kernels.

The paper reports practical generation speedups for a 3-bit OPT-175B setting. The interpretation should be careful. GPTQ reduces weight traffic, but the actual speedup depends on:

  • whether decoding is weight-bandwidth bound;
  • whether the low-bit kernel is optimized;
  • the batch size and sequence length;
  • how much dequantization work is fused into the matrix-vector operation;
  • whether KV-cache traffic starts to dominate.

The paper’s latency table reports a 4.53x speedup on A6000 and a 3.24x speedup on A100 for the measured batch-1 generation setup. That should be read as a kernel-and-workload result, not a universal property of every GPTQ checkpoint.

This is why a GPTQ checkpoint and a fast GPTQ serving path are different things. The checkpoint saves memory. The speedup requires kernels that turn low-bit storage into lower end-to-end latency.

Downstream Accuracy

LAMBADA accuracy after quantization: GPTQ tracks the FP16 curve much better than RTN, especially at aggressive precision.

Perplexity is a useful language-model metric, but downstream tasks reveal whether the compressed model still behaves sensibly. The LAMBADA plot follows the same pattern: GPTQ stays much closer to FP16, while 3-bit RTN can be unstable.

The broader appendix results show the same point across PIQA, ARC, and StoryCloze-style evaluations. GPTQ is not perfect, but the second-order update changes the failure mode from “low-bit rounding destroys the model” to “low-bit compression becomes a tunable tradeoff.”

Extra Tricks: Grouping And Extreme Quantization

The paper’s 2-bit experiment: smaller groups make extreme quantization less destructive.

Group-size comparison at 4 bits: finer-grained groups reduce perplexity loss on medium-sized OPT models.

The group-size results are a good reminder that quantization is not only about bit width. A model with 4-bit weights and one scale per large group is different from a model with 4-bit weights and much finer grouping. The second may preserve accuracy better, but it costs metadata and kernel complexity.

Extreme quantization around 2 bits is interesting, but it is also where implementation details matter the most. Ternary values, per-group scales, zero points, and packing format can dominate the practical memory/computation tradeoff.

For normal LLM serving, 4-bit GPTQ is usually the easier engineering point. 3-bit is attractive when memory is extremely tight. 2-bit is a research and custom-kernel problem unless the hardware/software stack is specifically built for it.

Practical Reproduction Notes

If I were reproducing GPTQ, I would track the following separately:

  • Calibration data: use representative text and enough samples to estimate the layer Hessians.
  • Damping: inspect ill-conditioned layers and dead columns; damping can change stability.
  • Layer order: quantize and evaluate layer reconstruction incrementally.
  • Group size: report effective bits including scales and zeros.
  • Block size: tune for runtime and memory, not only accuracy.
  • Kernel path: benchmark real decode latency, not only model file size.

If one layer spikes, inspect its activation statistics, Hessian diagonal, damping, and quantization range. Full-model perplexity is the final metric, but layer reconstruction tells you where the quantizer failed.

Reading Notes

GPTQ’s influence comes from combining three facts:

  1. LLM weights are huge and static.
  2. Weight-only quantization avoids the hardest activation problems.
  3. Second-order compensation is accurate enough if implemented at matrix scale.

The paper is also a useful warning about benchmark wording. “4-bit” is not enough information. A serious comparison needs group size, calibration set, damping, activation ordering, quantization scheme, metadata overhead, and kernel implementation.

My takeaway: GPTQ is the practical midpoint between naive rounding and retraining. It does not make quantization free, and it does not solve every inference memory bottleneck. But for W4A16 LLM serving, it is the method that turned second-order PTQ into a usable engineering tool.
