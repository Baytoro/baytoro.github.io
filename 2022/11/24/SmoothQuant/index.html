SmoothQuant: W8A8 LLM Quantization

H.J. Chen
  2022-11-24 2022-11-24 Created  
  • Paper Reading 
 
  • Quantization 
  • | LLM 

Reference

  • Paper: SmoothQuant: Accurate and Efficient Post-Training Quantization for Large Language Models
  • Code: mit-han-lab/smoothquant

SmoothQuant is one of the cleanest LLM quantization papers because the main idea is only a diagonal rescaling, but the consequence is large: it turns difficult W8A8 quantization into a regular INT8 GEMM problem.

The paper should be read as a system paper as much as an algorithm paper. LLM.int8() preserves activation outliers with a mixed INT8/FP16 decomposition. Weight-only methods such as GPTQ or AWQ reduce weight bandwidth but leave activations in high precision. SmoothQuant chooses a different target: both weights and activations are INT8 for the expensive matrix multiplications, so the runtime can use dense hardware-friendly kernels.

Figure 1 gives the deployment pressure. Model size grew faster than single-node accelerator memory. A GPT-3-size model already needs hundreds of GB in FP16, and MT-NLG 530B is far beyond a single accelerator. Weight quantization alone helps memory, but W8A8 also makes the main GEMMs faster when the hardware has strong INT8 support.

One Sentence

SmoothQuant is a training-free post-training quantization method that:

  • observes that LLM activations are much harder to quantize than weights;
  • divides each activation input channel by a calibrated scale ;
  • multiplies the matching weight channel by the same ;
  • keeps the floating-point function exactly unchanged before quantization;
  • then quantizes the smoothed activations and scaled weights to INT8.

The important phrase is “migrating difficulty”. SmoothQuant does not delete outliers, and it is not just clipping. It uses an algebraic equivalence to move some dynamic range from activations into weights. Since weights are usually easier to quantize, this trade is profitable.

Figure 2 is the whole paper in one picture. The activation matrix has a few huge columns. If one global INT8 scale is used, those columns determine the quantization step, and ordinary activation values receive very few effective levels. SmoothQuant makes those columns smaller and compensates by making the corresponding weight rows larger.

Hardware-Friendly Granularity

Figure 3 separates three choices:

  • per-tensor quantization: one scale for the whole activation or weight tensor;
  • per-token activation quantization: one activation scale per token row;
  • per-channel weight quantization: one weight scale per output channel.

The key hardware point is not just accuracy. For INT8 GEMM, the inner product dimension should use regular INT8 values, and scale factors should sit outside the dense integer multiplication. Per-token activation quantization and per-output-channel weight quantization satisfy this. Per-input-channel activation quantization would put a different activation scale inside the reduction dimension, which no longer maps cleanly to a standard INT8 GEMM.

Why Per-Channel Activation Quantization Is Not Enough

Table 1 is a useful negative result. If the activation is quantized per-channel, OPT accuracy is almost preserved even at 175B. But per-channel activation quantization is not compatible with efficient INT8 GEMM in the usual layout. Per-tensor or per-token activation quantization is hardware-friendly, but it collapses accuracy once activation outliers become large.

This table gives the central problem statement:

activation quantization accuracy kernel story
per-channel good bad for standard INT8 GEMM
per-token or per-tensor bad on large LLMs good for standard INT8 GEMM

SmoothQuant tries to get both sides: make the activation easier so that the hardware-friendly per-token/per-tensor activation scales become accurate enough.

Observation: Activation Outliers Are Structured

Figure 4 gives three observations.

First, weights are already relatively flat. Their channel maxima do not vary wildly, so INT8 quantization of weights is not the main blocker.

Second, activations contain a small number of channels with very large magnitude. The paper describes these activation outliers as about two orders of magnitude larger than typical channels in some cases.

Third, the outliers are persistent by channel. They are not random isolated elements. If channel is an outlier, it tends to be an outlier across many tokens. This is exactly the structure that a per-channel smoothing factor can exploit.

Applying SmoothQuant To Transformer Blocks

Figure 6 is important because it draws the deployment boundary. SmoothQuant does not quantize every single operator to INT8. It quantizes the compute-heavy linear layers and attention BMMs. Lightweight or numerically sensitive operations such as LayerNorm, Softmax, ReLU, and residual additions stay in FP16.

That is a pragmatic design. The speed and memory bottleneck is dominated by large matrix multiplications. Keeping small elementwise operations in FP16 avoids unnecessary accuracy risk and kernel complexity.

The smoothing scale can often be folded offline:

  • multiply the weight-side scale into the weight tensor before quantization;
  • fuse the activation-side inverse scale into the previous linear layer or nearby normalization when possible;
  • when a residual branch makes fusion awkward, keep a small extra scaling operation.

This is why the final runtime still looks like a regular INT8 model. The awkward part is calibration and folding, not a special outlier branch inside the main GEMM.

O1, O2, O3: Accuracy And Kernel Tradeoffs

Table 2 defines three SmoothQuant operating points.

setting activation scale weight scale expected runtime
SmoothQuant-O1 per-token dynamic per-tensor safest among SmoothQuant variants
SmoothQuant-O2 per-tensor dynamic per-tensor faster, less adaptive
SmoothQuant-O3 per-tensor static per-tensor most efficient, needs good calibration

O1 is closer to a conservative quantization recipe because activation scales are still dynamic per token. O3 is the system-friendly endpoint because scales can be calibrated statically. The paper’s strongest result is that O3 still preserves accuracy on very large models.

The calibration procedure is lightweight:

  • collect activation maxima from 512 random sentences from the Pile validation set;
  • compute smoothing scales from activation maxima and weight maxima;
  • calibrate static quantization step sizes once;
  • no weight update, no gradient descent, no reconstruction training.

The calibration data matters. The transform is exact before quantization, but the quantizer depends on the observed activation range. If calibration prompts miss deployment outliers, O3 can under-estimate scales.

OPT-175B: The Main Accuracy Table

Table 3 is the main accuracy proof for OPT-175B.

The naive W8A8 baseline collapses: LAMBADA becomes 0.0%, average accuracy is 35.5%, and WikiText perplexity explodes to 93080. ZeroQuant also fails at this scale. Outlier Suppression fails similarly. LLM.int8() preserves accuracy, but it uses an FP16 outlier path.

SmoothQuant-O3 reaches:

  • LAMBADA: 74.6% vs FP16 74.7%;
  • average over seven tasks: 66.8% vs FP16 66.9%;
  • WikiText perplexity: 11.17 vs FP16 10.99.

This is the core result: the most aggressive SmoothQuant setting keeps almost the same OPT-175B accuracy while using regular W8A8 quantization for the expensive layers.

I read this table as a separation between “quantization format” and “quantization recipe”. W8A8 itself is not enough. Naive W8A8 has the right hardware format but the wrong statistics. SmoothQuant keeps the same target format but changes the distributions seen by the quantizer.

System Results: PyTorch

Figure 8 compares FP16, LLM.int8(), and SmoothQuant-O3 in PyTorch on A100. SmoothQuant gives up to 1.51x speedup and around 1.96x memory reduction. LLM.int8() can preserve accuracy, but the mixed INT8/FP16 outlier path often slows inference in this benchmark.

This is the system reason the paper cares so much about regularity. If the quantized model needs exceptional high-precision paths, the hardware may not deliver the expected speedup. SmoothQuant spends complexity offline so that the online path stays dense.

Table 8 focuses on autoregressive decoding. This stage is often memory-bound and latency-sensitive. SmoothQuant reduces per-token decoding latency and memory footprint for OPT-30B and OPT-175B. The memory savings are close to the expected halving, while latency speedup ranges roughly from 1.19x to 1.42x depending on model size, batch size, and sequence length.

System Results: FasterTransformer And 530B Serving

Figure 9 shows the FasterTransformer integration. This is the more deployment-oriented result. SmoothQuant-O3 can reduce latency by up to 1.56x and nearly halve memory usage. It also reduces the GPU count for large OPT models: the figure reports OPT-66B on one GPU instead of two, and OPT-175B on four GPUs instead of eight.

Table 9 shows MT-NLG 530B accuracy. FP16 and INT8 SmoothQuant both report the same average, 73.1, over LAMBADA, HellaSwag, PIQA, and WinoGrande. This is a small table, but it supports the biggest deployment claim: W8A8 can be accurate even beyond 500B parameters.

Table 10 is the memory result for MT-NLG 530B. FP16 serving uses 16 GPUs, while INT8 SmoothQuant uses 8 GPUs. Latency is comparable and memory drops from roughly one TB to about half a TB depending on sequence length. This is exactly the regime where W8A8 matters: the method changes not only speed, but also whether the model fits within a single node.

Ablation: Why O3 Is Fastest

Table 11 compares O1, O2, and O3 latency. The trend is straightforward:

  • dynamic per-token activation quantization is more adaptive but more expensive;
  • per-tensor dynamic quantization removes some overhead;
  • per-tensor static quantization is fastest because runtime scale computation is minimized.

O3 is therefore the strongest system setting. The risk is calibration quality, because static scales have less opportunity to adapt to runtime inputs.

Limitations

SmoothQuant is not a universal answer to all LLM compression problems.

First, it targets W8A8. If the bottleneck is pure weight memory and the hardware has excellent W4A16 kernels, a weight-only method such as AWQ or GPTQ may be more attractive.

Second, O3 depends on calibration. Static activation scales are efficient, but they assume calibration maxima cover deployment prompts well enough.

Third, SmoothQuant reduces the main linear/BMM cost, but it does not solve KV cache memory by itself. For long-context decoding, KV cache quantization is a separate issue.

Fourth, the method relies on the empirical asymmetry that weights are easier to quantize than activations. That is true for the models in the paper, but the exact alpha and quantization granularity should still be validated per model family.

Takeaway

The key contribution of SmoothQuant is not the existence of a diagonal rescaling. The key contribution is identifying that LLM activation outliers are channel-structured, persistent, and movable into weights without changing the floating-point function.

The formulas tell a clean story:

  1. uniform INT8 quantization is controlled by the maximum absolute value;
  2. activation outliers waste effective quantization levels;
  3. a diagonal transform can divide activation channels and multiply weight channels equivalently;
  4. controls how much difficulty is migrated.

That is why the method is elegant. The runtime model is simple, but the calibration step reshapes the distributions so that simple INT8 kernels become accurate enough for very large LLMs.
