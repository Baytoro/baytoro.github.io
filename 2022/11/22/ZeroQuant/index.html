Paper: ZeroQuant: Efficient and Affordable Post-Training Quantization for Large-Scale Transformers

Code: microsoft/DeepSpeed

ZeroQuant is an important paper because it treats quantization as a modeling problem and a serving-system problem at the same time. The paper is not just saying “large Transformers can use INT8.” It asks a more practical question:

Can post-training quantization serve BERT-size and GPT-style models without full quantization-aware training, while still producing real GPU latency gains?

The answer is a system recipe:

  • use group-wise quantization for weights, because a single matrix scale wastes range on rows with small magnitude;
  • use token-wise quantization for activations, because different tokens can have very different ranges;
  • use layer-by-layer knowledge distillation when INT4 weights are involved;
  • fuse quantization and dequantization around INT8 GEMM, otherwise fine-grained quantization can lose its latency benefit to memory traffic.

All crops below are taken from the original PDF.

Why ZeroQuant Matters

Before ZeroQuant, there were already useful Transformer quantization papers. Q8BERT showed that BERT can tolerate 8-bit quantization with quantization-aware fine-tuning. Q-BERT pushed BERT weight precision down with Hessian information. But two gaps remained:

  1. Full QAT or hidden-state distillation becomes expensive when the model has hundreds of millions or billions of parameters.
  2. Accuracy-only quantization results do not prove that the method is useful for serving, because token-wise scales and low-bit formats can introduce extra quantize/dequantize kernels and memory movement.

ZeroQuant sits exactly at that boundary. It tries to keep the user-facing behavior close to FP16, while making the quantization process cheap enough for large models.

The paper evaluates:

Model family Examples in the paper Main benchmark
Encoder-only BERT-Base, BERT-Large GLUE development sets
Decoder-only GPT-3-style 350M and 1.3B 20 zero-shot tasks plus Wikitext-2
Larger open-source GPT models GPT-J 6B, GPT-NeoX 20B generation and zero-shot evaluation

The notation is WxAy: x bits for weights and y bits for activations. The paper also uses W4/8 for a mixed setting where multi-head self-attention weights stay INT8 and feed-forward weights are pushed to INT4. This is a sensible compromise because the feed-forward connection is a large fraction of Transformer parameters.

The Failure Mode Of Naive PTQ

Post-training quantization is attractive because it does not retrain the model. A common PTQ flow is:

That is cheap, but it assumes that a small number of scales can represent the distributions well enough. ZeroQuant shows why this is fragile for Transformers.

Figure 1. GPT-3 350M has large variation across token activation ranges and across rows of the attention output matrix. A single coarse scale either clips large values or wastes representational levels on smaller values.

The left plot is the activation problem. Token hidden states in the same layer can have very different max-absolute ranges. If all tokens share one activation scale, the largest token range determines the scale, and small-range tokens get a coarse quantization grid.

The right plot is the weight problem. Rows in the attention output matrix do not share the same magnitude. A matrix-wide scale is again inefficient: rows with small ranges are represented by too few integer values, and this becomes much worse when weights are pushed to INT4.

The first PTQ table makes the diagnosis concrete.

Table 1. Naive PTQ on GPT-3 350M. Activation quantization hurts more than INT8 weight quantization, and mixed INT4/INT8 weights can destroy generation quality.

The useful read is not only the average score:

  • W8A16 is close to the FP16 baseline on the shown tasks. Weight-only INT8 is not the main problem here.
  • W16A8 has a larger drop. Wikitext-2 perplexity moves from 21.5 to 24.6, so activation quantization is already painful.
  • W8A8 is worse again on Wikitext-2, with perplexity 26.2.
  • W4/8A16 collapses generation. Wikitext-2 becomes 1.76e5, which is effectively unusable.

This is why ZeroQuant is not a pure rounding paper. The method has to address the numerical range mismatch in both weights and activations.

Group-Wise Weight Quantization

For a weight matrix W, ZeroQuant partitions the matrix into groups and quantizes each group separately. This gives each group its own scale. Compared with matrix-wise quantization, group-wise quantization reduces the penalty from rows or blocks with small magnitude.

The group size is not arbitrary. The paper explicitly considers hardware constraints on NVIDIA Ampere GPUs, where Tensor Core throughput depends on WMMA tile shapes. This is the system-aware part of the design: very fine groups might improve accuracy, but if they do not map well to GPU kernels, the final model may not be faster.

The appendix gives the concrete settings used in the experiments:

Model Group count used for weight quantization
BERT-Base 48 groups
BERT-Large 64 groups
GPT-3 350M 64 groups
GPT-3 1.3B 128 groups

I read this as a core ZeroQuant principle: choose quantization granularity where the model distribution needs it, but keep the layout friendly to the backend.

Token-Wise Activation Quantization

The activation side is different because activations are dynamic. A static calibration range can be too conservative for many tokens and too small for outlier tokens.

ZeroQuant instead uses token-wise activation quantization. Each token has its own activation range during inference, so the quantizer can adapt to token-level variation.

Layer-By-Layer Knowledge Distillation

W8A8 is the moderate target. For the more aggressive W4/8 settings, ZeroQuant adds layer-by-layer knowledge distillation, abbreviated as LKD.

The usual full-model distillation setup is expensive for large models:

  • it may need both teacher and student models in memory;
  • optimizer states are kept for many student parameters;
  • training is end-to-end, so memory and compute scale with the whole model;
  • original training data may not be available.

ZeroQuant’s LKD makes the optimization local. For layer L_k, it compares the original FP layer with the quantized copy of the same layer. Only that layer is optimized.

This has three practical consequences.

First, it does not need a separate full teacher model. The original layer acts as the teacher for the quantized layer.

Second, optimizer memory is small because only one layer is being updated.

Third, labels are not required. The objective is local feature reconstruction, not task supervision. This makes it possible to use alternative text data when the original pretraining corpus is unavailable.

This local nature is also the limitation. LKD reconstructs one layer at a time. It can miss error accumulation across layers, and it is weaker than a fully tuned end-to-end student. But it is cheap enough to be practical, which is the whole point of the paper.

Quantization-Optimized Kernels

The kernel section is easy to skip, but it is essential. Token-wise activation quantization and group-wise weight quantization add scale handling around GEMM. A naive implementation can perform extra reads, writes, and kernel launches.

Figure 2. The normal path pays separate quantize and dequantize costs. ZeroQuant fuses activation quantization with the preceding operator and fuses dequantization into the GEMM epilogue.

The paper’s backend uses CUTLASS INT8 GEMM and fusion:

  • activation quantization is fused with preceding operations such as LayerNorm, GELU, or bias-add;
  • INT32 GEMM accumulation is dequantized in the GEMM epilogue using activation and weight scales;
  • the output is written back as FP16 when the next operator is still FP16;
  • CUDA Graph support is used to reduce CPU launch overhead for small models such as BERT-Base.

This explains why ZeroQuant can claim both accuracy and speed. Without these fusions, token-wise activation quantization would be a nice accuracy trick but a questionable serving method.

BERT Results

BERT is the cleanest place to see the difference between naive PTQ, ZeroQuant, and QAT.

Table 2. BERT-Base GLUE results. ZeroQuant recovers most of the W8A8 PTQ loss without QAT, and LKD helps the mixed INT4/INT8 settings.

The headline numbers:

Setting Average score Average quantization time
FP16 baseline W16A16 83.95 N/A
W8A8 PTQ 77.41 6 seconds
W8A8 QAT 83.37 2900 seconds
W8A8 ZeroQuant 83.75 0 seconds
W4/8A8 ZeroQuant 81.55 0 seconds
W4/8A8 ZeroQuant-LKD 82.71 31 seconds

For W8A8, ZeroQuant is almost at the FP16 average and slightly above the internal QAT row in this table, with no activation calibration cost. I would not over-read the small difference between 83.75 and 83.37; the important point is that ZeroQuant is in the same accuracy band as QAT without QAT’s retraining cost.

For W4/8, naive PTQ is not usable. W4/8A16 PTQ averages 33.11, close to random behavior on several tasks. ZeroQuant raises it to 81.65, and LKD raises it again to 82.35. The same pattern holds for W4/8A8: ZeroQuant gives 81.55, and LKD improves it to 82.71.

The BERT-Large table in the paper follows the same broad pattern:

  • W8A8 PTQ average drops to 73.54;
  • W8A8 ZeroQuant reaches 84.81 against an FP16 baseline of 85.03;
  • W4/8A8 ZeroQuant-LKD reaches 81.62;
  • LKD costs about 550 seconds per task on one A100, far below the reported QAT cost.

The main caveat is RTE. Both QAT and ZeroQuant struggle more on RTE, which is a small dataset and often has high variance. This is a reminder that average GLUE scores can hide task-specific fragility.

GPT-3-Style Results

Decoder-only generation makes the quantization problem sharper. A classification task can sometimes tolerate small hidden-state perturbations, but autoregressive generation exposes accumulated errors token by token.

Table 4. GPT-3 350M results. ZeroQuant fixes most of the W8A8 PTQ damage, while LKD is needed for usable mixed INT4/INT8 generation.

For GPT-3 350M, the W8A8 result is the strongest moderate-precision claim:

Setting Average over 19 accuracy tasks Wikitext-2 PPL
W16A16 38.9 21.5
W8A8 PTQ 37.8 26.2
W8A8 ZeroQuant 38.7 21.7

ZeroQuant nearly removes the generation penalty: Wikitext-2 moves from PTQ’s 26.2 back to 21.7, close to the FP16 baseline 21.5.

The low-bit setting is more revealing:

Setting Average over 19 accuracy tasks Wikitext-2 PPL
W4/8A16 ZeroQuant 33.5 88.6
W4/8A16 ZeroQuant-LKD 37.0 30.6
W4/8A8 ZeroQuant 33.4 92.1
W4/8A8 ZeroQuant-LKD 36.6 31.1

LKD does not fully restore FP16 generation, but it changes the result from badly degraded to meaningfully usable. The paper reports that this LKD pass costs about 1.1 hours on one A100 for GPT-3 350M, which is tiny compared with pretraining.

The GPT-3 1.3B table shows the same direction. W8A8 ZeroQuant gets Wikitext-2 PPL 15.7, close to FP16 15.3 and better than PTQ 18.9. For W4/8, LKD again improves both average accuracy and generation perplexity.

Latency

Accuracy preservation is only half the story. ZeroQuant also reports end-to-end latency with the fused INT8 path.

Table 6. BERT latency on one A100. The W8A8 path gives roughly 2.27x to 5.19x speedup on BERT-Base and 2.47x to 5.01x on BERT-Large depending on sequence length and batch size.

The speedup is larger at higher batch sizes because the integer GEMM path is better utilized and the fixed overhead is amortized. But the table also shows speedups at batch size 1, which matters for online serving.

The paper also reports decoder-side speedups:

Model Quantized setting Reported latency result
GPT-3 350M W8A8 4.16x speedup over FP16
GPT-3 1.3B W8A8 4.06x speedup over FP16
GPT-J 6B W8A8 29.13 ms to 7.94 ms for first-50-token generation, 3.67x
GPT-NeoX 20B W8A8/16 2 x 65 ms on two A100s to 1 x 25 ms on one A100, reported as 5.2x better efficiency

The GPT-NeoX 20B result has an important qualification. The paper could not quantize all activation inputs to self-attention in pure W8A8 without accuracy loss, so it uses A8/16: FP16 activation for self-attention calculation and INT8 elsewhere. This is a practical result, but it also shows that extra-large decoder models can still have sensitive activation paths.

Ablation: Which Component Matters?

The ablation table is one of the most useful parts of the paper because it separates the three pieces: group-wise weight quantization, token-wise activation quantization, and LKD.

Table 9. BERT-Large ablation under W4/8A8. Group-wise weight quantization prevents collapse; token-wise activation quantization gives the largest additional gain; LKD adds a smaller but consistent improvement.

The average score progression is clear:

Components Average score
no GQ, no TQ, no LKD 35.85
GQ only 66.52
GQ + TQ 81.06
GQ + TQ + LKD 81.62

My read:

  • group-wise weight quantization is the first gate. Without it, mixed INT4/INT8 weights are too destructive;
  • token-wise activation quantization is the biggest BERT-Large jump in this ablation, from 66.52 to 81.06;
  • LKD’s average gain is small on this BERT-Large table, but it matters more for GPT generation under W4/8.

So I would not summarize ZeroQuant as “LKD solves PTQ.” The stronger summary is: fine-grained quantization solves most of the W8A8 and W4/8A8 representation issue, and LKD repairs the remaining low-bit damage when the quantized layer needs local reconstruction.

Distillation Without Original Data

Because LKD uses layer outputs rather than labels, it can use data from outside the original training set.

Table 10. GPT-3 350M W4/8A8 LKD with different data sources. Wikipedia data is close to original training data, and even random token data improves over no LKD.

This table is interesting for deployment teams. The original pretraining data may be private, unavailable, or too large to reconstruct. ZeroQuant shows:

  • no LKD: Wikitext-2 PPL 92.1;
  • random data LKD: PPL improves to 40.6;
  • Wikipedia data LKD: PPL improves to 30.4;
  • original data LKD: PPL 31.1.

The random-data result should not be overstated. It does not mean random data is as good as real text. But it does support the paper’s local-reconstruction argument: even random token sequences can provide enough layer input variation for the quantized layer to learn a better approximation of the FP layer.

The Wikipedia result is more practically useful. A clean public text dataset can be enough for LKD when original data is not available.

Relationship To Later LLM Quantization

ZeroQuant is not the final word on LLM quantization. Later methods became more specialized:

Method Main idea Difference from ZeroQuant
LLM.int8() Keep outlier channels in higher precision Explicitly isolates activation outliers instead of relying mainly on token-wise quantization
SmoothQuant Move activation outlier difficulty into weights through equivalent scaling Cleaner W8A8 transform for serving large LLMs
GPTQ Weight-only second-order reconstruction Stronger local solver for low-bit weights, usually without activation quantization
AWQ Activation-aware weight quantization Protects salient weight channels based on activation statistics
ZeroQuant Fine-grained W8A8/W4/8A8 plus LKD and fused kernels Broader system recipe across BERT and GPT-style models

This is why ZeroQuant still matters. It makes the serving constraint explicit: a quantizer is not successful unless the backend can run it efficiently. It also shows that activation quantization is not a minor detail for generation models. W8A8 needs a real activation strategy, not just weight rounding.

Reproduction Notes

If I were reproducing ZeroQuant, I would start smaller than the full paper:

  1. Pick one Transformer block and implement symmetric quantization for its linear layers.
  2. Compare matrix-wise weight quantization with group-wise weight quantization using layer-output error.
  3. Compare static activation calibration with token-wise dynamic activation quantization.
  4. Evaluate both classification accuracy and generation perplexity. Perplexity is more sensitive to accumulated quantization error.
  5. Add LKD for one quantized layer and verify that the local MSE objective reduces output error.
  6. Stack quantized layers progressively and check where error accumulation becomes visible.
  7. Only after the numerical path works, optimize the kernels. Otherwise it is hard to tell whether failures come from quantization math or backend layout.

The kernel checks I would add:

Check Why it matters
Scale layout matches GEMM tiling Bad scale reads can erase Tensor Core gains
Quantization fused with LayerNorm/GELU/bias-add Separate kernels add memory traffic
Dequantization in GEMM epilogue Avoids writing and rereading INT32 outputs
Batch/sequence-specific schedules Small batch serving and large batch throughput have different bottlenecks
CUDA Graph path for small models Kernel launch overhead can dominate BERT-Base latency

Limitations

ZeroQuant has several clear limitations.

First, W4/8 generation still needs LKD and remains worse than FP16. The paper makes the low-bit setting practical, but it does not make it free.

Second, the local LKD objective does not directly optimize final task loss or long-range generation behavior. Layer-wise reconstruction can reduce local error while still allowing small errors to accumulate through the network.

Third, the best results depend on custom kernels. Token-wise activation quantization is not automatically fast in a generic framework. The method assumes a backend that can fuse quantization and dequantization with GEMM-adjacent operators.

Fourth, the GPT-NeoX 20B result uses W8A8/16, not pure W8A8 for every activation path. That is a useful engineering compromise, but it shows that some self-attention activations remain sensitive at larger scales.

Finally, this paper predates the modern 4-bit LLM deployment stack. If the target is weight-only 4-bit serving for very large decoder-only models, GPTQ/AWQ-style methods may be closer baselines. If the target is true W8A8 serving with integer GEMM, ZeroQuant and SmoothQuant are more directly relevant.

Takeaway

ZeroQuant’s main contribution is the combination:

The paper is worth reading because it does not separate algorithm and system concerns. Token-wise activation quantization fixes a real numerical problem, but it only becomes deployable after fusion. Group-wise weight quantization fixes a real representation problem, but the group layout has to respect GPU kernels. LKD helps low-bit weights, but it is designed around the memory constraints of large models.

That is the enduring lesson: for large Transformer quantization, accuracy tables, calibration cost, memory layout, and kernel fusion are one problem.
