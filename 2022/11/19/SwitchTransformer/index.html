Switch Transformers: Scaling to Trillion Parameter Models with Simple and Efficient Sparsity

H.J. Chen
  2022-11-19 2022-11-19 Created

Paper

Switch Transformer is a very practical MoE paper. It does not start from a complicated routing algorithm. It takes the Transformer FFN, replaces it with multiple FFN experts, and routes each token to only one expert.

That top-1 choice is the central simplification. Compared with earlier top-2 MoE designs, Switch reduces expert computation, reduces communication, makes the dispatch tensor easier to implement, and still preserves the main benefit of MoE: the model can have many more parameters without activating all of them for every token.

The paper is important because it makes sparse scaling look like an engineering path rather than only a modeling idea. The authors scale from T5-style baselines to 395B and 1.6T parameter Switch variants, while keeping the per-token compute close to dense baselines.

One Sentence

Switch Transformer increases total model capacity by adding many FFN experts, but keeps token-level compute controlled by routing each token to a single selected expert.

The scaling curve gives the main intuition. As the number of experts increases, parameter count grows, but each token still activates one expert. The result is a new scaling axis: more sparse parameters at roughly fixed per-token FLOPs.

Why Top-1 Routing Matters

Top-1 routing looks almost too simple, but it changes the system behavior:

  • The expert computation per token is reduced because only one FFN expert runs.
  • The expert capacity can be smaller because each token consumes one expert slot instead of two.
  • The all-to-all communication pattern is simpler because each token has only one destination expert.
  • The implementation has fewer combine paths because the output comes from one selected expert.

This is the core reason the paper calls the layer “Switch”. Each token is switched to one expert rather than softly mixing several experts.

Expert Capacity

The hard part of sparse routing is not the softmax. The hard part is batching tokens efficiently on accelerators. TPU/XLA-style systems need statically shaped tensors, but the number of tokens sent to each expert is dynamic.

Switch solves this with a fixed expert capacity:

Every expert gets a fixed number of token slots. The first fraction is the average number of tokens each expert would receive under perfectly balanced routing. The capacity factor adds extra buffer.

The figure shows the tradeoff. With capacity factor 1.0, there is no extra buffer. If the router sends too many tokens to one expert, some tokens overflow. In the paper’s implementation, an overflowed token skips the expert computation in that layer and continues through the residual connection.

With capacity factor 1.5, there is extra room, so fewer tokens overflow. But the empty slots still occupy compute and memory. This is the main capacity tradeoff:

  • lower capacity factor: faster and less memory, but more risk of dropped tokens;
  • higher capacity factor: fewer dropped tokens, but more wasted slots and communication.

The paper reports that dropped tokens are typically below 1% when the load balancing loss is strong enough.

Benchmark Against MoE

Table 1 compares T5, top-2 MoE, and Switch under the same hardware setting. The important comparisons:

  • At capacity factor 1.0, Switch-Base reaches the quality threshold in 62.8 hours, while MoE-Base needs 80.1 hours.
  • Switch-Base at capacity factor 1.0 runs at 1000 examples/sec, faster than MoE-Base at 860 examples/sec.
  • Switch-Base+ gets the best 100k-step quality in this table, -1.534 negative log perplexity, while still reaching the threshold in 67.6 hours.

The interesting point is that lower capacity factors help Switch. This matters for large sparse models because memory is limited. A design that only works with a large capacity factor is less attractive at scale.

Stability Tricks

Sparse expert models add hard routing decisions inside the network. That makes training less stable than a dense Transformer. The paper uses several practical fixes.

Selective Precision

Pure bfloat16 training is fast but unstable in the router: the table shows bfloat16 diverging. Full float32 is stable but slower. Switch uses selective precision:

  • cast the router computation to float32;
  • compute router probabilities, dispatch, and combine tensors;
  • cast the dispatch/combine path back to bfloat16 for the rest of the layer.

The result is almost the same speed as bfloat16, but with float32-like stability. In the table, selective precision reaches -1.716 quality at 1390 examples/sec, while full float32 reaches -1.718 at 1160 examples/sec.

Expert Dropout

Switch has many more parameters than a FLOP-matched dense model. During fine-tuning on smaller downstream tasks, this can overfit. The paper therefore uses larger dropout inside expert FFNs than in the rest of the model.

The useful setting is not “increase dropout everywhere”. The better pattern is lower regular dropout on non-expert layers and higher dropout inside experts, for example standard dropout 0.1 and expert dropout 0.4.

  • On a step basis, Switch-Base with more experts learns faster than T5-Base under the same per-token compute budget.

The paper notes that Switch-Base with 64 experts reaches the same quality around 60k steps that T5-Base reaches around 450k steps. That is about a 7.5x step-efficiency gain.

Wall-Clock Speed

Step efficiency alone is not enough. Sparse routing adds communication, and communication can erase theoretical compute savings. The paper therefore also measures wall-clock training time.

The 64-expert Switch-Base reaches the same quality in about one seventh of the time of T5-Base. This is the result that makes the paper feel practical: despite router overhead and all-to-all dispatch, the sparse model is still faster in real training time.

The paper also compares against scaling the dense model itself.

T5-Large uses about 3.5x more FLOPs per token than T5-Base, but Switch-Base is still more sample-efficient and gives a 2.5x wall-clock speedup over T5-Large in this setup. This is a stronger comparison than only beating T5-Base, because it asks whether the same resources should be spent on dense width/depth or sparse experts.

Downstream Results

The downstream table checks whether pretraining gains transfer after fine-tuning. They generally do:

  • Switch-Base improves over T5-Base on GLUE, SQuAD, SuperGLUE, Winogrande, XSum, ANLI, ARC Easy, and closed-book QA tasks.
  • Switch-Large improves over T5-Large on many of the same tasks.
  • Some tasks are not uniformly better, for example ARC Challenge is tied or worse in some comparisons.

This matters because a sparse model could in theory only improve the upstream language modeling metric. The table shows that the gains often survive task fine-tuning, although the behavior is not perfectly uniform.

Multilingual Pretraining

The multilingual setting uses 101 languages. The plotted result shows Switch improving over the dense multilingual baseline across all languages in the experiment.

The speedup histogram is also useful. The paper reports a mean step speedup around 5x over the dense mT5-Base baseline, and 91% of languages get at least 4x speedup to reach the final mT5-Base perplexity.

Parallelism and Communication

Sparse models are not just “bigger dense models”. They stress the system differently. Dense scaling mainly adds model-parallel tensor operations. Expert scaling adds routing, token packing, dispatch tensors, and all-to-all communication.

The figure separates data parallelism, model parallelism, expert parallelism, and combinations of them. Switch can use expert parallelism by placing different experts on different devices. But once tokens are routed to experts, the system must move token representations to the device holding the selected expert, then move outputs back.

The practical bottlenecks are:

  • whether each expert gets enough tokens to form efficient matmuls;
  • whether the all-to-all communication is hidden or exposed;
  • whether expert capacity creates too many padded slots;
  • whether the router distributes tokens evenly enough.

This is why the paper spends so much space on load balancing, capacity factor, and static tensor shapes.

Trillion-Parameter Models

Table 9 is the large-scale result. A few numbers stand out:

  • T5-XXL has 11B parameters and 6.3T FLOPs/sequence.
  • Switch-XXL has 395B parameters and the same 6.3T FLOPs/sequence.
  • Switch-C has 1.571T parameters, 2048 experts, and 890B FLOPs/sequence.

Switch-C is interesting because it uses expert parallelism without model parallelism in the same way as Switch-XXL. It has far more parameters than T5-XXL, but lower FLOPs/sequence in the table. The paper reports that Switch-C is 4x faster than T5-XXL to a fixed perplexity under the same compute budget.

The result also shows a limitation: not every sparse scale-up is equally stable. The paper notes that Switch-C showed no training instability, while Switch-XXL was sometimes unstable despite having better step-basis performance.

Implementation Sketch

The router logic can be summarized like this:

The important operations are:

  • top-1 selection chooses the destination expert;
  • cumulative position assigns each token a slot inside that expert’s fixed capacity;
  • overflow tokens are masked out;
  • dispatch tensor sends tokens to experts;
  • combine tensor brings expert outputs back and multiplies by the gate value.

This is the implementation side of the paper’s main idea. The model is sparse, but the tensors are shaped so accelerators can still run large batched operations.

Takeaway

Switch Transformer is important because it takes MoE from “powerful but complicated” toward “simple enough to scale”.

The main technical choices are:

  • replace dense FFN layers with expert FFN layers;
  • route each token to one expert using top-1 routing;
  • use fixed expert capacity to make shapes static;
  • add a load balancing loss to avoid expert collapse;
  • use selective precision so router softmax stays stable;
  • reduce initialization scale for sparse-model stability;
  • use expert dropout during fine-tuning;
  • combine data, model, and expert parallelism for very large models.

The tradeoff is also clear. Switch increases parameter capacity without linearly increasing per-token compute, but it introduces routing and communication complexity. The paper’s contribution is showing that this tradeoff can be favorable in real pretraining runs, not only in theory.
