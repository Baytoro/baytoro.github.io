Direct Federated Neural Architecture Search

H.J. Chen
  2022-01-01 2022-01-01 Created  
  • Paper Reading 
 
  • NAS 
  • | FL 

He et al. Direct Federated Neural Architecture Search. 2020.

Paper

DFNAS is a practical follow-up to read after FedNAS. FedNAS already asks how to search architectures when data stays on clients. DFNAS asks a more systems-oriented question: can the search be done directly inside the federated training loop, without a separate retraining stage and without DARTS-style multi-path memory cost?

The answer is a DSNAS-like one-path supernet. Each client samples one child network, updates operation weights and architecture parameters locally, and the server averages both.

Motivation

In standard federated learning, the global objective is a weighted sum of local client objectives:

The architecture is usually fixed before training starts. That is a weak assumption in FL:

  • client data can be non-IID, so a manually chosen architecture may fit some clients better than others;
  • the designer often cannot inspect private client data;
  • a second centralized search or retraining stage is expensive and sometimes impossible;
  • DARTS-style continuous relaxation keeps many candidate operations active, which is a bad fit for memory-limited clients.

DFNAS keeps the goal modest: search one global architecture that is ready to deploy after the federated process finishes.

Local Search

For client i, the local objective is written around a sampled structure:

Here Z is the one-hot architecture decision, alpha parameterizes the sampling distribution, and w is the operation weight. A local step roughly does this:

  1. sample a child network Z from p_alpha(Z);
  2. activate only that path in the parent network;
  3. update w with a normal batch gradient;
  4. update alpha with the estimator tied to the sampled architecture probability;
  5. prune weak operations when their architecture weights fall below a threshold.

The memory advantage comes from the one-path execution. If a DARTS cell keeps n candidate operations alive, the forward, backward, and activation memory cost can scale with n. DFNAS trains only one sampled path per step, so the client-side footprint is much closer to training an ordinary child model.

This is the “direct” part of DFNAS. The searched model is produced by the same communication rounds that train it. There is no proxy dataset, no separate architecture-transfer step, and no final retraining pipeline in the method.

Search Space

The parent network is ShuffleNet-like. That is a good engineering choice for cross-device FL because the candidates are already mobile-friendly. The paper uses:

  • 4 candidates per choice block for cross-silo experiments: ShuffleNet blocks with kernel sizes 3, 5, and 7, plus an Xception block;
  • 3 candidates per choice block for cross-device experiments;
  • a reported 4^20 search space for the cross-silo setting and 3^12 for the cross-device setting.

This is not an open-ended architecture generator. It is a constrained efficient-CNN search space, which makes the one-path federated search realistic.

Communication Curves

The round-accuracy curves are useful because they show a common NAS-in-FL behavior: DFNAS can look bad early while the sampled architecture is still unstable, then catch the fixed baselines after enough rounds.

On non-IID CIFAR-10 with 8 clients and 150 rounds:

Method Final test accuracy
ResNet56 + FedAvg 77.78%
MobileNetV1 + FedAvg 83.41%
DFNAS 88.31%

On non-IID CINIC-10 with 16 clients and 250 rounds:

Method Final test accuracy
ShuffleNetV1 + FedAvg 67.70%
DFNAS 68.35%

The CIFAR-10 gain is the stronger result. CINIC-10 is closer, but still shows that the searched architecture is not just overfitting the small CIFAR setting.

Search Cost

The main comparison with FedNAS is on CIFAR-10 with 8 non-IID clients:

Method Test accuracy Params Total time Search memory
FedNAS 91.43 +/- 0.13% 0.33M 1 GPU day 10,793 MB
DFNAS 92.11 +/- 0.10% 2.1M 0.18 GPU day 1,437 MB

This table should not be read as “DFNAS gives the smallest model.” It does not. The DFNAS model is larger than the FedNAS model in this comparison. The win is search efficiency: much lower memory and much less total search time.

The IID scaling table reports:

Clients Test accuracy Params Total time
2 93.53 +/- 0.10% 2.1M 0.83 GPU day
4 93.31 +/- 0.12% 2.1M 0.43 GPU day
8 92.79 +/- 0.15% 2.1M 0.18 GPU day

Accuracy drops slightly as more clients are used, while wall-clock search time decreases. I would treat this as an implementation scalability result rather than a full proof of robustness under arbitrary heterogeneity.

Takeaway

DFNAS makes architecture search look like normal federated optimization:

  • sample one child model on each client;
  • update weights and architecture parameters locally;
  • average both on the server;
  • derive the final architecture from the learned distribution.

The limitations are also clear. The search space is fixed to efficient CNN blocks, the final model is not always the smallest one, and the method does not add privacy protection beyond ordinary FL. Still, the paper is useful because it attacks the actual bottleneck of federated NAS: client memory and the cost of running search plus retraining as two separate jobs.
