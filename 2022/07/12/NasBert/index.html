NAS-BERT: Task-Agnostic and Adaptive-Size BERT Compression with Neural Architecture Search

H.J. Chen
  2022-07-12 2022-07-12 Created  
  • Paper Reading 
 
  • NAS 
  • | BERT

Reference

  • Paper: NAS-BERT: Task-Agnostic and Adaptive-Size BERT Compression with Neural Architecture Search
  • Venue: KDD 2021

NAS-BERT is a BERT compression paper, but the interesting part is not simply that it produces a smaller encoder. The paper changes the compression setting:

  • the compressed models should come in many sizes, not one fixed student;
  • the search should happen at the pre-training stage, not separately for every downstream task;
  • the final model should be selected under parameter and latency constraints;
  • the search space is allowed to change the block type, not only width and depth.

This makes the paper closer to Once-for-All / BigNAS than to ordinary BERT distillation. NAS-BERT trains a supernet once, then selects subnets such as 60M, 30M, 10M, and 5M parameter models for different deployment budgets.

One Sentence

NAS-BERT is a task-agnostic, adaptive-size BERT compression framework:

  1. build a supernet over MHA, FFN, separable convolution, identity, and hidden-size choices;
  2. train it block by block using a BERT teacher;
  3. progressively shrink weak candidate architectures while preserving different model-size bins;
  4. approximate latency and loss with lookup tables;
  5. select a subnet that satisfies a target size and latency budget, then pre-train/fine-tune it.

My short reading: the paper is valuable because it treats compressed BERT as a model family, not as a single distilled model.

Why This Setting Matters

Most BERT compression papers choose a single student. DistilBERT, TinyBERT, MiniLM, and BERT-PKD each define one typical compressed size around 60M to 66M parameters. That is convenient for comparison, but deployment usually has more than one target:

Scenario Constraint that matters
online service latency and throughput
mobile device memory, energy, and CPU latency
offline batch inference total compute cost
edge device strict parameter and memory budget

A fixed compressed model cannot be optimal for all of these. A 60M model may be fine for server inference but too large for an embedded device. A 5M model may fit memory but sacrifice too much accuracy for a normal CPU service.

The other issue is task-specific compression. AdaBERT and DynaBERT can adapt to downstream tasks, but that means extra work per task. NAS-BERT tries a different tradeoff: do the expensive compression/search work during pre-training, then reuse the resulting model family across downstream tasks.

The phrase “task-agnostic” needs a careful reading. In this paper it mainly means the architecture search and compression are not repeated for each downstream task. The authors still evaluate optional downstream knowledge distillation. Their ablation later shows a stricter setting without fine-tuning-stage distillation.

MHA and FFN keep the search space connected to the original Transformer. SepConv adds a cheaper non-attention operation with local context. Identity allows shallow networks because an identity operation can be removed after selection.

The hidden-size table is also structured. MHA uses 2, 3, 4, 6, or 8 heads as hidden size grows from 128 to 512. FFN uses intermediate sizes from 512 to 2048. This means the search is not merely “drop layers from BERT”; it can choose a different computation type and a different width at each block.

My interpretation: SepConv is a way to let the search escape the pure Transformer template while still remaining cheap. If the task does not need a full attention/FFN pair at every layer, the architecture can replace some blocks with local convolutional mixing.

Block-Wise Supernet Training

Directly training the entire supernet is too expensive. Weight sharing gives many paths access to the same operations, but with a search space around , random single-path optimization would give each architecture too little training signal.

NAS-BERT therefore divides the 24-layer supernet into blocks. Each block has 6 searchable layers. The BERT-base teacher is also divided into 4 corresponding blocks. For the -th student block, the training target is the output hidden state of the -th teacher block.

The formula says: “given the teacher’s input to this block, make the student block reproduce the teacher’s output.” This is not task-label supervision. It is representation matching inside the pre-trained BERT computation graph.

There is one extra engineering detail: student hidden size may be 128, 192, 256, 384, or 512, while the BERT-base teacher hidden size is 768. The paper uses learnable linear transformations before and after each student block to map hidden dimensions into the teacher-compatible space. Without these transformations, block-wise hidden-state matching would not be dimensionally valid.

Progressive Shrinking

Block-wise training reduces the search space, but each block is still large. NAS-BERT uses progressive shrinking: after training epochs, it evaluates sampled architectures and removes weak candidates. This gives surviving architectures more training budget.

The figure is a useful sanity check. Progressive shrinking starts at epoch 4. After that, the red curve drops lower than the no-shrinking baseline. The interpretation is not that shrinking magically improves the model; it improves the allocation of training. Weak candidates are removed, so the remaining candidates receive more effective optimization.

Naive pruning has a problem: it may remove large models early because they are harder to train, and remove small models late because they have less capacity. Then the final supernet would lose the ability to serve different deployment budgets.

The paper uses bins. It first trains for 3 epochs without progressive shrinking as a warm start. Then at the end of each later epoch, it samples architectures for validation and removes architectures per bin. The process stops when only architectures remain in each bin.

This says the latency of the whole architecture is estimated by summing the measured latency of its operations. It is not perfect because real systems have memory effects, kernel launch overhead, batching behavior, and cache behavior. But it is cheap and hardware-specific: one can measure the 26 candidate operations on a target device and use that device’s latency table.

This is my notation for the paper’s procedure. The method evaluates sub-architectures in each block on the dev set, then adds those block losses to estimate a complete architecture’s quality. The approximation is only valid if block-wise losses are informative enough after teacher-guided training. This is exactly why the earlier block-wise distillation matters.

The final selection pipeline is:

  1. build the architecture lookup table;
  2. filter candidates that violate parameter or latency constraints;
  3. choose the top candidates with low approximate loss;
  4. evaluate those full architectures on the dev set;
  5. select the best compressed model.

Two-Stage Distillation

NAS-BERT’s architecture search is task-agnostic, but the paper also evaluates knowledge distillation during both pre-training and fine-tuning. The appendix summarizes the two-stage pipeline:

  1. pre-train the teacher;
  2. pre-train the student with distillation from the pre-trained teacher;
  3. fine-tune the teacher on the downstream task;
  4. fine-tune the student with distillation from the fine-tuned teacher.

Training Cost

The training setup is large but not absurd for BERT-era compression:

Item Setting
Teacher BERT-base
Searchable layers 24
Blocks 4
Search bins per block 10
Warm start 3 epochs before shrinking
Validation samples during shrinking 2000 architectures
Stop condition 10 architectures per bin per block
Corpus English Wikipedia + BookCorpus
Supernet training 3 days on 32 NVIDIA P40 GPUs
Teacher training in paper 5 days

The cost story is central. Training a supernet on masked language modeling is expensive, but the cost is amortized over many final model sizes. If one needed to repeat the entire search per downstream task or per device, the method would be much less attractive.

The gap is much larger at 5M. This is the most interesting part of the table. When the model is still fairly large, a hand-designed BERT-like stack is competitive. When the budget becomes tiny, allowing the search to mix SepConv, MHA, FFN, identity, and width choices becomes more valuable.

The 5M result is also faster in the paper’s latency proxy: NAS-BERT5 reports 23.6x speedup, while BERT5 reports 20.7x. So the smaller model is not gaining accuracy by secretly becoming slower.

Comparison With Prior Compression Work

The common-size comparison uses NAS-BERT60 against previous 60M to 66M models.

On the dev set:

  • Teacher: 84.4 average.
  • DynaBERT with augmentation: 82.7 average.
  • NAS-BERT: 84.2 average.
  • NAS-BERT with augmentation: 84.8 average.

On the GLUE test set:

  • BERT-of-Theseus: 79.4 average.
  • TinyBERT with augmentation: 80.6 average.
  • NAS-BERT: 81.1 average.
  • NAS-BERT with augmentation: 81.7 average.

This table should be read with some caution. Compression papers often differ in teacher strength, data augmentation, distillation details, and training budgets. The authors explicitly do not compare with MobileBERT in this table because MobileBERT uses a stronger teacher. Still, the table supports the main claim: NAS-BERT60 is competitive with strong BERT compression methods while being produced from an adaptive architecture search framework.

This is where NAS-BERT’s task-agnostic design looks strongest. AdaBERT searches task-specific students, but NAS-BERT5 uses a single searched architecture family from pre-training and still obtains better scores with fewer parameters in these comparisons.

My reading: the absolute numbers are from the 2021 BERT compression ecosystem, but the qualitative lesson is useful. At very small sizes, architecture matters more than simply scaling down a Transformer template.

Ablations

The ablations answer three questions.

First, does progressive shrinking help? Table 5 says yes:

Setting AVG
without progressive shrinking 83.1
with progressive shrinking 84.2

The gain is +1.1 average GLUE points for NAS-BERT60. The explanation matches Figure 3: without shrinking, each candidate path is under-trained; with shrinking, the remaining paths receive more useful optimization.

Second, should shrinking prune whole architectures or operations? Table 6 favors pruning architectures:

Setting AVG
PS-arch 84.2
PS-op 82.8

This makes sense. Operation-level pruning is too coarse. Removing an operation globally from a layer can damage many potentially good paths. Architecture-level pruning keeps the operation set alive but removes weak paths inside each bin.

Third, how much does distillation matter? Table 7 compares pre-training distillation (PD) and fine-tuning distillation (FD). NAS-BERT60 stays better than the BERT60 baseline in all corresponding settings:

Setting BERT60 AVG NAS-BERT60 AVG
PD + FD 83.5 84.2
PD only 82.9 83.5
FD only 82.6 83.1

The PD only row is especially important. Without fine-tuning-stage distillation, the compressed model is closer to the fully task-agnostic story: search and compression happen during pre-training, and each downstream task only needs normal fine-tuning. NAS-BERT60 still reaches 83.5 average.

What The Selected Architectures Look Like

Table 10 is useful because it shows the selected architectures are not just shallow BERTs. The notation is:

  • E: embedding size;
  • M: MHA;
  • F: FFN;
  • S3, S5, S7: SepConv with kernel size 3, 5, or 7;
  • the subscript is the hidden size.

Several observations stand out:

  • Large models such as 60M and 55M still contain many MHA and FFN operations.
  • Middle-size models start mixing in more SepConv while keeping some MHA/FFN.
  • Very small models use mostly SepConv and a few MHA operations.
  • Embedding size also shrinks: the 5M model uses E64, while larger models use E512, E384, E256, or E128.

This is the core architectural result. NAS-BERT is not only choosing “how many BERT layers”. It is changing the composition of the encoder under size constraints.

My Reading Notes

The paper is strongest when read as an amortized deployment method. If I only need one 60M BERT student, a strong distillation method may be simpler. If I need many models under different latency and memory budgets, a trained supernet becomes more attractive.

The most important engineering ideas are:

  • Block-wise distillation turns a huge pre-training search into smaller block searches.
  • Progressive shrinking improves training allocation and search accuracy.
  • Size/latency bins preserve diversity so the supernet does not collapse into one budget range.
  • Lookup-table selection makes final architecture selection cheap enough.
  • Mixed operations let tiny models move away from pure Transformer structure.

The limitations are also clear:

  • The supernet still costs 3 days on 32 P40 GPUs in the paper.
  • Latency lookup is hardware-specific and approximate.
  • The results are for BERT-base-era encoder compression, not decoder-only LLMs.
  • The “task-agnostic” claim has a practical caveat: optional fine-tuning-stage distillation still uses downstream-task teachers, although the architecture search itself is task-agnostic.
  • The search space is manually designed. NAS decides within that space; it does not invent arbitrary efficient Transformer blocks.

Overall, I would place NAS-BERT between AdaBERT and Once-for-All. Compared with AdaBERT, it moves compression earlier and avoids per-task search. Compared with Once-for-All, it brings the elastic-supernet idea into BERT compression and adds block-wise teacher supervision to make the pre-training search feasible.
