EDD: Efficient Differentiable DNN Architecture and Implementation Co-search

H.J. Chen
  2022-08-28 2022-08-28 Created

Paper

EDD is a useful paper to read after ProxylessNAS and Single-Path NAS. The common hardware-aware NAS recipe is:

  1. Define an architecture search space.
  2. Build or measure a latency model on the target hardware.
  3. Add latency into the architecture-search objective.

EDD asks for one more step: what if the hardware implementation is not fixed during NAS? For a GPU this may mean precision and measured kernel latency. For an FPGA it may mean quantization, parallel factors, resource sharing, and whether the accelerator is recursive or pipelined. The paper’s main point is to put these implementation variables into the same differentiable search loop as the DNN architecture variables.

Motivation

Hardware-aware NAS improves over pure FLOPs-aware search, but it often assumes a fixed implementation. That is a strong assumption. A model can look good under one implementation schedule and become less attractive after quantization, FPGA resource allocation, or pipeline structure changes.

EDD describes the gap as:

Existing hardware-aware NAS searches architecture variables , while implementation variables are fixed. EDD searches together.

The distinction is especially important for FPGA. If the accelerator shares one IP across many layers, the objective is closer to end-to-end latency with resource sharing. If every layer has its own pipelined accelerator, the objective is closer to throughput and resource budgeting across all blocks. These two deployment modes should not necessarily produce the same network.

Contribution

The paper contributes a co-search formulation rather than just another MobileNet-like architecture:

  1. Fuse DNN architecture variables and hardware implementation variables into one differentiable search space.
  2. Use Gumbel-Softmax to sample both operation choices and quantization choices.
  3. Formulate performance and resource terms differently for GPU, recursive FPGA, and pipelined FPGA targets.
  4. Search three EDD-Net models within 12 GPU-hours on a P100 GPU.
  5. Report similar ImageNet accuracy to prior hardware-aware NAS models, with 1.40x lower GPU latency than Proxyless-GPU and 1.45x higher FPGA throughput than DNNBuilder.

The important engineering idea is not that EDD invents a new operator. It still works inside an MBConv-style search space. The useful part is that the implementation knobs can push the architecture search while the architecture is still being selected.

GPU and FPGA details

For GPU, the target metric is batch-1 latency. The paper uses measured latency for candidate operations under supported precisions. At the time of the paper, TensorRT support limited the GPU precision choices to 8-bit integer and 16-/32-bit floating point. Mixed precision inference was also not treated as generally supported, so the searched GPU model uses one precision choice across the whole DNN.

For FPGA, the implementation variables are richer. The paper models:

  • operation latency under a selected bit-width
  • DSP usage as the main resource term
  • parallel factors, expressed as powers of two
  • recursive accelerator resource sharing
  • pipelined accelerator throughput

The FPGA quantization choices used in search are 4-/8-/16-bit weights with 16-bit activations. For the recursive FPGA case, EDD optimizes end-to-end latency with shared IP resources. For the pipelined FPGA case, it optimizes throughput with a resource budget across pipeline stages.

Search loop

The optimization follows a bilevel differentiable NAS loop:

  1. Fix , , and ; update DNN weights on the training set.
  2. Fix ; update , , and by descending the co-search objective on the validation set.
  3. Repeat until convergence or a fixed epoch budget.

In the experiments, the search runs for 50 epochs on a randomly sampled 100-class subset of ImageNet. The final searched models are then trained from scratch on full ImageNet with 1000 classes. The paper reports each EDD-Net is produced within a 12-hour search on one P100 GPU.

Results

The paper searches three models:

  • EDD-Net-1: low-latency GPU target.
  • EDD-Net-2: recursive FPGA accelerator target.
  • EDD-Net-3: pipelined FPGA accelerator target.

The key rows from Table 1 are:

Model Top-1 Error Titan RTX Latency ZCU102 Latency
MNasNet-A1 24.8 17.94 ms 8.78 ms
FBNet-C 24.9 22.54 ms 12.21 ms
Proxyless-GPU 24.9 15.72 ms 10.79 ms
EDD-Net-1 25.3 11.17 ms 11.15 ms
EDD-Net-2 25.4 13.00 ms 7.96 ms

For GPU, EDD-Net-1 reaches 25.3% ImageNet top-1 error and 11.17 ms latency on Titan RTX. The accuracy is close to Proxyless-GPU (24.9% top-1 error), but the latency is lower than Proxyless-GPU’s 15.72 ms. This is where the paper gets the 1.40x speedup claim.

The 1080 Ti TensorRT numbers show the expected precision tradeoff:

Precision Top-1 Error Latency
32-bit floating 25.5% 2.83 ms
16-bit floating 25.3% 2.29 ms
8-bit integer 26.4% 1.74 ms

For the recursive FPGA target, EDD-Net-2 reaches 7.96 ms latency on Xilinx ZCU102 with 25.4% top-1 error. It is faster than the listed FPGA implementations of MNasNet, FBNet, and Proxyless variants under the same CHaiDNN framework.

For the pipelined FPGA target, EDD-Net-3 is compared against DNNBuilder on ZC706:

Model Top-1 Error Top-5 Error Throughput
VGG16 on DNNBuilder 29.5 10.0 27.7 fps
EDD-Net-3 25.6 7.7 40.2 fps

The throughput ratio is about 40.2 / 27.7 = 1.45x, while the accuracy is also better.

Architectures

The searched architectures are visibly hardware-dependent. EDD-Net-3, targeting a pipelined FPGA accelerator, is shallower but uses more channels and larger kernels. That makes sense: more blocks complicate resource allocation and pipeline control, while wider stages can expose parallel work.

EDD-Net-1 and EDD-Net-2 stay closer to deeper MBConv chains, but the details still differ because the GPU and recursive FPGA latency/resource models are different.

This is the same lesson as ProxylessNAS, but pushed one level deeper. The best architecture is not only hardware-dependent; it is implementation-dependent.

Takeaway

EDD is most valuable as a formulation paper. It gives a way to ask:

  • What are the architecture variables?
  • What are the implementation variables?
  • Which parts can be relaxed into differentiable expectations?
  • Which hardware constraints should be modeled as performance loss and resource penalty?

The limitations are also clear. The search space is still a hand-designed MBConv space, not arbitrary DNN discovery. The GPU implementation search is relatively narrow because framework support restricts mixed precision and kernel choices. The FPGA performance/resource models are useful approximations, but the final implementation variables still need to be re-tuned after search.

Even with those constraints, the paper makes a good engineering point: hardware-aware NAS should not stop at “add latency to the loss.” If deployment quality depends on quantization, parallelism, resource sharing, or pipeline structure, those variables should influence the architecture while the architecture is being searched.
