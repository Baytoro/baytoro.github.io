BANANAS: Bayesian Optimization with Neural Architectures for NAS

H.J. Chen
  2021-06-08 2021-06-08 Created  
  • Paper Reading 
 
  • NAS 

White C, Neiswanger W, Savani Y. BANANAS: Bayesian Optimization with Neural Architectures for Neural Architecture Search. AAAI 2021.

Paper / Code

BANANAS is a predictor-based NAS method. It does not build a differentiable supernet like DARTS, and it does not train a controller like early RL-based NAS. The loop is closer to black-box Bayesian optimization: evaluate a small set of architectures, train a predictor from those observations, use an acquisition function to choose the next candidates, and repeat.

The useful part of this paper is that it does not treat “neural predictor for NAS” as one vague block. It studies five design choices separately:

Component BANANAS choice
Architecture encoding path encoding
Predictor feedforward neural network ensemble
Uncertainty ensemble variance
Acquisition independent Thompson sampling
Acquisition optimization mutation around strong evaluated architectures

The paper is therefore more valuable as an analysis of the BO + neural predictor framework than as a single named algorithm.

BO + Neural Predictor Setup

The search space is a set of architectures. Training an architecture gives its validation error, but this evaluation is expensive. BO tries to spend evaluations where they are likely to improve the best architecture found so far.

The practical loop is:

  1. randomly sample and evaluate several initial architectures;
  2. encode all evaluated architectures;
  3. train an ensemble of neural predictors on architecture/error observations;
  4. generate candidate architectures;
  5. score candidates with an acquisition function;
  6. evaluate the best candidates and update the dataset.

This is attractive because the expensive operation is still actual architecture training, while the predictor is cheap. But the predictor is only useful if the encoding makes architecture similarity visible. That is where path encoding becomes the main idea.

Path Encoding

Most NAS predictors before this paper used an adjacency matrix plus operation labels. That representation is faithful, but it gives the predictor an awkward feature space: node indices are arbitrary, edges are highly dependent, and an edge can be meaningless if it does not belong to an input-output path.

BANANAS instead encodes paths. Each binary feature means that a specific input-to-output operation path exists in the cell.

For NASBench-101, the paper reports that the path encoding can be reduced to about 20 bits without hurting the 150-evaluation BANANAS result. Their explanation is practical: many long or rare paths almost never appear under the random graph sampling procedure, so including them can make the predictor overfit noise.

This is the reusable idea from the paper. The representation is not only smaller than it first looks; it also matches the structure that determines architecture behavior.

Predictor And Uncertainty

BANANAS compares several predictor families on NASBench-101: feedforward networks with adjacency encoding, feedforward networks with path encoding, truncated path encoding, Bayesian neural networks, GCNs, and VAEs.

There are three different measurements in this figure:

Plot What it checks What I read from it
left predictor MAE on held-out architectures path encoding and GCN are the strongest predictors
middle RMSCE calibration error ensembles give better uncertainty estimates than the BNN setup used here
right full BO performance predictor quality must still translate into better search

The right plot matters most. A predictor can have low average error but still rank the best candidates poorly. NAS cares about the top of the ranking, not only global regression quality. In the paper’s full BO setting, the path-encoding feedforward ensemble slightly edges the GCN ensemble, while being simpler and less sensitive to GCN hyperparameters.

The uncertainty story is also pragmatic. The authors use an ensemble of predictors, not because it is theoretically perfect, but because it gives a simple mean and standard deviation for each candidate architecture. That is enough to drive acquisition functions such as expected improvement, UCB, Thompson sampling, and independent Thompson sampling.

BANANAS Pipeline

The final predictor is simple: encode architectures with paths, feed the vectors into an ensemble of feedforward networks, then use the ensemble outputs as performance estimates and uncertainty estimates.

The actual search algorithm adds one more strong engineering choice: do not optimize the acquisition function by sampling candidates uniformly from the whole search space. Generate candidates by mutating architectures that already look good.

The mutation step is doing a lot of work. A neural predictor trained on limited observations is usually more reliable near architectures related to what it has already seen. Mutating good architectures keeps the candidate set in that local neighborhood. This also makes the acquisition function easier to optimize than searching the entire discrete architecture space.

The final BANANAS recipe in the paper is:

Part Choice
predictor input path encoding
predictor model feedforward neural network ensemble
predictor loss MAPE-style loss that emphasizes low validation error
acquisition independent Thompson sampling
candidate generation mutation from the best evaluated architectures

The name sounds broad, but the algorithm is a specific combination of these components.

Results

The main experimental result is on NASBench-101, where the paper can run many controlled trials because architecture accuracies are precomputed. The setup uses about 150 architecture evaluations, reported as 47 TPU hours in the NASBench-101 accounting.

The three panels give useful ablations:

  1. acquisition functions are close, but independent Thompson sampling is a strong default;
  2. mutation beats random, local search, and evolution as the candidate-generation strategy in this setting;
  3. the final BANANAS curve is among the strongest baselines under the same evaluation budget.

The paper also evaluates the DARTS search space. This is less clean than NASBench-101 because it is not a precomputed tabular benchmark, but the comparison is still useful because it checks whether the method can leave a small tabular cell benchmark.

The reported DARTS-space result is:

Method Avg. test error Runtime Note
DARTS, paper 2.76 5 GPU-days gradient-based
DARTS, authors’ rerun 2.68 5 GPU-days same evaluation pipeline
BANANAS 2.64 11.8 GPU-days BO + neural predictor

I would not overread the small difference between 2.68 and 2.64. The more important point is that predictor-based BO remains competitive outside the exact NASBench-101 table, at a cost that is still far below early full-training NAS methods.

Reading Notes

What I would keep from BANANAS:

  • Architecture representation is not a detail. Path encoding changes the predictor’s job from graph interpretation to data-flow feature learning.
  • Predictor accuracy and uncertainty calibration should be checked together. A calibrated but inaccurate predictor is not useful for NAS.
  • Candidate generation matters as much as acquisition scoring. The mutation strategy makes BO practical in a huge discrete search space.
  • Truncating path encodings is not just a memory trick. It can remove rare-path noise and improve predictor behavior.
  • NASBench-style experiments are good for controlled optimizer comparisons, but DARTS-space or real training checks are still needed before treating a method as generally strong.

My main caveat is that BANANAS still relies on a search-space-specific encoding and mutation operator. That is fine for cell-based NAS, but it means the method is not plug-and-play for every architecture family. For a new space, I would first ask: what is the equivalent of an input-output path, and can mutation stay near architectures where the predictor has support?

Overall, BANANAS is a clean paper because it separates the NAS problem into pieces that can be tested: encoding, predictor, uncertainty, acquisition, and candidate generation. The final algorithm works because all five choices are aligned, not because Bayesian optimization alone solves NAS.
