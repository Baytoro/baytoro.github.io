Paper: Q8BERT: Quantized 8Bit BERT

Code: NLP Architect

Q8BERT is a compact paper, but it is a useful baseline for reading later BERT quantization work. The main question is practical:

If we are allowed to run quantization-aware fine-tuning, can BERT’s dominant matrix multiplications and embedding tables be moved to INT8 with small task accuracy loss?

The answer is mostly yes. Q8BERT quantizes the weights of BERT’s embedding and fully connected layers to 8-bit integers, simulates the quantized path during fine-tuning, and keeps higher-risk nonlinear operators such as Softmax, LayerNorm, and GELU in FP32.

That makes Q8BERT different from I-BERT:

  • Q8BERT is an 8-bit quantization-aware training baseline for the GEMM-heavy parts of BERT.
  • I-BERT later asks for integer-only inference and replaces Softmax, GELU, and LayerNorm with integer approximations.
  • BinaryBERT later goes to the opposite extreme: 1-bit weight compression with distillation and special initialization.

All crops below are taken from the original 2019 PDF.

The Problem

BERT-Base has about 110M parameters. BERT-Large has about 334M parameters. In FP32, that means large memory footprint, high bandwidth demand, and expensive feed-forward computation during inference. For latency-sensitive NLP services, this is not just a training cost problem; it is a production deployment problem.

Q8BERT’s target is conservative: stay at 8 bits, keep the original BERT architecture, and use quantization-aware training during downstream fine-tuning.

The abstract already states the scope: compress BERT by 4x with minimal accuracy loss and make the resulting model suitable for hardware with optimized 8-bit integer arithmetic.

The 4x number is straightforward. Moving most model weights from FP32 to INT8 reduces storage from 4 bytes per parameter to 1 byte per parameter. Since the paper quantizes all fully connected and embedding weights, which account for more than 99% of the model weights, the total model footprint approaches this 4x reduction.

What Is Quantized

The implementation goal is narrow and clear:

Component Q8BERT treatment
Embedding layer weights Quantized to INT8
Fully connected layer weights Quantized to INT8
FC input activations Fake-quantized during training; INT8 path for inference
GEMM accumulation INT32 accumulation
Bias Quantized to INT32
Softmax Kept in FP32
LayerNorm Kept in FP32
GELU Kept in FP32

This is why I read Q8BERT as a practical partial-integer inference paper, not an integer-only inference paper. It attacks the dominant memory and GEMM cost, but it does not eliminate floating-point islands from the Transformer block.

The implementation section is explicit: quantized embedding and FC layers replace the original layers, while Softmax, LayerNorm, and GELU remain FP32 because they require higher precision.

Why 8-bit GEMM Is The Main Target

BERT inference is dominated by dense matrix multiplications:

  • Q/K/V projections in self-attention;
  • output projection after attention;
  • the two feed-forward network linear layers;
  • embedding lookup storage and movement.

INT8 helps in two ways:

  1. Weight memory shrinks, reducing model footprint and memory bandwidth.
  2. Matrix multiplication can use integer hardware paths, such as VNNI-style instructions or other accelerator INT8 kernels.

The paper cites prior transformer INT8 GEMM work reporting 3.7x speedup over FP32 matrix multiplication on Intel Xeon Cascade Lake VNNI. Q8BERT does not prove a universal end-to-end 3.7x BERT speedup; it uses that hardware fact to justify targeting the GEMM-heavy parts of BERT.

This distinction matters. End-to-end latency depends on operator coverage, layout conversion, dequantization/requantization boundaries, memory movement, batch size, and backend implementation. Q8BERT’s accuracy result is strong evidence that BERT tolerates this INT8 GEMM path under QAT, but deployment speed still depends on the runtime.

QAT During Fine-tuning

The central training choice is to insert fake quantization into the fine-tuning graph. Forward propagation sees quantized values, but the underlying trainable parameters remain floating point.

Fake quantization creates the same rounding/clipping noise that the model will see at inference. During backpropagation, Q8BERT uses the straight-through estimator:

This is the standard QAT compromise. Rounding is not differentiable, but if the backward pass treats it as identity, the model can adapt its FP32 latent weights to produce quantization-friendly forward activations.

The practical pipeline is:

  1. Start from a pre-trained BERT checkpoint.
  2. Replace embedding and FC layers with quantized versions.
  3. During fine-tuning, run fake quantization for weights and activations.
  4. Keep latent weights in FP32 for optimization.
  5. Export INT8 weights and INT8 activation scales for inference.
  6. Run quantized embedding/FC/GEMM while keeping Softmax, LayerNorm, and GELU in FP32.

QAT is done during downstream fine-tuning, not during the original large-scale pre-training. This is why the paper is practical: it does not require pre-training BERT again.

Dynamic Quantization Baseline

The paper compares QAT with a dynamic quantization baseline. In this baseline, activations are quantized during inference, and the activation scale is computed from each incoming activation tensor using a max-absolute rule, similar to the weight scale.

The distinction is:

Method Scale source Why it behaves differently
DQ Current tensor max abs at inference The task fine-tuning stage never sees quantization noise
QAT EMA statistics from training Fine-tuning adapts to rounding and clipping noise

The authors find that dynamic quantization is consistently worse. This is not surprising: BERT is fine-tuned for a downstream task, and the quantized model needs that fine-tuning stage to see the same perturbations it will face at inference.

Main Results

The paper evaluates on GLUE tasks and SQuAD v1.1. It reports the mean and standard deviation over five runs. Most experiments use BERT-Base, with selected BERT-Large rows marked as Large.

The important pattern is that QAT stays close to FP32 while DQ often drops more:

Task FP32 baseline QAT INT8 DQ INT8
CoLA 58.48 58.48 56.74
MRPC F1 90.00 89.56 87.88
QNLI 90.30 90.62 89.34
QQP F1 87.84 87.96 84.98
RTE 69.70 68.78 63.32
SST-2 92.36 92.24 91.04
STS-B 89.62 89.04 87.66
SQuAD v1.1 F1 88.46 87.74 80.02

QAT sometimes slightly exceeds the baseline due to run variance, for example QNLI and QQP in the table. I would not over-interpret those small gains. The main claim is that QAT preserves accuracy, not that INT8 improves BERT.

Relative Error

Table 2 is a cleaner way to read the result because it reports the relative accuracy drop from quantization.

QAT has less than 1% relative error on every listed task except RTE:

Method Typical behavior
DQ Often multiple percent relative drop; 9.13% on RTE and 9.54% on SQuAD
QAT Usually below 1% relative drop; 1.32% on RTE and 0.81% on SQuAD

RTE is a small dataset and tends to have higher variance. The QAT row still improves substantially over DQ, but the relative drop is larger than the other GLUE tasks.

What The Paper Does Not Claim

Q8BERT is easy to overstate. The paper does not claim:

  • post-training quantization is enough for BERT;
  • every Transformer operator runs in INT8;
  • Softmax, LayerNorm, and GELU are solved in integer arithmetic;
  • end-to-end latency must improve by the same ratio as INT8 GEMM;
  • 4-bit or 2-bit BERT is covered by the same recipe.

The actual claim is narrower and more defensible:

With quantization-aware downstream fine-tuning, the GEMM-heavy embedding and fully connected layers of BERT can be quantized to INT8 while preserving most task accuracy.

This is why Q8BERT is still useful. It establishes a strong simple baseline for 8-bit QAT. Any more complex BERT quantization paper should explain what extra constraint it solves: lower bit-width, no task fine-tuning, integer-only nonlinear ops, better latency, or smaller memory.

Relationship To I-BERT

I-BERT directly addresses Q8BERT’s main limitation. Q8BERT leaves Softmax, LayerNorm, and GELU in FP32. I-BERT replaces them with integer-friendly approximations and keeps the whole inference path in integer arithmetic.

The comparison:

Aspect Q8BERT I-BERT
Main goal 8-bit BERT with QAT Integer-only BERT inference
Linear layers INT8 GEMM INT8 GEMM
Embeddings INT8 INT8
GELU FP32 Integer polynomial approximation
Softmax FP32 Integer exponential approximation
LayerNorm FP32 Integer sqrt and normalization
Practical message 8-bit QAT is enough for accuracy Operator coverage matters for integer-only deployment

So Q8BERT is not obsolete; it is a different operating point. If the backend already handles mixed INT8/FP32 efficiently, Q8BERT is a simple baseline. If the target hardware prefers integer-only execution, I-BERT’s stricter graph coverage becomes necessary.

Implementation Notes

A faithful reproduction should pay attention to quantization boundaries. It is not enough to say “BERT is INT8.” The questions are:

  1. Are embedding tables stored and returned as INT8?
  2. Are Q/K/V, attention output, and FFN matrix multiplications using INT8 inputs and weights?
  3. Are accumulators INT32?
  4. How are bias tensors quantized?
  5. Where does the graph dequantize before Softmax, LayerNorm, or GELU?
  6. Are activation scales static from training EMA, dynamic per batch, or calibrated post-training?
  7. Does the exported graph run on an actual INT8 backend, or only evaluate fake quantization?

The last point is important. Fake-quantized evaluation measures numerical robustness. It does not by itself measure speed. Speed requires an execution backend that maps the quantized FC layers to optimized INT8 kernels.

Reproduction Checklist

For a clean reproduction, I would separate accuracy, model size, and runtime:

Check What to measure
Accuracy GLUE/SQuAD metrics for FP32, DQ, and QAT over multiple seeds
Model size Serialized parameter footprint before and after INT8 export
Operator coverage Which layers run INT8, INT32, or FP32
GEMM speed Isolated FC/GEMM latency on the target hardware
End-to-end latency Full BERT request latency with tokenization excluded and included
Dequant overhead Cast/requant time around Softmax, LayerNorm, and GELU

The expected result is not just “the model is 4x smaller.” A deployment-oriented reproduction should show whether the model is also faster under the intended batch size and hardware backend.

Takeaway

Q8BERT is the clean 8-bit QAT baseline for BERT. It shows that if downstream fine-tuning is available, BERT’s embedding and fully connected layers can tolerate INT8 quantization with small accuracy loss across GLUE and SQuAD.

The most important caveat is operator coverage. Q8BERT quantizes the parts that dominate parameters and GEMM compute, but it keeps Softmax, LayerNorm, and GELU in FP32. That makes it practical and accurate, but not integer-only. Later papers like I-BERT should be read as tightening this exact gap.
