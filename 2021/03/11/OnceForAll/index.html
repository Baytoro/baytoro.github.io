Once-for-All: Train Once, Specialize Everywhere

H.J. Chen
  2021-03-11 2021-03-11 Created  
  • Work hard

  • NAS

Cai H, Gan C, Wang T, Zhang Z, Han S. Once-for-All: Train One Network and Specialize it for Efficient Deployment. ICLR 2020.

Paper / Code

Once-for-All (OFA) is a deployment paper disguised as a NAS paper. The problem is not only “can we find one efficient CNN?” The real problem is that deployment has many targets: different phones, CPUs, GPUs, FPGAs, battery modes, batch sizes, and latency budgets. Repeating neural architecture search and full training for every target is expensive and slow.

OFA changes the cost model. It trains one elastic network once, then specializes subnetworks for each deployment scenario without retraining from scratch.

All figures and tables below are cropped from the original paper PDF.

Core Idea

The first figure is the whole paper in one picture.

The left side is the model view: train a large elastic supernet and deploy different subnetworks for cloud AI, mobile AI, or tiny AI. The middle plot is the cost view: classic NAS has design cost that grows with the number of deployment scenarios, while OFA tries to make the expensive training step a one-time cost. The right plot shows the accuracy-latency menu produced by one trained OFA network.

The important phrase is “direct deploy.” OFA does not train a separate model after every architecture is selected. A subnet inherits weights from the once-for-all network. This is why the method is interesting for product deployment: many operating points can be shipped from one shared training run.

Why This Is Different From Ordinary NAS

Classic hardware-aware NAS usually does three things for every target:

  1. Define a search space and latency target.
  2. Search an architecture under that target.
  3. Train the selected architecture.

That workflow is fine for a paper with one benchmark setting. It is awkward for deployment. A model team may need one variant for Pixel latency, another for Samsung latency, one for CPU batch size 1, one for GPU batch size 64, and another for an FPGA accelerator. If every target needs search plus training, the cost is linear in the number of targets.

OFA decouples the expensive part:

  • Train one elastic once-for-all network.
  • Train cheap accuracy predictors and use hardware-specific latency lookup tables.
  • Run evolutionary search over subnet choices for each target.
  • Deploy the inherited subnet weights.

This turns NAS from “find one model” into “train a reusable model family.”

ImageNet Frontier

The paper’s headline ImageNet comparison is not a tiny-model result. OFA reaches 80.0% top-1 at 595M MACs, below the paper’s mobile setting threshold of 600M MACs.

This plot is useful because it compares against both hand-designed networks and AutoML-designed networks. OFA moves to the upper-left region: high ImageNet accuracy with low MACs. The result is not just “NAS found another point.” OFA can produce a family of points by selecting subnetworks from the same trained weights.

Progressive Shrinking

Training such a large shared-weight space naively is unstable. Small subnetworks and large subnetworks interfere with each other. OFA’s answer is progressive shrinking: start from the largest network, then gradually introduce smaller choices.

The order is:

  1. Train the full network.
  2. Support elastic resolution.
  3. Add elastic kernel size.
  4. Add elastic depth.
  5. Add elastic width.

Resolution is sampled throughout training. Kernel size, depth, and width are introduced progressively so smaller subnetworks inherit useful weights from already trained larger subnetworks. The paper also uses knowledge distillation after training the largest network: smaller subnetworks learn from both the real labels and soft labels from the largest network.

Relation To Pruning

Progressive shrinking is easy to confuse with pruning. The similarity is that both start from a large model and shrink it. The difference is the training target.

Network pruning usually produces one smaller model. OFA tries to keep a large family of subnetworks valid at the same time. It also shrinks across four dimensions, not only width.

That distinction matters. A pruned model is a single deployment point. OFA is closer to a trained architecture space: after training, a search procedure can choose a subnet for a new constraint without running full training again.

Elastic Kernel And Depth

The kernel and depth mechanisms are simple but important.

For elastic kernel size, the center of a larger kernel is reused by smaller kernels. A 7x7 kernel contains a 5x5 center, and the 5x5 contains a 3x3 center. OFA adds transformation matrices so the smaller centered kernels do not have to share raw weights blindly with the larger kernel.

For elastic depth, OFA keeps the first layers in a unit and skips the later layers. This is more structured than randomly dropping layers. It preserves a clear prefix-sharing pattern, which makes the inherited subnet easier to reason about.

Elastic Width

Width shrinking uses channel sorting.

The paper sorts channels by importance and keeps the most important channels when shrinking width. In the toy example, a 4-channel layer can shrink to 3 or 2 channels by preserving the highest-ranked channels. The practical benefit is that a smaller subnet starts from the most useful subset of the larger subnet instead of an arbitrary slice.

This is one of the reasons progressive shrinking is more stable than random subnet sampling. The smaller networks are not fighting the largest model from scratch; they are initialized as structured subsets.

Does Progressive Shrinking Help?

The ablation says yes. OFA compares subnetworks trained with progressive shrinking against subnetworks from a once-for-all network trained without it.

Across the sampled configurations, progressive shrinking improves top-1 accuracy by about 2.5 to 3.7 points. One concrete row is especially useful: at , , , OFA with progressive shrinking reaches 74.8% top-1 with 226M MACs, while the version without progressive shrinking reaches 71.5%.

This is the main training lesson. The elastic search space is only useful if inherited weights preserve ranking and accuracy. Progressive shrinking is what makes the inherited weights good enough to search over.

The #25 and #75 rows fine-tune the selected subnet for 25 or 75 epochs after inheriting weights. The no-retraining OFA row is already strong: 76.0% at 230M MACs and 58 ms, which beats MobileNetV3-Large in the table while keeping similar mobile latency.

The cost plot makes the scaling argument more obvious.

For 40 deployment scenarios, the paper reports OFA as 16x lower in CO2 emission than ProxylessNAS, 19x lower than FBNet, and 1300x lower than MnasNet. The exact accounting assumptions can be debated, but the direction is hard to miss: if deployment has many targets, training once and specializing later changes the economics.

Resource-Constrained Frontiers

OFA is not only cheaper. It also produces better trade-off curves under MAC and measured latency constraints.

The left plot compares MAC-constrained models. OFA reaches 79.1% top-1 at 389M MACs and 80.0% at 595M MACs. The right plot compares Pixel 1 latency. OFA reaches 80.1% at 143 ms and is reported as 2.6x faster than EfficientNet-B2 at a similar accuracy point.

The green curve, “OFA - Train from scratch,” is also important. It shows that the architecture alone is not the whole story. The inherited once-for-all weights matter; training the same selected architecture from scratch does not reach the same accuracy in the plotted setting.

Mobile Device Transfer

Mobile latency is not a single number. Different phones can rank architectures differently.

The six plots show Samsung, Google, and LG devices. OFA produces a dense accuracy-latency curve on each device, while MobileNetV3 is shown as a smaller set of reference points. This is where the once-for-all setup pays off: the method can search a new subnet for a new device using a measured latency table, without training a new supernet.

This is more useful than a single headline model. A deployment team often needs a curve, not one checkpoint.

Beyond Phones

The paper also evaluates CPU, GPU, mobile GPU, and FPGA platforms.

The key observation is that “efficient” is hardware-dependent. A model that is good on a phone CPU is not automatically good on an FPGA or GPU. OFA’s specialization step can choose different subnetworks for different latency models.

The FPGA analysis makes this concrete.

OFA improves arithmetic intensity and FPGA utilization compared with MobileNetV2 and MnasNet in the reported setup. This is a useful reminder that FLOPs are not enough. If an architecture has poor memory access behavior or poor accelerator utilization, fewer operations may not translate into faster inference.

Different Hardware Selects Different Architectures

The final architecture figure is one of the most practical parts of the paper.

The FPGA-specialized model heavily prefers 3x3 mobile blocks. The CPU and GPU examples use wider blocks and sometimes larger kernels. That matches the cost model intuition: an FPGA pipeline can favor simple point-wise/depth-wise structure, while CPU and GPU parallelism can make wider blocks or larger kernels worthwhile.

This is the strongest argument against one-size-fits-all mobile scaling. Changing only a width multiplier cannot express all hardware-specific trade-offs.

What I Would Use OFA For

OFA is useful when the product needs a model family:

  • multiple latency targets for the same task;
  • different devices with different kernels and runtimes;
  • a need to ship many checkpoints without retraining each one;
  • a hardware-aware search loop where latency measurement is cheap but training is expensive.

It is less useful when the architecture family itself is wrong. The paper is about CNNs for ImageNet-style vision models. It does not directly solve Transformer or LLM serving constraints, where KV cache, sequence length, batching, tensor parallelism, and memory bandwidth dominate the runtime story.

There is also a supernet ranking assumption. The selected subnet is only good if inherited weights and the accuracy predictor correlate with standalone performance. OFA improves this with progressive shrinking and distillation, but the assumption still needs validation when moving to a new task or search space.

Takeaway

OFA’s main contribution is not a clever single architecture. It is a reusable deployment workflow:

  1. Train one elastic network.
  2. Keep many subnetworks accurate through progressive shrinking.
  3. Build cheap accuracy and latency feedback.
  4. Select specialized subnetworks for each hardware and latency target.

That makes the expensive part of NAS amortized. For deployment, this is often more valuable than finding one more point on an ImageNet leaderboard.
