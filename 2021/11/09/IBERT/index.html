I-BERT: Integer-only BERT Quantization

H.J. Chen
  2021-11-09 2021-11-09 Created  
  • Paper Reading 
 
  • Quantization 
  • | BERT 

Kim S, Gholami A, Yao Z, Mahoney M W, Keutzer K. I-BERT: Integer-only BERT Quantization. ICML 2021.

Paper / Code

I-BERT is the paper I use as a checklist for whether a Transformer quantization method really covers the inference graph. Many BERT quantization methods store weights and activations in INT8, but still run GELU, Softmax, or LayerNorm in floating point. That is useful compression, but it is not integer-only inference.

The paper’s claim is stricter:

  • Embedding and MatMul run with INT8 multiplication and INT32 accumulation.
  • GELU, Softmax, and LayerNorm are approximated with integer-only arithmetic.
  • Intermediate tensors are not dequantized into floating point during inference.
  • The final graph can target hardware where integer logic is the natural execution path.

All figures and tables below are cropped from the original ICML PDF.

Motivation

BERT inference is dominated by matrix multiplications, but the graph is not only GEMM. A Transformer block also contains:

  • attention Softmax;
  • GELU in the feed-forward network;
  • LayerNorm before or after sublayers;
  • residual adds and requantization boundaries.

If the runtime dequantizes for every nonlinear operator, then the deployed graph alternates between integer and floating-point execution. This adds casts, memory movement, and backend complexity. It also prevents deployment on integer-only processors.

Figure 1 compares three regimes:

Regime What happens
simulated quantization parameters may be stored as integers, but inference is effectively FP32
partial integer quantization MatMul is integer, but Softmax still forces dequantize and requantize
I-BERT the whole self-attention path avoids floating-point arithmetic

The last case is the important one. I-BERT is not primarily about a new quantizer for linear layers. It is about removing floating-point islands from the Transformer block.

End-to-End Inference Path

In I-BERT, the rough inference contract is:

Component Arithmetic
Embedding INT8 representation
Q/K/V and FFN MatMul INT8 multiplication, INT32 accumulation
GELU integer polynomial approximation, INT32 path
Softmax integer exponential approximation and integer normalization
LayerNorm integer mean/variance/square-root path
Requantization output tensors returned to INT8 where needed

This is not the same as saying every intermediate scalar is stored in 8 bits. The nonlinear operators use INT32 intermediate values where needed. The stronger claim is that the graph avoids floating-point arithmetic and dequantization during inference.

That distinction matters. INT32 accumulation is normal for INT8 inference. Floating-point fallback is the thing I-BERT is trying to remove.

GLUE Results

The paper evaluates RoBERTa-Base and RoBERTa-Large on GLUE development tasks. Representative averages:

Model Precision Integer-only Average GLUE
RoBERTa-Base baseline FP32 no 86.0
RoBERTa-Base I-BERT INT8 yes 86.3
RoBERTa-Large baseline FP32 no 89.0
RoBERTa-Large I-BERT INT8 yes 89.5

I would not overread the small average improvements as “quantization is better than FP32.” The robust conclusion is that the integer-only approximations do not create the usual accuracy collapse. For a graph-level quantization paper, preserving full-precision accuracy while removing floating-point nonlinear operators is already the result.

The table also shows task-level variation. RoBERTa-Base loses 0.3 on MNLI-m and STS-B, gains 1.3 on CoLA, and gains 1.4 on RTE. RoBERTa-Large is more uniformly positive in the reported run. This kind of movement is normal when quantization-aware fine-tuning and task variance interact.

Latency

The latency table reports INT8 speedup over FP32 on a Tesla T4 setup:

Model Average speedup Best reported speedup
BERT-Base 3.08x 3.39x
BERT-Large 3.56x 4.00x

This is a useful systems signal, but there is a caveat. T4 is not an integer-only edge processor. The authors choose it because TensorRT and Turing Tensor Cores give usable INT8 deployment support. The paper’s deeper value is that the same arithmetic contract can target hardware where floating point is expensive or unavailable.

For reproduction, I would report latency together with:

  • sequence length;
  • batch size;
  • whether attention kernels are fused;
  • whether nonlinear operators are custom integer kernels;
  • how many dequantize or FP32 nodes remain in the exported graph.

Without that graph-level accounting, “INT8 speedup” can hide important fallback behavior.

GELU Ablation

The GELU ablation isolates the approximation quality:

Method Integer-only Avg.
GELU no 92.3
h-GELU yes 92.0
i-GELU yes 92.7

This is the best evidence that the polynomial details matter. A crude integer-friendly GELU is not enough. h-GELU is integer-only but loses accuracy, especially on RTE in this table. i-GELU is both integer-only and closer to the true GELU shape.

My reading: the method succeeds because it treats numerical approximation as part of model quality, not merely as kernel engineering. If the approximation changes the nonlinear function too much, quantization-aware fine-tuning has to compensate for a shifted model.

Reproduction Notes

If I were implementing I-BERT, I would check the following before trusting the result.

First, verify operator coverage. The exported graph should not contain hidden FP32 GELU, Softmax, LayerNorm, division, square root, or dequantize nodes inside the Transformer block.

Second, log scales at every sublayer boundary. Integer-only inference depends on scale propagation. Residual adds are especially easy to get wrong because two branches may carry different scales.

Third, test approximation error independently. Before running GLUE, compare i-GELU and i-exp outputs against their floating references over the expected activation ranges. This catches coefficient, rounding, clipping, and bit-shift mistakes.

Fourth, stress LayerNorm. The integer square-root path must handle small variance, large variance, and long sequences without overflow or divide-by-zero behavior. LayerNorm bugs often appear as rare unstable examples rather than as a clean average drop.

Fifth, keep latency honest. Measure an actual backend graph. A PyTorch simulation of integer arithmetic is useful for accuracy, but the deployment claim depends on kernels that actually execute the integer path.

Limitations

I-BERT is a strong paper, but its scope is clear.

  • It studies 8-bit integer-only inference, not ultra-low-bit BERT.
  • It evaluates RoBERTa/BERT-style encoders, not decoder-only LLMs with KV cache and causal attention.
  • Nonlinear operators use INT32 intermediate arithmetic, so “integer-only” does not mean every intermediate is INT8.
  • The latency experiment uses a Tesla T4/TensorRT path, not a low-end integer-only microcontroller.
  • Static quantization requires reliable calibration and fine-tuning; bad ranges can still break the graph.

The paper also predates many later LLM quantization constraints: long context, rotary embeddings, activation outliers, group-wise weight-only INT4, KV cache quantization, and mixed backend execution. Still, the operator-coverage lesson transfers directly.

Takeaway

I-BERT is valuable because it changes the question from “are the weights INT8?” to “can the whole Transformer inference graph run without floating point?”

The core recipe is:

  • use ordinary INT8/INT32 arithmetic for linear layers;
  • approximate GELU and Softmax with low-order integer-friendly polynomials;
  • implement LayerNorm’s dynamic square root with integer arithmetic;
  • preserve scale information across every sublayer and requantization point.

When I read later quantization papers, I-BERT is the baseline for honesty. If GELU, Softmax, LayerNorm, or residual rescaling still dequantize into FP32, the method may still be useful, but it is not making the same integer-only claim.
