FBNetV2: Differentiable Neural Architecture Search for Spatial and Channel Dimensions

H.J. Chen
  2021-11-27 2021-11-27 Created  
  • Work hard 
  • >
  • PaperReading 
 
  • NAS 
  • | Mobile 

Wan A, Dai X, Zhang P, et al. FBNetV2: Differentiable Neural Architecture Search for Spatial and Channel Dimensions. CVPR 2020.

Paper / Code

FBNetV2 is a follow-up to FBNet, but the problem is different. FBNet searches layer-wise operator choices under a target latency objective. FBNetV2 asks a more structural question: can differentiable NAS search channel width and input resolution directly?

Those two dimensions matter a lot for mobile networks. Width changes activation memory, parameter count, kernel efficiency, and FLOPs. Resolution changes early feature-map cost and receptive field behavior. But they are awkward for DNAS because different choices produce tensors with different shapes.

FBNetV2’s answer is DMaskingNAS: represent channel and resolution choices with masks and feature-map reuse, so the memory cost stays almost constant as the search space grows.

All figures and tables below are cropped from the original arXiv PDF.

Motivation

Standard differentiable NAS is expensive because the supernet instantiates all candidate operations. If a layer can choose among many blocks, all those blocks must exist in memory during search. This becomes worse when the candidate choices are not just operator types but also tensor shapes.

Channel search creates two direct problems:

  • outputs with different numbers of channels cannot be naively summed;
  • instantiating every width option increases memory and compute.

Resolution search creates similar problems:

  • feature maps with different spatial sizes cannot be naively summed;
  • padding or upsampling can create pixel/receptive-field misalignment.

The figure compares four cases:

  • normal DNAS without channel search;
  • naive DNAS with all possible channel counts, which creates shape mismatches and high memory cost;
  • pruning-style search, which explores channel counts sequentially;
  • DMaskingNAS, which keeps all possible channel choices inside one weight-sharing graph.

The abstract gives the headline: with up to 421x less search cost, DMaskingNAS finds models with 0.9% higher accuracy and 15% fewer FLOPs than prior efficient models in one comparison, and it can outperform MobileNetV3 by 2.6% accuracy at comparable model size.

Search Dimensions

FBNetV2 expands the search space beyond block type.

Dimension Why it matters
operator/block controls kernel type, activation, expansion, and SE
channel width controls activation size, memory traffic, and parameter count
input resolution controls early feature-map cost and receptive field
depth/stage shape changes how computation is distributed across the network

This is closer to how mobile networks are actually designed. A real model family is rarely defined only by “which MBConv block goes here.” Width and resolution dominate the accuracy-cost tradeoff.

The search-space table shows the macro search space and the micro block choices. Macro choices include maximum input resolution, bottleneck type, expansion-rate range, output-channel range, number of blocks, and stride. Micro choices include kernel size, squeeze-and-excitation, and nonlinearity.

Channel Masking

The channel-search idea is to represent width choices with masks. A mask selects the first k active channels from a larger tensor. Instead of training separate convolutions for every channel count, DMaskingNAS uses a shared full-width computation and applies masks to reuse feature maps.

On the left side, channel masking builds a weighted mask from several candidate masks. On the right side, resolution subsampling represents different input resolutions without storing a separate feature map for every candidate resolution.

The intuition:

  • channel choices are nested subsets of a maximum channel tensor;
  • candidate masks have negligible memory cost compared with feature maps;
  • sharing the larger feature map avoids keeping many parallel tensors alive;
  • Gumbel-Softmax weights decide which candidate mask is preferred.

Figure 3 explains why the naive formulation breaks. If each candidate width has a different output channel count, the outputs cannot be summed. Zero-padding makes them summable, but it still computes several separate convolutions. DMaskingNAS approximates this with weight sharing: compute one convolution, then combine masks.

This is the main memory trick. The graph can represent many channel options without materializing a full candidate path for each one.

Resolution Subsampling

Resolution search is harder than “resize input and continue.” If feature maps with different spatial sizes are padded incorrectly, pixels do not align. If a convolution sees a subsampled feature map naively, the effective receptive field changes.

FBNetV2 handles this through resolution subsampling. The smaller-resolution branch is represented as a sampled subset of the larger feature map. Values are placed back into a larger map at the corresponding positions, while missing positions are left as zeros. This avoids building a separate feature map for each resolution candidate.

Two details matter:

  • zero-padding should not contaminate pixels from different resolutions;
  • receptive field should stay consistent, so subsampling must happen before the operation where needed.

The result is a DNAS search space that can include input resolution choices without exploding memory in the same way as naive all-path DNAS.

Effective Shape Propagation

During search, the network is not yet a single discrete architecture. Channel and resolution choices have weights, so the model has an effective shape:

  • effective output channels;
  • effective height and width;
  • effective FLOPs or parameter cost.

This lets FBNetV2 assign a resource penalty during search even when the current supernet choice is still relaxed. For example, if a 16-channel option has weight 0.8 and a 12-channel option has weight 0.2, the effective channel count is 15.2. That fractional value is not a deployed tensor shape; it is a search-time proxy for cost.

This is an important distinction. DMaskingNAS is not saying the final model has fractional channels. It uses effective shapes to guide the continuous search, then samples a discrete architecture and trains it normally.

Memory Cost

Figure 7 is the most important diagnostic. Conventional DNAS memory rises quickly as the number of channel options grows. With only 8 options per block, the paper reports that conventional DNAS fails to fit in 16GB V100 memory. DMaskingNAS remains roughly constant even with 32 channel options per block.

The text reports that DMaskingNAS adds roughly 1MB memory for every two orders of magnitude increase in channel search space, about 0.1% of the total memory cost during training in their setup. That is the concrete reason the method can search wider dimensions than ordinary DNAS.

Search Setup

The paper implements DMaskingNAS in PyTorch and uses 8 Tesla V100 GPUs with 16GB memory. It searches architectures under different resource objectives and trains final models from scratch.

The naming convention is:

  • FBNetV2-F: FLOP-efficient models;
  • FBNetV2-P: parameter-efficient models;
  • FBNetV2-L: larger models.

For the FLOP-efficient search space, the maximum input resolution is 224. For larger FBNetV2-L models, the maximum input resolution is 256. The supplementary material lists the final macro-architectures.

The strongest small-model comparison is FBNetV2-F1 versus MobileNetV3-Small: 68.3% versus 67.4% top-1 with fewer FLOPs in the reported table. In the middle range, FBNetV2-F3 reaches 73.2% top-1 at 126M FLOPs, much smaller than many baselines around the same accuracy.

The FLOPs-accuracy curve shows the F-series models on a compact frontier. The black markers are FBNetV2; they sit above many hand-designed and searched baselines at similar FLOPs.

The bottom plots separate two regimes:

  • parameter-efficient models, where model size matters more than FLOPs;
  • larger models, where FBNetV2-L is compared with EfficientNet, MobileNetV3, and other larger baselines.

The paper’s broader claim is not only that one model is good. It is that searching channel and resolution dimensions opens a better family of tradeoffs.

What Changed From FBNet

FBNet and FBNetV2 attack different bottlenecks.

Paper Main search dimension Main technical trick
FBNet operator choice under latency stochastic supernet plus latency lookup table
FBNetV2 channel width and input resolution feature-map masks plus effective shape propagation

FBNet asks: which operator should each layer use for this device?

FBNetV2 asks: how can DNAS even afford to search over tensor shapes?

The second question is more structural. Once channel and resolution are in the search space, the architecture family can move in ways a fixed-width MobileNet-style search cannot.

Reproduction Notes

A reproduction should not only report final top-1 accuracy. I would check:

  • maximum GPU memory during supernet search;
  • number of channel and resolution candidates per block;
  • whether masks are nested and aligned correctly;
  • whether the final architecture is sampled and trained from scratch;
  • how effective FLOPs and effective shape are computed during search;
  • whether BatchNorm/statistics are handled consistently when channel masks change.

The most important debugging view is the memory curve. If memory grows linearly with the number of channel options, the implementation is probably instantiating candidate paths instead of using the intended masking formulation.

Limitations

FBNetV2 is still constrained by a manually designed mobile search space. It does not discover arbitrary network topologies, and its final quality depends on the candidate ranges for width, resolution, expansion, depth, kernel, SE, and activation.

The method also relies on a relaxed search proxy. Effective shapes guide the supernet, but the final model is discrete. The proxy must preserve enough ranking information for the sampled architecture to be good after full training.

Finally, the paper emphasizes FLOPs, parameters, and ImageNet accuracy more than direct latency on every target runtime. For deployment, FBNet-style measured latency should still be checked after the final architecture is materialized.

Takeaway

FBNetV2 is useful because it moves differentiable NAS from operation choice toward shape choice. Channel width and input resolution are central mobile design variables, but they break naive DNAS because tensors no longer match.

DMaskingNAS solves this by reusing feature maps with masks, keeping memory nearly constant as the channel/resolution search space expands. That makes layer-wise search over width and resolution practical, and the resulting FBNetV2 models show stronger accuracy-cost tradeoffs than simply scaling a fixed backbone.
