NAS-Bench-201: Extending the Scope of Reproducible Neural Architecture Search

H.J. Chen
  2021-08-30 2021-08-30 Created  
  • Paper Reading 
 
  • NAS 
  • | Benchmark 

Dong X, Yang Y. NAS-Bench-201: Extending the Scope of Reproducible Neural Architecture Search. ICLR 2020.

  • Paper: https://arxiv.org/pdf/2001.00326.pdf
  • Code/API: https://github.com/D-X-Y/NAS-Bench-201

NAS-Bench-201 is the natural follow-up to NAS-Bench-101. NAS-Bench-101 made a large cell space queryable, but it used only one dataset and imposed graph constraints that excluded some NAS algorithms. NAS-Bench-201 chooses a smaller fully enumerated space, then spends the saved budget on cleaner diagnostics: multiple datasets, more operations, and better support for different optimizer families.

The result is one of the most useful sanity-check benchmarks for NAS. It is small enough to be completely tabular, but rich enough to expose failure modes such as skip-connection collapse, weak transfer across datasets, and misleading early validation signals.

Search Space

NAS-Bench-201 uses a four-node cell. Every directed edge chooses one operation from a fixed set:

  • zeroize;
  • skip connection;
  • 1x1 convolution;
  • 3x3 convolution;
  • 3x3 average pooling.

There are 6 edges and 5 possible operations per edge, so the encoded search space has architectures.

The macro network repeats the searched cell inside a fixed skeleton. Compared with NAS-Bench-101, the cell is smaller, but the operation set is broader and the graph is unconstrained enough to support reinforcement learning, evolution, differentiable NAS, and hyperparameter-optimization-style search.

The paper also reports fewer unique topologies after accounting for equivalence: 12,751 if skip-connection isomorphism is considered, and 6,466 if both skip and zeroize isomorphisms are considered. That is a good reminder that an encoded search space and a semantic search space are not always the same thing.

What It Adds Over NAS-Bench-101

The paper includes a concise comparison table. The main differences are not only size. NAS-Bench-201 is multi-dataset, supports more NAS families, and exposes more diagnostic information.

NAS-Bench-201 stores results on:

  • CIFAR-10;
  • CIFAR-100;
  • ImageNet16-120.

For each architecture, it stores training, validation, and test loss/accuracy, plus compute-related properties such as parameter count, FLOPs, and latency. The latency measurement in the released benchmark was collected on a GTX 1080 Ti with batch size 256 for the non-CIFAR-10 settings.

This changes the kind of question the benchmark can answer. Instead of asking only “which method wins on CIFAR-10?”, we can ask whether a search method finds architectures that transfer across datasets and whether its behavior is stable when the target distribution changes.

Distribution of Architectures

The full enumeration gives a view of the entire space, not just the subset visited by a search algorithm.

The scatter plots show training, validation, and test behavior over all 15,625 architectures on all three datasets. The orange ResNet marker is a useful anchor. It is competitive, but not optimal: the paper notes that there is still about a 2% gap to the best architecture on CIFAR-100 and ImageNet16-120, and about a 1% gap among models with comparable parameter count.

The benchmark therefore has room for search algorithms to improve over a hand-designed baseline, while still being small enough that we can know the actual optimum.

Cross-Dataset Transfer

One of the strongest reasons to use NAS-Bench-201 is cross-dataset analysis. The paper sorts architectures by CIFAR-10 ranking and then shows where the same architectures rank on CIFAR-100 and ImageNet16-120.

The rankings are broadly correlated, but not identical. This matters for NAS claims. An optimizer that looks strong on CIFAR-10 may be exploiting a region that does not transfer cleanly to the other two datasets.

The correlation matrices make the same point more explicitly.

Within-dataset validation/test correlation is high. Cross-dataset correlation is lower, and it becomes weaker when focusing only on high-performing subsets. That is the practical regime of NAS: after a method filters out weak models, it still needs to rank good models, and that ranking is much harder to transfer.

Dynamic Ranking During Training

NAS-Bench-201 also records training curves, which makes it possible to ask how early validation accuracy relates to final test ranking.

The rank ordering becomes clearer as training progresses. At 1 epoch, the ranking is noisy. By 150 to 200 epochs, the validation ranking is much closer to final test ranking. This is the same lesson as NAS-Bench-101: early signals are useful, but using them as exact rank labels for the top architectures is risky.

Search Algorithm Results

The paper evaluates ten search algorithms, including random search, regularized evolution, REINFORCE, BOHB, DARTS variants, GDAS, SETN, ENAS, and random search with parameter sharing.

The table is valuable because it includes both search time and final validation/test performance across all three datasets. A few points stand out:

  • Random search is already a strong baseline in this compact space.
  • Regularized evolution is consistently competitive and extremely cheap when evaluated through the benchmark API.
  • Differentiable and parameter-sharing methods can fail badly if their search dynamics collapse to degenerate cells.
  • The optimal row is known, so the gap to the true best architecture is visible.

The paper also runs 500 trials for several non-weight-sharing search methods and plots trajectories across datasets.

This plot is closer to how NAS optimizers should be compared: many runs, explicit distribution, and both validation and test behavior. A single lucky search run is not enough evidence.

Parameter-Sharing Failure Mode

NAS-Bench-201 is especially useful for diagnosing parameter-sharing methods. In the reported experiments, DARTS-V1 and DARTS-V2 quickly move toward architectures dominated by skip connections, causing poor final performance.

The batch-normalization statistic strategy also matters. When using batch statistics instead of keeping running estimates for BN layers in each searched cell, the trajectories change.

This is a good example of why benchmarks need fine-grained traces. If a paper reports only the final architecture, we cannot tell whether the method failed because the search space is bad, the optimizer is bad, or the shared-weight evaluation protocol is biased.

Early Training Correlation

The appendix compares early-budget correlations with full-budget metrics.

Twelve-epoch training already gives a useful signal. For example, the 12-epoch diagnostic setting has strong correlations with full validation/test metrics across the three datasets. But the correlations are not perfect, especially for transfer to ImageNet16-120. Early stopping is a useful accelerator, not a replacement for final evaluation.

API Shape

The released API makes the benchmark easy to use from a script. The paper includes a short example showing architecture lookup, metric access, compute-cost access, and query by architecture string.

A typical use should keep the protocol explicit:

When reporting results, it is worth stating the dataset split, search budget, number of seeds, whether validation or test accuracy was queried during search, and whether any training-curve information was allowed.

Limitations

NAS-Bench-201 is controlled and compact, which is exactly why it is useful. But the same design also limits its scope:

  • the search space has only 15,625 encoded architectures;
  • all tasks are image classification;
  • the macro skeleton is fixed;
  • latency is measured in a limited hardware setting;
  • operation choices are small compared with modern mobile or Transformer spaces;
  • parameter-sharing results can depend strongly on implementation details.

Success on NAS-Bench-201 is therefore not proof that a method will work on every large real search space. It is evidence that the method survives a clean, fully observable diagnostic environment.

Takeaway

NAS-Bench-201 is a stronger NAS sanity check than a single-dataset benchmark. It tests whether a search algorithm beats simple baselines, avoids degenerate skip-heavy cells, and transfers across CIFAR-10, CIFAR-100, and ImageNet16-120. I would use it after NAS-Bench-101 and before moving to larger surrogate or real-training benchmarks.
