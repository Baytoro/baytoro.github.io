SpQR: Sparse-Quantized LLM Weight Compression

H.J. Chen
  2023-12-27 2023-12-27 Created  
  • Paper Reading 
 
  • Quantization

Paper: SpQR: A Sparse-Quantized Representation for Near-Lossless LLM Weight Compression
Code: Vahe1994/SpQR

SpQR is a post-training weight compression method for LLMs. The short version is simple: most weights are stored in a dense 3-4 bit group-wise format, while a very small set of high-sensitivity weights is stored separately in a sparse high-precision component.

That makes SpQR different from a plain W4 quantizer. It is a representation format:

  1. a dense low-bit matrix for the common case;
  2. compressed quantization metadata for scales and zero points;
  3. a sparse matrix of sensitive outlier weights;
  4. a kernel path that must combine the dense and sparse parts efficiently.

The paper’s target is “near-lossless” compression: keep the quantized model within roughly 1% relative perplexity degradation compared with the 16-bit model, while reducing model memory by more than 4x.

Why This Paper Matters

The useful observation is not merely that outliers exist. The useful observation is that the outlier budget can be tiny if the detector measures the right thing.

Figure 1 from the paper. SpQR gets a better quality-size tradeoff than RTN and GPTQ on LLaMA models, both for WikiText2 perplexity and zero-shot accuracy.

On the left plot, lower is better. On the right plot, higher is better. The green SpQR curve is usually closer to the fp16 frontier for the same model size. This is the core reason the method is interesting: it does not just squeeze the same dense quantizer harder, it changes the storage format so that difficult weights do not ruin the dynamic range of normal groups.

Sensitivity, Not Magnitude

A tempting outlier rule is “large absolute value means outlier”. SpQR uses a stricter criterion: a weight is important if quantizing it causes output error that cannot be compensated well by nearby weights.

This figure is the strongest motivation for the sparse component. Sensitive weights are not only clean columns. Some are row-like, some are head-local, some follow RoPE-related structure, and some are simply unstructured. A channel-only rule would miss part of the picture.

Representation

SpQR has three compression ideas that must be read together.

First, it uses very small groups for normal weights. A typical first-level group size is 16 contiguous weights. Small groups reduce local dynamic-range waste, which is helpful at 3-4 bits.

Second, it compresses the quantization statistics themselves. If every 16-weight group stores high-precision scale and zero-point values, metadata becomes too expensive. SpQR therefore quantizes those statistics with a second-level grouping scheme. In the paper’s example, a 256-weight block can be split into 16-weight first-level groups, and the scale/zero statistics for those groups are themselves quantized with compact second-level statistics.

Third, it extracts high-sensitivity weights into a sparse high-precision path. These outliers are usually less than 1% of all weights. The sparse representation stores a 16-bit value and a 16-bit column index for each outlier, plus a row-prefix structure. The average cost is about 32 bits per outlier, so the method only works if the sparse set stays small.

Figure 3 from the paper. The stored tensor consists of quantized weights, first-level quantized scales/zeros, second-level statistics, and a sparse outlier component.

One subtle implementation detail matters: an outlier still has a low-bit value in the dense matrix, and the sparse path stores a correction-like high-precision value. This keeps the dense memory layout regular. The outlier value is also affected by GPTQ-style error compensation, so it should not be read as merely “copy the original fp16 weight into sparse storage”.

The algorithm is closest in spirit to GPTQ: it processes layers with calibration data, estimates reconstruction error, and performs error compensation. SpQR adds an outlier-detection step and a storage format that can actually keep those outliers.

Main Results

The headline result is near-lossless compression for LLaMA and Falcon models at about 4.4-4.7 average bits per parameter. The average-bit number includes weights, quantization statistics, and sparse metadata.

Table 1 from the paper. LLaMA perplexity on WikiText2, C4, and Penn Treebank.

Selected LLaMA rows:

  • 7B fp16: 16.00 average bits, 5.68 WikiText2, 7.08 C4, 8.80 PTB.
  • 7B SpQR near-lossless: 4.63 average bits, 5.73 WikiText2, 7.13 C4, 8.88 PTB.
  • 7B GPTQ W4: 4.00 average bits, 6.13 WikiText2, 7.43 C4, 9.27 PTB.
  • 7B SpQR low-bit: 3.94 average bits, 5.87 WikiText2, 7.28 C4, 9.07 PTB.
  • 65B fp16: 16.00 average bits, 3.53 WikiText2, 5.62 C4, 6.91 PTB.
  • 65B SpQR near-lossless: 4.71 average bits, 3.57 WikiText2, 5.64 C4, 6.93 PTB.
  • 65B GPTQ W4: 4.00 average bits, 3.83 WikiText2, 5.80 C4, 7.07 PTB.
  • 65B SpQR low-bit: 3.90 average bits, 3.68 WikiText2, 5.70 C4, 6.99 PTB.

The near-lossless rows are the important ones for the paper’s main claim. For LLaMA-65B, SpQR at 4.71 average bits moves WikiText2 from 3.53 to 3.57 and C4 from 5.62 to 5.64. The lower-bit SpQR row is also useful: at 3.90 average bits, it still beats the 4-bit GPTQ baseline in this table.

Table 2 from the paper. Falcon perplexity results show the same pattern: near-lossless SpQR is close to fp16, while the lower-bit setting remains competitive with 4-bit GPTQ.

The Falcon table is a good sanity check because the calibration and model family differ from LLaMA. For Falcon-40B, fp16 gets 5.23 on WikiText2 and 7.76 on C4. SpQR at 4.46 average bits gets 5.26 and 7.79, while the 3.90-bit SpQR setting gets 5.29 and 7.85.

Ablations

The ablation table answers two practical questions:

  1. Does compressing quantization statistics hurt?
  2. Are unstructured sensitive weights actually better than row/column-style outliers?

Table 3 and Figure 4 from the paper. Quantized statistics remain effective, and unstructured SpQR outliers reduce perplexity faster than row or column outlier choices.

The 65B ablation is useful because it shows why metadata compression is not optional. With 3-bit quantized statistics, SpQR reports 3.74 WikiText2 perplexity at 3.63 average bits. Using 16-bit statistics is not better in this setting: it reports 3.84 at 3.67 average bits. In other words, spending more bits on metadata is not automatically the right allocation.

The outlier-type plot also supports the sensitivity-based design. The unstructured SpQR outlier rule gives the best perplexity improvement as the sparse share increases. Row outliers and the Dettmers et al. column outlier criterion help less for this weight-only setting.

Bit Accounting

SpQR should always be compared by effective bits per parameter, not only by the dense weight bit-width. The stored model includes:

  • low-bit dense weights;
  • first-level scales and zero points;
  • second-level statistics used to quantize those scales and zero points;
  • sparse outlier values;
  • sparse outlier indices and row-prefix metadata.

Inference

The runtime story is more complicated than the compression story. A naive sparse correction path can erase the benefit of smaller weights. The paper therefore implements a custom sparse matrix multiplication path instead of relying only on a standard PyTorch sparse operator.

Table 4 from the paper. Batch-1 A100 decoding speed in tokens per second.

Selected numbers:

  • 7B scratch: fp16 47, PyTorch sparse 30, optimized SpQR 57 tokens/s.
  • 7B prefix 1024: fp16 46, PyTorch sparse 27, optimized SpQR 55 tokens/s.
  • 13B scratch: fp16 37, PyTorch sparse 24, optimized SpQR 44 tokens/s.
  • 13B prefix 1024: fp16 31, PyTorch sparse 21, optimized SpQR 37 tokens/s.
  • 30B scratch: fp16 19, PyTorch sparse 8.8, optimized SpQR 22 tokens/s.
  • 30B prefix 1024: fp16 17, PyTorch sparse 6.5, optimized SpQR 22 tokens/s.
  • 65B scratch: fp16 OOM, PyTorch sparse OOM, optimized SpQR 12 tokens/s.
  • 65B prefix 1024: fp16 OOM, PyTorch sparse OOM, optimized SpQR 11 tokens/s.

Two points stand out.

First, the PyTorch sparse path is slower than fp16 even though the model is compressed. This is the warning sign: a sparse-plus-dense format is not automatically fast.

Second, the optimized SpQR path is faster than fp16 for the model sizes that fit, and it runs 65B where the fp16 baseline is out of memory. This is the real systems contribution: the representation needs a kernel implementation that respects GPU memory behavior.

The paper still leaves a limitation here. Dense low-bit matrix multiplication and sparse correction are not fully fused. A fused implementation could be faster, but it is also harder to engineer.

Relation To Other Quantization Work

GPTQ is the closest ancestor. It uses a second-order reconstruction objective and layer-wise error compensation, but stores the final result as dense low-bit weights. SpQR keeps the GPTQ-style sensitivity signal and adds a sparse high-precision escape path.

AWQ protects activation-salient channels by rescaling weights before quantization. That is attractive because the runtime can remain a regular dense quantized path. SpQR is more explicit about storing exceptions, which can preserve quality but requires sparse metadata and kernels.

SqueezeLLM is conceptually nearby because it also studies weight sensitivity and compressed low-bit storage for LLMs. The design details differ: SpQR emphasizes group-wise uniform quantization, bilevel statistics, and a sparse outlier representation.

LLM.int8() should not be confused with SpQR. LLM.int8() isolates activation outlier dimensions during matrix multiplication. SpQR isolates weight outliers in the stored model.

Reproduction Checklist

If I were reproducing this paper, I would track these items explicitly:

  • Start from a working GPTQ-style layer reconstruction implementation.
  • Verify the calibration data path first. The paper uses RedPajama for LLaMA and RefinedWeb for Falcon.
  • Plot sensitivity maps for a few late transformer layers. If the detector only finds clean columns, something may be too simplistic.
  • Tune the outlier threshold by target outlier rate, not by raw threshold value alone.
  • Report effective bits per parameter, including statistics and sparse indices.
  • Compare three variants: dense-only GPTQ, SpQR with sparse storage disabled at runtime, and full SpQR.
  • Benchmark the sparse correction path separately from dense dequantization.
  • Report both perplexity and zero-shot tasks. Perplexity alone is useful but not enough to understand downstream behavior.

The easy mistake is to celebrate low dense bit-width while hiding metadata. SpQR is convincing because the paper keeps the average-bit accounting visible.

Limitations

SpQR is not the simplest deployment format. A regular W4 group-wise model has easier kernels, easier packing, and fewer metadata edge cases. SpQR buys quality by accepting an irregular sparse path.

The sparse path can also become a failure mode. If a model, target bit-width, or calibration setup requires too many outliers, the index/value cost and irregular memory access can dominate. At that point the representation is no longer “dense with rare exceptions”; it becomes two competing formats.

The evaluation also focuses on predictive metrics such as perplexity and zero-shot accuracy. The paper explicitly does not settle open-ended generation quality. For a serving system, I would still run task-specific generation checks after perplexity looks good.

Takeaway

SpQR is a good example of quality-oriented compression. It treats a small number of sensitive weights as first-class citizens instead of forcing them through the same dense low-bit quantizer as everything else.

The tradeoff is engineering complexity. If the serving stack has an optimized sparse correction path, SpQR can deliver near-lossless compression with useful speedups. If the sparse path is slow or poorly integrated, a simpler dense W4 format may be less accurate but easier to run well.
