DistServe: Disaggregated LLM Serving

H.J. Chen
  2025-02-06 2025-02-06 Created  
  • Work hard

Zhong et al. DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving. 2024.

Paper / Code

DistServe is a systems paper about taking the prefill/decode split seriously. Many LLM serving engines already know that the two phases behave differently, but they still colocate them on the same worker pool. DistServe asks what happens if prefill and decoding are assigned to different GPU groups and optimized with separate parallelism plans.

The paper’s metric is goodput, not raw token throughput. A request only counts if it satisfies both latency constraints.

For LLM serving, the two SLOs are usually time to first token (TTFT) and time per output token (TPOT).

The Interference Problem

Figure 1 is the motivating result. On a 13B model with input length 512 and output length 64, colocated serving reaches about 1.6 requests/s per A100 GPU under a 90% SLO attainment target. If the two phases are measured separately, prefill-only can support about 5.6 requests/s and decode-only about 10 requests/s.

That gap is the opportunity. The shared worker pool is not only under-optimized; it couples two phases with different bottlenecks and different latency targets.

Chunked prefill helps but does not remove the problem. Adding a long prefill job to a decode batch delays decode steps, increasing TPOT. Adding decode jobs to prefill increases prefill execution time, hurting TTFT. The paper’s point is that better batching still leaves a fundamental resource-coupling issue.

Phase Behavior

The two phases stress hardware differently:

Phase Computation shape Main pressure SLO link
Prefill many prompt tokens processed together compute and prompt-length throughput TTFT
Decode one new token per active sequence per step memory bandwidth, KV access, queueing TPOT

Prefill benefits from enough parallelism to reduce first-token latency. Decode benefits from batching many active sequences, but each decode step is small and repeated. A single colocated plan has to compromise between these shapes.

Disaggregation lets the system choose different GPU allocation and model-parallel settings for each phase. The tradeoff is that the KV cache produced by prefill must move to the decode side.

That KV transfer is the main skepticism point for this paper. The architecture only wins when the benefit from eliminating interference is larger than the communication and orchestration overhead.

DistServe Runtime

At runtime, DistServe has a centralized controller. A request is sent to a prefill instance, which computes the first token and KV cache. Then the request is assigned to a decode instance, which fetches the KV cache and continues autoregressive generation.

The implementation details that matter:

  • prefill and decode instances can use different parallelism settings;
  • the placement algorithm accounts for inter-node bandwidth;
  • the controller uses queue lengths to dispatch work;
  • KV cache transfer is pull-based, so decode instances fetch cache when they are ready instead of being flooded by prefill workers;
  • workload profiling can trigger replanning when input length, output length, or arrival rate shifts.

This is more than “put prefill on one GPU and decode on another.” The resource plan is a joint choice over phase split, parallelism, replication, and placement.

End-to-End Results

The chatbot workload uses OPT-13B, OPT-66B, and OPT-175B on ShareGPT. The paper reports that DistServe sustains 2.0x to 4.6x higher request rate than vLLM and 1.6x to 7.4x higher request rate than DeepSpeed-MII under the 90% SLO attainment target.

The second row of the figure varies the SLO scale. DistServe handles 1.8x to 3.2x tighter SLOs than vLLM and 1.7x to 1.8x tighter SLOs than DeepSpeed-MII on the chatbot setting.

The result makes sense: chat has a strong TPOT component. Colocated systems may satisfy TTFT for many requests but fail because decode steps get delayed by prefill interference.

The code completion and summarization tasks stress different sides of the system:

  • Code completion on OPT-66B demands low TTFT. DistServe reports 5.7x higher request rate than vLLM and 1.6x higher than DeepSpeed-MII.
  • Summarization on OPT-66B uses long inputs and a looser TTFT SLO, so TPOT becomes more important. DistServe reports 4.3x higher request rate and 12.6x tighter SLO than vLLM, and 1.8x higher request rate and 2.6x tighter SLO than DeepSpeed-MII.

The same figure also includes the latency breakdown. For OPT-175B on ShareGPT, KV transmission is reported as less than 0.1% of total latency, and over 95% of requests have transfer delay below 30 ms in the testbed. That does not mean transfer is always free, but it supports the paper’s claim that bandwidth-aware placement can keep the cost small.

Ablation And Planner Cost

The ablations separate three ideas:

  1. disaggregate the phases;
  2. choose phase-specific parallelism and resource allocation;
  3. use bandwidth-aware placement.

The paper argues that all three are needed for high goodput. A naive split can still lose if the KV path is bad or if one phase is over-provisioned while the other queues.

The placement algorithm is also designed to be cheap enough for replanning. The paper reports that the largest setting in its evaluation can be solved in under 1.3 minutes, while normal workload shifts happen at a much slower time scale.

What I Would Measure First

Before implementing this design in another serving stack, I would measure four things separately:

Measurement Why it matters
Prefill execution time vs prompt length estimates TTFT pressure and prefill GPU allocation
Decode step time vs active batch size estimates TPOT pressure and decode batching capacity
KV cache size and transfer time decides whether disaggregation overhead is acceptable
SLO attainment under load prevents raw throughput from hiding missed deadlines

If prefill and decode saturate the same resource in the same way, disaggregation is less compelling. If they bottleneck differently, DistServe’s design gives the scheduler more degrees of freedom.

Takeaway

DistServe is the architectural counterpart to continuous batching and chunked prefill. Instead of only improving scheduling inside a colocated worker, it changes the worker layout so prefill and decode can be scaled independently.

The main win is goodput under latency constraints. The main risks are operational: KV transfer, bandwidth-aware placement, failure coupling between phase instances, and workload drift. I read the paper as a strong argument that production LLM serving should evaluate TTFT and TPOT separately before treating a single token/s number as the capacity metric.
