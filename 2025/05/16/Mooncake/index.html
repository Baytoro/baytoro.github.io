Mooncake: KVCache-Centric LLM Serving

H.J. Chen
  2025-05-16 2025-05-16 Created  
  • Paper Reading 
 
  • LLM 
  • | KV-Cache 
  • | Serving 

Paper: Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving

Mooncake is valuable because it reads like a production systems paper. The design is organized around KV cache: where it is produced, stored, reused, moved, and evicted.

Motivation

Long-context serving changes the cost model. A request may spend a large amount of time and memory in prefill, then reuse or transfer a huge KV state during decode. Treating KV cache as temporary scratch memory is no longer enough.

The figure shows Mooncake’s disaggregated architecture. Prefill, decode, and KV-cache management are separated into components that can be scheduled independently.

Methodology

Mooncake is KV-cache centric in three senses:

  1. Placement. The system decides where KV cache should live across workers.
  2. Transfer. Prefill-generated KV must be moved efficiently to decode resources.
  3. Reuse and overload behavior. Long-context workloads benefit from managing cache lifetime explicitly.

Compared with DistServe, Mooncake emphasizes production traffic and long context. The system is less about one theoretical split and more about operating the split under real workload pressure.

Results

The paper reports improvements for Moonshot/Kimi-like serving workloads. The benefits come from better KV placement and disaggregated resource management rather than a single faster kernel.

Takeaway

Mooncake pushes the PagedAttention lesson to the cluster level. KV cache is a large data object. For long-context LLMs, serving architecture should be designed around KV movement and lifetime, not only model weight placement.

Production Angle

Mooncake matters because real long-context traffic is not a clean benchmark. Requests may have huge prompts, repeated context, overloaded queues, and uneven decode lengths. A production system must decide not only how to execute a request, but where to keep the KV state and when to move it.

KV Cache As Data

The paper treats KV cache like a data object with lifecycle:

  1. created by prefill;
  2. transferred or placed for decode;
  3. possibly reused;
  4. evicted under pressure.

This is different from viewing KV cache as temporary tensors inside one GPU process.

Relation To PagedAttention

PagedAttention solves memory layout inside a worker. Mooncake asks cluster-level questions around KV movement and disaggregation. Both are necessary for long-context serving; they operate at different layers of the stack.

Source-Level Notes

Mooncake takes the disaggregation idea into a KV-cache-centric production design. Long-context workloads make KV cache the dominant state object. The model weights are static, but KV cache is request-specific, large, and constantly moving through the system.

The paper’s architecture should be read around this question: where should KV cache live so that prefill, decode, reuse, and overload handling remain efficient?

Production Reading

The interesting part is that KV cache becomes data, not a temporary tensor. Once contexts are long and prefix reuse matters, the serving system needs placement, transfer, eviction, and reuse policies for KV cache.

This is a different layer from PagedAttention. PagedAttention manages KV memory inside a GPU worker. Mooncake reasons about KV cache across a disaggregated service. The same object moves from kernel memory layout to cluster-level scheduling policy.

Experiment Reading

Mooncake is most convincing under long-context and overloaded scenarios. Short prompts with little prefix reuse do not stress KV-cache management enough to show the architecture’s value. The paper should be read with production traffic in mind: uneven prompt lengths, repeated prefixes, and changing load.

The KV-centric view also changes what metrics matter. GPU compute utilization is not enough. KV transfer volume, cache hit rate, cache eviction behavior, and SLO satisfaction become first-class metrics.

A useful comparison is DistServe. DistServe separates phases for goodput. Mooncake adds a stronger claim that KV cache placement and reuse should organize the system. That is a production architecture argument, not only a scheduling heuristic.

Reproduction Checklist

A useful reproduction should generate traffic with long prompts, repeated prefixes, and overload periods. Then report TTFT, TPOT, goodput, KV-cache hit rate, and KV transfer volume. Average latency alone is too weak for this paper.

I would also separate prefill cache creation from decode cache consumption. Mooncake’s architecture is built around moving and reusing KV cache as a first-class object, so the metrics should show where that object is stored, reused, evicted, and transferred.

Boundary / Failure Mode

The limitation is operational complexity. Once KV cache is a distributed object, failures, migration, eviction, and load balancing all affect correctness and latency. The paper is valuable because production long-context serving needs that machinery, but it is not the first system I would build for a small single-node deployment. The architecture pays off when KV cache dominates service behavior.
