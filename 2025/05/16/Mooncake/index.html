Paper: Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving
Trace / code: kvcache-ai/Mooncake

Mooncake is a production serving paper from the Kimi system. I read it as a cluster-level continuation of the KV-cache story started by systems such as PagedAttention, SGLang/RadixAttention, DistServe, and Splitwise. The main point is not only “separate prefill and decode”. The stronger claim is:

In long-context production serving, KV cache is no longer temporary worker-local scratch space. It is the central data object that should drive placement, scheduling, transfer, reuse, overload control, and admission decisions.

The paper is unusually concrete because it is organized around a real service trace. The trace is sanitized, but it still preserves request arrival time, input length, output length, and remapped prefix block hashes. That is exactly the kind of evidence needed for this problem: without repeated prefixes, long prompts, bursty load, and SLO pressure, KV-cache-centric serving looks over-engineered.

One-Sentence Summary

Mooncake disaggregates prefill workers, decode workers, and a distributed KV-cache pool, then schedules requests by estimating three things together: how much prefix KV cache can be reused, how expensive it is to move that KV cache, and whether the future prefill/decode latency can still satisfy TTFT and TBT SLOs.

Figure 1 from the paper. The important detail is that the Conductor schedules around KV cache state, not only around free GPU slots.

Why This Paper Matters

For short prompts, a serving engine can often pretend that KV cache is just part of the runtime’s internal memory allocator. For long-context workloads, that view breaks down:

  • The prompt can be tens of thousands of tokens.
  • The decode length can be much shorter than the prompt length.
  • The same long prefix may be reused by many requests.
  • KV cache can exceed what is convenient to keep in GPU memory.
  • Moving KV cache across machines can dominate the request path if it is scheduled carelessly.
  • Under overload, accepting a request into prefill can waste a lot of GPU time if the decode stage is already doomed to miss SLO.

The paper uses two service-level metrics:

  • TTFT: time to first token. This is mostly affected by prefill queueing, prefill execution, prefix cache reuse, and KV transfer before decode can start.
  • TBT: time between tokens. This is mostly affected by decode batching, decode GPU load, and the amount of KV cache decode workers must hold or load.

This distinction is important. A system can have acceptable TTFT but poor TBT if decode is overloaded. It can also have good TBT but terrible TTFT if prefill cannot keep up. Mooncake tries to keep both sides within SLO while maximizing accepted throughput.

Prefill And Decode Have Different Scaling Laws

Figure 2. Prefill gets worse as input length grows; decode throughput improves with larger decode batch size until the system saturates.

The prefill phase computes the model over the prompt and produces KV cache. Its cost grows strongly with prompt length. For very long prompts, attention work and KV materialization make prefill expensive, and prefill latency can increase faster than a simple linear mental model.

Decode is different. It advances generation one token at a time. The per-step work is usually small enough that batching many decode requests can improve GPU utilization. This is why colocating prefill and decode can be painful: prefill wants large prompt computation, while decode wants stable token-by-token batching. Interference between the two phases can damage both TTFT and TBT.

Mooncake’s split is therefore not cosmetic. It reflects a real phase mismatch:

  • Prefill workers should be scheduled for prompt throughput, prefix reuse, and KV-cache production.
  • Decode workers should be scheduled for continuous batching and TBT stability.
  • KV cache must move between the two sides without becoming the hidden bottleneck.

Architecture: Three Pools Plus A KV-Aware Conductor

The architecture in Figure 1 has four central pieces:

  • Prefill pool: GPU workers that compute prompt prefill and generate incremental KV cache.
  • Decoding pool: GPU workers that run continuous batching for token generation.
  • KVCache pool: CPU DRAM and SSD resources used to store KV cache outside GPU memory.
  • KVCache-centric Conductor: the scheduler that chooses prefill worker, decode worker, KV reuse, KV transfer, and rejection decisions.

The paper’s design objective can be read as three linked constraints:

  • For prefill: maximize prefix reuse while keeping TTFT acceptable and keeping prefill GPU utilization high.
  • For decode: maximize decode throughput while keeping TBT acceptable and not exceeding GPU KV memory.
  • For KV storage: use cheaper non-GPU memory when possible, but avoid making KV transfer the new latency bottleneck.

This is an important shift from a simple worker-centric serving model. In a worker-centric model, the scheduler mostly asks “which GPU is free?” Mooncake asks “which worker has, or can cheaply obtain, the right KV prefix, and will the downstream decode stage still meet SLO?”

This is a production-oriented cache model. It cares about where blocks are, whether they are hot, whether they should be replicated, and whether moving them is worth the latency.

Request Workflow

Figure 4. A request reuses prefix KV cache, runs incremental prefill, transfers KV cache, then enters decoding.

The workflow is easier to understand as four stages:

  1. KVCache reuse: the selected prefill instance loads the longest useful prefix KV cache from CPU memory to GPU memory.
  2. Incremental prefill: the prefill GPU computes only the missing prompt suffix and produces new KV cache.
  3. KVCache transfer: the full KV cache needed for decode is transferred to the decode side, usually through CPU memory and RDMA across machines.
  4. Decoding: the decode instance asynchronously loads KV cache and adds the request into continuous batching.

The key design detail is overlap. Mooncake does not want prefill to finish all compute and then block on a huge serialized KV store. It stores and loads KV cache layer by layer, overlapping transfer with computation where possible. That matters because for long prompts, the KV object can be large enough that a naive store/load path eats the TTFT gain from prefix reuse.

Trace: Why Real Traffic Changes The Problem

Figure 5. The public trace has long input prompts and much shorter outputs.

The trace has 23,608 entries. The paper reports an average input length around 7,590 tokens and an average output length around 182 tokens. The largest requests are much longer: inputs can reach 128k tokens and outputs can reach 2k tokens.

This matters for two reasons.

First, prefill dominates many requests. A prompt can be large while the generated answer is small. If decode is short, wasting prefill work on a request that will later miss decode SLO is especially bad.

Second, repeated prefixes create a realistic cache opportunity. If many users or internal tools reuse the same long documents, system prompts, retrieval contexts, or conversation prefixes, then prefix KV cache is not a corner-case optimization.

Cache Hit Distribution And Eviction

Figure 6. Most blocks are cold, while a small number of blocks are hit many times.

The CDF says the cache access distribution is skewed. More than half of cached blocks are not reused in this trace window, while a small number of blocks can be accessed many times. That has a direct scheduling implication: hot blocks can become both valuable and dangerous.

  • Valuable, because moving or replicating them can remove a lot of repeated prefill work.
  • Dangerous, because too many requests chasing the same hot prefix can create a load hotspot on the instance that holds it.

Mooncake therefore needs both cache-aware scheduling and cache-balancing behavior. Pure cache awareness would send every request to the worker with the longest matching prefix. Pure load balancing would ignore expensive prefix reuse. The paper’s scheduler tries to sit between those extremes.

Table 1. On this trace, LRU is slightly better than LFU and length-aware policies at smaller capacities.

Table 1 is also interesting because infinite cache still gives about 0.51 hit rate on this sample. I would not read that as “only half of KV cache can ever be useful” in general. I read it as “this trace has a mixture of repeated and non-repeated prefixes, and the public sample is not the entire production universe.”

The relative result is more practical:

  • LRU works well because temporal locality is strong.
  • LFU is not automatically better because old hot blocks can outlive their usefulness.
  • Length-aware eviction is not automatically better because long blocks are expensive but not always reusable.

For a production system, the eviction policy is part of the scheduler. If the cache keeps the wrong blocks, the prefill scheduler will make good-looking decisions using bad state.

Multi-Node Prefill And Chunked Pipeline Parallelism

Long-context prefill creates a model-parallel problem. A single 8-GPU node may not be enough for very long contexts, but naive cross-node tensor parallelism is expensive because every layer may require RDMA communication. Sequence parallelism helps by splitting the sequence dimension, but it can reduce MFU and competes with the same network resources needed for KV transfer.

Mooncake instead proposes Chunked Pipeline Parallelism for the prefill cluster. The idea is:

  • Group multiple prefill nodes.
  • Split a long prompt into chunks no longer than a configured prefill_chunk.
  • Pipeline chunks across the grouped nodes.
  • Keep communication mainly at pipeline boundaries instead of doing heavy cross-node all-reduce at every layer.

This is different from chunked prefill in systems such as SARATHI, where chunking is mainly used to interleave prefill with decode inside a colocated worker. In Mooncake, the chunking is also about multi-node prefill scaling and about fitting long contexts into a prefill-specific resource pool.

Overload-Oriented Scheduling

Disaggregated serving creates a delayed-load problem. A request accepted into prefill becomes decode load later. If the system only looks at current decode load, it can accept too many requests during a temporary decode valley and then overload decode after prefill completes.

Figure 9. Without prediction-based early rejection, prefill and decode load can fluctuate in opposite phases.

The paper’s early rejection idea is straightforward: reject requests before prefill if the system predicts that they cannot meet downstream SLO. This avoids wasting prefill GPU time.

The subtle part is prediction. Naive early rejection can create oscillation:

  • Decode looks overloaded, so the system rejects new prefill work.
  • Later decode drains, but prefill has too little queued work.
  • The system accepts again.
  • Then decode becomes overloaded again after the accepted prefill work arrives.

Figure 10. Prediction-based early rejection smooths the accept/reject behavior by looking at future decode load rather than only current load.

Evaluation Setup

Table 2. The datasets cover no-reuse public data, high-reuse public data, simulated long contexts, and real production-like traffic.

The evaluation uses a high-performance cluster where each node has 8 NVIDIA A800-SXM4-80GB GPUs, NVLink, and high-bandwidth RDMA networking. The experiments replay workloads using a dummy LLaMA2-70B-style model architecture. That means the content is not real user content, but the request shapes and cache behavior are meant to reflect realistic serving pressure.

The dataset choices are useful:

  • ArXiv Summarization: long input, moderate output, almost no cache reuse.
  • L-Eval: longer input, short output, high cache reuse.
  • Simulated Data: controlled 16k/32k/64k/128k prompts, 512-token outputs, 50% cache ratio.
  • Real Data: timestamp-based arrivals and around 50% cache ratio.

This is the right evaluation shape. A KV-cache-centric system should be tested under both low-reuse and high-reuse traffic; otherwise it is easy to mistake prefix caching for the whole contribution.

Public Dataset Results

Figure 11. Mooncake is compared with vLLM on ArXiv Summarization and L-Eval under normalized P90 TTFT/TBT constraints.

The public-dataset results show two different regimes.

On ArXiv Summarization, cache reuse is almost zero. Mooncake can still outperform vLLM because phase disaggregation reduces prefill/decode interference. The reported improvement is about 20% for the best Mooncake configuration.

On L-Eval, cache reuse is high. Mooncake benefits more because prefix caching and KV movement now matter. The paper reports about 40% throughput improvement in the best configuration.

The plot also shows a useful warning: the split between prefill and decode workers matters. A configuration such as [2P+2D] can have decode capacity but insufficient prefill capacity, which hurts TTFT. Disaggregation is not magic; it creates a resource allocation problem.

Simulated Long-Context Results

Figure 12. As prompt length grows, the gap between Mooncake and vLLM becomes much larger.

The simulated data is the strongest evidence for the long-context argument. As prompt length grows from 16k to 128k, colocated serving has a harder time protecting decode latency from prefill pressure. Mooncake separates the phases and manages KV movement explicitly, so it can keep TBT under control at higher request rates.

The paper reports throughput improvements from about 50% up to 525% over vLLM in these simulated scenarios. I read the 525% number as a stress-case result: it appears when prompt length and cache behavior make the baseline’s colocated prefill/decode interference particularly severe. The general conclusion is still robust: long prompts amplify the value of disaggregation and KV-aware scheduling.

Real Workload Result

Figure 13. In the real-workload replay, TTFT is similar, but Mooncake has much better TBT SLO satisfaction.

The real-workload result is the most production-relevant one. The paper compares Mooncake [10P+10D] against vLLM [20M].

The TTFT CDFs are close. That tells me Mooncake is not simply winning by delaying or rejecting more prefill work. The TBT CDF is the real difference: Mooncake keeps almost all requests within the TBT SLO, while vLLM only satisfies the TBT criterion for about 57% of requests.

The paper states that Mooncake enables Kimi to handle about 75% more requests under the same SLO target. This is the central production claim. For an interactive product, stable decode cadence is often more visible to users than a small average TTFT difference.

Relationship To Other Serving Systems

I find Mooncake easiest to place by separating the layers of the stack:

System idea Main layer How it relates to Mooncake
PagedAttention GPU-worker KV memory layout Makes KV allocation efficient inside a worker. Mooncake moves the KV-cache question to cluster-level placement and transfer.
SGLang / RadixAttention Program and prefix reuse Exploits reusable prefixes. Mooncake needs similar reuse signals but also schedules storage, transfer, and decode admission.
SARATHI Chunked prefill / decode scheduling Reduces interference by chunking prefill. Mooncake also uses chunking, but its chunked pipeline parallelism targets multi-node prefill and KV movement.
DistServe / Splitwise Prefill-decode disaggregation Separates phases for better goodput. Mooncake adds KV-cache pool, cache-aware scheduling, hot-prefix balancing, and overload prediction.

So I would not describe Mooncake as replacing these systems. It composes several ideas at a production architecture level, then makes KV cache the organizing abstraction.

What I Would Measure When Reproducing

A weak reproduction would only report average latency. That would miss most of the paper. A useful reproduction should report:

  • P50/P90/P99 TTFT.
  • P50/P90/P99 TBT.
  • Effective throughput under TTFT/TBT SLO.
  • Rejected request count under overload.
  • Wasted prefill work for requests that later miss decode SLO.
  • Prefix KV-cache hit rate.
  • Cache hit rate by block age and block popularity.
  • KV transfer volume between prefill, KV pool, and decode.
  • RDMA bandwidth utilization and queueing delay.
  • CPU DRAM and SSD KV-cache occupancy.
  • Prefill GPU utilization and decode GPU utilization separately.
  • Hot-prefix load skew across prefill instances.

The workload should include at least three regimes:

  • Long prompts with little prefix reuse, to test pure prefill/decode disaggregation.
  • Long prompts with high prefix reuse, to test KV-cache-centric scheduling.
  • Bursty overload, to test early rejection and prediction stability.

Without all three regimes, it is hard to tell whether the system is winning because of disaggregation, prefix caching, admission control, or simply a favorable trace.

Limitations And Questions

Mooncake is not the first architecture I would build for a small single-node deployment. The operational cost is real:

  • KV cache becomes distributed state.
  • Cache migration and replication can affect latency.
  • Worker failures now involve request state and KV state.
  • CPU DRAM and SSD cache tiers need eviction, accounting, and backpressure.
  • RDMA bandwidth is shared by KV transfer and other model-parallel communication.
  • Security and isolation matter because KV cache encodes user context.
  • The optimal prefill/decode split can change with workload mix.

I also want more detail on a few engineering questions:

  • How often do hot-prefix migrations happen in production?
  • What is the failure recovery path if decode-side KV transfer partially completes?
  • How does the scheduler behave when CPU DRAM is full and SSD becomes active?
  • How sensitive are results to block size ?
  • How does the design interact with speculative decoding, prefix compression, or quantized KV cache?
  • Can the prefill/decode split be adjusted online without destabilizing SLO?

These questions do not weaken the paper. They are exactly the questions that appear once KV cache is treated as a first-class distributed object.

Takeaway

The sentence I would keep from this paper is:

Long-context LLM serving should be scheduled around KV cache lifecycle, not only around GPU availability.

Mooncake’s contribution is the full lifecycle view: prefix hash, KV-cache pool, layer-wise store/load, prefill-decode disaggregation, cache-aware and cache-balancing scheduling, decode admission, and prediction-based early rejection. The paper is convincing because the pieces are connected by real workload pressure. Long prompts make KV cache large; repeated prefixes make it reusable; overload makes admission control necessary; decode SLO makes phase interference visible.

For me, Mooncake is a reminder that the next serving bottleneck is often not a kernel alone. It is the data movement and scheduling policy around the tensors the kernels produce.
