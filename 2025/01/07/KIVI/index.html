Paper: KIVI: A Tuning-Free Asymmetric 2bit Quantization for KV Cache
Code: jy-yuan/KIVI

KIVI is a KV-cache quantization paper, not a weight quantization paper. That distinction matters. GPTQ, AWQ, and similar weight-only methods reduce the static model footprint. KIVI targets the state that grows with batch size and sequence length during autoregressive decoding.

For every generated token, each attention layer stores key and value vectors for all previous tokens. During the next token step, the GPU reads that cache again to compute attention. With long prompts or large batches, the cache becomes both a capacity problem and a memory-bandwidth problem. The paper’s central claim is that this runtime state can be compressed to 2 bits without tuning the model, but only if key and value caches are quantized differently.

The Key Observation

Figure cropped from the paper PDF: per-token quantization groups along the token row, while per-channel quantization groups along the channel column.

KIVI starts from a simple question: if a KV tensor has shape , should the scale and zero point be shared across a token row or a channel column?

The answer is asymmetric:

  • key cache: quantize per channel;
  • value cache: quantize per token.

That asymmetry is the whole paper. A generic “2-bit KV cache” description hides the important part, because using the same granularity for both K and V is exactly what breaks in the experiments.

Why Uniform KV Quantization Fails

Ablation cropped from the paper PDF: among 2-bit fake KV-cache settings, key per-channel and value per-token is the only low-bit configuration that stays close on CoQA and TruthfulQA.

Table 1 is a useful sanity check before reading the method. The paper simulates KV-cache quantization on Llama-2-13B with group size 32 and compares different grouping choices. The compact reading is:

  • 16-bit gives 66.37 on CoQA and 29.53 on TruthfulQA.
  • 4-bit per-token quantization for both K and V remains close to full precision.
  • 2-bit per-token quantization for both K and V drops noticeably.
  • 2-bit per-channel quantization for V collapses, regardless of the key setting.
  • 2-bit K per-channel and V per-token is the best low-bit fake quantization setting in this table.

The pattern is sharp enough that this is not just a metadata optimization. Per-channel value quantization is bad no matter what happens to the key. Per-token key quantization is also noticeably weaker at 2 bits. The paper then explains this through tensor statistics and attention behavior.

Why Keys Want Per-Channel Quantization

Figure cropped from the paper PDF: key caches show persistent high-magnitude channels, while value caches do not show the same channel-stable outlier structure.

The key cache is used to compute attention logits:

If a few key channels are consistently much larger than the others, a per-token scale has to cover both normal channels and outlier channels inside the same row. That wastes precision on normal channels and makes the attention logits noisy. Per-channel quantization contains the outlier inside its own channel group.

This matches the activation-outlier story seen in LLM quantization work such as SmoothQuant: some transformer dimensions carry persistent large values. KIVI’s point is that the same phenomenon appears in the key cache and should influence the cache quantizer.

Error statistics cropped from the paper PDF: key per-channel quantization greatly reduces attention-score error; value per-token quantization greatly reduces attention-output error.

Table 2 makes the key result more concrete. For Llama-2-13B, key per-channel quantization has lower key reconstruction error than key per-token quantization, but the more important number is attention-score error: 9.60 for K per-channel versus 47.00 for K per-token. The cache is not judged by reconstruction alone; it is judged by how the next attention computation changes.

Why Values Want Per-Token Quantization

The value cache has a different role. Attention output is a weighted sum over token rows. In compact notation, one output row looks like .

Because attention is sparse, a few token rows can dominate the output for a given query. If value quantization is per token, the quantization error for one token is mostly contained in that token. If value quantization is per channel, the scale is shared across many tokens, so error from unimportant or differently scaled tokens can pollute the rows that actually matter for the attention output.

That is why Table 2 reports value reconstruction errors that look similar at first, but attention-output error is dramatically different: 3.55 for V per-token versus 49.89 for V per-channel. The relevant metric is not “how close is after dequantization” in isolation. The relevant metric is “how close is ” after the attention mixer uses it.

KIVI’s Streaming Data Structure

KIVI overview cropped from the paper PDF: grouped low-precision cache is combined with a small full-precision residual cache during decoding.

Value per-token quantization is easy to stream: a newly generated value vector can be quantized and appended along the token dimension. Key per-channel quantization is harder because the grouping spans multiple tokens. KIVI handles this by splitting the cache into two parts:

  • grouped cache: old tokens stored in quantized form;
  • residual cache: recent tokens kept in full precision until enough tokens accumulate.

For keys, KIVI groups every tokens and quantizes the grouped key cache per channel. The recent residual key cache remains full precision. When the residual reaches the configured residual length , it is quantized and appended to the grouped cache.

For values, KIVI also keeps a recent full-precision value window, but the old value rows are quantized per token. During attention, the logits and output are computed by combining the quantized grouped cache with the residual full-precision cache.

Two implementation choices are worth noting:

  • Dequantization is fused with matrix multiplication, so the method is not meant to materialize a full FP16 cache before attention.
  • The method is compatible with weight-only quantization, because it touches runtime KV cache rather than model weights.

Algorithm excerpt cropped from the paper PDF: prefill builds quantized grouped caches plus residual windows; decoding updates the residual windows and flushes them into low-bit storage.

The algorithm also explains why KIVI performs better than “fake” quantization in the hard tasks. Fake quantization in Table 1 quantizes every token. KIVI keeps a sliding full-precision residual window for local recent tokens. That window is small compared with a long context, but it protects the part of the cache most likely to be used immediately in decoding.

Accuracy Results

Main benchmark table cropped from the paper PDF: KIVI-2 usually stays close to 16-bit on Llama and Mistral, while Falcon-7B is less forgiving because its KV cache is already compressed by multi-query attention.

The main table compares 16-bit, 4-bit per-token, several fake 2-bit configurations, and actual KIVI on CoQA, TruthfulQA, and GSM8K. Three readings matter to me:

  1. The asymmetric fake 2-bit setting is consistently the best fake 2-bit configuration.
  2. Actual KIVI-2 is much better than fake 2-bit on GSM8K because of the full-precision residual window.
  3. Falcon-7B behaves differently because multi-query attention already reduces the number of KV heads. The paper reports that KIVI-4 is needed there to maintain accuracy, while KIVI-2 has a larger drop.

For Llama-2-13B, the GSM8K row is a good example. The fake 2-bit asymmetric setting gives 12.21, while KIVI-2 gives 20.77 and the 16-bit baseline is 22.67. The residual cache is not an implementation footnote; it changes the quality profile.

Long Context Behavior

LongBench table cropped from the paper PDF: KIVI keeps average scores close to the 16-bit baseline across QA, summarization, few-shot, and code-completion tasks.

Long-context tasks are the right place to evaluate KIVI. For short multiple-choice tasks with only one decoding step, the KV cache is not stressed enough. The paper uses LongBench with tasks such as Qasper, QMSum, MultiNews, TREC, TriviaQA, SAMSum, LCC, and RepoBench-P.

The average LongBench numbers are close to 16-bit for most Llama and Mistral settings. This is the behavior one wants from a cache compression method: it should buy memory headroom without changing the model into a different system.

Needle-in-a-Haystack results cropped from the paper PDF: KIVI preserves retrieval behavior for the tested Llama-3 and Mistral instruction models at long lengths.

The Needle-in-a-Haystack plot is more qualitative but still useful. It checks whether the model can retrieve a passkey-like fact placed at different depths in a long context. The KIVI-2 and KIVI-4 plots largely preserve the retrieval pattern of the baselines in the shown settings, which supports the claim that 2-bit KV compression does not simply erase old context.

System Results

Efficiency figure cropped from the paper PDF: on a single A100 80GB setup, KIVI enables larger batch sizes and higher throughput under similar peak memory.

The systems story is straightforward: less KV memory means more requests fit in the same GPU memory budget. The paper reports 2.6x peak memory reduction including model weights for Llama-2-7B, and the workload in Figure 5 shows up to 4x larger batch size with 2.35x to 3.47x throughput improvement.

This should be read as a serving-capacity result, not just a compression ratio. If the workload is short or compute-bound, the benefit may be smaller. If the workload has long prompts, long generation, or high concurrency, KV cache dominates more and the benefit should become more visible.

KIVI also complements vLLM-style memory management. PagedAttention changes how KV blocks are allocated and paged. KIVI changes how many bits those blocks consume. One is layout and scheduling; the other is representation.

Hyperparameters

Ablation table cropped from the paper PDF: group size and residual length affect GSM8K, with group size 128 hurting more than 32 or 64 in this setting.

The method is described as tuning-free in the sense that it does not fine-tune model weights, but it still has engineering hyperparameters:

  • : group size for quantization;
  • : residual length for the full-precision cache window;
  • bit width: KIVI-2 versus KIVI-4;
  • kernel implementation details for packing, dequantization, and mixed-precision matmul.

The paper usually sets and for accuracy experiments, while some efficiency experiments also report . Table 5 suggests that group size 32 and 64 are similar on GSM8K for Llama-2-13B, while group size 128 hurts. Residual length is less monotonic in the table, but a nontrivial residual window is still important for difficult generation tasks.

Relation To Other Quantization Work

KIVI sits in a different place from weight-only methods:

Method family Main target Typical deployment form
GPTQ / AWQ weights W4A16 or W3A16 checkpoints plus low-bit kernels
SmoothQuant activations and weights INT8-friendly activation/weight transformation
KIVI KV cache low-bit cache storage plus fused dequantized attention
vLLM / PagedAttention KV memory layout paging and allocation efficiency

These methods are not mutually exclusive. A realistic serving stack may use weight-only quantization to reduce model memory, PagedAttention to manage cache allocation, and KV-cache quantization to support longer contexts or higher batch sizes.

The harder question is kernel support. A KIVI checkpoint is not a static artifact like a GPTQ weight file. It requires the runtime to store, pack, dequantize, and multiply with low-bit KV cache efficiently during prefill and decode.

Practical Reproduction Notes

If I were reproducing KIVI, I would separate quality checks from serving checks.

For quality:

  • Compare key-only, value-only, and both K/V quantization.
  • Reproduce the per-channel key versus per-token key attention-score error.
  • Reproduce the per-token value versus per-channel value attention-output error.
  • Evaluate hard generation tasks, not only perplexity or short closed-form tasks.
  • Test long-context retrieval and code/summarization tasks where old context matters.

For serving:

  • Measure peak memory including model weights, KV cache, scales, zero points, packing overhead, and residual windows.
  • Report maximum batch size under a fixed GPU memory budget.
  • Report decode throughput and prefill overhead separately.
  • Check whether fused dequantization is actually used in the attention kernels.
  • Compare with a strong layout baseline such as PagedAttention rather than a naive cache allocator.

Takeaway

KIVI is useful because it treats KV cache as its own quantization target. The key cache and value cache are not interchangeable tensors: keys create attention scores and have persistent channel outliers; values are mixed by sparse attention and need token-local error containment.

That is the lesson I would keep from the paper. The bit width matters, but the grouping dimension matters more. A practical 2-bit KV-cache method is not just “compress K and V”; it is “quantize K per channel, quantize V per token, and keep a small full-precision residual window so streaming decode remains stable.”
