DeepSeek-AI. DeepSeek-V3 Technical Report.

Paper

DeepSeek-V3 should be read as both a model report and a training-systems report. The model keeps the DeepSeek-V2 direction, namely MLA for efficient inference and DeepSeekMoE for economical sparse activation, but the important additions are not only architectural. The report also introduces auxiliary-loss-free MoE load balancing, a multi-token prediction objective, DualPipe pipeline parallelism, and a large-scale FP8 training framework.

The headline numbers are unusually explicit: 671B total parameters, 37B activated parameters per token, 14.8T training tokens, 2.788M H800 GPU hours for the full training process, and a stated training cost of about USD 5.576M assuming USD 2 per H800 GPU hour. The paper’s core argument is that frontier-scale capability can come from a co-design of sparse architecture, routing, low-precision training, and communication scheduling.

The first benchmark figure is meant to establish the output side of the story: DeepSeek-V3 is competitive with strong open and closed models on standard benchmarks. The rest of the report explains how that result was made trainable and affordable.

The cost table is one of the most cited parts of the report. Pre-training accounts for 2664K H800 GPU hours, context extension for 119K, and post-training for 5K, giving 2788K H800 GPU hours in total. The paper states that one trillion pre-training tokens require about 180K H800 GPU hours under their framework.

Continuity From V2

DeepSeek-V3 keeps the two structural ideas from DeepSeek-V2:

  1. MLA reduces the decoding cache by storing a compressed latent KV representation plus a small decoupled RoPE key.
  2. DeepSeekMoE separates total capacity from activated compute through shared experts and routed experts.

The architecture diagram still has the V2 shape: MLA inside attention, DeepSeekMoE inside FFN. The changes are in the details: V3 uses more routed experts, fewer shared experts per MoE layer, sigmoid affinities with normalized selected gates, node-limited routing, and a different load-balancing strategy.

Auxiliary-Loss-Free Balancing

The routing problem in MoE is not only “choose the best experts.” If the router collapses, some experts are undertrained. If routing is balanced poorly across devices, the training system slows down. The expert-load figure is also useful because it shows a qualitative difference: auxiliary-loss-free routing allows more domain-specific expert specialization than the auxiliary-loss-based baseline. The point is not simply balanced load; the router can still specialize when the balancing pressure is not injected as a large optimization loss.

Node-Limited Routing

DeepSeek-V3 uses node-limited routing, analogous to V2’s device-limited routing. Experts are distributed across 64 GPUs belonging to 8 nodes, and each token is constrained to be sent to at most 4 nodes. This keeps cross-node all-to-all communication bounded.

This is an important modeling-system boundary. If the best top-k experts for a token are spread across too many nodes, a naive router would maximize local affinity but hurt global throughput. V3’s router therefore optimizes inside a communication budget.

DualPipe

Sparse MoE training creates a communication problem. Cross-node expert parallelism introduces all-to-all dispatch and combine operations. The report states that DeepSeek-V3’s cross-node expert-parallel communication creates an inefficient computation-to-communication ratio of roughly 1:1 unless it is aggressively overlapped.

DualPipe is their pipeline schedule for overlapping forward and backward computation with communication. Each chunk is decomposed into attention, all-to-all dispatch, MLP, all-to-all combine, and pipeline communication. Backward computation is further split into backward-for-input and backward-for-weights pieces, following the ZeroBubble idea.

The schedule is bidirectional: micro-batches are fed from both ends of the pipeline. The visual point is that green, yellow, and blue compute regions are interleaved with communication so that all-to-all and pipeline communication can be hidden behind useful work.

FP8 Training

DeepSeek-V3’s training stack uses FP8 for most compute-heavy GEMMs while retaining higher precision for sensitive components. This is not a blanket “train everything in FP8” recipe.

The framework runs the Linear operator’s Fprop, Dgrad, and Wgrad GEMMs in FP8. Outputs are BF16 or FP32, and the optimizer-facing state keeps higher precision where needed. The report keeps embeddings, output head, MoE gating, normalization, and attention operators in higher precision. Master weights, weight gradients, and optimizer states are also retained in higher precision, with optimizer moments tracked in BF16.

The most important low-precision issue is outliers. A tensor-wise FP8 scale can be dominated by a few large values, wasting resolution for the majority of elements. V3 uses fine-grained scaling:

  1. Activations are grouped and scaled on a tile basis.
  2. Weights are grouped and scaled on a block basis.

Base Model Results

The base model table compares DeepSeek-V3 against DeepSeek-V2, Qwen2.5 72B, and LLaMA-3.1 405B. I would read the table by task family rather than by single rows. V3 is especially strong on code and math rows, and it competes with or beats the large dense baseline while activating only 37B parameters per token.

The comparison is also an efficiency statement. A 671B total-parameter MoE is not directly comparable to a 405B dense model by total parameters alone. The paper’s preferred lens is activated parameters, training cost, and achieved accuracy.

Chat And Post-Training

The chat comparison places DeepSeek-V3 against DeepSeek-V2 variants, Qwen2.5, LLaMA-3.1, Claude-3.5-Sonnet, GPT-4o-0513, and other models. Again, small row-wise differences should not be overinterpreted, but the broad result is that V3 becomes competitive with strong frontier chat systems while remaining an open-weight MoE model in the paper’s framing.

The RewardBench table and distillation table connect V3 to the later R1-style line. The report describes distillation from DeepSeek-R1 into V3 during post-training. This is worth separating from the base model story: some final chat/reasoning behavior is not only from architecture and pre-training, but also from post-training data, reward modeling, and distillation.

V2 proves that MLA and DeepSeekMoE are a strong efficiency pair. V3 makes the training stack mature enough to scale the same pair to a much larger model.

Takeaways

My main takeaway is that DeepSeek-V3 is a systems co-design paper disguised as a model technical report. The model formula alone does not explain the result. The result comes from several constraints being solved together:

  1. MLA reduces decoding memory:
  1. DeepSeekMoE reduces activated compute:

  1. Auxiliary-loss-free balancing keeps batch-level expert load controlled without making a large auxiliary loss fight the language-modeling objective.

  2. MTP adds denser prediction supervision without increasing standalone inference cost, because the auxiliary modules can be discarded.

  3. DualPipe and custom communication kernels hide the all-to-all cost introduced by fine-grained cross-node experts.

  4. FP8 training reduces compute and memory cost, but only after the report adds fine-grained scaling, high-precision accumulation, and precision exceptions for sensitive modules.

The paper is valuable because it does not treat these as independent optimizations. MLA changes what is cached. MoE changes what is computed. Routing changes what is communicated. DualPipe changes when communication happens. FP8 changes what precision the training system can afford. MTP changes how much supervision each token contributes. DeepSeek-V3 is the combination, not any single component.
