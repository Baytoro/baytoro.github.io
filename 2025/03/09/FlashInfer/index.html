FlashInfer: An Attention Kernel Engine for LLM Serving

Ye et al. FlashInfer: Efficient and Customizable Attention Engine for LLM Inference Serving.

Paper | Code | Docs

FlashInfer is a paper about the layer below the LLM serving runtime. Systems like vLLM, SGLang, and MLC-Engine decide which requests are batched, where KV cache lives, which prefixes are reused, and when CUDA Graphs are replayed. FlashInfer asks a more kernel-level question: given those irregular serving shapes, how should attention kernels read KV cache, specialize attention variants, and keep SMs busy?

The key point is that LLM serving attention is not one kernel. A clean training benchmark usually means dense causal prefill with a large query length. Real serving means one-token decode, ragged prompts, paged KV cache, shared prefixes, GQA/MQA, sliding windows, logits soft caps, RoPE fusion, speculative/tree decoding, FP8 KV cache, and changing sequence lengths. FlashInfer is interesting because it treats these differences as first-class API and compiler/runtime inputs rather than as a pile of one-off kernels.

The headline numbers from the paper are also concrete: FlashInfer reports 29-69% lower inter-token latency than the Triton backend in SGLang-style serving, 28-30% lower latency for a Streaming-LLM long-context path, and 13-17% speedup for parallel generation with composable formats. I would not read those as universal constants. I read them as evidence that the kernel layer matters once the runtime produces irregular attention layouts.

Figure 1 is the best overview of the design. The left side says FlashInfer wants one logical representation for page tables, radix trees, sparse masks, and related KV-cache structures. The right side says FlashInfer separates compile-time information from runtime information: attention variants, task type, and KV layout feed JIT compilation, while sequence lengths feed a runtime load-balancing scheduler.

Design Snapshot

KV layout: paged, ragged, prefix-shared, and sparse KV layouts differ across serving systems. FlashInfer represents them through block-sparse and composable formats.

Attention variant: new models add custom masks, logits transforms, RoPE placement, GQA, FP8 KV, and other variants. FlashInfer uses JIT templates and functors instead of maintaining a fixed kernel for every variant.

Runtime scheduling: sequence lengths change every generation step, but CUDA Graph prefers static launch shapes. FlashInfer splits planning from execution, dynamically plans work queues, and replays static kernels.

Reduction: a long KV range may be split into multiple work tiles. FlashInfer uses attention-state composition over output and log-sum-exp so partial results can be reduced exactly.

The rest of the paper can be read as filling in this table. FlashInfer does not only say “use block sparse attention.” It defines a serving boundary: the runtime supplies metadata, the compiler specializes the kernel variant, and the scheduler turns dynamic lengths into deterministic work queues.

KV Cache As Block Sparse Matrix

Serving systems do not store KV cache as one neat dense tensor. PagedAttention stores KV in pages. Prefix-cache systems may represent shared prefixes through radix trees. Long-context pruning methods may keep sparse KV pages. A kernel library cannot realistically ask every runtime to convert its cache into one contiguous tensor before attention.

FlashInfer’s first move is to view those layouts as block-sparse matrices.

Figure 2 maps a page table into a Block Sparse Row (BSR) view. The row axis is query tiles. The column axis is KV-cache pages. Non-zero blocks mark the physical KV pages that a query tile must attend to. If the query tile size is and the KV page/block size is , the logical sparse attention structure can be viewed as:

This is a useful abstraction because a page table, a prefix tree, and a sparse mask are different metadata structures but similar attention work: for each query tile, load a subset of KV blocks, compute score blocks, apply masks/transforms, and reduce.

The cost is that sparse KV loading is not the same as dense KV loading. Tensor Cores want regular tiles. KV pages may be scattered. Hopper TMA is excellent for affine contiguous loads, but sparse page gathering is not a simple TMA load. FlashInfer therefore has to bridge a layout abstraction and the actual global-to-shared memory path.

Composable Formats For Shared Prefixes

The second storage idea is composable formats. A single BSR block size is not always ideal. Shared prefixes are a good example. If many requests share the same prefix, it is wasteful for each query row to load the same prefix KV through separate thread blocks. Larger row blocks can reuse shared KV in shared memory/registers, but a larger row block can also create fragmentation when requests do not share enough structure.

Figure 3 shows the decomposition. The shared-prefix part uses a larger block size so several queries can access the same KV cache through faster on-chip storage. The unique suffix part remains in a smaller block format. Importantly, this does not require moving KV cache. It changes the sparse metadata and index arrays that describe which submatrices are executed.

I find this design practical because shared-prefix serving is common but irregular. Parallel generation, multi-sample decoding, retrieval reuse, system prompts, and prefix caching all create some overlap, but not necessarily enough to justify one monolithic layout. FlashInfer’s composable format gives the runtime a way to say: this submatrix is shared and should be executed with one block shape; this other submatrix is private and should use another.

Figure 4 is the low-level memory consequence. Dense KV loading can use row-index affine transformations. Sparse KV loading needs indirection through BSR indices. FlashInfer tries to make the post-load computation path converge so that the sparse and dense implementations share most of the attention kernel, while only the data-loading module differs.

JIT Attention Variants

Attention variants are not a small detail anymore. Current LLM serving stacks use GQA/MQA, RoPE placement differences, ALiBi, sliding windows, logits soft caps, custom masks, FP8 KV cache, speculative decoding masks, and model-specific score transforms. Maintaining a hand-written CUDA kernel for every combination is not sustainable.

FlashInfer’s second major design is a customizable CUDA template with JIT specialization.

The figure uses a FlashSigmoid example to show the compiler path. The user describes an attention variant in Python. The JIT compiler inserts variant functors, additional variables/tensors, data types, and kernel traits into CUDA templates. PyTorch JIT then compiles and registers the result as a custom operator.

The paper breaks the attention variant into functor-like hooks:

QueryTransform, KeyTransform, ValueTransform: transform Q/K/V before attention.

LogitsTransform: transform logits before softmax or an alternative score normalization.

LogitsMask: apply custom masking, such as sliding window or sparse patterns.

OutputTransform: transform the final attention output.

This is a good boundary. A serving runtime should not need to fork a whole kernel just to add a score transform or model-specific mask. The variant should be injected into a stable skeleton that still controls tiling, memory movement, and reduction.

There is still an engineering tradeoff. JIT specialization improves performance and supports variants, but serving systems cannot compile during every request. The practical path is compile common variants during initialization, cache them, and make runtime metadata selection cheap.

Tile Sizes And Decode Kernels

FlashInfer also changes tile-size selection. Traditional FlashAttention-2 tile sizes such as are good for dense prefill on A100-like workloads, but inefficient for short-query decode. FlashInfer supports multiple tile sizes, roughly over query tile sizes and KV tile sizes , then selects based on task and hardware constraints.

This is the kernel-level version of a simple serving fact: prefill and decode are different phases.

Prefill: and both can be large. The kernel has enough compute to use large Tensor Core tiles.

Decode: is tiny while grows over time. The pressure shifts to memory bandwidth, occupancy, and load balance.

Incremental/chunked prefill: is moderate and the request already has existing KV. The kernel has mixed prefill/decode behavior.

Shared-prefix decode: many queries share prefix KV. The kernel should reuse shared KV and avoid duplicated loading.

The tile choice is therefore not a fixed property of the GPU. It depends on the serving shape produced by the scheduler.

Load-Balanced Runtime Scheduler

The third major design is dynamic scheduling. Sequence lengths change every generation step. Some requests are short, some are long, and long KV ranges may need to be split into several work chunks. If work is assigned naively, some CTAs finish early while others are stuck processing long contexts.

The important detail is determinism. Stream-K-style scheduling is a natural reference, but the paper avoids atomic aggregation because serving attention should be reproducible for identical inputs. FlashInfer instead computes a deterministic work plan and a deterministic reduction map.

Figure 6 shows the runtime flow. The attention kernel writes partial attention states for work tiles. A contraction kernel reduces those partial states into final outputs using the attention-state composition operator. The scheduler produces three pieces of plan information:

  1. the work queue for each CTA;
  2. the mapping from partial outputs to final outputs;
  3. the reduction map used by the contraction stage.

The plan is generated on CPU for each generation step because sequence lengths change. The paper argues this overhead can be amortized across layers because the same plan information is reusable for every layer in that generation step.

End-To-End Serving Results

The first end-to-end experiment integrates FlashInfer into SGLang and compares with a Triton backend.

The paper evaluates Llama 3.1 8B on 1xH100 and Llama 3.1 70B on 4xH100 under ShareGPT and synthetic variable-length workloads. The reported result is consistent speedup in both inter-token latency and time-to-first-token. I read this as a sign that the kernel layer matters even when the runtime is already doing continuous batching and scheduling.

One caveat: end-to-end serving numbers depend heavily on request rate, SLO policy, model implementation, CPU overhead, and integration quality. The paper’s SGLang result is useful because it tests FlashInfer inside a real serving engine, but I would still reproduce it under the target workload before assuming the same percentage.

Kernel Utilization Under Dynamic Lengths

Kernel-level results explain why the end-to-end result is plausible.

Figure 8 compares achieved bandwidth utilization for decode and FLOPs utilization for prefill under constant, uniform, and skewed sequence length distributions. FlashInfer improves especially in uniform and skewed distributions. That is exactly where static work assignment struggles: different requests have different KV lengths, and the long ones can create tail CTAs.

For prefill, the gains are smaller and depend on hardware and shape. This matches intuition. Dense prefill already exposes enough work for FlashAttention-style kernels. Decode and variable-length serving are where dynamic scheduling and tile-size selection matter more.

Customization For Long Context

FlashInfer also evaluates a Streaming-LLM path where RoPE and attention can be fused.

The paper reports 28-30% latency reduction in the Streaming-LLM setting and higher bandwidth utilization for the fused RoPE path. The point is not only that RoPE fusion is good. The point is that serving kernels need a customization mechanism. If the runtime or model wants a special score/key transform, an attention engine should make it possible to fuse that transform instead of launching a separate kernel around attention.

This connects directly to the JIT design. A fixed attention kernel library can be fast for common cases, but the long tail of model-specific variants will keep appearing.

This is a useful result because it shows composable formats are not a universal win. They are a tool for a specific shape: enough shared prefix to benefit from a larger shared block, but not so much extra overhead that the metadata path dominates.

GQA Head-Group Fusion

The appendix includes one implementation detail I find important: head-group fusion for grouped-query attention.

In GQA, multiple query heads share one KV head. A naive decode implementation can assign separate thread blocks to different query heads and reload the same KV cache repeatedly. FlashInfer fuses query heads into the query-length dimension, so the same shared-memory KV load can serve all query heads in the group.

Sparse Versus Dense KV Overhead

Sparse KV support is only useful if the sparse gathering overhead does not erase the benefit. The appendix compares sparse and dense KV-cache performance.

For decode, the paper reports negligible difference between sparse and dense KV cache in this experiment. For prefill, sparse KV has an approximately 10% gap. That is a reasonable tradeoff: decode is the phase where scattered KV reads are unavoidable in paged/sparse serving, and keeping sparse decode close to dense decode is valuable.

The paper also explains a hardware reason for the remaining gap. Hopper TMA helps dense contiguous KV loading, but sparse gathering needs arbitrary row indices, so FlashInfer falls back to async-copy style loading and pointer arithmetic for sparse paths.

FlexAttention And Variant Benchmarks

The appendix compares FlashInfer with FlexAttention on AttentionGym-style variants.

FlashInfer is faster in these tables, especially at longer sequence lengths and on variants such as causal attention, logits soft cap, ALiBi, and sliding window. The paper attributes much of the advantage to Hopper-specific features such as warp specialization and TMA, plus CUTLASS-level resource control compared with Triton. That caveat is important: the gap is not purely algorithmic; it is also an implementation and backend maturity result.

Shared Prefix And Load-Balancing Ablations

The shared-prefix table is one of the clearest places where composable formats show up numerically.

For a shared prefix length of 32768, composable format with batch size 16 reports 217.42 us versus 945.67 us for the single format in the same batch-size setting. With batch size 64, it reports 254.54 us versus 4090 us. The exact numbers are workload-specific, but the direction is easy to understand: if the prefix is huge and shared, one format should exploit that sharing instead of reloading the same prefix independently.

The load-balancing and vLLM tables are also useful because they show limits.

Tables 6 and 7 show that load balancing helps most when sequence lengths are highly variable and long. In the setting, ITL improves from 13.89 ms without load balancing to 8.63 ms with load balancing. TTFT improves from 421.60 ms to 411.02 ms, while Triton is much worse at 566.30 ms. For ShareGPT and shorter variable lengths, the gains are smaller.

Table 8 is a useful warning. In the vLLM integration, FlashInfer with e4m3 KV cache reduces median ITL from 12.56 to 10.92, but the bf16 integration does not improve median ITL because host-side Python overhead offsets the kernel gain. This is exactly why kernel papers should include integration results: a faster kernel can disappear under runtime overhead if the boundary is not engineered carefully.

Fine-Grained Sparsity

The last appendix table compares fine-grained KV sparsity latency against PyTorch SDPA and FlexAttention.

The scale of the difference is large. At sequence length 32768 and page_budget=64, FlashInfer reports 22.371 us, while PyTorch SDPA is 1711.955 us and FlexAttention is 1169.109 us. This is the strongest evidence that the BSR/sparse-row gathering design is not just a cleaner API abstraction. For sparsity patterns such as long-context KV pruning, the right sparse attention kernel can change the cost model.

I would still be careful when generalizing this result. Fine-grained sparsity only helps if the model or runtime can produce a useful sparse KV pattern without hurting quality. FlashInfer supplies the kernel substrate; it does not solve the modeling question of which KV pages are safe to drop.

How I Would Place FlashInfer In The Serving Stack

FlashInfer sits below the scheduler and above raw CUDA templates:

Request scheduler: decides which requests are batched and when. It supplies dynamic sequence metadata to FlashInfer.

KV-cache manager: decides where KV pages live and which pages are shared. It supplies page, ragged, and sparse layout metadata.

Attention variant layer: owns model-specific masks, logits transforms, RoPE placement, FP8 KV, and GQA. These become JIT specialization inputs.

FlashInfer runtime: owns work queues, chunking, and partial-state reduction. It plans deterministic CTA work and reductions.

FlashInfer kernels: execute the actual global/shared/register/Tensor Core work through specialized attention kernels.

The most important contract is that the runtime should describe the layout and variant precisely enough, while FlashInfer owns the optimized execution. If that boundary is leaky, every serving framework ends up maintaining special-case kernels. If the boundary is clean, serving systems can focus on batching, SLOs, memory placement, and prefix reuse.

Reproduction Checklist

If I were reproducing this paper or evaluating FlashInfer for a serving system, I would not start with only one tokens/s benchmark. I would test the following cases separately:

  1. Single-token decode with long KV cache. This is the most memory-bound case and should reveal tile-size and GQA behavior.
  2. Ragged prefill. Variable prompt lengths should test dynamic scheduling and packed/ragged metadata handling.
  3. Paged KV decode. This checks the page-table path and sparse/dense gather overhead.
  4. Shared-prefix parallel generation. This is where composable formats should matter.
  5. A custom attention variant. Sliding window, logits soft cap, ALiBi, or fused RoPE can test whether JIT specialization actually avoids extra launches.
  6. CUDA Graph replay. Plan/run separation should avoid graph recapture while still adapting to changing sequence lengths.
  7. End-to-end integration. Measure TTFT, ITL, throughput, CPU overhead, and graph replay overhead inside vLLM/SGLang/MLC, not only kernel microbenchmarks.

The vLLM appendix table is the reason for the last item. A kernel can be excellent and still fail to improve a serving system if the host/runtime integration adds enough overhead.

Limitations And Open Questions

FlashInfer increases the expressiveness of the attention-kernel layer, but that also increases API surface area. The hard questions are mostly at boundaries:

  • How many variants should be JIT-compiled and cached ahead of time?
  • How should a serving runtime choose among composable formats without expensive planning?
  • When does sparse KV metadata overhead exceed sparse compute savings?
  • Can the scheduler move more planning work to device without breaking CUDA Graph compatibility?
  • How should kernel libraries expose new hardware features without making runtime integration too fragile?

The paper does not fully answer all of these. It does show a plausible architecture: block-sparse/composable layouts for KV heterogeneity, JIT templates for attention variants, and deterministic load-balanced planning for runtime dynamism.

Takeaways

FlashInfer’s core idea is that LLM serving attention should be designed around runtime-generated shapes, not training-time dense attention benchmarks. The useful mental model is:

The paper is valuable because it connects all four:

  1. BSR and composable formats represent paged, sparse, and shared-prefix KV layouts.
  2. JIT templates specialize model-specific attention variants without rewriting the whole kernel.
  3. Attention-state composition makes split KV chunks reducible exactly.
  4. Load-balanced planning keeps CTAs busy under ragged sequence lengths.
  5. Plan/run separation preserves CUDA Graph replay while sequence lengths change.

My main takeaway for CUDA work is simple: a beautiful dense attention kernel is not enough for serving. The real kernel has to read the KV cache layout that the runtime actually produces, fuse the transforms that the model actually uses, and survive the dynamic sequence lengths that users actually send.
