[CUDA] Warp Timeline with NVBit and Modal

  2025-07-01 2025-07-01 Created

Reference

  • GitHub repo: Baytoro/warptrace
  • Main entrypoint: warp_timeline_modal.py
  • NVBit tool: nvbit_tool/warp_timeline_nvbit.cu, nvbit_tool/inject_funcs.cu
  • Example kernel: example/warp_paths.cu
  • Exported viewer: build/warp-timeline/timeline.html
  • NVIDIA NVBit release used by the repo: nvbit-Linux-x86_64-1.8

This note is about a small but useful CUDA profiling project. The repo has one clear goal: run a CUDA executable on a remote Modal B200 machine, inject an NVBit tool with LD_PRELOAD, collect warp-level basic-block timestamps, map those basic blocks back to SASS, and render the result as a local HTML timeline.

I like this project because it sits between two common debugging levels. It is lower level than Nsight Systems, because it records warp/basic-block behavior inside a kernel. It is higher level than reading raw SASS, because it groups basic blocks into visible timeline spans: load, compute, sync, and store. It is not a replacement for Nsight Compute metrics. It is closer to an explanatory microscope for one kernel.

End-To-End Flow

The whole pipeline can be read as a dataflow:

flowchart TB
    src["CUDA executable
target_app"] --> modal["Modal B200 container"]
    toolsrc["nvbit_tool/*.cu"] --> buildtool["build NVBit shared object"]
    nvbit["warp_timeline_nvbit.so"] --> preload["LD_PRELOAD"]
    buildtool --> nvbit
    modal --> preload
    preload --> run["run target CUDA program"]
    run --> events["managed event buffer
basic-block records"]
    events --> trace["trace.json"]
    run --> sass["cuobjdump --dump-sass"]
    sass --> enrich["map PC offsets to SASS"]
    trace --> enrich
    enrich --> viewer["timeline.html"]

The important design choice is that the CUDA source does not need to be changed. The target program is launched normally, except that the process loads warp_timeline_nvbit.so through LD_PRELOAD. NVBit then instruments the CUDA function at runtime before the kernel launch.

What NVBit Records

The event schema lives in nvbit_tool/common.h:

Each record is intentionally small:

time: the GPU globaltimer value at basic-block entry.

grid_launch_id: a monotonically increasing launch id assigned by the host-side NVBit callback.

pc_offset: SASS PC offset of the first instruction in the basic block.

bb_id: the tool’s basic-block id inside the function CFG.

num_instrs: number of instructions in that basic block.

cta_id_*: CUDA block coordinates.

warp_id: warp id inside the block.

sm_id: SM that executed the recording lane.

There are two details here that I would keep:

First, only one active lane records the event. The function computes the first active lane with __ffs(active_mask) - 1, then returns for all other lanes. This makes each basic-block entry a warp-level event instead of a thread-level event.

Second, the timestamp is taken from globaltimer:

That gives a single device-wide time base. The viewer does not convert it to seconds. It keeps raw ticks, which is honest for this kind of tool: the relative shape of the timeline matters more than pretending to have calibrated wall-clock units.

Where The Injection Happens

The host-side NVBit code instruments the first instruction of each basic block:

This is the core idea of the project. Instead of instrumenting every instruction, it instruments basic-block entries. That has three consequences:

  1. The trace is smaller.
  2. The overhead is lower than instruction-level tracing.
  3. The timeline loses instruction-by-instruction detail, but keeps the control-flow path and approximate phase shape.

For this project, that tradeoff is reasonable. I usually want to know whether a warp is in a load-heavy region, compute-heavy region, barrier region, or store region. Basic-block granularity is enough for that first pass.

The launch callback wires everything together:

On launch entry, the function is instrumented and the event counter is reset. On launch exit, the host synchronizes, reads the managed event buffer, converts records into spans, and appends them to the trace.

From Records To Spans

The raw event records are point samples: one timestamp per basic-block entry. The viewer needs spans. The conversion is simple:

  1. Sort events by launch id, block, warp, time, and basic-block id.
  2. For each event, use the next event from the same block and warp as the end time.
  3. If there is no next event, use time + 1.

For every bb_*_pc_* span, it extracts the PC offset and instruction count, then looks up the corresponding SASS slice:

The next step is classification. The tool assigns each instruction an opcode category, then assigns the basic block a phase class:

This heuristic is intentionally practical. It does not try to prove what the block does semantically. It asks: what kind of operations dominate the block enough to color the timeline?

That is why the viewer can show four fixed phase colors:

Phase Meaning in this viewer
load data movement or tile staging, including selected shared/global memory instructions
compute arithmetic, address arithmetic, predicate work, and general non-memory execution
sync barriers and synchronization/wait blocks
store global stores

What The HTML Viewer Adds

The HTML renderer normalizes time by subtracting the first event timestamp. It also merges adjacent spans from the same row when they share the same phase class:

This is why the screenshot reports 332 phase spans, even though the raw trace contains 783 events. The viewer is not hiding information permanently. It is compressing adjacent same-phase basic blocks into readable bars, while still keeping the list of merged basic-block ids for hover/click details.

The selected-span view shows the payoff:

After selecting a bar, the viewer can show:

  • row identity: SM, block, warp;
  • start/end/duration in cycles;
  • merged basic-block count;
  • opcode summary;
  • basic-block id and PC offset;
  • SASS sample for the selected basic block.

This is the part I find most valuable. A normal timeline can tell me that a warp had a long green region. This viewer lets me click into that region and see which basic-block path and SASS sample produced it.

Reading The Example Timeline

The overview screenshot is already enough to confirm that the example kernel is behaving as intended.

Warp rows:

The rows match one CUDA block, four warps, one SM. In the unzoomed overview, most of the visible time is compute-colored because adjacent compute blocks are merged. In the more zoomed selected-span screenshot, the repeated structure appears: short load segments, compute regions, sync regions, and store at the end.

The expected warp-specialized behavior is:

W0: mostly data movement into shared memory for the A tile.

W1: mostly data movement into shared memory for the B tile.

W2 and W3: compute-heavy regions for two row groups, with synchronization between K tiles and stores near the end.

One thing to remember: this is basic-block tracing, not occupancy analysis. If a row is green, it does not mean the warp was continuously executing useful floating-point math with perfect efficiency. It means the merged basic blocks were classified as compute. To understand throughput, memory transactions, issue stalls, or cache behavior, I would still use Nsight Compute.

Why Basic-Block Level Is A Good Compromise

Instruction-level tracing is tempting, but it can explode quickly. Every instruction from every active lane would create a massive trace and heavy overhead. This tool uses one record per warp per basic-block entry. That keeps the trace small enough for a browser viewer.

Modal Side

The Modal part is mostly engineering glue, but it is important glue. The runner builds an image from:

Then the remote function:

  1. checks architecture with uname -m;
  2. checks the GPU with nvidia-smi;
  3. downloads or reuses the NVBit archive;
  4. builds warp_timeline_nvbit.so;
  5. runs the target with LD_PRELOAD;
  6. captures cuobjdump --dump-sass;
  7. returns trace, log, and SASS text to the local machine.

NVBit is cached under /cache/warp-timeline/, and the built tool is keyed by a hash of the nvbit_tool source files. That avoids rebuilding the instrumentation shared object every time if the tool source did not change.

This is also why no local GPU is required for profiling. The local machine runs Python and receives artifacts. The CUDA execution and NVBit instrumentation happen remotely.

Things I Would Improve Next

The current tool is already useful, but the design leaves several obvious next steps.

First, I would add an option to record only selected kernels. Right now the NVBit callback instruments launched CUDA functions as they appear. For a larger application, the trace could include setup kernels or library kernels that are not the current target.

Second, I would make phase classification configurable. The current opcode heuristic is a good default, but a kernel author may want to label selected PC ranges manually as prologue, tile-load, mma-mainloop, epilogue, or store.

Third, I would add a small summary table next to the viewer:

This would make it easier to compare loader warps and compute warps without eyeballing bar widths.

Fourth, I would preserve multidimensional block ids as structured fields in the viewer. The current renderer flattens block coordinates into one integer. That is convenient for the first version, but a 2D/3D grid would be easier to inspect if block coordinates stayed as (x, y, z).

Fifth, I would add a direct “open source line” mapping only when debug/source information is available. For optimized CUDA kernels, SASS and PC offsets are often the real source of truth, but source correlation would still help during early kernel development.

Takeaways

This repo is a compact example of how to build a custom CUDA introspection tool:

The strongest part is the workflow. I can run an unmodified CUDA binary, get a trace, open one HTML file, and inspect warp paths with SASS context. The exported timeline is not trying to be a full profiler. It is a focused tool for answering one question:

What did each warp do, in what order, and which SASS basic blocks explain the visible phases?

For warp-specialized kernels, that is exactly the kind of question I want to answer before going deeper into Nsight Compute metrics.
