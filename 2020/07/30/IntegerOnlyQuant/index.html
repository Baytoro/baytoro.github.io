Integer-Arithmetic-Only INT8 Inference

Paper: Quantization and Training of Neural Networks for Efficient Integer-Arithmetic-Only Inference

This paper is the practical INT8 reference. Many quantization papers before it compressed weights or simulated low precision, but this one defines an arithmetic path that can actually run on integer hardware: uint8/int8 operands, int32 accumulation, integer bias handling, and a requantization step into the next layer’s activation range.

Motivation

For mobile inference, reducing model size is not enough. If the runtime stores weights in 8-bit but repeatedly dequantizes into float, it still pays a floating-point execution cost and loses much of the hardware benefit. The paper’s target is stricter: train the model so that the deployed graph can execute with integer arithmetic only during inference.

Figure 1 is the whole story. The left graph is the inference path: input and weights are uint8, convolution accumulates into int32, bias is int32, ReLU6 is represented in integer space, and the output is requantized. The middle graph is the training path: fake quantization nodes are inserted so the float model learns the same discretization error it will see at inference time.

Training

The training path uses simulated quantization. During the forward pass, weights and activations are rounded and clipped as if they were low precision. During backward propagation, the quantizer is handled with a straight-through estimator. The important consistency rule is that training-time fake quantization must match deployment-time integer quantization closely enough that the model does not learn an unrealistic float behavior.

The paper also discusses batch normalization folding. In inference, BatchNorm can be folded into the preceding convolution weights and biases before quantization. This avoids leaving a floating-point normalization operator in the integer graph.

Results

The paper evaluates MobileNet-style classification and detection models on ImageNet and COCO, with mobile CPU latency as the practical target. The central result is that 8-bit quantized MobileNets can preserve almost all of the floating-point accuracy while improving the latency/accuracy tradeoff on ARM and Qualcomm-class hardware.

A simplified way to read the results:

Component Deployment choice
Weights 8-bit integer, often per-layer/per-channel depending on op support
Activations 8-bit integer with affine scale and zero-point
Accumulation int32
Bias int32, matched to input and weight scales
Nonlinearity represented in quantized range, especially ReLU6

Takeaway

This paper is the baseline for practical quantization engineering. Later LLM papers often use symmetric scales, group-wise scales, per-channel scales, weight-only INT4, or NF4, but the deployment question is unchanged: where are the scales, where is zero represented, what is the accumulator type, and does the graph avoid hidden floating-point islands?

When reading newer methods, I keep this paper in mind as a checklist. A quantization method is not just an accuracy table. It is an arithmetic contract between the model and the kernel implementation.

Bias is another easy place to make mistakes. Bias is stored in int32 because its scale is the product of input and weight scales. If the bias is quantized with the wrong scale, the layer output shifts even if the convolution itself is correct.

The paper also uses ReLU6 intentionally. ReLU6 bounds activations, making activation quantization easier than unbounded ReLU. This is one reason MobileNet-style models were friendly to early mobile quantization.

What I Would Check In A Runtime

If implementing this in a backend, I would verify:

  • whether weights use per-tensor or per-channel scales;
  • whether output requantization uses a fixed-point multiplier rather than float;
  • whether BatchNorm is folded before quantization;
  • whether padding value maps to the activation zero-point;
  • whether residual/add ops require matching output scales.

This is the paper’s real legacy: quantization is a graph-level contract, not a single rounding formula.

Implementation Checklist

There are three places where a reproduction usually goes wrong. First, batch normalization must be folded into convolution before quantization; otherwise inference still depends on floating point normalization parameters. Second, activation ranges collected during fake quantization must match the inference kernels. Third, accumulator overflow and rounding mode matter. The paper’s path is designed around int8 inputs with int32 accumulation, then requantization back to int8.

The long-term influence is TensorFlow Lite style quantization. Later Transformer papers such as I-BERT reuse the same principle, but need extra work because GELU, Softmax, and LayerNorm are not naturally integer-friendly operators.
