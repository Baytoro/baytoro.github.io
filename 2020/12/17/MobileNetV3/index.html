Searching for MobileNetV3

Howard A, Sandler M, Chu G, et al. Searching for MobileNetV3. ICCV 2019.

Paper

MobileNetV3 is not a pure “NAS found everything” paper. It is a practical mobile-model design paper that combines platform-aware NAS, NetAdapt, and manual architecture edits. That combination is the main lesson: real efficient networks usually come from search, measurement, pruning, and human profiling work together.

Design Pipeline

The design flow is roughly:

  1. use platform-aware NAS to find a strong starting architecture;
  2. use NetAdapt to adjust channels and layers toward latency targets;
  3. manually inspect bottlenecks and redesign activations, SE placement, and final layers.

The figure compares MobileNetV3 against MobileNetV2 and MnasNet under real Pixel latency measurements. The important detail is that latency is measured on device, not inferred only from multiply-add counts.

Hard Swish

Swish is effective but expensive on mobile hardware:

MobileNetV3 uses hard-swish:

This is a piecewise-linear approximation that is friendlier to mobile inference kernels. It is a small operator-level edit, but it has system-level consequences because activations are executed everywhere.

SE And Last-Stage Redesign

The model uses squeeze-and-excitation selectively. SE improves accuracy, but it is not free; where it is placed matters for the latency-accuracy tradeoff.

The paper also redesigns the final stage. MobileNetV2’s tail layers were not latency-efficient enough, especially after channel expansion. MobileNetV3 reduces unnecessary computation in the last layers while keeping classification quality.

Large And Small Models

The paper releases two model families:

Model Target
MobileNetV3-Large higher accuracy under moderate mobile latency
MobileNetV3-Small lower-resource mobile use cases

This is a deployment-oriented design choice. There is no single universally optimal model; there is a family of models for different budgets.

Reproduction Notes

For this paper, FLOPs are not enough. A faithful comparison should record device, runtime, thread count, warmup, input resolution, and batch size. The reported latency is tied to Pixel/TFLite measurements. A different inference runtime can change the Pareto frontier.

I would also separate the effects of NAS, NetAdapt, hard-swish, SE, and last-stage redesign. Otherwise it is easy to over-credit the search algorithm and under-credit the engineering edits.

Takeaway

MobileNetV3 is a strong example of search-assisted engineering rather than fully automatic architecture discovery. NAS provides a good candidate, but profiler-driven manual edits turn it into a deployable model.
