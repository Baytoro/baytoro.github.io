MobileNetV3: Search-Assisted Engineering for Mobile CNNs

H.J. Chen
  2020-12-17 2020-12-17 Created  
  • Work hard 
  • >
  • PaperReading 
 
  • NAS 
  • | Mobile 

Howard A, Sandler M, Chu G, et al. Searching for MobileNetV3. ICCV 2019.

Paper

MobileNetV3 is easy to misread as “NAS found a better MobileNet.” That is not the main lesson. The paper is closer to a deployment engineering log: start from a platform-aware searched model, run a layer-wise adaptation procedure, inspect the expensive pieces, then make operator and layout changes that are outside the search space.

The result matters because the metric is not just MAdds. The paper measures single-thread latency on real Google Pixel phones through TFLite. That makes the work a useful bridge between architecture search papers and the kind of model surgery that actually determines mobile runtime.

What The Paper Is Optimizing

MobileNetV3 keeps the MobileNetV2/MnasNet lineage:

  • inverted residual blocks remain the basic building block;
  • depthwise separable convolution remains the compute-saving primitive;
  • squeeze-and-excitation is used, but selectively;
  • the final model is evaluated by measured Pixel latency, not only by operation count.

The pipeline has three layers:

Stage Role Why It Is Not Enough Alone
Platform-aware NAS Find a global block-level architecture under a latency-aware reward. The search space still cannot express every useful manual layout change.
NetAdapt Adjust channels layer by layer toward a target latency. It is a local adaptation method and depends on a good seed model.
Manual redesign Change activations, the first layer, the last stage, and SE details. These choices need profiling and implementation knowledge.

That last row is the part I care about most. MobileNetV3 is a strong model because the authors combine automated search with engineering constraints instead of pretending the search algorithm owns the whole design.

Accuracy And Real Latency

The front page result is the Pixel latency frontier. MobileNetV3-Large competes in the 40-100 ms range, while MobileNetV3-Small competes in the 20-40 ms range.

The important comparison is not just “higher accuracy.” The paper reports that MobileNetV3-Large reaches the same 75.2% ImageNet top-1 as MnasNet-A1 while reducing Pixel 1 latency from 71 ms to 51 ms. MobileNetV3-Small reaches 67.4% top-1 at 15.8 ms, compared with MnasNet-small at 64.9% and 20.3 ms.

Model Top-1 Pixel 1 latency
V3-Large 1.0 75.2 51 ms
MnasNet-A1 75.2 71 ms
V2 1.0 72.0 64 ms
V3-Small 1.0 67.4 15.8 ms
MnasNet-small 64.9 20.3 ms

The table makes the paper’s position clear. V3-Large is not merely a slightly larger model with better accuracy. It is a measured-latency improvement over another platform-aware NAS model at the same top-1 point.

The MAdds plot is still useful, but it is secondary.

MAdds tells us how many arithmetic operations a model nominally performs. Pixel latency tells us whether those operations map well onto the runtime, memory hierarchy, fused kernels, quantized operators, and thread setup. MobileNetV3 is designed against the second target.

From MobileNetV2 Blocks To V3 Blocks

MobileNetV2 uses the inverted residual and linear bottleneck block. The narrow representation sits at the input and output of the block, and the expensive work happens in the expanded channel space.

MobileNetV3 keeps this general form, but it brings in MnasNet-style squeeze-and-excitation and changes where nonlinearities are used.

This is not a cosmetic detail. SE is an accuracy booster, but it introduces extra small matrix/vector work and activation functions. Nonlinearity placement also matters because early feature maps are spatially large. An activation that looks cheap in a paper formula can become expensive when it is applied to many pixels.

Search Strategy

The paper uses two search/adaptation tools:

  1. Platform-aware NAS for block-wise global architecture search.
  2. NetAdapt for layer-wise channel adjustment.

For the large model, the authors reuse MnasNet-A1 as the starting point because the earlier MnasNet search already targets roughly the same 80 ms latency regime. For the small model, they adjust the reward because accuracy changes more sharply with latency in the small-model regime.

This is a practical detail. The algorithm is not optimizing an abstract FLOPs proxy; it is trying to spend every millisecond of latency reduction where the accuracy damage is smallest.

The Last Stage Was Too Expensive

One of the most valuable pieces of the paper is the last-stage redesign. MobileNetV2-like networks often expand to a high-dimensional feature tensor before global pooling. That is expensive because the expansion is still applied at a spatial resolution such as 7x7.

MobileNetV3 moves the expensive feature generation after global average pooling. Once the tensor is 1x1, the 1x1 expansion is almost free compared with doing it over a spatial map.

The paper reports that this efficient last stage reduces latency by 7 ms, about 11% of runtime, and removes roughly 30M MAdds with almost no accuracy loss. This is exactly the type of edit a search space may miss: it is not just “choose another kernel size,” it is a structural observation about where expensive features are needed.

There is also an early-layer edit. The authors reduce the first convolution filters from 32 to 16 and find that hard-swish preserves accuracy there. That saves about 2 ms and 10M MAdds.

Hard-Swish

Swish is:

It often improves accuracy over ReLU, but sigmoid is not a friendly primitive on many mobile inference paths. MobileNetV3 replaces it with a piecewise-linear approximation:

This is not just an approximation for mathematical neatness. ReLU6 is widely optimized in mobile frameworks, and hard-swish avoids the precision and implementation variability of approximate sigmoid in quantized inference. The authors also avoid using h-swish everywhere. They use it mainly in the second half of the network because early activations have larger spatial maps and are more expensive.

The ablation table shows why the placement matters.

Variant Top-1 Pixel 1 latency
V3-Large 1.0 75.2 51.4
ReLU 74.5 50.5
h-swish @16 75.4 53.5
h-swish @112 75.0 51.0

Using h-swish from the 16-channel point gives a slight accuracy gain but costs more latency. Starting it later at the 112-channel point is closer to the final design tradeoff. The paper’s final choice is not “h-swish is always better”; it is “h-swish is worth it where the accuracy gain buys enough latency budget.”

The optimized implementation also matters:

Without an optimized h-swish kernel, the same architecture can move to a worse point on the latency curve. That is a useful warning for reproduction: changing the runtime implementation can change the conclusion.

Architecture Definitions

The final paper defines two model families. The large model targets higher accuracy under moderate mobile latency, and the small model targets lower-resource cases.

The large architecture has a mixed block layout: 3x3 and 5x5 bottlenecks, selective SE, ReLU in earlier blocks, and h-swish in later blocks. The tail uses the efficient last-stage pattern discussed above.

The small model is not just a width multiplier of the large one. It has its own searched/adapted structure, uses more 5x5 blocks in the middle, and is tuned for a different part of the latency curve.

Main ImageNet Results

The main floating-point table is the best compact evidence for the paper.

Three observations stand out:

  • V3-Large 1.0 and MnasNet-A1 both report 75.2% top-1, but V3-Large is 20 ms faster on Pixel 1.
  • V3-Small 1.0 is much smaller in MAdds than MnasNet-small while being both more accurate and faster.
  • V2 1.0 has more MAdds and lower accuracy than V3-Large, and it is slower on Pixel 1.

The last point is a reminder that MobileNetV3 is not only a NAS story. The final-stage edit, activation implementation, SE scaling, and channel adaptation all contribute to the measured latency.

The quantized results are worth checking separately because the paper is targeting mobile inference, not just floating-point research models.

For the full-size model, quantized MobileNetV3-Large keeps 73.8% top-1 and runs at 44 ms on Pixel 1, while MobileNetV2 1.0 reports 70.9% and 52 ms. For the small regime, MobileNetV3-Small keeps 64.9% top-1 at 15.5 ms, compared with MobileNetV2 0.35 at 57.2% and 16.7 ms. This is also where the hard-sigmoid/hard-swish choice matters: the activation has to survive the actual inference path.

Resolution And Width Scaling

MobileNetV3 is also evaluated across width multipliers and input resolutions.

The paper notes that changing input resolution can provide a better accuracy-latency tradeoff than changing the width multiplier. That makes sense: resolution changes the spatial cost of almost every layer, while width changes channel dimensions. But resolution is not always a free tuning knob. Detection and segmentation often need higher spatial detail, so deployment constraints can force a resolution choice before the architecture is selected.

The appendix table makes the deployment menu explicit.

Model Accuracy Pixel 1 latency
large 224/1.25 76.6 77.0
large 224/1.0 75.2 51.2
large 160/1.0 71.7 27.8
small 224/1.0 67.5 15.8
small 160/1.0 62.8 8.6
small 96/1.0 51.7 4.4

For a mobile product, this table is more useful than a single headline model. It gives several operating points that can be selected according to latency, battery, memory, and task accuracy requirements.

Component Progression

The most honest figure in the paper is the component progression plot.

The path is roughly:

Step Effect
MnasNet seed Strong baseline around 75.2% top-1.
SE/4 Improves accuracy with modest parameter cost.
NetAdapt Moves the model to a lower latency region.
Compact / last-stage edits Saves latency without giving up much accuracy.
h-swish and optimized h-swish Recovers or improves accuracy while depending on runtime support.

This figure is why I would not describe MobileNetV3 as a fully automatic NAS method. The final point is reached by a sequence of searched, adapted, and hand-designed changes.

Detection Transfer

The paper also uses MobileNetV3 as a drop-in SSDLite backbone on COCO.

The interesting detail is the channel reduction between C4 and C5. The last part of the classifier backbone is tuned for 1000 ImageNet classes, but COCO detection has 90 classes and different feature needs. Reducing channels in the late feature layers improves latency with little or no mAP loss.

Backbone mAP Latency
V2 22.1 162 ms
MnasNet 23.0 174 ms
V3 22.0 137 ms
V3 with channel reduction 22.0 119 ms
V3-Small 16.0 52 ms
V3-Small with channel reduction 16.1 43 ms

This is another example of post-search adaptation. A backbone that is good for classification still needs task-specific trimming when transferred to detection.

Semantic Segmentation

For segmentation, the paper proposes Lite R-ASPP, a lightweight head designed for MobileNetV3.

The head keeps the ASPP intuition but removes expensive branches. It uses global-average-pooling-like context and a small number of 1x1 convolutions. The authors also use atrous convolution for denser features when output stride is 16.

On Cityscapes validation, the MobileNetV3 rows are broadly similar in mIOU to MobileNetV2 rows but usually faster. The small model is especially useful: MobileNetV3-Small with LR-ASPP reaches 68.38 mIOU at 327 ms half-resolution Pixel 3 latency in the table.

The Cityscapes test table shows the expected tradeoff. Output stride 16 is more accurate and slower; output stride 32 is faster and slightly less accurate. Again, the paper is not claiming one universal best point. It is giving a set of mobile operating points.

Reproduction Notes

For a faithful reproduction, I would record these details before comparing results:

  • Device model: the paper reports Pixel 1/2/3 single large core measurements.
  • Runtime: the paper uses TFLite benchmark tooling.
  • Threading: measurements are single-threaded, not multi-core throughput.
  • Batch size: latency is batch size 1.
  • Input resolution: changing resolution can dominate the measured curve.
  • Operator implementation: optimized h-swish changes the latency conclusion.
  • Quantization path: hard-swish and hard-sigmoid were chosen partly because they are quantization-friendly.

I would also separate five ablations: NetAdapt, SE ratio, efficient last stage, first convolution reduction, and h-swish placement. Without that separation, it is too easy to over-credit the architecture search and under-credit the manual deployment work.

Limitations

The paper is tied to a specific software and hardware stack. Pixel/TFLite latency is a useful target, but it is not a universal latency oracle. A GPU delegate, a different ARM core, a DSP/NPU backend, or a runtime without optimized h-swish can reorder the frontier.

The search process is also not cheap or simple to reproduce. The paper reuses MnasNet machinery, runs NetAdapt, and trains models at scale. The engineering lesson transfers more easily than the exact search recipe.

Another limitation is that the paper reports a strong final design but not a fully exhaustive decomposition of every design interaction. For example, activation placement, SE placement, and channel adaptation are coupled. A clean ablation of each dimension would be expensive.

Takeaway

MobileNetV3 is a search-assisted engineering paper. NAS provides a good seed, NetAdapt sharpens the layer widths, and profiler-aware manual edits remove the pieces that the search space did not express. The strongest message is simple: for mobile CNNs, the real objective is not FLOPs, and the best architectures usually come from search plus runtime-aware model surgery.
