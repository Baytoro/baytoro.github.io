Efficient Neural Architecture Search via Parameter Sharing

H.J. Chen
  2020-01-12 2020-01-12 Created  
  • Work hard 
  • >
  • PaperReading 
 
  • NAS 

Paper / Code

ENAS is the paper that pushed weight sharing into the center of NAS. Earlier reinforcement-learning NAS trained each sampled child architecture almost independently, so the controller could only improve after spending a huge amount of GPU time. ENAS keeps the controller idea, but changes the performance-estimation problem: instead of training every child model from scratch, all child models are subgraphs of one large computational graph and share parameters.

The important point is not only “use an LSTM controller”. The important point is that architecture search becomes a cheap subgraph-selection problem during search, and only the final selected architecture is trained normally from scratch.

One caveat for the released code: the repository is still useful for reading the CIFAR-10 scripts and architecture encoding, but its README warns that the Penn Treebank language-model implementation in that repo is wrong.

Motivation

The original NAS result from Zoph & Le and the later NASNet line made the controller-RNN recipe visible, but the cost was hard to ignore. NASNet is reported with hundreds of GPUs for several days. The expensive part is not sampling an architecture string; it is repeatedly training sampled networks well enough to produce a useful validation reward.

ENAS asks a very direct question: if two sampled architectures reuse the same operation or edge, why train two separate copies of that parameter during search?

The full graph represents the whole search space. A sampled child model is only a subgraph. Parameters live on the graph and are reused whenever the corresponding computation is active. This turns NAS into a one-shot style training problem: keep a large shared model, sample subgraphs from it, and use validation reward to update the sampler.

This is the main cost reduction. ENAS is not making the search space tiny; it is making each architecture evaluation much cheaper.

Contribution

The useful contributions are:

  1. Represent the NAS search space as a directed acyclic graph where child architectures share parameters.
  2. Train two parameter sets alternately: shared child-model weights omega on training data, and controller parameters theta on validation reward.
  3. Apply the same idea to recurrent cells for Penn Treebank and convolutional architectures for CIFAR-10.
  4. Keep both macro search over full CNNs and micro search over reusable convolution/reduction cells.
  5. Report competitive NAS results with a single GTX 1080Ti in hours instead of hundreds of GPUs for days.

Historically, the first point matters most. Many later NAS methods use some version of a supernet, one-shot model, or over-parameterized search graph. ENAS is one of the clean early examples of that shift.

Methodology

Subgraphs and shared parameters

For recurrent cells, the controller samples a sequence of decisions. At each node, it chooses a previous node and an activation function. The sampled decisions define a small DAG, and unused loose ends are averaged to form the cell output.

The paper uses N = 12 recurrent nodes and four candidate activations: tanh, ReLU, identity, and sigmoid. With predecessor choices included, the recurrent-cell search space is about 10^15 models. The large search space is not the bottleneck by itself. The bottleneck is how to score candidates without training 10^15 independent RNNs.

ENAS solves this by making the candidate cells share the same matrix pool. If a sampled cell uses an edge from node j to node l, it uses the shared matrix for that edge. If a different sampled cell uses the same edge later, it reuses the same parameter.

This is a biased estimate of architecture quality. A child architecture is scored using weights it co-trained with many other architectures, not weights optimized only for itself. But it is cheap enough to make the controller loop practical.

The reward is task-specific. For Penn Treebank, the paper uses a constant divided by validation perplexity. For CIFAR-10, it uses validation accuracy on a minibatch. This train/validation split is important: shared weights are trained on training data, but the controller is rewarded for validation behavior.

One practical detail is surprisingly aggressive: for the shared-weight update, the paper says M = 1 sampled model works well. So a minibatch update usually trains only one sampled child architecture, not an average over many architectures.

CNN search spaces

ENAS evaluates two CNN search spaces.

The macro search space designs the whole convolutional network layer by layer. At layer k, the controller chooses:

  • one operation among conv 3x3, sep conv 3x3, conv 5x5, sep conv 5x5, avg pool 3x3, and max pool 3x3
  • skip connections from previous layers

With L = 12, the paper reports about 1.6 x 10^29 possible macro networks.

The micro search space follows the NASNet-style cell idea. Instead of designing the whole network directly, ENAS searches for a convolution cell and a reduction cell, then stacks them into a final network.

For each non-input node inside a cell, the controller chooses two previous nodes and two operations. The operation set is smaller than macro search:

  • sep conv 3x3
  • sep conv 5x5
  • avg pool 3x3
  • max pool 3x3
  • identity

With B = 7, the paper reports about 1.3 x 10^11 final cell-based networks.

The cell search space is smaller and more structured than the macro space. That structure is useful: the discovered cell can be repeated, scaled, and compared more directly with NASNet-style baselines.

Results

Penn Treebank

The RNN cell found by ENAS is shown below. The final output averages six loose-end nodes, which is similar in spirit to letting several intermediate states contribute to the next hidden state.

The reported search takes about 10 hours on a single Nvidia GTX 1080Ti. The final ENAS cell reaches 55.8 test perplexity on Penn Treebank without post-training processing.

Model Params Test PPL
LSTM, Zaremba et al. 66M 78.4
LSTM, Merity et al. 24M 57.3
LSTM, Yang et al. + MoS 22M 56.0
NAS, Zoph & Le 54M 62.4
ENAS 24M 55.8

The comparison with MoS should be read carefully: MoS is a strong output-layer technique, while ENAS is changing the recurrent cell. The paper emphasizes that ENAS does not apply MoS to its cell in this result.

CIFAR-10

On CIFAR-10, ENAS reports both macro and micro search results. The headline number is the micro search space with CutOut: 2.89% test error using 4.6M parameters.

Method GPU Days Params Err
NAS + filters 800 21-28 37.4M 3.65
NASNet + CutOut 450 3-4 3.3M 2.65
ENAS macro+ 1 0.32 38.0M 3.87
ENAS micro 1 0.45 4.6M 3.54
ENAS micro+CutOut 1 0.45 4.6M 2.89

The cost gap is the reason this paper became influential. The micro search takes 0.45 GPU-days in the table, which is roughly 11 hours on one GPU. The result is not better than NASNet-A with CutOut, but it is close enough that the cost reduction becomes the main story.

The discovered micro cells are also interpretable as normal NASNet-style cells:

The cell contains mostly separable convolutions, pooling, identity paths, and concatenated loose ends. In other words, ENAS does not discover a fundamentally new operator. It finds a useful wiring pattern inside a constrained operator set.

Was the controller doing real work?

The paper includes a useful sanity check. If the controller were irrelevant, random sampling from the same search space should be close to ENAS.

That is not what the paper reports:

Setting Result
Random recurrent cell on PTB 81.2 PPL
ENAS recurrent cell on PTB 55.8 PPL
Random macro CNN on CIFAR-10 5.86% error
ENAS macro CNN on CIFAR-10 4.23% error
Random micro cells on CIFAR-10 6.77% error
ENAS micro cells on CIFAR-10 3.54% error

They also disable controller training and train only the shared weights. In the macro space, that converges to 8.92% test error; an ensemble of 250 sampled configurations gets 5.49%. That is still worse than the trained ENAS controller. So the controller is not just decoration around a good search space.

Takeaway

ENAS is best understood as a performance-estimation paper. It keeps the RL controller, but the big idea is weight sharing:

  • train a supergraph instead of thousands of separate child models
  • use validation reward to train the controller
  • retrain the chosen architecture from scratch at the end

The weakness is also clear. Shared weights are a proxy for final architecture quality. A child model may look good because it happened to receive favorable shared-weight training, or look bad because its weights were under-trained by the sampling process. This ranking bias is the main tradeoff behind one-shot NAS.

Still, ENAS changed the practical baseline. After this paper, an NAS method that trains every candidate from scratch needs a strong reason. Most later efficient NAS methods either improve the supernet training, make the relaxation differentiable, add hardware-aware objectives, or try to reduce the bias introduced by weight sharing.
