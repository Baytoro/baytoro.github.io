Neural Architecture Search with Reinforcement Learning

H.J. Chen
  2020-01-02 2020-01-02 Created  
  • Paper Reading 
 
  • NAS 

Zoph B, Le Q V. Neural Architecture Search with Reinforcement Learning. arXiv:1611.01578, 2016.

Paper

This is the paper that made the phrase “Neural Architecture Search” concrete for a lot of people: use an RNN controller to generate a network description, train that child network, then use its validation accuracy as the reward for the controller.

It is expensive and not how most practical NAS is done now. But the formulation is still worth reading because later papers either accelerate it, constrain it, or replace its controller/search space while keeping the same basic feedback loop.

Motivation

Before NAS, architecture design was mostly manual: AlexNet, VGG, Inception, ResNet, DenseNet, and so on. The authors’ question is simple: if a neural network architecture can be serialized as a sequence of design decisions, can another neural network learn to emit that sequence?

The proposed loop is:

The controller samples an architecture with probability . The child model with architecture is trained and evaluated. The resulting accuracy scales the gradient used to update the controller, so better architectures become more likely.

Contribution

The paper contributes:

  1. An autoregressive RNN controller that samples architecture tokens.
  2. A REINFORCE update using child validation accuracy as a non-differentiable reward.
  3. Extensions for skip connections, pooling, and recurrent-cell search.
  4. Large-scale distributed training to make the otherwise brutal search loop feasible.

The headline results are strong for the time:

Task Result
CIFAR-10 3.65% test error
PTB word-level LM 62.4 test perplexity
PTB character LM 1.214 bits/char

The cost is also very real: for CIFAR-10, the controller evaluated 12,800 architectures and the paper reports 800 child networks trained concurrently.

Methodology

Controller as a token generator

For a convolutional child network, the controller emits architecture tokens layer by layer: filter height, filter width, stride, number of filters, and so on.

This turns architecture design into a sequence modeling problem. After the controller emits a complete sequence, a child model is built from those tokens and trained.

Distributed training

The expensive part is child training. One controller update needs feedback from many architectures, and every architecture may take hours to train.

The paper uses a parameter-server setup with many controller replicas. For CIFAR-10, it uses 20 parameter-server shards, 100 controller replicas, and 8 child replicas per controller replica. That is where the famous 800 concurrent networks number comes from.

Skip connections and recurrent cells

A plain token list can describe sequential CNNs, but modern networks need skip connections. The controller therefore adds anchor-point decisions to select previous layers as inputs.

For language modeling, the controller searches over a recurrent cell instead of a CNN. The cell is built as a tree of operations combining , , and memory variables.

This part is important historically: the method is not tied to CNN layer hyperparameters. It is a general “emit a discrete architecture, train it, reward it” recipe.

Results

CIFAR-10

Model variant Depth Params Error
NAS v1, no stride/pooling 15 4.2M 5.50%
NAS v2, predicting strides 20 2.5M 6.01%
NAS v3, max pooling 39 7.1M 4.47%
NAS v3 + more filters 39 37.4M 3.65%

The best CIFAR result is 3.65% test error. The model is not tiny, but it shows that the controller can discover competitive CNNs from scratch.

Penn Treebank

Model Params Test perplexity
Variational RHN, shared embeddings 24M 66.0
NAS cell, base 8 32M 67.9
NAS cell, shared embeddings 25M 64.0
NAS cell, larger shared embedding model 54M 62.4

The discovered recurrent cell beats the reported LSTM/RHN baselines in the paper, with the best word-level model reaching 62.4 test perplexity. The paper also reports 1.214 bits per character on PTB character modeling.

RL versus random search

The random-search comparison is a useful control. The controller does not just find one lucky architecture; the top-k average improves over random search as training progresses.

Takeaway

The biggest contribution is the formulation: architecture search as policy learning over discrete design choices. It gave later NAS papers a common template to improve:

  • reduce search cost with weight sharing,
  • design a more transferable search space,
  • add hardware-aware objectives,
  • or replace the RL controller with differentiable relaxation.

The obvious limitation is cost. Training thousands of child networks is too expensive for ordinary use. Reading this paper today, I treat it less as a practical recipe and more as the baseline that later NAS work is reacting to.
