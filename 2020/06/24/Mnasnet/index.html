MnasNet: Platform-Aware Neural Architecture Search for Mobile

H.J. Chen
  2020-06-24 2020-06-24 Created  
  • Work hard 
  • >
  • PaperReading 
 
  • NAS 
  • | Mobile 

Tan M, Chen B, Pang R, Vasudevan V, Sandler M, Howard A, Le Q V. MnasNet: Platform-Aware Neural Architecture Search for Mobile. CVPR 2019.

Paper / Code

MnasNet is one of the papers that made hardware-aware NAS feel real. The important change is simple: the search reward uses measured mobile latency, not FLOPs.

That sounds obvious now, but it changes the whole NAS problem. If the target is a phone, the architecture is not good because it has fewer multiply-adds on paper. It is good if it runs fast on that phone while keeping accuracy. Kernel implementation, memory access, operator fusion, thread scheduling, and hardware-specific behavior can make two networks with similar FLOPs behave very differently.

The paper gives a concrete example: MobileNetV1 has 575M multiply-adds and 113ms latency on a Pixel 1 phone, while NASNet-A has 564M multiply-adds and 183ms latency. FLOPs alone would suggest they are similar. The phone says otherwise.

MnasNet combines three ideas:

  1. put real device latency into a multi-objective reward;
  2. search a factorized hierarchical space instead of repeatedly stacking one cell;
  3. use the resulting model family as a mobile backbone for ImageNet and COCO.

All figures and tables below are cropped from the original paper PDF.

Core Question

The paper is not only asking “can NAS find a good image classifier?” It asks a more deployment-shaped question:

Which architecture gives the best accuracy-latency trade-off on a specific mobile platform?

This is different from the older NASNet/AmoebaNet-style setup, where the search often optimizes accuracy and reports resource cost afterward. In MnasNet, latency is part of the objective from the beginning.

The search loop has three parts:

  • a controller samples an architecture from the search space;
  • a trainer estimates its accuracy;
  • a mobile-phone inference engine measures latency.

The controller receives a reward that combines accuracy and measured latency. This means the search can learn that some operators are expensive on the target platform even if their FLOP count looks acceptable.

Accuracy-Latency Frontier

The headline plot is the accuracy-latency comparison on ImageNet.

The red MnasNet points form a better frontier than MobileNetV1, MobileNetV2, NASNet-A, and AmoebaNet-A under the reported Pixel 1 latency measurement. The most useful comparison is around the 75-80ms region:

Model Top-1 Latency Read
MobileNetV2 72.0 75ms hand-designed reference
MnasNet-A1 75.2 78ms +3.2 top-1 at similar latency
MobileNetV2 1.4x 74.7 143ms slower and slightly less accurate
NASNet-A 74.0 183ms much slower
MnasNet-A3 76.7 103ms larger searched model

This is the paper’s main empirical claim: optimizing with measured latency can move the Pareto frontier, not merely produce a smaller model.

Two settings are useful:

Setting Meaning
hard-ish latency constraint: models under target are judged mainly by accuracy, models over target are sharply penalized
soft constraint: latency continuously affects reward on both sides of the target

The paper chooses for the main experiments. The heuristic is based on an empirical trade-off: doubling latency often gives roughly 5% relative accuracy gain. Setting the exponent around -0.07 makes those two points receive similar reward, so the search does not over-prefer either side too aggressively.

The hard-constraint version is easier to reason about, but it can be too brittle. A soft reward lets the controller explore a wider set of Pareto candidates in one run.

Why Search Space Matters

Earlier NAS papers often search for a cell, then stack the same cell many times. That makes the search easier, but it is a poor fit for mobile networks. Early layers operate at high resolution and dominate latency; later layers operate at lower resolution and can afford different choices. A single repeated cell cannot express that trade-off well.

MnasNet uses a factorized hierarchical search space.

The network is divided into blocks according to resolution and filter size. Inside each block, the searched layer is repeated times. Different blocks can choose different operations.

For each block, the controller searches:

Choice Options described in the paper
convolution op regular conv, depthwise conv, mobile inverted bottleneck conv
kernel size 3x3 or 5x5
SE ratio 0 or 0.25
skip op pooling, identity residual, or no skip
output filters relative to MobileNetV2, in {0.75, 1.0, 1.25}
number of layers relative to MobileNetV2, in {-1, 0, +1}

Search Algorithm

The controller is an RNN that emits architecture tokens. Each sampled architecture is trained briefly, measured on the phone, assigned a reward, and then used to update the controller with PPO.

The expensive part is that the paper does not search on CIFAR. It searches directly on ImageNet with fewer training steps:

Item Setting
proxy task ImageNet training with 5 epochs
validation split fixed 50K images from ImageNet training set
controller same RNN controller style as NASNet
update method Proximal Policy Optimization
latency device Pixel 1 phone
latency protocol batch size 1, single-thread big CPU core
search cost about 4.5 days on 64 TPUv2 devices
sampled models about 8K architectures
full ImageNet training top 15 searched models
COCO transfer one selected model

This setup is expensive, but it avoids a common trap: if the search is performed on a small proxy task and then scaled up, the latency behavior can change. MnasNet treats mobile latency as part of the target task, not as an afterthought.

ImageNet Results

Table 1 is the main ImageNet comparison.

The most important rows:

Model Top-1 Latency
MobileNetV2 72.0 75ms
MobileNetV2 1.4x 74.7 143ms
NASNet-A 74.0 183ms
AmoebaNet-A 74.5 190ms
MnasNet-A1 75.2 78ms
MnasNet-A2 75.6 84ms
MnasNet-A3 76.7 103ms

The comparison with MobileNetV2 is especially strong. MnasNet-A1 is only 3ms slower than MobileNetV2 in the reported setup, but it is 3.2 points better in top-1 accuracy. It also stays compact: 3.9M parameters and 312M multiply-adds. Compared with MobileNetV2 1.4x, MnasNet-A1 is faster and slightly more accurate.

The NAS comparison is also useful. NASNet-A and AmoebaNet-A have similar parameter counts and multiply-adds, but their Pixel latency is much worse. This is exactly the point of measuring latency instead of relying on model-size proxies.

Squeeze-and-Excitation Ablation

MnasNet includes squeeze-and-excitation in the search space. The authors also run a no-SE variant to check whether the whole gain comes from adding SE blocks.

Model SE in space Latency Top-1
MobileNetV2 no 75ms 72.0
NASNet no 183ms 74.0
MnasNet-B1 no 77ms 74.5
MnasNet-A1 yes 78ms 75.2
MnasNet-A2 yes 84ms 75.6

SE helps, but it is not the entire story. Even without SE, MnasNet-B1 reaches 74.5% at 77ms, already ahead of MobileNetV2 and NASNet under the reported mobile latency constraint.

Scaling Behavior

A common deployment workflow is to scale a known architecture with width multipliers or input resolution. MnasNet checks whether the searched architecture remains better under those scaling operations.

The left plot varies depth multiplier from 0.35 to 1.4. The right plot varies input image size from 96 to 224. In both cases, the MnasNet curve stays above MobileNetV2. The paper reports up to a 4.1 point accuracy gain across input sizes.

This matters because a mobile model is rarely deployed at one fixed point. Product constraints change: 20ms for video, 80ms for interactive camera features, higher latency for offline batch work. A good base architecture should scale gracefully.

But scaling is not always enough.

For a tight 22ms target:

Model Top-1 Latency
MobileNetV2 0.35x 60.3 21.4ms
MnasNet-A1 0.35x 64.1 22.8ms
MnasNet-search1 64.9 22.0ms
MnasNet-search2 66.0 23.2ms

All four models are tiny, between 1.66M and 2.0M parameters and between 59M and 68M multiply-adds. Scaling down MnasNet-A1 already beats scaling down MobileNetV2. A fresh search at the new latency target does even better. This is a useful deployment lesson: width scaling is convenient, but a target-specific search can find a better operator allocation for a very different latency regime.

COCO Transfer

The paper also plugs MnasNet-A1 into SSDLite for object detection.

Representative rows:

Detector mAP Latency

MobileNetV2 + SSDLite 22.1 200ms
MnasNet-A1 + SSDLite 23.0 203ms
SSD300 23.2 -

MnasNet-A1 + SSDLite uses 4.9M parameters and 0.8B multiply-adds, close to the MobileNetV2 + SSDLite compute budget. It improves mAP over the MobileNet backbones at roughly the same latency scale. It is also close to SSD300 mAP while using far fewer parameters and multiply-adds. This does not prove MnasNet is universally best for detection, but it shows the searched classification backbone transfers reasonably.

Hard Versus Soft Latency

The paper compares hard and soft latency rewards.

With , the reward behaves more like a hard target. The controller avoids over-target models and samples more tightly on the faster side. With , the controller samples a wider latency range around the target, including models below 40ms and above 110ms.

My reading: the soft setup is better if the goal is to get a frontier from one expensive search run. A hard setup is better if violating a latency target is unacceptable, but it can miss useful candidates just above the threshold.

Search Space Versus Reward

MnasNet has two contributions, so the paper separates them:

  1. use a multi-objective reward with latency;
  2. use a factorized hierarchical search space.

Reward Search space Latency Top-1
single-objective cell-based 183ms 74.0
multi-objective cell-based 100ms 72.0
multi-objective MnasNet 78ms 75.2

The reward alone makes the cell-based model faster, but it loses accuracy. The full MnasNet setup is both faster and more accurate. This is the strongest argument that the search space matters, not just the latency penalty.

MnasNet-A1 Architecture

The selected MnasNet-A1 architecture mixes operation types across stages.

The architecture uses both 3x3 and 5x5 kernels, with different MBConv expansion ratios and SE placements. This is exactly what a repeated-cell search space struggles to express. Early stages, middle stages, and late stages have different resolution, channel count, and latency sensitivity.

The paper then tests whether this layer diversity is actually useful.

Variant Top-1 Latency
MnasNet-A1 75.2 78ms
MBConv3 3x3 only 71.8 63ms
MBConv3 5x5 only 72.5 79ms
MBConv6 3x3 only 74.9 116ms
MBConv6 5x5 only 75.6 146ms

The single-op variants show the trade-off. MBConv3 is faster but loses too much accuracy. MBConv6 can recover accuracy but becomes much slower. MnasNet-A1 gets a better balance by mixing choices by stage.

Reproduction Notes

If I were reproducing this paper, I would start with the latency protocol, not the controller.

First, match the measurement target. The paper reports latency on the big CPU core of a Pixel 1 phone with batch size 1 and single-thread execution. Changing the phone, backend, thread count, warmup, precision, or operator library changes the reward.

Second, measure latency repeatedly. Since latency is inside the reward, noisy measurement becomes noisy supervision for the controller. A few milliseconds matter when the target is around 75ms.

Third, keep the proxy task honest. The paper searches on ImageNet for 5 epochs rather than CIFAR. That is expensive, but it avoids searching for architectures that only look good after scaling from a toy task.

Fourth, separate “reward works” from “space works.” Table 5 is the right sanity check: latency reward on a cell-based space is not enough.

Fifth, track the full frontier, not just one checkpoint. The soft reward is designed to recover multiple Pareto candidates from one search run.

Limitations

MnasNet is a strong deployment-oriented NAS paper, but its assumptions are clear.

  • The search is expensive: the paper reports about 4.5 days on 64 TPUv2 devices.
  • The latency target is platform-specific. A Pixel 1 CPU frontier is not automatically the frontier on a GPU, NPU, DSP, or newer phone.
  • The search space is still manually designed around mobile CNN primitives and MobileNetV2-style choices.
  • The RL controller is not the main reusable lesson; later hardware-aware NAS methods often use differentiable search, predictors, or once-for-all supernets.
  • Latency is measured for a fixed inference setup. Real products may care about memory, energy, thermal throttling, startup overhead, and mixed workloads.
  • The paper searches classification backbones and transfers one model to COCO; detection-specific search could make different choices.

The most important limitation is also the main lesson: “hardware-aware” means “aware of this hardware and this runtime.” The result is only as valid as the measurement loop.

Takeaway

MnasNet changes NAS from a model-design exercise into a deployment optimization loop. The two technical choices that matter are measured latency in the reward and a block-factorized search space that permits layer diversity without exploding into per-layer search.

The compact reading:

  • FLOPs are not reliable enough for mobile latency.
  • Latency should be measured on the target device and included in the reward.
  • A soft multi-objective reward can produce a useful Pareto frontier.
  • Repeated-cell search spaces are too rigid for mobile CNNs.
  • Stage-wise layer diversity is a real accuracy-latency advantage.

When reading later papers such as ProxylessNAS, FBNet, MobileNetV3, Once-for-All, and BigNAS, MnasNet is the reference point: it made the deployment target part of architecture search itself.
