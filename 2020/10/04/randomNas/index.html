Random Search and Reproducibility for NAS

H.J. Chen
  2020-10-04 2020-10-04 Created  
  • Work hard 
  • >
  • PaperReading 
 
  • NAS 

Li L, Talwalkar A. Random Search and Reproducibility for Neural Architecture Search. UAI 2020.

  • Paper
  • Code

This paper is useful because it attacks a boring but important question: when a NAS method looks good, how much of the gain comes from the search algorithm itself, and how much comes from the search space, the training recipe, the evaluation shortcut, or the final retraining protocol?

The answer is uncomfortable. In the DARTS-style PTB and CIFAR-10 spaces, carefully implemented random search is a hard baseline. Random search with early stopping already reaches competitive results, and random search with weight sharing can match or beat several specialized NAS methods under similar budgets.

NAS As Hyperparameter Optimization

The paper frames NAS as a special case of hyperparameter optimization. There are three moving parts:

  • the search space, such as a cell DAG or a macro architecture;
  • the search method, such as random search, RL, evolution, or gradient-based optimization;
  • the evaluation method, such as full training, partial training, or weight sharing.

This split is the main mental model of the paper. If a new algorithm is evaluated with a stronger training recipe or cheaper evaluation oracle than the baseline, it is not clear whether the algorithm did the work.

For NAS papers I think the minimum unit test should be:

Check What it catches
Same search space Avoids crediting a hand-designed space to the search method
Same evaluation budget Makes best-so-far comparisons meaningful
Same final training recipe Prevents retraining tricks from looking like search improvements
Multiple random seeds Measures variance instead of one lucky architecture
Released code and architecture Allows independent retraining and debugging

Reproducibility Audit

The authors first audit recent NAS papers. Their table checks whether a paper releases architecture-search code, model-evaluation code, random seeds, and hyperparameter-tuning details.

The important point is not that every paper is careless. NAS experiments are expensive, often multi-stage, and sensitive to implementation details. The problem is that missing seeds or missing hyperparameter logs make it impossible to separate an algorithmic contribution from a lucky or under-documented experimental setup.

The paper distinguishes two levels:

  • Exact reproducibility: rerun the same code with the same seed and get the same result.
  • Broad reproducibility: repeat the experiment with different seeds or equivalent code and get statistically similar conclusions.

Exact reproducibility is a low bar for a single-machine deterministic setup. Broad reproducibility is the bar that matters for judging whether a NAS method is robust.

Method: Random Search With Weight Sharing

The paper evaluates two random-search baselines:

  • Random search with early stopping. This uses ASHA to allocate more budget to promising architectures and stop poor ones early.
  • Random search with weight sharing. This samples architectures uniformly, trains one shared-weight supernet by activating one architecture per minibatch, then scores many sampled architectures using the shared weights.

The second baseline is the most interesting one. It removes the sophisticated controller from methods like ENAS and keeps the cheap evaluation mechanism. If that baseline works, then the search controller may not be the main contribution.

For PTB, the search space is a recurrent-cell DAG with (N=8) intermediate nodes. Each node selects a previous node as input and an operation from tanh, relu, sigmoid, or identity.

For CIFAR-10, the setup follows the DARTS normal-cell and reduction-cell space.

The search algorithm is simple, but the meta-hyperparameters are not. The result changes with the number of search epochs, batch size, network size, gradient clipping, number of sampled architectures, and final retraining length.

PTB Results

The PTB table is the cleanest evidence that random search is not a strawman.

Key rows from the table:

Method Test perplexity Total search cost Search method
ENAS, published 56.3 N/A RL
DARTS second order, published 55.7 2 GPU days gradient-based
DARTS second order, reproduced 55.9 2 GPU days gradient-based
ASHA baseline 56.4 2 GPU days random
Random search WS 55.5 1.25 GPU days random

Random search with weight sharing gets 55.5 test perplexity, better than the reproduced DARTS run and the ASHA baseline in this setup. This does not prove that random search is universally better. It proves that the NAS comparison is weak if it does not include this baseline.

The paper then digs into stage (2), where candidate architectures are retrained with a proxyless network for 300 epochs before choosing what to fully evaluate.

The table shows that the best Random (4) run has validation perplexity 63.8 after stage (2), close to the best published DARTS intermediate result. A second Random (4) run is worse, which is already a warning that a single search run is not enough.

The ranking table makes that warning more concrete.

At 300 epochs, several methods are close. By 3600 epochs, Random (4) Run 1 becomes best, while Random (4) Run 2 ends fourth. Intermediate validation rank is a noisy selection signal.

CIFAR-10 Results

The CIFAR-10 comparison is less one-sided, but it makes the same methodological point.

Key rows:

Method Best test error Average test error Total search cost Search method
ENAS, published 2.89 N/A N/A RL
DARTS second order, published N/A 2.76 +/- 0.09 5 GPU days gradient-based
DARTS second order, reproduced 2.62 2.78 +/- 0.12 10 GPU days gradient-based
ASHA baseline 2.85 3.03 +/- 0.13 9 GPU days random
Random search WS 2.71 2.85 +/- 0.08 9.7 GPU days random

Random search with weight sharing is competitive with the published DARTS/ENAS-style results, although the reproduced DARTS run still has the best average in this table. The important part is that the random baseline is in the same performance regime.

The authors also tune the random-search-with-weight-sharing setup. This table is a good reminder that even a “random” baseline has important engineering choices.

The large proxyless setting, lower gradient clipping, and more evaluated architectures improve the random-search baseline. Without reporting those tuning choices, it would be easy to compare against a weak version of the baseline.

Broad Reproducibility

The paper repeats CIFAR-10 random search with weight sharing across six independent runs.

The six-run average is 2.92 test error. Runs 1 to 3 are around 2.85 to 2.88, while Runs 4 to 6 degrade to 2.95, 2.98, and 3.00. This is still competitive, but the spread is large enough that reporting only the best discovered architecture would be misleading.

This is the most useful practical lesson for me: NAS results need distributions, not just a best architecture and a GPU-day number.

Cost Accounting

The computational-cost section is short but important. The paper compares cost per architecture under three evaluation styles:

Evaluation style PTB cost per architecture CIFAR-10 cost per architecture
Full training 0.5 GPU days 4 GPU hours
ASHA partial training 9 minutes 19 minutes
Random search WS, amortized 0.2 minutes 0.8 minutes

Weight sharing makes each architecture extremely cheap to score, but that number can hide the real total cost. If many supernet trials, seed sweeps, and final retraining runs are needed to get a stable result, the headline search cost is not the whole story.

Takeaways

Random search is not the conclusion of NAS. It is the control experiment.

My takeaways:

  • A NAS method should beat random search in the same search space and under the same final training recipe.
  • Early stopping and weight sharing are evaluation methods, not search algorithms by themselves.
  • Intermediate validation rankings can change after longer retraining, so short proxy evaluations need skepticism.
  • Reproducibility requires seeds, code, architecture definitions, and hyperparameter-tuning logs.
  • Best-run reporting is fragile. Average, variance, and rerun cost are part of the result.

The paper is a useful calibration point: before trusting a more complex NAS controller, first make the random baseline strong enough that beating it actually means something.
