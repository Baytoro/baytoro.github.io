NAS-Bench-101: Towards Reproducible Neural Architecture Search

H.J. Chen
  2020-11-21 2020-11-21 Created  
  • Paper Reading 
 
  • NAS 
  • | Benchmark 

Ying C, Klein A, Christiansen E, Real E, Murphy K, Hutter F. NAS-Bench-101: Towards Reproducible Neural Architecture Search. ICML 2019.

  • Paper: https://arxiv.org/pdf/1902.09635.pdf
  • Code: https://github.com/google-research/nasbench

NAS-Bench-101 is a benchmark paper rather than a new NAS optimizer. Its main contribution is to turn a large but still controlled cell search space into a queryable table. The table maps each valid architecture to fixed training results, so an optimizer can be evaluated without retraining thousands of CIFAR-10 models.

That sounds simple, but it fixes a real problem in early NAS papers: algorithm comparisons were often dominated by GPU budget, implementation choices, and hidden training recipes. NAS-Bench-101 changes the experiment into a cleaner question: under the same query budget, which optimizer finds better architectures, and how stable is that behavior over many independent runs?

Search Space

NAS-Bench-101 uses the familiar cell-based CNN setup. A macro skeleton repeats a learned cell several times, and the cell itself is a directed acyclic graph. The original encoded space contains about 510 million possible graphs before validity checks and canonicalization. After removing invalid and isomorphic cases, the benchmark contains 423k unique valid architectures.

The cell has at most 7 vertices and at most 9 edges. The input and output nodes are fixed, while intermediate nodes select one of three operations:

  • 3x3 convolution;
  • 1x1 convolution;
  • 3x3 max pooling.

This is intentionally narrower than a production architecture search space. It does not include inverted residual blocks, device latency choices, width multipliers, activation choices, or Transformer-style dimensions. The point is controlled diagnosis, not direct deployment search.

Query Protocol

For every architecture, NAS-Bench-101 stores multiple training budgets: 4, 12, 36, and 108 epochs. Each architecture is trained and evaluated three times, so the API can return either repeated observations or a particular trial index. This matters because a realistic search algorithm should see noisy observations, not an oracle with the exact mean performance.

The paper is also explicit about validation and test usage. During search, the optimizer should use training and validation metrics. Test accuracy should only be queried offline after the search has selected an architecture. If an algorithm uses test accuracy during search, it is no longer measuring generalization; it is optimizing the benchmark’s hidden answer key.

The stored metrics include:

  • training time;
  • train accuracy;
  • validation accuracy;
  • test accuracy.

The cleanest evaluation is a best-so-far curve under a fixed budget. Reporting only the final architecture hides whether the method was sample efficient or just used enough queries to eventually stumble into a good cell.

Dataset Shape

The ECDF plots show two useful properties. First, most valid architectures are not terrible after 108 epochs; a large fraction already exceeds 90% validation and test accuracy. Second, stochastic training noise shrinks with longer training budgets, which is why early-epoch signals are useful but not equivalent to final ranking.

The best architecture in the table reaches 94.32% mean test accuracy. The paper compares this with two hand-designed cells: a ResNet-like cell at 93.12% and an Inception-like cell at 92.95%. The final validation and test accuracies are almost perfectly correlated at 108 epochs, with correlation around 0.999. That makes NAS-Bench-101 a good place to study optimizer behavior without getting too distracted by validation/test mismatch.

Training time is not just a function of parameter count. The plot below shows that more parameters usually cost more time, but topology still matters: two cells with similar parameter counts can have different runtime because of branching and operation placement.

That is one reason a benchmark table is useful. If the only feedback is accuracy, an optimizer may overfit to expensive cells. If the table also exposes time, one can evaluate regret over estimated wall-clock time instead of only over number of queries.

Architecture Diagnostics

The operation replacement experiment is one of the most useful parts of the paper. The authors replace one operation type with another across architectures and measure the average effect on validation accuracy and training time.

Replacing 3x3 convolution with 1x1 convolution drops average validation accuracy by about 1.16%, while replacing it with max pooling drops it by about 1.99%. The training-time changes go in the opposite direction: 1x1 convolution and max pooling are cheaper. A simple search algorithm can therefore get an apparent speed benefit while moving into a weaker region of the space.

The depth/width analysis is also a useful sanity check. In this benchmark, average validation accuracy peaks around depth 3, while increasing width helps up to the maximum width considered in the space.

This is a reminder that “deeper is better” is not a universal claim inside a constrained DAG cell. The combine semantics and edge constraints shape the distribution of architectures. A benchmark should be interpreted together with its encoding rules.

Locality

NAS algorithms often assume locality: a small architecture edit should usually cause a small performance change. NAS-Bench-101 lets the paper test that assumption directly.

The random-walk autocorrelation and fitness-distance correlation suggest locality up to a rough edit distance of about 6. The paper also notes that high-performing cells are rare in the encoded space: the chance of sampling one of the top graphs is roughly 1 in 50,000, while about 35.4% of the search space lies within distance 6 of the closest top graph. This explains why local search can be meaningful here, but also why pure random search needs many queries.

Search Algorithm Benchmarking

The benchmark section compares random search, regularized evolution, reinforcement learning, SMAC, TPE, BOHB, and Hyperband-like methods. Each algorithm is run 500 times, and performance is plotted as test regret over estimated wall-clock time.

This presentation is more informative than a single best score. The left plot captures convergence speed. The right ECDF shows how often an optimizer ends near the optimum. A method with a strong median but a bad tail may be unreliable, while a method with slower median progress but high robustness may be preferable for expensive real searches.

The comparison also highlights a subtle issue: algorithms that exploit lower training budgets, such as Hyperband and BOHB, are using a different kind of signal from optimizers that query only 108-epoch results. That is legitimate, but it must be stated. Otherwise “query count” is not a fair budget unit.

Mini-Benchmark and Early Epochs

The paper bootstraps a smaller NASBench-Mini with at most 6 vertices, giving around 64.5k cells instead of the full 423k. The relative ranking of random search, non-regularized evolution, and regularized evolution remains consistent across the smaller and larger tables.

This is useful because it suggests that a reduced space can still preserve some optimizer-ordering signal. It does not mean every algorithm conclusion transfers, but it gives evidence that the benchmark is not completely brittle to space size.

Early-epoch correlation is more complicated. The appendix reports Spearman rank correlations between early and final accuracies under different percentile slices.

The full-space 36-to-108-epoch correlation is high, around 0.902. But within the top 10% of architectures it drops sharply, to about 0.495. That is exactly the regime where strong NAS algorithms operate. Early training is useful for pruning weak models, but it is much less reliable for sorting the best models.

How I Would Use It

For a new black-box NAS optimizer, I would use NAS-Bench-101 as a first diagnostic step:

  1. Fix a query budget and wall-clock budget model.
  2. Run at least dozens of independent seeds, not just one or three.
  3. Use validation accuracy for search and reserve test accuracy for post-search reporting.
  4. Report best-so-far curves, not only the final best cell.
  5. Compare against random search and regularized evolution.
  6. State whether the optimizer can query 4/12/36-epoch results or only 108-epoch results.
  7. Check whether improvements survive on NAS-Bench-201 or a larger surrogate benchmark.

The important part is not to claim too much. A win on NAS-Bench-101 says that the optimizer navigates a small CIFAR-10 cell space well. It does not prove that the method will discover strong ImageNet, mobile, language, or hardware-aware architectures.

Limitations

NAS-Bench-101 is deliberately constrained:

  • only CIFAR-10 is used;
  • the operation set has only three choices;
  • the macro skeleton is fixed;
  • latency and memory are not first-class objectives;
  • the benchmark is small enough that repeated querying can turn into table exploitation;
  • the top region is narrow enough that early-epoch ranking becomes noisy.

These limitations do not make the benchmark weak. They define what the benchmark is for: controlled, reproducible optimizer analysis.

Takeaway

NAS-Bench-101 made NAS evaluation much more scientific. It replaced many expensive and hard-to-reproduce claims with a shared table, a clear query protocol, and enough repeated runs to study robustness. I would treat it as a unit test for NAS optimizers. Passing that unit test is not enough for real architecture design, but failing it is a strong warning sign.
