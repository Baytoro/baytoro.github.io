ChamNet: Platform-Aware Model Adaptation

H.J. Chen
  2020-02-20 2020-02-20 Created  
  • Work hard

  • NAS 
  • | Mobile 

Paper / Code

ChamNet is a platform-aware model adaptation paper. It is not mainly about inventing a new operator or cell. It starts from practical building blocks, then reallocates channels, depths, expansion ratios, and input resolution so the resulting model matches a concrete deployment target.

That makes it different from reading a pure NAS paper. The core claim is deployment-oriented: FLOPs are not enough. A model that is good on a mobile CPU may not be good on a DSP, GPU, or server CPU, because each backend has different kernel behavior and memory bottlenecks.

Chameleon Framework

Chameleon separates the main search loop from one-time predictive models for accuracy, latency, and energy.

The framework has two parts:

  • A main search loop using efficient evolutionary search (EES).
  • Predictive models that estimate accuracy, latency, and energy without repeatedly training and measuring every candidate.

The optimization target is straightforward:

ChamNet folds the resource constraint into a fitness score. Candidates that violate the latency or energy budget get penalized, while candidates inside the budget are ranked mostly by predicted accuracy.

This predictor-first design is the paper’s scalability argument. If the accuracy predictor and platform resource predictors are already built, searching for a new use scenario becomes much cheaper than running RL or full hardware-in-the-loop search from scratch.

Accuracy Predictor

The paper compares several accuracy predictors and reports the best leave-one-out MSE from the Gaussian Process regressor.

Only a small number of sampled architectures are fully trained, so the accuracy predictor must work in a low-data regime. ChamNet uses a Gaussian Process regressor because it gives both a prediction and an uncertainty estimate.

The selected samples concentrate near the useful accuracy/FLOPs frontier, while still keeping exploration points.

The sampling rule mixes exploitation and exploration:

  • Exploitation: sample models that look accurate relative to FLOPs.
  • Exploration: sample models where the predictor is uncertain.

This is a practical detail worth remembering. If the predictor only exploits its current belief, it can overfit early mistakes. If it only samples uncertain regions, it wastes training budget. ChamNet deliberately does both.

Platform Metrics

A 1x1 convolution can have very different latency surfaces on different platforms, even when FLOPs look similar.

ChamNet builds an operator latency lookup table from real device measurements. The paper’s latency surface figure is the reason: channel counts create visible discontinuities, and CPU/DSP behavior differs. This is the kind of effect that a FLOPs-only objective misses.

Energy is handled with a predictor too, but it is measured directly from device runs. This makes the framework more expensive to set up than a purely analytical model, but much more relevant for deployment decisions.

Mobile Results

ChamNet-Mobile on Snapdragon 835 CPU.

ChamNet-Mobile on Hexagon v62 DSP.

The mobile experiments adapt MobileNetV2-style inverted residual blocks. The search space includes input resolution, channel count, expansion factor, number of repeated blocks, and stride.

The headline points are:

Platform Constraint ChamNet top-1
Snapdragon 835 CPU 20 ms 73.8
Hexagon v62 DSP 20 ms 75.3
Snapdragon 835 CPU 4 ms 64.2
Hexagon v62 DSP 4 ms 63.6

The tight-latency points are important. At 4 ms, the method still finds a useful architecture instead of only working at comfortable budgets.

Server Results

ChamNet-Res on Intel CPU.

ChamNet-Res on Nvidia GPU.

For server settings, ChamNet adapts ResNet-style building blocks. The paper evaluates Intel Xeon Broadwell CPU and Nvidia GTX 1060 GPU. The curves differ across CPU and GPU, which reinforces the same point as the mobile results: the best architecture family member depends on the platform, not only on the target FLOPs.

Representative reported points:

Platform Constraint ChamNet-Res top-1
Intel CPU 400 ms 78.5
Intel CPU 200 ms 77.2
Nvidia GPU 15 ms 78.6
Nvidia GPU 10 ms 77.7

Energy Results

Energy-constrained ChamNet-Mobile on Snapdragon 835 CPU.

The energy experiment is a good reminder that latency and energy are related but not identical. The paper reports that MobileNetV2 0.75x at 96x96 gets 58.8 top-1 at 19 mJ per run, while an adapted ChamNet model gets 60.0 top-1 at 14 mJ per run. That is a 26% energy reduction while gaining 1.2 percentage points of accuracy.

Comparison And Search Cost

Comparison with manual scaling, RL-based NAS, pruning, and related platform-aware methods.

The table is useful because it mixes accuracy with scaling complexity. RL-based methods such as MnasNet are listed as O(m * n * k), where the factors correspond to models, platforms, and use scenarios. ChamNet separates model accuracy predictors from platform resource predictors and reports O(m + n).

That does not mean ChamNet is free. It still needs a one-time cost for trained architecture samples and platform measurements. The point is that after paying this cost, many platform/budget searches become cheap.

Computation Redistribution

ChamNet shifts compute across stages instead of using a uniform width multiplier.

This is the most concrete design lesson in the paper. The adapted model is not just MobileNetV2 with one global width multiplier. ChamNet moves FLOPs away from some early high-resolution stages and spends more computation later, where it improves the accuracy-latency tradeoff.

The paper reports 71.6 top-1 at 15.0 ms for ChamNet-C, compared with 69.8 top-1 at 16.6 ms for MobileNetV2 0.75x. The method is doing stage-wise allocation, not only shrinking the network.

Reading Notes

ChamNet is strongest as a deployment workflow:

  • Keep proven efficient blocks.
  • Measure the real target platform.
  • Build reusable predictors.
  • Search for stage-wise allocation under the actual budget.

The limitation is also clear. ChamNet depends on the base architecture family and predictor quality. It will not discover a fundamentally new operator class, and it still needs training and profiling samples. But for organizations deploying variants across many devices and budgets, this is a sensible tradeoff: pay the setup cost once, then adapt quickly.
