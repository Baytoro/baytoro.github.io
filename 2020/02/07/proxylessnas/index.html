ProxylessNAS: Direct Neural Architecture Search on Target Task and Hardware

H.J. Chen
  2020-02-07 2020-02-07 Created  
  • Paper Reading 
 
  • NAS 

Paper / Code

ProxylessNAS is one of the NAS papers that is worth reading from an engineering angle. The main point is not just “NAS can find a good MobileNet-like model”. The more interesting part is that the search is done directly on the target task and the target hardware, while keeping GPU memory close to training a single compact network.

Motivation

Earlier NAS methods usually searched on a proxy task: fewer cells, fewer channels, smaller input resolution, or a smaller dataset. That made search affordable, but it also introduced a mismatch. A model that looks good on CIFAR or a tiny ImageNet setting may not be the best model after it is scaled and deployed on a phone/GPU/CPU.

ProxylessNAS removes this extra transfer step:

The figure is simple but important. The left side learns an architecture on a proxy task, then transfers it to the real task. The right side learns the architecture with the target task and hardware in the loop. This matters especially for latency, because FLOPs and measured latency are not interchangeable once the hardware backend changes.

Contribution

The paper contributes three things that are easy to mix together:

  1. Search directly on large target tasks, including ImageNet, without shrinking the problem into a proxy task.
  2. Reduce the memory cost of differentiable NAS through path binarization, so only one candidate operation is active in each mixed operation during one forward/backward pass.
  3. Add hardware latency into the search objective, either through a differentiable latency regularizer or through a REINFORCE-style update for non-differentiable rewards.

The result is also practical: ProxylessNAS reports 74.6% ImageNet top-1 accuracy at 78 ms mobile latency, using about 200 GPU hours for search. For comparison, the paper reports MnasNet at 74.0% top-1, 76 ms latency, and 40,000 GPU hours.

Methodology

Path-level pruning

The search space is represented as an over-parameterized network. Each learnable block contains several candidate operations, such as MBConv variants with different kernel sizes and expansion ratios. NAS then becomes a pruning problem: keep one path and remove the rest.

A standard differentiable NAS implementation would keep all candidate paths in memory and compute a weighted sum. That is the expensive part. If every layer has multiple MBConv choices, keeping all activations quickly becomes much heavier than training the final compact model.

Binarized paths

ProxylessNAS samples a binary gate , where only one candidate path is active:

The training alternates between two updates:

  • Update weight parameters while freezing architecture parameters. Only the sampled active path is kept in memory.
  • Update architecture parameters while freezing weight parameters. The gradient is estimated through the binary gate.

This is the key implementation trick. The supernet still contains all candidate operations as parameters, but a single minibatch only activates one path per mixed operation. So the peak activation memory is close to a normal compact network instead of a huge all-paths supernet.

Results

CIFAR-10

On CIFAR-10, ProxylessNAS reaches 2.08% test error with 5.7M parameters. The paper compares this with AmoebaNet-B at 2.13% test error and 34.9M parameters. I would not over-read this result because the paper’s bigger claim is ImageNet direct search, but it shows that the method is not only a hardware trick.

ImageNet mobile setting

Model Top-1 Top-5 Mobile latency
MobileNetV2 72.0 91.0 75 ms
MnasNet 74.0 91.8 76 ms
Proxyless-G 71.8 90.8 83 ms
Proxyless-G+LL 74.2 91.9 79 ms
Proxyless-R 74.6 92.2 78 ms

MnasNet is hardware-aware but still proxy-based, with 40k GPU hours reported for search. The ProxylessNAS rows search directly on ImageNet with about 200 GPU hours; +LL adds the latency loss, and R uses the reinforcement-learning style architecture update.

The left plot is the result I care about most. At around the same top-1 accuracy, the searched model is much faster than a width-scaled MobileNetV2. The right plot is also important: the latency predictor is close enough to real mobile latency to be useful during search.

ImageNet GPU setting

Model Top-1 Top-5 GPU latency
MobileNetV2 72.0 91.0 6.1 ms
MnasNet 74.0 91.8 6.1 ms
ProxylessNAS for GPU 75.1 92.5 5.1 ms

This is the part that supports the paper title. The best architecture is not a universal object. If the objective is GPU latency, the search picks a different network than it does for mobile latency.

Hardware specialization

Optimized for Top-1 Target latency
GPU 75.1 5.1 ms
CPU 75.3 138.7 ms
Mobile 74.6 78 ms

The hardware-specific architectures are visibly different. The GPU model is shallower and wider, which exposes more parallel work. The CPU model becomes deeper and narrower. The mobile model tends to use larger MBConv blocks around downsampling stages. This is exactly why optimizing only FLOPs can be misleading.

Takeaway

My main takeaway is that ProxylessNAS is less about finding one pretty architecture and more about making NAS deployable:

  • The search objective should include the real deployment target.
  • Memory usage has to be controlled at the supernet level, not only in the final discovered network.
  • Latency needs to be measured or modeled on the actual hardware backend.

The limitation is also clear. The method still depends on a predefined MobileNetV2-style search space, so it is not discovering arbitrary neural network structures. But within that constrained space, the paper gives a clean recipe: train the supernet directly on the real task, activate one path at a time, and let measured hardware latency shape the final architecture.
