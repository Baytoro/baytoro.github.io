Single-Path NAS: Designing Hardware-Efficient ConvNets in Less Than 4 Hours

Paper: Single-Path NAS: Designing Hardware-Efficient ConvNets in less than 4 Hours

Code: dstamoulis/single-path-nas

Motivation

The paper targets a very specific bottleneck in hardware-aware NAS: one-shot NAS methods usually build a multi-path supernet. For each searchable layer, every candidate operator is inserted as a separate trainable path, and the search learns which path to keep.

That formulation is easy to understand, but expensive to maintain. If a MobileNet-like model has 22 searchable layers and each layer has 5 candidate choices, the discrete space is about architectures. A multi-path supernet avoids training every architecture from scratch, but it still keeps separate path weights in memory and updates them during search.

Single-Path NAS changes the question from:

Which operator/path should this layer choose?

to:

Which subset of weights inside one over-parameterized kernel should this layer use?

The left side is the common multi-path view: separate operators and separate path weights. The right side is the paper’s core idea: put the candidates into one larger “superkernel”, then select a subset of its weights.

Contribution

The paper’s contribution is not just “NAS becomes faster”. The useful part is the encoding:

  1. A single-path search space for MobileNetV2-style MBConv blocks.
  2. Kernel size, expansion ratio, and skip-op decisions are all encoded inside one searchable superkernel.
  3. The latency objective remains differentiable by using a profiled runtime model for Pixel 1.
  4. The final result reaches 74.96% ImageNet top-1 accuracy at 79.48ms on Pixel 1.
  5. The search uses 8 epochs, reported as 3.75 hours on TPUv2, or 30 TPU-hours.

The last point is the reason this paper is interesting. The method is not searching an arbitrary operator graph; it is carefully redesigning the search space so the search itself becomes cheap.

Methodology

Search Space

The macro-architecture follows a MobileNetV2/MnasNet-like layout. The model has several blocks, and each block contains MBConv layers. For each searchable MBConv layer, NAS chooses:

The largest candidate can represent the smaller candidates. A larger kernel contains the smaller kernel as its inner core; a larger expansion ratio contains the lower expansion ratio as a subset of channels. That observation is what makes the one-path formulation possible.

Results

The headline result is easy to summarize:

Method Top-1 Acc (%) Top-5 Acc (%) Pixel 1 Runtime (ms) Search Cost
MobileNetV2 1.0x 72.00 91.00 75.00 -
MnasNet 1.0x 74.00 91.80 76.00 40,000 epochs
ProxylessNAS-R 74.60 92.20 78.00 200 epochs
FBNet-B 74.1 - - 90 epochs
Single-Path NAS 74.96 92.21 79.48 8 epochs / 3.75 hours

The accuracy improvement over ProxylessNAS-R is modest, around +0.31 top-1, but the search-cost reduction is the real result. The paper reports 8 search epochs, compared with much larger search budgets in previous mobile NAS work.

The search curve is also useful: cross entropy decreases, while the runtime term is eventually pulled down toward the 80ms target. The early noisy runtime region is caused by dropout over kernel subsets.

The final architecture is still a MobileNetV2-style network. Most layers are MBConv variants with different kernel size and expansion ratio. This matters because the method is not discovering arbitrary operators; it is searching a compact and hardware-aware MBConv design space.

Takeaway

I think the main value of this paper is the reframing of NAS from path selection to weight-subset selection. Multi-path supernets pay memory and optimization cost for maintaining many candidate branches. Single-Path NAS avoids that by forcing candidate operators to share one superkernel.

The limitation is also clear: this trick works because the candidate operations are nested. A 3x3 kernel is naturally contained in a 5x5 kernel, and a lower expansion ratio is naturally contained in a higher one. If the search space contains very different operators, such as attention, pooling, deformable conv, or arbitrary graph motifs, this encoding is not directly applicable.

So this is not a universal NAS recipe. It is a clean engineering solution for a constrained MobileNetV2-like space, and that constraint is exactly why it is fast.
