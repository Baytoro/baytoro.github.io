FBNet: Hardware-Aware Efficient ConvNet Design via Differentiable Neural Architecture Search

H.J. Chen
  2020-02-03 2020-02-03 Created  
  • Paper Reading 
 
  • NAS 
  • | Mobile 

Wu B, Dai X, Zhang P, et al. FBNet: Hardware-Aware Efficient ConvNet Design via Differentiable Neural Architecture Search. CVPR 2019.

Paper / Code

FBNet is a practical hardware-aware NAS paper. It does not search arbitrary cell graphs. It searches a constrained MobileNet-style layer space, measures operator latency on the target phone, and makes that latency part of a differentiable search objective.

The engineering lesson is simple: if the final user cares about phone latency, the search loop should see phone latency. FLOPs are useful for sanity checks, but they are not the deployment objective.

All figures and tables below are cropped from the original CVPR PDF.

Motivation

FBNet is motivated by three deployment problems.

  1. Efficient ConvNet design has a large combinatorial space.
  2. The best architecture depends on input resolution, width, runtime, and target device.
  3. FLOPs are a weak proxy for measured latency.

The third point is the important one. Two operators can have similar FLOPs but very different runtime because of memory access, kernel implementation, vectorization, cache behavior, and backend support. This is why hardware-aware NAS papers such as MnasNet, ProxylessNAS, and FBNet measure latency directly instead of only reporting multiply-adds.

Figure 1 summarizes the FBNet loop:

  1. Define a layer-wise search space.
  2. Benchmark candidate operators on the target device.
  3. Train a stochastic supernet.
  4. Sample compact architectures from the learned distribution.
  5. Train selected architectures from scratch.

FBNet calls the final models Facebook-Berkeley-Nets. The headline result is FBNet-B: 74.1% ImageNet top-1, 295M FLOPs, and 23.1 ms latency on a Samsung S8 under the reported Caffe2 int8 setup. The paper estimates 216 GPU-hours for search, much smaller than the RL search cost it attributes to MnasNet.

Search Space

FBNet keeps the macro skeleton fixed and searches operator choices inside 22 searchable layers. The first stem and the last projection/classifier layers are fixed.

Each searchable layer chooses from 9 candidates:

Candidate Kernel Expansion Group
k3_e1 3 1 1
k3_e1_g2 3 1 2
k3_e3 3 3 1
k3_e6 3 6 1
k5_e1 5 1 1
k5_e1_g2 5 1 2
k5_e3 5 3 1
k5_e6 5 6 1
skip - - -

So the rough search space size is , around architectures. That is large enough to require an efficient search method, but still structured enough that an additive latency lookup table is plausible.

The candidate block is an inverted-bottleneck style block.

The block has:

  • a first 1x1 pointwise convolution, optionally grouped;
  • a 3x3 or 5x5 depthwise convolution;
  • a final 1x1 pointwise convolution;
  • a residual connection when shape and stride permit it.

This search space is conservative by modern NAS standards, but that is also why the deployment story is credible. FBNet is not searching exotic operators that may be unsupported by mobile runtimes.

Differentiable Search

FBNet uses a stochastic supernet. At each searchable layer, the architecture parameter vector controls a probability distribution over candidate blocks. During search, the layer output is a weighted or sampled mixture of candidates. Gumbel Softmax makes the sampling path differentiable enough for gradient-based optimization.

The useful mental model:

  • weights decide how well candidate operators perform;
  • architecture parameters decide which operator each layer prefers;
  • Gumbel temperature controls how close the relaxed choice is to a one-hot discrete choice;
  • after search, FBNet samples/selects a discrete architecture and trains it from scratch.

This is still a supernet proxy. The searched architecture is not deployed directly from the supernet weights. The paper uses the supernet to learn a distribution over good architectures, then does final training separately.

Latency-Aware Objective

FBNet adds target-device latency to the training objective. Measuring every full architecture would be too expensive, so the paper benchmarks every candidate operator in context and stores the results in a lookup table.

The architecture latency is estimated additively:

Latency(architecture) = sum of selected block latencies.

In the stochastic supernet, the expected latency is the probability-weighted sum over candidate block latencies. Since each lookup-table entry is a constant, this latency estimate is differentiable with respect to the architecture probabilities.

That is the paper’s main trick. FBNet makes measured hardware latency usable inside gradient-based NAS.

There are two assumptions to remember:

  • Operator latency is approximately additive across the network.
  • The measured latency table matches the final runtime, device, input shape, and quantization/backend setup.

Those assumptions are reasonable for the paper’s mobile CPU/Caffe2 int8 target, but they are not universal.

Search Protocol

For the main ImageNet experiment, FBNet targets Samsung Galaxy S8 with Qualcomm Snapdragon 835 and Caffe2 int8 inference. The protocol is:

  1. Measure candidate operator latency on the target phone.
  2. Train a stochastic supernet for 90 epochs.
  3. Use 100 randomly selected ImageNet classes during search.
  4. Train operator weights on 80% of the selected training data with SGD.
  5. Train architecture parameters on the remaining 20% with Adam.
  6. Sample architectures from the learned distribution.
  7. Train final models from scratch on ImageNet.

This is a pragmatic compromise. Searching on all ImageNet classes would be more direct, but using 100 classes makes the search cost manageable.

ImageNet Results

Representative rows from Table 3:

Model Search Search cost FLOPs S8 latency Top-1
1.0-MobileNetV2 manual - 300M 21.7 ms 72.0
MnasNet RL 91K GPUh estimated 317M 23.7 ms 74.0
1.3-MobileNetV2 manual - 509M 33.8 ms 74.4
FBNet-A gradient 216 GPUh 249M 19.8 ms 73.0
FBNet-B gradient 216 GPUh 295M 23.1 ms 74.1
FBNet-C gradient 216 GPUh 375M 28.1 ms 74.9

FBNet-B is the central comparison. It is close to MnasNet latency but slightly better in the reported accuracy/latency point, and the paper estimates a much lower search cost. Compared with 1.3-MobileNetV2, FBNet-B has similar accuracy with far fewer FLOPs and lower latency.

I would read the search-cost comparison carefully. The 91K GPUh MnasNet number is an estimate by the FBNet authors, not a perfectly controlled benchmark under identical infrastructure. The more robust takeaway is still strong: differentiable NAS made the search cheap enough that device-specific redesign became plausible.

Architecture Patterns

The architecture visualization is useful because FBNet is not just selecting one repeated block. Different layers choose different kernel sizes, expansion ratios, grouping, and skip behavior.

Two patterns stand out:

  • Larger models use more high-expansion k5 blocks in later stages.
  • Tiny low-resolution variants skip more layers, which matches the lower need for depth and receptive-field growth.

This is also where FBNet differs from a simple width multiplier. A width multiplier uniformly scales a hand-designed backbone. FBNet changes operator choices layer by layer.

Scaling And Devices

FBNet searches again for different input resolutions and channel scaling factors instead of only scaling one discovered model.

Examples from Table 4:

Setting MobileNetV2 baseline FBNet result

192, 0.50 63.9%, 8.4 ms 65.9%, 9.9 ms
128, 0.50 57.7%, 4.8 ms 60.0%, 5.1 ms
96, 0.35 45.5%, 3.8 ms 50.2%, 2.9 ms

The 96, 0.35 setting is the cleanest example: FBNet is both more accurate and faster than the scaled MobileNetV2 baseline.

The paper also searches separate models for iPhone X and Samsung S8:

Model iPhone X latency Samsung S8 latency Top-1
FBNet-iPhoneX 19.84 ms target 23.33 ms 73.20
FBNet-S8 27.53 ms 22.12 ms target 73.27

The operator runtime plot explains the non-transferability. Some operator types are faster on iPhone X; others are faster on Samsung S8. A single FLOP count cannot see this difference.

Reproduction Notes

If I were reproducing FBNet, I would check five things before trusting the result.

First, benchmark latency with the final runtime. A lookup table measured under a different backend, thread count, quantization mode, or batch size can mislead the search.

Second, validate the additive latency model. It is usually good enough for a constrained mobile network, but residual adds, memory layout changes, and cache behavior can introduce non-additive effects.

Third, separate supernet ranking from final training. The final architecture must be trained from scratch; otherwise the result measures supernet weight sharing more than the architecture.

Fourth, record the search split. FBNet trains operator weights and architecture parameters on different slices of the 100-class ImageNet subset. Changing this split changes the proxy.

Fifth, report device and runtime details next to accuracy. “23 ms mobile latency” is not meaningful without the phone, backend, quantization type, and measurement protocol.

Limitations

FBNet is deployment-oriented, but its scope is still limited.

  • The search space is manually shaped around MobileNet/ShiftNet-like blocks.
  • The latency model assumes block latencies add cleanly.
  • Search uses a 100-class ImageNet proxy, then final models are trained separately.
  • The reported latency is tied to Caffe2 int8 inference on 2018-era devices.
  • The method optimizes one target runtime at a time; a different device may need a different search.

These are not flaws in the paper so much as the engineering contract. FBNet is useful because it defines that contract clearly.

Takeaway

FBNet is a clean example of hardware-aware differentiable NAS. The core idea is to benchmark candidate blocks on the real target device, put those latency values into a differentiable objective, and let the supernet learn layer-wise operator preferences.

I read FBNet less as a general architecture discovery paper and more as a deployment recipe: constrain the search space to runnable operators, measure the metric the user feels, and make search cheap enough that target-specific redesign is possible.
