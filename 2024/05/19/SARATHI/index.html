SARATHI: Chunked Prefill Scheduling

H.J. Chen
  2024-05-19 2024-05-19 Created  
  • Paper Reading 
 
  • LLM 
  • | Serving 

Paper: SARATHI: Efficient LLM Inference by Piggybacking Decodes with Chunked Prefills

SARATHI focuses on a scheduling problem: prefill and decode have very different shapes. A long prefill is compute-heavy and parallel. Decode is iterative, one token per sequence, and latency-sensitive.

Motivation

Serving metrics are usually split into:

  • TTFT: time to first token, dominated by prefill;
  • TPOT: time per output token, dominated by decode;
  • throughput: completed tokens or requests per second.

If a scheduler runs a long prefill as one monolithic batch, decode requests can wait too long. If it prioritizes decode too aggressively, GPU utilization can fall.

The figure shows SARATHI’s basic idea: split long prefills into chunks and mix them with decode work.

Methodology

SARATHI uses chunked prefill. Instead of processing an entire prompt in one step, it divides the prompt into smaller chunks. Decode tokens from active requests can piggyback with these chunks.

The scheduler tries to create decode-maximal batches:

  1. include decode work to protect TPOT;
  2. fill remaining compute capacity with prefill chunks;
  3. avoid letting one long prompt monopolize the GPU.

This differs from PagedAttention. vLLM solves KV memory allocation; SARATHI solves the phase-mixing problem between prefill and decode.

Results

The paper reports better latency-throughput behavior on workloads with long or variable prompts. Chunking reduces stalls caused by monolithic prefills and improves GPU utilization compared with naive phase scheduling.

Takeaway

SARATHI is a scheduler paper about the shape mismatch in LLM inference. It is useful to read before DistServe: SARATHI mixes prefill and decode more carefully on the same workers, while DistServe separates the phases onto different workers.

Prefill/Decode Interference

A useful mental model is that prefill wants large matrix-multiply batches, while decode wants predictable per-token service. If decode waits behind long prefill, TPOT becomes bad. If prefill is always interrupted, TTFT and throughput become bad.

Chunked prefill creates smaller scheduling units. This lets the scheduler interleave work without throwing away GPU utilization.

What The Scheduler Is Really Optimizing

The scheduler is not simply maximizing tokens/s. It is balancing two latency distributions. A system can have high aggregate throughput and still be unusable if decode tokens arrive with high jitter. SARATHI’s decode-maximal batching protects active conversations while still admitting prefill work.

Boundary With DistServe

SARATHI keeps phases on the same hardware and changes scheduling. DistServe changes the architecture by separating phase resources. SARATHI has less KV transfer overhead; DistServe has more independent scaling.

Source-Level Notes

SARATHI studies the interference between prefill and decode. Prefill processes many prompt tokens in parallel and is compute-heavy. Decode processes one new token per sequence and is often memory/KV-cache bound. Naively mixing them can hurt both TTFT and TPOT.

The paper’s main idea is chunked prefill: split a long prompt into chunks and piggyback those chunks with decode batches. The scheduler tries to remain decode-maximal, meaning decode tokens keep making progress while prefill work fills otherwise underused compute.

Scheduler Reading

The method is not only batching. It changes the unit of scheduling from whole prompts to prompt chunks. That lets a long prompt stop monopolizing the GPU before existing decode requests get their next token.

The relationship with DistServe is useful. SARATHI keeps prefill and decode on the same serving workers but schedules them more carefully. DistServe later argues that the two phases are different enough to place on separate resources. Both papers start from the same observation: prefill and decode stress hardware differently.

Experiment Reading

The result curves should be read across request length distributions. Chunked prefill matters most when prompts are long enough to block decode progress. If prompts are uniformly short, the scheduler has less room to improve over ordinary batching.

TTFT and TPOT can move in opposite directions. A scheduler that prioritizes prefill may improve TTFT but hurt ongoing decode latency. SARATHI’s decode-maximal framing is useful because it treats decode progress as the steady-state heartbeat of the system.

A reproduction should log GPU utilization by phase. The goal is not just larger batches; it is filling compute slack from decode with prefill chunks without making decode wait too long.

Reproduction Checklist

The scheduler should log how many prefill chunks and decode tokens are placed in each iteration. If decode batches are often delayed by large prefill chunks, the implementation is not decode-maximal. If prefill chunks are too small, overhead can dominate.

I would sweep chunk size. The best value depends on prompt length distribution and GPU. This is a scheduling parameter, not a universal constant from the paper.
