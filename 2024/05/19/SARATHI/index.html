SARATHI: Piggybacking Decodes with Chunked Prefills

Paper: SARATHI: Efficient LLM Inference by Piggybacking Decodes with Chunked Prefills

SARATHI is a paper about the execution shape of LLM inference. The key observation is not just that prompts can be long. It is that the prefill phase and the decode phase stress the GPU in opposite ways:

  • prefill has many tokens per request, so it can form large matrix-matrix multiplications and saturate compute quickly;
  • decode has one new token per active request, so it is often a small vector-matrix-like workload dominated by loading weights and KV cache state;
  • pipeline parallelism makes this worse, because consecutive micro-batches can have very different runtimes and leave pipeline stages idle.

SARATHI’s answer is simple but subtle: split prefill into chunks, and schedule each chunk with as many decode tokens as possible. The prefill chunk keeps the GPU compute-bound; the decode tokens reuse the weight loads and “piggyback” on that work. In pipeline-parallel deployments, the same chunking also makes micro-batches more uniform, reducing bubbles.

Figure 1. Orca-style iteration-level scheduling can still create non-uniform pipeline work. SARATHI cuts prefills into smaller chunks and mixes them with decode tokens, making the per-iteration work more regular.

The Problem Shape

An autoregressive LLM request has two major phases.

The prefill phase consumes all prompt tokens. If the prompt length is , the hidden size is , and the batch size is , a transformer block sees tensors shaped like . The model can run many token positions in parallel.

The decode phase generates one token per iteration. The same block now sees for most linear operations. Attention still needs to read the previous KV cache, but the new query side is tiny.

This difference matters because GPU efficiency is not decided by token count alone. A prefill batch can do large dense GEMMs. A decode iteration may touch the same large weight matrices for only a few tokens, which gives poor arithmetic intensity.

The paper profiles LLaMA-13B on an A6000 with sequence length 1024. Prefill per-token time is almost flat across batch sizes because even one long prompt can saturate compute. Decode behaves very differently: at batch sizes 1, 2, and 18, decode per-token cost is about 200x, 100x, and 16.7x the prefill per-token cost, respectively.

Figure 3. Prefill cost per token is almost constant; decode becomes cheaper only as the active decode batch grows.

Figure 4 explains why this happens. Prefill reaches high throughput when is large enough. For LLaMA-13B on A6000, the paper reports that prefill throughput saturates around 180 tokens/ms once . Decode throughput grows with batch size, but practical full-model decode batches are limited by model weights and KV cache memory.

The immediate consequence is a bad serving tradeoff:

  • run big prefill batches, and active decodes can wait too long;
  • prioritize decode-only iterations, and the GPU spends too much time doing low-arithmetic-intensity work;
  • use pipeline parallelism, and variable prefill/decode runtimes create bubbles between stages.

Pipeline Bubbles

Pipeline parallelism splits the model by layers. It is attractive when tensor parallel all-reduces are too expensive across nodes, but it depends on a stream of similarly sized micro-batches. SARATHI points out that LLM inference violates this assumption.

Figure 5. Even with iteration-level scheduling, different prompt lengths and decode contexts create pipeline bubbles.

The paper names three bubble sources:

  1. PB1: varying prefill length. Consecutive micro-batches can contain different numbers of prompt tokens.
  2. PB2: prefill/decode mismatch. A prefill-heavy micro-batch and a decode-heavy micro-batch have different runtimes.
  3. PB3: decode context mismatch. Decode runtime changes with accumulated context length because attention reads more KV cache.

The usual fix in training is to increase the number of micro-batches, but inference has no backward pass and a constantly changing mix of request states. If the serving engine cannot make each unit of work more uniform, pipeline stages still go idle.

SARATHI’s core idea is to manufacture uniform units of work:

  • cut large prefills into chunks that are still compute-efficient;
  • add decode tokens to each chunk until the batch is decode-maximal;
  • make each micro-batch close to the same compute cost.

Chunked Prefills

Chunked prefill means a long prompt is not processed as a single monolithic prefill. Instead, the prompt is split into chunks, and each chunk is scheduled in a separate iteration.

The key correctness issue is attention masking. A token in a later chunk must be allowed to attend to all previous chunks, but it must not attend to future tokens. With the right mask and KV cache updates, chunked prefill is mathematically equivalent to full prefill.

Figure 6. Each prefill chunk can attend to all earlier prompt tokens and the earlier tokens inside the same chunk, but not to future tokens.

Chunking is useful only if each chunk is still large enough to run efficiently. The paper gives two reasons this is often possible:

  • LLaMA-13B on A6000 reaches peak prefill throughput once the number of prefill tokens is around 512 or higher; using 256 tokens costs only about 12.5% of peak prefill throughput.
  • Larger hidden sizes need fewer tokens to saturate compute. For GPT-3 with hidden size 12288 on A100, a single layer peaks around chunk size 256.

There is overhead. Smaller chunks reduce arithmetic intensity. They also reread old KV cache in attention: if a prompt is split into chunks, the first chunk’s KV cache is read by later chunk attentions many times. SARATHI argues this is acceptable because attention is a smaller part of the full forward pass than the linear layers, but the ablation later shows that very small chunks can still be expensive.

Decode-Maximal Batching

Chunking alone only creates more prefill scheduling units. The important scheduling rule is decode-maximal batching.

Each SARATHI batch contains:

  • one prefill chunk;
  • as many decode tokens as the remaining batch slots can hold.

The compute trick is in the linear layers. Prefill and decode run the same weight matrices. Baseline decode loads those weights for only a tiny number of new tokens. SARATHI concatenates the prefill chunk tokens and the decode tokens for linear operations, so the decode tokens reuse the same weight loads. Attention still runs separately for prefill and decode because their attention shapes are different.

Table 2. In the LLaMA-13B/A6000 example, decode-only costs 12.49 ms/token. In a decode-maximal batch, the marginal decode cost falls to 1.2 ms/token.

This table is the cleanest numerical explanation of the paper. The decode-maximal batch has almost the same total time as a prefill-only batch, but it also advances decode tokens. The decode tokens are not free, but their marginal cost is much lower because the expensive weight movement is already paid for by the prefill chunk.

This also explains why the paper’s headline improvements differ by metric:

  • decode throughput can improve by up to an order of magnitude;
  • end-to-end throughput improves less, because SARATHI mostly improves decode and does not make pure prefill much faster.

Picking Chunk Size

The chunk size is not a universal constant. It depends on workload mix, model size, GPU, KV memory, and matmul tile behavior.

Small chunks create more opportunities to piggyback decode tokens, but they reduce prefill efficiency. Large chunks keep prefill efficient, but they create fewer mixed batches and may leave decode tokens uncovered.

There is another hardware detail: tile quantization. GPU matmuls are partitioned into tiles. If the relevant matrix dimension is just over a tile multiple, the kernel may do a lot of wasted work.

Figure 7. Adding one token past a tile-friendly boundary can cause a large runtime jump. The paper reports 69.8 ms at 256 tokens and 92.33 ms at 257 tokens in this example.

The practical rule is:

  1. choose a chunk size that gives acceptable prefill efficiency;
  2. make prefill_chunk_tokens + decode_tokens align with the matmul tile size.

Implementation Setup

SARATHI is implemented on nanoGPT with support for chunked prefills and decode-maximal batching. For fair comparison with Orca-style iteration-level scheduling, the authors use the same mixed batching mechanism but remove SARATHI’s constraints for the baseline. They also use xFormers attention because it was fastest in their setup, and they pre-allocate KV cache for the maximum sequence length to avoid per-iteration allocation overhead.

Table 3. The paper evaluates single-GPU physical deployments for LLaMA-13B/A6000 and LLaMA-33B/A100, and a profile-driven 64xA100 GPT-3 simulation.

The model configurations are standard:

  • LLaMA-13B: 40 layers, 40 attention heads, hidden size 5120;
  • LLaMA-33B: 60 layers, 52 attention heads, hidden size 6656;
  • GPT-3: 96 layers, 96 attention heads, hidden size 12288.

Single-GPU Results

The first experiment measures decode-only speedup on LLaMA-13B with chunk size 256. SARATHI computes decode speedup by comparing the marginal decode time inside a decode-maximal batch against the baseline decode-only iteration.

Figure 8. SARATHI gives the largest decode speedup at smaller batch sizes, where baseline decode is most memory-bound.

The reported decode speedup ranges from about 2.8x to 10x. It decreases as batch size grows because baseline decode becomes less inefficient. It also decreases as sequence length grows because attention becomes a larger fraction of total decode time, and SARATHI mostly improves linear layers.

The end-to-end throughput gains are smaller but still meaningful:

The peak cases in Table 4 are:

  • LLaMA-13B on A6000: 1K/2K/3K sequence lengths reach 1.33x, 1.26x, and 1.22x throughput gain, with decode speedups of 5.45x, 3.26x, and 2.51x.
  • LLaMA-33B on A100: 1K/2K/3K sequence lengths reach 1.25x, 1.22x, and 1.14x throughput gain, with decode speedups of 3.83x, 4.25x, and 3.51x.

Two things stand out.

First, the A6000 gains are higher than the A100 gains. The paper attributes this to the A100’s higher FLOPs-to-memory-bandwidth ratio. On A100, a larger chunk size or larger hidden dimension is needed to avoid losing prefill efficiency.

Second, a 5x to 10x decode speedup does not become a 5x to 10x serving speedup. That is expected. SARATHI attacks the decode inefficiency; the remaining prefill work still costs real time.

The paper’s useful takeaway is that a scheduler should not blindly use the smallest possible chunk. If the request mix is decode-heavy, smaller chunks can help. If the request mix has a higher P:D ratio, larger chunks are often better. If the mix is far away from the selected chunk’s balance point, SARATHI can fall back toward normal prefill-only or decode-only behavior.

The operation breakdown supports the same point.

Figure 10. Linear layers, especially the FFN, benefit most from decode-maximal batching. Attention is not the main source of speedup.

The FFN sees the largest runtime reduction, around 1.3x to 1.6x in the paper’s reported cases. Pre-projection and post-projection improve less, around 1.05x to 1.38x. This matches the mechanism: SARATHI improves the linear operations by turning tiny decode work into a larger fused matrix multiplication. Attention remains a different shape and is less affected.

Comparison With Orca-Style Iteration-Level Scheduling

Orca, vLLM, and TGI use iteration-level scheduling: requests can enter or leave the batch at iteration boundaries. This avoids padding all requests to the longest sequence and lets completed requests exit early.

But iteration-level scheduling does not guarantee a good prefill/decode composition. A batch can contain:

  • only prefills;
  • only decodes;
  • a random mixture of full prefills and decodes.

Orca may overlap a newly arriving full prefill with ongoing decodes, but that overlap is incidental. It still submits the entire prompt as one prefill unit. SARATHI’s difference is that it creates many chunked prefill units, each of which can carry decodes.

Figure 11. SARATHI consistently beats the baseline and Orca best case in these experiments because it actively creates piggyback opportunities instead of relying on arrival timing.

The paper compares Orca in two scenarios:

  • best case: a full prefill overlaps with ongoing decodes;
  • worst case: requests begin and end together, so there is little useful overlap.

For LLaMA-13B on A6000:

  • best-case Orca gets about 1.11x throughput at 1K sequence length, then drops closer to baseline at longer sequence lengths;
  • SARATHI reaches 1.27x, 1.25x, and 1.23x for 1K, 2K, and 3K sequence lengths.

The reason is coverage. A full prefill provides only one overlap opportunity. Chunked prefill turns one long prompt into many opportunities, so more decode iterations can piggyback.

Pipeline-Parallel Results

SARATHI’s second major contribution is applying the same uniform-work idea to pipeline parallelism.

The GPT-3 experiment is simulated but carefully profile-driven:

  • 64 A100 GPUs across eight servers connected with InfiniBand;
  • 8-way tensor parallelism inside a node plus 8-way pipeline parallelism across nodes;
  • comparison against eight 8-way tensor-parallel replicas;
  • max batch size 27 for TP+PP and 11 for TP-only;
  • P:D ratio fixed at 10;
  • request sequence lengths sampled between 1K and 4K from a Zipf distribution with ;
  • chunk size 256;
  • simulator predictions validated within 5% on an 8-GPU 80GB A100 DGX box.

Figure 12. SARATHI reduces pipeline bubble time and improves request completion time for GPT-3 in the 64xA100 simulation.

The reported result is strong:

  • median bubble time per request drops by 6.29x;
  • SARATHI’s TP+PP setup is 1.91x faster than the TP+PP baseline with Orca-style scheduling;
  • it is also 1.48x faster than the TP-only replica setup.

The TP-only setup is already 1.28x faster than the baseline TP+PP setup because the baseline suffers from large pipeline bubbles. SARATHI changes that conclusion by making pipeline-parallel work units much more uniform.

This is the part of the paper that connects scheduling to cluster architecture. Without uniform micro-batches, PP can waste enough time that TP-only replicas look better despite smaller batch capacity. With chunked-prefill and decode-maximal batching, PP can use its memory advantage without paying as much bubble overhead.

Chunking Overhead

The ablation asks whether chunked-prefill overhead cancels the decode gain.

Figure 13. Very small chunks hurt prefill efficiency, but moderate chunks can still improve the full batch because decode gets cheaper.

The main numbers:

  • chunk size 64 causes around 3x attention overhead and about 5x total prefill overhead;
  • chunk sizes 256 and 512 keep end-to-end prefill loss within about 20% and 10%;
  • chunk size 64 can still roughly match baseline overall because it piggybacks more decodes;
  • chunk size 128 can reach up to 1.16x overall throughput even though prefill is more than 2x slower;
  • tile quantization appears again: chunk size 256 does better than 320 because 256 aligns with the tile size.

This is the clearest warning for implementers. Chunked prefill is a scheduler parameter, not a magic constant. It needs profiling on the actual model and GPU.

Relationship To PagedAttention And DistServe

SARATHI sits between memory management and cluster-level phase separation.

PagedAttention / vLLM solves KV cache allocation and fragmentation. It lets the serving engine fit more active requests and avoid wasting memory on over-reserved KV blocks. SARATHI assumes a serving engine can maintain active decode requests and KV state, then asks: given those requests, how should prefill and decode work be composed in each iteration?

DistServe separates prefill and decode onto different workers. It argues that the two phases have different parallelism and latency requirements, so they should be scaled independently. SARATHI keeps the phases colocated and improves the mixed execution schedule. This avoids cross-phase KV transfer, but it also means the same workers still handle both phase types.

So the boundary is:

  • PagedAttention: “How do I store KV cache efficiently enough to support many active requests?”
  • SARATHI: “How do I mix prefill chunks and decode tokens so decode becomes cheap and pipeline bubbles shrink?”
  • DistServe: “Should prefill and decode live on separate resource pools?”

These ideas are complementary in principle. A production serving stack could use paged KV memory, SARATHI-like chunked prefill scheduling, and some form of phase-aware placement or disaggregation.

Implementation Notes I Would Check

If I were implementing SARATHI in an inference runtime, I would start with these invariants.

The scheduler state needs to distinguish:

  • waiting prefill requests;
  • active decode requests;
  • partial prefill chunks that have already written KV cache;
  • per-request generated length and remaining decode budget;
  • max sequence length and current KV allocation.

The batch builder should be decode-maximal:

The real version needs more policies:

  • what to do when there is no waiting prefill;
  • what to do when there are too few active decodes;
  • how to age waiting prefills to avoid TTFT starvation;
  • how to choose chunk size when P:D changes over time;
  • how to preserve fairness when some requests have very long prompts;
  • how to account for partial chunks near the end of a prompt;
  • how to handle memory pressure if KV cache allocation fails.

The paper mainly optimizes execution efficiency. A production engine still needs admission control, SLO-aware queuing, preemption behavior, and fairness. SARATHI is the compute layer mechanism, not the whole serving policy.

Limitations

The paper is explicit about several limitations.

First, SARATHI focuses on throughput and execution efficiency. Real serving systems also care about TTFT, TPOT, queueing delay, fairness, cancellation, and request priorities. A decode-maximal scheduler that ignores these can still create bad user-visible latency.

Second, chunk size selection is workload-dependent. The paper can choose good values for the evaluated P:D ratios, models, and GPUs, but a production workload may have changing prompt and output distributions. Dynamic chunk-size selection is left open.

Third, many experiments assume requests in a batch have similar prefill and decode token counts. The pipeline simulation adds variable sequence lengths, but real traffic can be more irregular.

Fourth, the paper focuses on sequence lengths up to about 3K for most experiments and P:D ratios from 1 to 200. Very long-context serving changes the attention cost substantially. When attention dominates, SARATHI’s linear-layer piggybacking has less room to help.

Finally, SARATHI does not replace KV memory management. If KV cache fragmentation or over-reservation prevents large active batches, the scheduler may not have enough decodes to piggyback.

Takeaway

My mental model for SARATHI:

Decode is inefficient because it is too small to amortize weight movement. Prefill is efficient because it is large enough to make the GPU compute-bound. SARATHI slices prefill into enough compute-saturating chunks, then attaches decode tokens to those chunks so decode inherits prefill’s efficiency.

The paper is valuable because it turns a vague serving intuition into a concrete execution rule:

  • one prefill chunk per batch;
  • fill the rest with decodes;
  • align the combined token count with GPU tile behavior;
  • use chunking to create uniform pipeline micro-batches.

That is why SARATHI improves both single-GPU decode efficiency and pipeline-parallel utilization. It is not just “interleave prefill and decode”; it is “interleave them in the shape that the GPU wants.”
