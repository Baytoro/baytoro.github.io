Paper: Efficient Memory Management for Large Language Model Serving with PagedAttention

vLLM/PagedAttention is a serving paper, but the core bottleneck is not a scheduler abstraction. It is GPU memory layout. During autoregressive decoding, every request grows a KV cache token by token. If that memory is allocated badly, batching capacity collapses.

Motivation

The figure shows why this matters. For a 13B model on an A100, KV cache can occupy a large fraction of memory. If existing systems reserve contiguous memory for each request, fragmentation and over-reservation waste memory that could have been used for larger batches.

Methodology

PagedAttention borrows from OS virtual memory. A sequence’s KV cache is split into fixed-size blocks. The logical token positions map to physical blocks through a block table.

This gives three properties:

  1. Near-zero fragmentation. Blocks can be allocated and freed independently.
  2. Continuous batching. New requests can join and finished requests can leave without rebuilding contiguous buffers.
  3. KV sharing. Multiple samples sharing the same prompt can share prompt KV blocks with copy-on-write.

The attention kernel must follow the block table when reading K/V. That is the price of the abstraction. The benefit is much better memory packing.

Results

The paper reports roughly 2-4x throughput improvement over systems such as FasterTransformer and Orca at similar latency. The gain is larger for long sequences and varied output lengths because those workloads create more KV allocation waste.

Takeaway

PagedAttention changes how I think about LLM serving. The bottleneck is not only FLOPs or one-token latency. It is how many active sequences can be packed into GPU memory while decoding. Later systems like DistServe, Mooncake, SGLang, KIVI, and FlashInfer all build on this idea that KV cache is a first-class systems object.

Why Fragmentation Is So Expensive

If a serving system reserves memory for the maximum possible sequence length, most requests waste memory. If it grows contiguous buffers dynamically, allocation and copying become expensive. PagedAttention avoids both by making KV cache block-granular.

The block table is the core abstraction. It means sequence position maps to a logical block id and an offset inside that block. The physical block can live anywhere in the KV pool. This is exactly why the analogy to virtual memory is appropriate.

Relationship With Continuous Batching

Continuous batching only works if memory can also change continuously. If finished requests leave holes that cannot be reused, the batch scheduler has theoretical capacity but no physical memory. PagedAttention makes continuous batching practical by allowing small KV blocks to be recycled.

Limitation

The attention kernel becomes more complex because it must dereference block tables. That extra indirection has a cost. vLLM wins because the memory-packing benefit is larger than the kernel-layout overhead for real serving workloads.

Source-Level Notes

The OS analogy is not decoration. In normal virtual memory, a process sees contiguous virtual pages while physical pages can be scattered. PagedAttention gives each sequence a logical KV address space and maps it to physical KV blocks.

The attention kernel reads the block table to find physical K/V blocks. This creates extra indirection, but it avoids reserving contiguous max-length KV buffers for every request.

Systems Reading

The paper’s throughput gains should be read as memory-capacity gains. If KV fragmentation wastes half of memory, the scheduler cannot form large batches even if the GPU has compute headroom. PagedAttention improves the number of active sequences that fit simultaneously.

The copy-on-write prompt sharing detail is also important. Sampling multiple outputs from the same prompt should not duplicate prompt KV cache. The block abstraction makes sharing natural until a sequence diverges and needs private decode blocks.

Reproduction Checklist

A minimal implementation should stress fragmentation. Generate requests with varied prompt and output lengths, then compare contiguous allocation with block allocation under the same memory budget. The expected result is not just lower memory waste, but more active sequences admitted into the batch.

I would also test prompt sharing with multiple samples from one prompt. Copy-on-write should keep shared prompt blocks physically shared until continuations diverge. If memory doubles immediately, the block table is not being used correctly.
