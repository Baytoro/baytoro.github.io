PagedAttention and vLLM: KV Cache Paging for High-Throughput LLM Serving

Paper: Efficient Memory Management for Large Language Model Serving with PagedAttention

Code: vllm-project/vllm

PagedAttention is one of those serving papers where the main idea is easy to say but easy to under-read. The one-line summary is “use virtual-memory-like paging for KV cache.” The important part is why this becomes a throughput primitive for online LLM serving:

  • The KV cache is large enough to be a first-class memory object, not a small side buffer.
  • Its lifetime and size are dynamic because output lengths are unknown.
  • Fine-grained batching only helps if the runtime can pack many live sequences into GPU memory.
  • Advanced decoding methods, such as parallel sampling, beam search, and shared prefixes, create sharing opportunities that contiguous KV allocation cannot exploit cleanly.

The paper is not claiming that the PagedAttention kernel is faster than a contiguous attention kernel. In fact, its attention kernel is slower in the microbenchmark. vLLM wins because better memory packing lets the system admit a larger effective batch before latency explodes.

Figure 1 in the paper: for a 13B model on an A100 40GB GPU, model weights are static, while KV cache is dynamic and consumes a large fraction of memory. Smoother KV growth translates into larger effective batches.

The hardware trend makes this worse. The paper points out that from A100 to H100, FLOPs grow much faster than maximum GPU memory capacity. If compute grows but the number of requests that fit in memory does not, memory management becomes the limiter.

Why Existing Allocation Wastes Memory

Existing systems before vLLM typically keep the KV cache of a request in a contiguous memory region. Because output length is unknown, the system must either reserve for a maximum length, reserve for a predicted length, or allocate/copy as the sequence grows. All three choices are awkward in an online server.

The paper separates the waste into three buckets:

Waste type Meaning Why it hurts batching
Reservation Memory reserved for future tokens that might be generated Other requests cannot use it while the current request is alive
Internal fragmentation Allocated slots that will never be used because the final output is shorter than the reserved length Memory is permanently unavailable until the request finishes
External fragmentation Free space exists, but not in a shape that can satisfy a contiguous allocation Total free memory is misleading because it cannot be packed

Figure 2 in the paper: in the evaluated existing systems, only 20.4%-38.2% of KV cache memory stores actual token states. vLLM raises that fraction to 96.3%.

The graph is the key motivation for the paper. The gap is not a small allocator inefficiency. If most KV memory is not storing useful token states, the scheduler cannot form a large batch, and throughput collapses at a lower request rate.

Figure 3 in the paper: contiguous KV regions create reserved slots, internal fragmentation, and external fragmentation. The same token content at different positions also has different KV states, so the runtime cannot simply deduplicate token strings.

This is why “just use continuous batching” is not enough. Continuous batching changes which requests are executed together at each decoding iteration. It does not by itself solve the physical memory layout. If finished requests leave holes that cannot be reused by growing requests, the batch scheduler has logical capacity but no usable KV memory.

The Core Abstraction

PagedAttention borrows the address-translation idea from virtual memory. A sequence sees a logical KV address space, split into fixed-size logical blocks. The runtime maps each logical block to a physical KV block from a GPU memory pool.

Only the last logical block of a sequence can be partially empty. Therefore, with block size , the unused KV slots per live sequence are bounded by less than one block, instead of being proportional to the difference between maximum sequence length and actual generated length.

Figure 5 in the paper: the query attends over K/V vectors stored in non-contiguous physical blocks. The attention kernel follows the block table instead of assuming one contiguous KV array.

The OS analogy is useful, but it is not a copy-paste of CPU virtual memory. vLLM uses application semantics:

  • All KV blocks of a sequence are read together during attention, so eviction can be sequence-level.
  • The runtime knows when a sequence forks, appends a token, or finishes.
  • Copy-on-write is applied at KV block granularity for decoding algorithms.
  • Recovery can use recomputation, which is not a normal OS page fault strategy.

vLLM Runtime Architecture

vLLM wraps PagedAttention in a serving runtime. The architecture has a centralized scheduler, a KV cache manager, GPU/CPU block allocators, and distributed workers that execute model shards.

Figure 4 in the paper: the scheduler coordinates requests, the KV cache manager owns block tables, and workers use cache engines to read/write physical KV blocks.

The control flow during serving is roughly:

  1. The scheduler chooses which sequences or sequence groups to run in the next iteration.
  2. The KV cache manager allocates new physical blocks only when a logical block needs storage.
  3. The scheduler sends input token IDs and block tables to GPU workers.
  4. The model executes the next step. Attention layers read past KV through the block table.
  5. Newly generated K/V tensors are written into the allocated physical blocks.
  6. Finished sequences release their blocks; forked sequences may share blocks with copy-on-write.

This runtime design makes memory management explicit. KV cache is not a tensor hidden inside a framework allocator; it is a managed serving resource.

Block Tables

The block table is the most important data structure in the paper. It records, for each sequence, which physical block stores each logical block and how many slots in the current block are filled.

Figure 6 in the paper: a request has logical KV blocks, while physical KV blocks can live anywhere in GPU DRAM. The block table translates logical block ids to physical block ids.

In the example, the prompt “Four score and seven years ago our” is split into logical blocks of four tokens. Its logical blocks do not have to be adjacent in GPU memory. The first logical block can map to physical block 7, the second to physical block 1, and a newly generated token can later trigger allocation of another physical block.

This solves the reservation problem directly:

  • At prompt time, vLLM allocates just enough blocks for the existing prompt and generated tokens.
  • During decoding, it allocates more blocks only when the current final block is full.
  • When a request completes, its physical blocks return to the free pool and can be reused by any other request.

Figure 7 in the paper: two requests can use interleaved physical blocks without needing neighboring logical blocks to be contiguous in GPU memory.

This is the memory-side requirement for high-throughput continuous batching. The batch can change every iteration because the KV memory layout can also change every iteration.

PagedAttention Kernel

The kernel has to compute attention while K/V blocks are non-contiguous. The paper rewrites attention over blocks. If the block size is , the -th key block is:

This has a real cost. Compared with a contiguous attention kernel, PagedAttention needs to:

  • Load block table entries.
  • Follow non-contiguous physical block ids.
  • Handle variable sequence lengths in the same batch.
  • Execute extra branches around block boundaries and partially filled blocks.

The paper reports 20%-26% higher attention kernel latency than FasterTransformer in the kernel microbenchmark. That sounds bad if attention is evaluated in isolation. It is acceptable at the serving-system level because the memory savings allow much larger batches.

Implementation details from the paper:

  • Fused reshape and block write: new K/V tensors are split, reshaped, and written to physical blocks in one kernel.
  • Fused block read and attention: the attention kernel reads K/V according to block tables and computes attention on the fly.
  • Warp-level block read: a GPU warp is assigned to read each block for coalesced memory access.
  • Fused block copy: copy-on-write block copies are batched into one kernel launch instead of many small cudaMemcpyAsync calls.

Copy-On-Write For Parallel Sampling

Many generation requests ask for multiple samples from the same prompt. Without sharing, each sample would duplicate the prompt KV cache even though the prompt part is identical.

PagedAttention makes this natural. Multiple sequences can map their logical prompt blocks to the same physical blocks. Each physical block has a reference count. When a sequence needs to write into a shared block, vLLM allocates a private physical block and copies the old content once.

Figure 8 in the paper: two samples share prompt blocks. When one sample writes to a shared final block, copy-on-write creates a private block only for the modified block.

The subtle point is the final block. If the prompt length is not a multiple of the block size, the last prompt block has empty slots. When different samples begin generating different tokens, they may need to write into that same logical final block. That is where copy-on-write is needed. Earlier full prompt blocks can remain shared.

This is a block-level version of process fork:

The paper presents fork, append, and free as the common API for supporting different decoding algorithms. That is a clean abstraction: the model execution kernel only sees physical block ids, while the scheduler and block manager handle sharing.

Beam Search Sharing

Beam search creates even more sharing than parallel sampling. Candidates share the original prompt, and many candidates also share intermediate prefixes. As beams are pruned and expanded, the sharing pattern changes dynamically.

Figure 9 in the paper: beam candidates share prefix blocks. When candidates are pruned, their blocks are released; when new candidates are created, they reuse shared prefix blocks and allocate only new suffix blocks.

The old way to implement this often involves copying KV cache between beam candidates when a candidate inherits another candidate’s prefix. With PagedAttention, inheritance is mostly block-table manipulation plus reference-count changes. Only a shared block that is being modified requires an actual block copy.

This matters because beam search multiplies the number of live candidate sequences. If each candidate duplicated its full KV history, the KV budget would shrink quickly. If most prefix blocks are shared, the same GPU can keep more beams alive.

Shared Prefixes

Shared prefix is the prompt-engineering version of the same idea. Many requests may share a long system prompt, task description, or few-shot examples. The service provider can precompute the shared prefix KV cache and map user requests to those physical blocks.

Figure 10 in the paper: multiple translation prompts share the same instruction and examples, while each user input adds a different suffix.

For shared prefixes, vLLM can reserve physical blocks for the prefix, then map the prefix part of many requests to those cached blocks. The final prefix block may still need copy-on-write when user-specific suffix tokens are appended.

This is distinct from semantic prompt caching. The paper does not solve how to discover arbitrary reusable prefixes across traffic. It shows that once a shared prefix is known, the block table makes the memory sharing mechanism straightforward.

Scheduling And Preemption

PagedAttention also affects request scheduling. When GPU KV blocks are exhausted, vLLM has to preempt some work. The paper chooses FCFS fairness: earlier requests are served first, and later requests are preempted first.

The eviction policy is all-or-nothing at sequence granularity. This is different from normal virtual memory, where an OS may evict individual pages. In LLM decoding, attention needs all previous KV blocks for a sequence, so evicting only some blocks of a sequence is not useful.

Sequence groups, such as beam candidates in one request, are gang-scheduled. They are preempted and resumed together because they may share blocks.

The paper studies two recovery options:

Recovery method What happens Tradeoff
Swapping Copy evicted KV blocks from GPU memory to CPU RAM, then copy them back later Can be expensive with many small block transfers
Recomputation Discard evicted KV blocks and regenerate them when the sequence is resumed Uses GPU compute, but prompt-phase recomputation can be efficient

Recomputation is possible because the generated tokens can be concatenated with the original prompt and processed as one prompt during recovery. That generates KV cache for all positions in a prompt-like pass instead of replaying one token at a time.

Distributed Execution

The paper supports Megatron-LM style tensor parallelism. Each worker stores the shard of KV cache corresponding to its attention heads, but the workers share the same logical-to-physical block mapping from the centralized scheduler.

At each decoding iteration:

  1. The scheduler builds a control message with input token IDs and block tables.
  2. The scheduler broadcasts it to all GPU workers.
  3. Each worker executes the model shard and reads local KV blocks according to the shared block table.
  4. Workers synchronize intermediate tensors through all-reduce as in tensor parallel inference.
  5. Workers send sampled tokens back to the scheduler.

The key observation is that model parallelism shards the content of KV tensors, but not the sequence positions. All shards still need the same block-table structure.

Evaluation Setup

The paper evaluates OPT-13B, OPT-66B, OPT-175B, and LLaMA-13B on A100 GPUs. The configurations show how KV memory changes with model and GPU setup.

Table 1 in the paper: model sizes, GPU memory, parameter memory, KV cache memory budget, and maximum KV cache slots.

Two workload traces are synthesized from ShareGPT and Alpaca. ShareGPT is much longer and more variable. Alpaca is shorter and therefore less memory-stressing.

Figure 11 in the paper: ShareGPT has average input length 161.31 and output length 337.99, while Alpaca has average input length 19.31 and output length 58.45.

The baselines are:

Baseline Description
FasterTransformer Highly optimized inference engine, with a custom dynamic batching scheduler in the paper
Orca (Max) Reserves KV space up to the model maximum length, such as 2048 tokens
Orca (Pow2) Reserves output space rounded to the next power of two, at most 2x the real output length
Orca (Oracle) Knows the true output length in advance, which is not feasible but gives an upper bound for contiguous allocation

Basic Sampling Results

For single-sequence generation, vLLM sustains much higher request rates at similar normalized latency.

Figure 12 in the paper: vLLM shifts the latency explosion point to higher request rates across OPT models and both datasets.

On ShareGPT, the paper reports:

  • vLLM sustains 1.7x-2.7x higher request rates than Orca (Oracle).
  • vLLM sustains 2.7x-8x higher request rates than Orca (Max).
  • vLLM sustains up to 22x higher request rates than FasterTransformer.

The comparison to Orca (Oracle) is the most interesting. Orca (Oracle) already knows the actual output length, so it removes one source of over-reservation that real systems do not know. vLLM still wins because block-level allocation removes fragmentation and makes live KV packing denser.

Figure 13 in the paper: for OPT-13B, vLLM batches more live requests. On ShareGPT at 2 req/s, it batches 30.42 requests on average versus 13.62 for Orca (Oracle) and 7.00 for Orca (Max).

The Alpaca results follow the same pattern, but the OPT-175B Alpaca case has a smaller gap against Orca (Oracle) and Orca (Pow2). The paper’s explanation is important: OPT-175B in the evaluated configuration has a large KV memory budget, while Alpaca sequences are short. The system becomes more compute-bound, so better memory packing has less room to improve throughput.

This is the right way to read PagedAttention: its benefits are largest when the workload is memory-bound because KV cache capacity constrains the batch.

Parallel Sampling And Beam Search Results

PagedAttention becomes more valuable when generation creates multiple related sequences per request.

Figure 14 in the paper: vLLM improves throughput for parallel generation and beam search. The gain grows as parallel size or beam width increases.

For OPT-13B on Alpaca:

  • In basic sampling, vLLM improves over Orca (Oracle) by about 1.3x.
  • In beam search with beam width 6, the improvement over Orca (Oracle) grows to 2.3x.

This difference makes sense. Beam candidates share prefixes beyond the original prompt. The block table and reference counts turn that sharing into memory savings.

Figure 15 in the paper: sharing saves 6.1%-9.8% memory for parallel sampling and 37.6%-55.2% for beam search on the Alpaca trace.

The paper also reports larger memory savings on ShareGPT:

  • Parallel sampling: 16.2%-30.5%.
  • Beam search: 44.3%-66.3%.

Longer prompts and longer continuations increase the amount of reusable KV history.

Shared Prefix And Chatbot Results

For shared-prefix translation prompts, vLLM reuses the prefix KV blocks. The paper evaluates one-shot and few-shot translation prefixes.

Figure 16 in the paper: when prompts share an 80-token one-shot prefix, vLLM reaches 1.67x higher throughput than Orca (Oracle). With a 341-token five-shot prefix, the gain becomes 3.58x.

Again, the longer the reusable prefix, the more useful block sharing becomes.

The chatbot workload is also memory-heavy because each prompt includes conversation history. The paper truncates prompts to the last 1024 tokens for OPT-13B and lets the model generate up to 1024 tokens.

Figure 17 in the paper: vLLM sustains about 2x higher request rates than Orca baselines on the chatbot workload.

The reason Orca variants behave similarly here is that long prompts force large reservation behavior. vLLM can still allocate only the blocks needed and recycle them at block granularity.

Ablations

The ablation section is important because it shows the cost of the abstraction.

Figure 18 in the paper: PagedAttention has higher attention kernel latency than FasterTransformer, but block size 16-128 works well on ShareGPT and 16/32 works best on Alpaca.

Two details matter:

  1. PagedAttention’s attention kernel is 20%-26% slower than FasterTransformer’s attention kernel in the microbenchmark.
  2. The end-to-end system is still faster because the extra kernel overhead is outweighed by better memory utilization and larger batches.

Block size controls a tradeoff:

Block size choice Benefit Cost
Smaller blocks Less internal fragmentation, more precise sharing More block-table entries and weaker kernel parallelism per block
Larger blocks Better block-level compute efficiency More wasted tail slots and less sharing granularity

The paper sets the default block size to 16. That is small enough to keep fragmentation low for short sequences, but large enough to use GPU parallelism reasonably well.

Figure 19 in the paper: swapping is expensive for small blocks because it creates many small CPU-GPU transfers. Recomputation is more stable across block sizes, and both methods are comparable around medium block sizes.

This result is a good reminder that paging on GPU is not the same as paging on CPU. PCIe/NVLink transfer granularity, kernel launch overhead, and recomputation throughput all matter.

What The Paper Actually Contributes

My reading is that the paper has three contributions, ordered by importance:

  1. It identifies KV cache memory waste as a primary throughput bottleneck for LLM serving.
  2. It introduces a block-table abstraction that makes KV cache allocation dynamic, packed, and shareable.
  3. It implements the abstraction in a full serving runtime with kernels, scheduling, preemption, tensor parallel execution, and support for complex decoding algorithms.

PagedAttention is not just “attention over paged KV.” The serving runtime matters. Without a scheduler, block manager, refcounts, and kernels that understand block tables, the abstraction would not translate into throughput.

Limitations And Caveats

The paper is very strong, but the technique has boundaries.

First, PagedAttention adds indirection. If a workload is compute-bound and KV memory is not limiting batch size, a slower paged attention kernel can reduce performance. This is why the Alpaca OPT-175B case shows less advantage against strong baselines.

Second, block size tuning is workload-dependent. Short sequences punish large blocks because the tail waste becomes large relative to the useful KV. Very small blocks reduce waste but increase metadata and memory-access overhead.

Third, preemption is not free. Swapping has bandwidth and small-transfer overhead. Recomputation consumes GPU cycles. The best recovery policy depends on interconnect bandwidth, GPU compute, model size, sequence length, and current load.

Fourth, prefix sharing requires the runtime to know which prefix is shared. PagedAttention gives the memory mechanism, not a full semantic cache discovery system.

Fifth, the centralized scheduler and block manager become critical runtime components. At very high request rates, CPU-side scheduling, block-table construction, and metadata transfer can matter, even if the paper’s evaluated workloads are dominated by GPU memory capacity.

Reproduction Checklist

If I were reproducing this paper or debugging an implementation, I would not start with end-to-end throughput. I would first test the memory behavior directly.

  1. Build a synthetic trace with varied prompt and output lengths.
  2. Compare contiguous allocation, max-length reservation, power-of-two reservation, and block allocation under the same KV memory budget.
  3. Track useful token-state slots versus reserved, internal-fragmented, and external-fragmented slots.
  4. Measure average active sequences per decoding iteration.
  5. Add parallel sampling and verify that prompt blocks are shared.
  6. Add beam search and verify that pruned candidates decrement refcounts and free physical blocks.
  7. Sweep block sizes and plot both memory waste and attention-kernel latency.
  8. Stress preemption and compare recomputation with CPU swap.

The expected signal is not merely lower memory usage. The expected signal is a later latency explosion point because more live sequences fit in GPU memory.

Takeaway

PagedAttention changed the framing of LLM serving. Before this paper, it was natural to think about throughput mainly through batching and kernel speed. vLLM shows that the KV cache itself needs an OS-like memory manager.

The central insight is simple but deep: a sequence should have a logical KV address space, and physical KV memory should be allocated, shared, copied, evicted, and freed at block granularity. Once that is true, continuous batching, parallel sampling, beam search, shared prefixes, and preemption all become much easier to support in one runtime.

That is why this paper sits underneath so much later LLM serving work. It turns KV cache from an implementation detail into a first-class systems object.
