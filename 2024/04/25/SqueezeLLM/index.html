SqueezeLLM: Dense-and-Sparse Quantization

H.J. Chen
  2024-04-25 2024-04-25 Created  
  • Paper Reading 
 
  • Quantization 
  • | LLM 
  • | Inference 

Reference

  • Paper: SqueezeLLM: Dense-and-Sparse Quantization
  • Code: SqueezeAILab/SqueezeLLM
  • Related notes: GPTQ, AWQ, SpQR

I read the arXiv v4 / ICML 2024 version. SqueezeLLM belongs to the same weight-only quantization family as GPTQ, AWQ, and SpQR, but it makes a different bet: if decoding is memory-bandwidth bound, we can afford a slightly more complicated dequantization format as long as it cuts weight traffic and preserves perplexity.

The method has two pieces:

  1. sensitivity-based non-uniform quantization, where each output channel gets a small LUT of quantized values chosen by weighted k-means;
  2. Dense-and-Sparse decomposition, where a tiny set of outliers and highly sensitive weights is kept in an FP16 sparse matrix.

The headline is mainly a 3-bit story. On LLaMA-7B C4 perplexity, uniform RTN at 3-bit collapses to 28.26, dense-only SqueezeLLM gets 7.75, and the 0.45% sparse variant gets 7.56. The FP16 baseline is 7.08, so the remaining gap is small enough that the kernel and format details become the real deployment question.

Why Weight-Only Quantization Matters

For batch-1 autoregressive decoding, most large linear layers behave like matrix-vector products. The same weight matrix is streamed for every generated token, and there is not much batch reuse to amortize that read. That is the setting where W3A16 / W4A16 formats are attractive: keep activations in FP16/BF16, but store weights in a few bits.

Figure 2 is a useful sanity check. The paper models LLaMA-7B on an A5000 and shows that reducing only the weight precision from 16-bit to 8-bit and 4-bit lowers normalized runtime substantially for sequence lengths 128 and 2048. This does not mean every LLM workload is memory-bound. Prefill, large-batch serving, attention kernels, and KV-cache pressure can shift the bottleneck. But for single-batch generation, weight bandwidth is a good first target.

This figure is the core intuition. The green bars are uniform quantization levels, while the purple levels from sensitivity-aware non-uniform quantization cluster around sensitive values. The paper’s ablation is pretty decisive here: for 3-bit LLaMA-7B on C4, sensitivity-agnostic non-uniform quantization gives 18.08 perplexity, while sensitivity-based non-uniform quantization gives 7.75 before adding any sparse values.

One detail I like: SqueezeLLM optimizes for final loss perturbation rather than only layer-wise output perturbation. GPTQ/AWQ/SpQR mostly protect layer outputs or activation-weighted layer behavior. SqueezeLLM’s Fisher score is more expensive because it needs gradients through the model, but it is closer to the quantity we actually evaluate.

Dense-And-Sparse Decomposition

Non-uniform centroids help, but outliers still waste codebook capacity. If a few very large weights stretch the range, the 8 centroids available in a 3-bit codebook spend too much capacity on values that almost never occur. SqueezeLLM handles this directly:

where is the dense matrix after removing selected values, and stores those selected values in sparse FP16 form.

The sparse matrix stores two kinds of values:

  • outlier weights selected by percentile thresholds;
  • highly sensitive weights selected by Fisher scores.

The default setting in the main experiments is small: 0.45% sparse values, split as 0.05% sensitive values plus 0.4% outliers.

Figure 5 explains why this works. Across output projection and down projection layers in LLaMA-7B, most weights are packed into a narrow range, while the full range is stretched by rare outliers. Removing less than 1% of values can shrink the dense range enough that the same 3-bit codebook becomes much more useful.

This is close in spirit to SpQR, but the emphasis is different. SpQR is a sparse-quantized representation with a strong outlier/sensitivity story. SqueezeLLM first makes the dense part better with non-uniform Fisher-weighted codebooks, then uses the sparse part as a small correction path. That difference matters for runtime because sparse paths are not free.

Main Results

The most useful slice for me is LLaMA-7B at 3-bit. First, the quality numbers:

Method Bits C4 Wiki2
FP16 16 7.08 5.68
RTN 3.00 28.26 25.61
GPTQ 3.00 9.55 7.55
SqueezeLLM 3.02 7.75 6.32
AWQ g128 3.24 7.90 6.44
SqueezeLLM 0.45% 3.24 7.56 6.13

And the corresponding serving numbers:

Method Speed Mem
FP16 1.0x 12.7 GB
RTN 2.3x 2.9 GB
GPTQ 2.3x 2.9 GB
SqueezeLLM 2.1x 2.9 GB
AWQ g128 2.0x 3.0 GB
SqueezeLLM 0.45% 1.9x 3.1 GB

The comparison I care about is not just “lower perplexity”. It is lower perplexity at similar average bit-width and measured memory. The 0.45% sparse setting has the same average bit-width as grouped GPTQ/AWQ in this table, but better C4 and WikiText2 perplexity.

At 4-bit, the picture is more compressed. Several methods are already close to FP16, so the extra method complexity is harder to justify unless the deployment target really needs the smaller gap. At 3-bit, the gap is large enough that sensitivity-aware non-uniform quantization is doing real work.

Figure 6 is a better way to read the 3-bit result than a single row. The x-axis is relative model size, adjusted by group size for GPTQ/AWQ and by sparsity level for SqueezeLLM. SqueezeLLM stays below GPTQ/AWQ across 7B, 13B, 30B, and 65B. The separation is most visible on smaller models, where 3-bit quantization has less redundancy to absorb mistakes.

Kernel Notes

SqueezeLLM’s dense path stores packed 3-bit or 4-bit indices. Each index points into a per-output-channel FP16 LUT, and the CUDA kernel dequantizes values while performing matrix-vector multiplication. Arithmetic stays FP16; the saving comes from reading fewer weight bits.

The sparse path is implemented with CSR-style storage and a balanced sparse kernel. The balanced part matters because sparse nonzeros are skewed across output channels. A naive one-row-per-thread CSR kernel gives poor load balance; the paper instead assigns a fixed number of nonzeros per thread.

On 128-token generation with an A6000:

  • LLaMA-7B FP16 takes 3.2 s and 12.7 GB.
  • dense-only 3-bit SqueezeLLM takes 1.5 s and 2.9 GB.
  • 0.45% sparse SqueezeLLM takes 1.7 s and 3.1 GB.

That is the tradeoff in one line: the sparse correction improves 7B C4 perplexity from 7.75 to 7.56, and the latency cost is 1.5 s to 1.7 s in this benchmark.

The GPTQ g128 row is also a warning. With activation ordering, GPTQ gets good perplexity but very poor latency in this implementation because the kernel has to handle distributed group scales and memory accesses. Accuracy tricks that look cheap in a table can become expensive once the packed layout is real.

Reproduction Checklist

If I were reproducing this paper, I would separate the algorithmic gain from the format gain:

  1. Run RTN, GPTQ/AWQ, and dense-only non-uniform quantization at the same average bit-width.
  2. Estimate diagonal Fisher scores from the same calibration sample budget used by the paper.
  3. Compare ordinary k-means against Fisher-weighted k-means before introducing sparsity.
  4. Add the sparse path in two steps: sensitive values only, then outliers plus sensitive values.
  5. Report effective bits including codebooks, sparse values, and sparse indices.
  6. Benchmark generation with the final packed kernels, not only fake-quantized PyTorch matmuls.

The important control is step 3. Without it, it is too easy to attribute all improvement to the sparse FP16 escape hatch. The paper’s ablations show that the dense non-uniform codebook is already responsible for most of the recovery from RTN collapse.

Takeaway

SqueezeLLM is a strong paper because it treats 3-bit LLM quantization as both a numerical problem and a layout problem. The numerical side says: uniform bins are a bad fit when only 8 values are available, and sensitive weights should influence centroid placement more than ordinary weights. The layout side says: a small sparse FP16 path is acceptable only if the dense LUT kernel and sparse kernel are implemented carefully.

I would reach for this idea when the target is near-lossless 3-bit weight-only inference and custom kernels are acceptable. If a plain 4-bit AWQ/GPTQ format already meets the quality and latency target, the simpler dense format is probably easier to ship. The value of SqueezeLLM is the low-bit corner where the extra format complexity buys back enough perplexity to matter.
