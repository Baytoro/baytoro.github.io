Paper: SGLang: Efficient Execution of Structured Language Model Programs

Code: sgl-project/sglang

SGLang is easy to under-read if it is described as “a prompting language” or “a prefix cache.” My reading is different:

SGLang is a paper about making LLM application structure visible to the serving runtime.

That visibility is the real contribution. A normal OpenAI-style completion API receives strings. It does not know that several calls are branches of the same program, that the same few-shot prefix is reused by all options, that a tree-search branch inherits a search history, or that a JSON literal has only one valid continuation for the next several tokens. SGLang’s frontend exposes those relationships through a small Python-embedded DSL. Its backend then turns them into concrete runtime optimizations: KV-cache reuse through RadixAttention, cache-aware scheduling, parallel execution inside one program, compressed finite-state-machine decoding, and speculative execution for black-box APIs.

The important lesson is not only “use a radix tree for prefix caching.” The stronger lesson is:

If the serving runtime sees a workload as unrelated strings, it can only optimize generic batching. If it sees the workload as a structured program, it can optimize the graph of shared prefixes, forks, joins, and constraints.

The System In One Figure

Figure 1. SGLang has a frontend language and a backend runtime. The runtime optimizations are not bolted on after the fact; they depend on the frontend exposing program structure.

The frontend contains language primitives for prompt state, generation, selection, multimodal input, and parallelism. The backend runtime includes three main optimizations:

  • RadixAttention for automatic KV-cache reuse across calls and program instances.
  • Compressed FSM decoding for faster structured output generation, such as JSON under a regex constraint.
  • API speculative execution for API-only models where the runtime cannot modify the model backend.

The paper reports up to 6.4x higher throughput and up to 3.7x lower latency compared with the evaluated systems across workloads such as MMLU, ReAct agents, tree-of-thought, skeleton-of-thought, LLM-as-judge, HellaSwag, JSON decoding, multi-turn chat, and DSPy RAG.

I would summarize the paper as a three-layer system:

Layer What it sees What it can optimize
String API independent prompt strings batching and generic model execution
SGLang frontend prompt state, gen, select, fork, join, constraints dependency order, intra-program parallelism, frontend hints
SGLang runtime token prefixes, KV pages, FSM states, batch queues prefix reuse, eviction, scheduling, constrained decoding

The last two rows are inseparable. The runtime optimization works because the frontend gives the runtime a better shape of the computation.

What Is A Language Model Program?

The paper uses “language model program” for applications that are no longer a single prompt and a single completion. Examples include:

  • an agent loop that repeatedly calls an LLM and a tool;
  • a few-shot benchmark where all questions share the same demonstrations;
  • self-consistency sampling where several generations branch from the same prompt;
  • tree-of-thought search where nodes share search history;
  • an LLM judge that evaluates several dimensions in parallel and then merges them;
  • a RAG pipeline where many queries share retrieved context or examples;
  • a JSON decoder that must obey a schema.

The two common properties are:

  • Multiple dependent LLM calls: there is control flow, branching, and synchronization.
  • Structured inputs or outputs: multimodal inputs, schemas, choices, tool results, or downstream parsers.

If these calls are submitted as independent strings, the backend cannot exploit the application structure. It can still do continuous batching, but it misses two categories of reuse:

  • Prefix reuse: repeated prompt tokens should reuse the same KV cache.
  • Program-level parallelism: independent branches should execute concurrently rather than serially through Python glue code.

This is why SGLang belongs in the serving-system family. It is not only a nicer syntax for writing prompts. It changes what information the runtime can use.

Programming Model

Figure 2. The running example is a multi-dimensional essay judge. The red primitives are SGLang operations that expose generation, selection, constraints, and parallel branches.

The frontend is a Python-embedded DSL. The core object is a prompt state, usually named s. Strings and primitives are appended to it. The primitives that matter most are:

  • gen: generate text and store it under a variable name.
  • select: choose the highest-probability option from a list.
  • += or extend: append text to the prompt state.
  • s["name"]: fetch a generated variable and synchronize if needed.
  • fork: create parallel copies of the prompt state.
  • join: merge prompt states.
  • image and video: add multimodal inputs.
  • regex: constrain gen output to match a regular expression.

  • The image input can be hashed and reused if the same image appears again.

This is a useful programming model because it does not hide the prompt from the user. SGLang is closer to LMQL and Guidance than to high-level agent frameworks such as LangChain or DSPy. The user still controls the low-level prompt state, but the runtime sees more structure than a raw completion server would see.

My reading of this comparison: SGLang is not trying to be the most abstract programming layer. It is trying to be low-level enough that runtime optimization remains possible.

RadixAttention

SGLang’s most important backend idea is RadixAttention.

The observation is simple:

The KV cache for a token prefix depends only on that exact prefix.

If two token sequences share the prefix , then their KV tensors for those first positions can be reused. The catch is that this is exact prefix reuse, not semantic similarity. “Same text after a different earlier context” is not the same KV state, because self-attention conditions on all previous tokens.

RadixAttention stores reusable KV cache in a radix tree keyed by token prefixes. A radix tree is a compressed trie: edges can contain token spans rather than one token per edge. This is a good fit because prompts often share long segments such as:

  • a system message;
  • few-shot demonstrations;
  • a retrieved document;
  • earlier chat turns;
  • a tree-search path;
  • a common schema or instruction block.

Figure 3. RadixAttention maintains a radix tree under an LRU eviction policy. It handles chat history, few-shot sharing, branching, splitting, insertion, and eviction.

The runtime operations are:

  1. Prefix match: find the longest cached prefix for an incoming token sequence.
  2. Reuse: load/use the cached KV prefix and prefill only the unmatched suffix.
  3. Reference counting: protect nodes used by currently running requests.
  4. Insertion: after a request finishes, insert its prompt and generated continuation into the tree.
  5. Edge splitting: if two prompts share only part of an edge, split the edge so the shared prefix becomes reusable.
  6. Eviction: when memory is needed, evict least-recently-used leaves first.

The leaf-first eviction detail matters. If a leaf is removed, common ancestors remain cached and can still be reused. If the runtime evicted internal shared nodes first, it would destroy reuse for many descendants.

This is a prefill-centric metric. A higher hit rate means fewer prompt tokens must be recomputed. It can also reduce memory pressure because shared KV cache allows a larger effective batch.

One implementation detail I like: cached tokens and currently running requests share the same memory pool. There is no fixed cache quota. When the waiting batch needs memory, cached tokens can be evicted in favor of active execution. That is the right serving tradeoff. A cache is useful only if it helps throughput or latency; it should not block new work indefinitely.

Frontend Hints

The paper notes a subtle but important frontend-runtime interaction. During fork, the frontend can send the shared prefix first as a hint, then send the remaining branch prompts. This helps ensure the shared prefix is inserted correctly and gives the runtime a cleaner scheduling/matching structure.

This is the “co-designed” part of the system. The backend can do prefix matching on full strings by itself, but the frontend can make the relationship explicit earlier. That matters when execution is asynchronous and when multiple branches arrive around the same time.

My interpretation: frontend hints are not an implementation convenience. They are the mechanism by which the programming model becomes scheduling information.

Cache-Aware Scheduling

Prefix caching is not enough if the scheduler destroys locality. Suppose the waiting queue contains many requests from several prefix groups. A first-come, first-served schedule may keep switching groups and evict useful prefixes before all related requests are processed.

SGLang schedules requests by matched prefix length. Requests with longer cached prefixes are prioritized, approximating a depth-first traversal of the implicit request tree.

Algorithm 1. The scheduler matches waiting requests against the radix tree, sorts by prefix length, selects requests that fit available memory, protects prefix nodes with reference counters, evicts if needed, runs the batch, and inserts finished requests back into the tree.

What Patterns Does RadixAttention Cover?

Figure 9. The appendix shows common KV sharing structures: few-shot learning, self-consistency, multi-turn chat, and tree-of-thought.

The four examples are worth reading separately.

Few-shot learning: all questions share the same demonstrations. If the demonstrations are long, caching them once saves a large amount of prefill.

Self-consistency: several answers are sampled from the same prompt. The prompt KV cache is shared, while generated answers diverge.

Multi-turn chat: later turns share earlier chat history. This is a natural prefix reuse pattern, but the reusable prefix grows over time.

Tree-of-thought: branches share search history. This is the irregular case where a simple one-level prefix cache is not enough. A tree is the natural representation.

This is why a radix tree is a better abstraction than a flat hash table. A table can cache full prompts, but it does not naturally represent multi-level partial sharing or subtree locality.

Compressed FSM For Structured Outputs

SGLang’s second runtime optimization targets constrained decoding.

When a model must output JSON or another structured format, a common method is:

  1. Convert the regex or grammar into a finite state machine.
  2. Track the current FSM state.
  3. At each decode step, mask out invalid next tokens.
  4. Generate one token.
  5. Update the FSM state and repeat.

This is correct but slow when the next several characters or tokens are deterministic. For example, after the model begins a JSON object, the literal prefix {"summary": " may have only one valid continuation for many positions. A normal FSM still steps token by token.

The paper reports that compressed FSM increases JSON-decoding throughput by 1.6x. It also notes an important engineering detail: FSM preprocessing should be reused across a batch. Redoing the preprocessing for every request makes throughput 2.4x lower.

There are two caveats I would keep in mind.

First, regex is character/string-level, while LLM decoding is token-level. The runtime must retokenize carefully so the jump-forward text aligns with the tokenizer’s behavior. Bad partitioning can create invalid token boundaries.

Second, compressed choices can distort probabilities. If a broad textual choice maps onto several tokenizations, comparing choices is not always equivalent to comparing one next-token probability. The paper mentions this as future work. For schema enforcement, compressed FSM is very practical; for exact probability accounting over choices, I would be more cautious.

End-To-End Evaluation

The evaluation covers:

  • Models: Llama-2 7B/70B, Mixtral-8x7B, LLaVA image/video models, and GPT-3.5 for API experiments.
  • Hardware: mainly AWS G5 instances with A10G 24GB GPUs, plus A100G 80GB for some larger experiments.
  • Baselines: Guidance, vLLM, and LMQL.
  • Workloads: MMLU, HellaSwag, ReAct agents, generative agents, tree-of-thought, skeleton-of-thought, LLM judge, JSON decoding, multi-turn chat, and DSPy RAG.
  • Metrics: maximum throughput in programs per second, and average single-program latency.

The results should be interpreted by workload type:

  • MMLU benefits because the 5-shot examples are shared.
  • HellaSwag benefits from both few-shot reuse and common question-prefix reuse across choices.
  • ReAct and generative agents reuse agent templates and previous calls.
  • Tree-of-thought and skeleton-of-thought benefit from parallel branches and shared search/skeleton prefixes.
  • JSON decoding benefits mainly from compressed FSM.
  • Multi-turn chat short outputs benefit because prefill reuse matters more when decode is short.
  • Multi-turn chat long outputs benefits less because decode dominates and different sessions have less sharing.
  • DSPy RAG benefits from shared context examples.

This breakdown is more useful than the headline speedup. SGLang is strongest when the workload has visible structure: shared prefixes, branches, short outputs, constrained literals, or repeated context. It is less special when requests are independent and decode dominates.

The appendix cache-hit figure is important. The paper reports cache hit rates from 50% to 99% across workloads, and says cache-aware scheduling reaches about 96% of the optimal hit rate on average. That is strong evidence that the scheduler is doing more than opportunistic prefix matching.

Multimodal Results And Production Deployment

Table 2. SGLang improves throughput on LLaVA image and video workloads, using image/video primitives and cache reuse for repeated visual inputs.

For multimodal models, the paper hashes image inputs and uses that hash as part of the radix-tree key, allowing reuse of image-token KV cache when the same image appears across questions. This is a practical detail. Multimodal prompts often contain expensive visual tokens, and repeated questions about the same image are common in evaluation and applications.

The production deployment note is also useful. In Chatbot Arena, after one month, the paper reports:

  • 52.4% RadixAttention cache hit rate for LLaVA-Next-34B.
  • 74.1% cache hit rate for Vicuna-33B.
  • 1.7x average first-token latency reduction for Vicuna-33B.

I like this result because it grounds the paper in real traffic. Cache hits came from common system messages, reused example images, and multi-turn chat histories. Those are exactly the repeated prefixes one would expect in a serving product.

Ablation Study

Figure 8. Higher cache hit rate improves batch size, throughput, total latency, and first-token latency. The component ablation shows that cache, tree structure, scheduling, frontend parallelism, and frontend hints all matter.

Figure 8 is the best evidence for the system design.

The left two plots show that as cache hit rate increases:

  • batch size increases;
  • throughput increases;
  • total latency decreases;
  • first-token latency decreases.

That aligns with the cost model: fewer prefill tokens mean less compute and memory pressure, which allows larger batches.

The right plot is more interesting. Disabling different components hurts different workloads:

  • No cache removes the main prefill reuse benefit.
  • No tree structure weakens multi-level sharing.
  • FCFS or random scheduling loses locality and cache-hit rate.
  • No frontend parallelism loses parallel branches inside one program.
  • No frontend hint makes runtime matching and scheduling less effective.

This ablation supports the paper’s central claim: the frontend and runtime must be designed together. A backend-only prefix cache helps, but it does not recover the full effect.

The overhead result is also important. On a ShareGPT benchmark without KV-cache reuse opportunities, the paper reports 74.3 seconds for 100 requests, with only 0.2 seconds spent managing RadixAttention data structures. That is less than 0.3% overhead. This justifies turning RadixAttention on by default, at least for the evaluated implementation.

Compiler Mode

The main paper uses interpreter mode, but the appendix also discusses compiler mode. SGLang can trace a program into an intermediate representation with streams, nodes, and dependencies.

Figure 14. An SGLang program and its corresponding dataflow graph. The graph exposes streams, constants, generated values, and synchronization dependencies.

This is conceptually important even if the paper’s main results are interpreter-based. Once the program becomes an IR graph, the system can apply compiler-like transformations:

  • reduce interpreter overhead;
  • serialize programs;
  • schedule streams more aggressively;
  • move code to increase prefix sharing;
  • plan memory and execution statically.

The paper’s code-movement case study is deliberately aggressive. It asks GPT-4 to reorder natural-language prompt components to increase the constant prefix length. On 15 test templates, GPT-4 successfully rewrote 12 without changing semantics by manual inspection, increasing shareable prefix length by 60 tokens on average.

I would treat this as a research direction, not a production-safe transformation. Natural-language code motion can silently change meaning. But the idea is valuable: once prompts are represented as a graph, prompt layout becomes an optimization target.

How SGLang Fits With vLLM, FlashInfer, And Mooncake

I would place these systems at different levels of the serving stack:

System Main abstraction What it optimizes
vLLM / PagedAttention KV blocks inside a worker memory fragmentation, continuous batching, copy-on-write
SGLang / RadixAttention structured LM programs and prefix trees prefix reuse across calls, branch parallelism, constrained decoding
FlashInfer serving attention kernels irregular KV layouts, dynamic scheduling, JIT variants
Mooncake distributed KV-cache lifecycle prefill/decode disaggregation, KV movement, SLO-aware scheduling

SGLang is closest to vLLM in implementation space, but its conceptual level is higher. It asks: what if the runtime sees program structure before it sees token tensors?

The systems are complementary:

  • SGLang can use paged KV memory layouts.
  • FlashInfer can accelerate the irregular attention shapes produced by SGLang.
  • Mooncake can extend KV-cache-aware thinking to cluster-level placement and transfer.

The throughline is that KV cache has become a first-class serving object. PagedAttention manages it as pages, SGLang manages it as a reusable prefix tree, FlashInfer consumes it through layout-aware kernels, and Mooncake schedules it as distributed state.

What I Would Measure In A Reproduction

A normal tokens-per-second benchmark is not enough for this paper. I would reproduce SGLang with metrics that separate the mechanisms:

  1. Prefix cache hit rate: measured in prompt tokens, not request count.
  2. Saved prefill tokens: compare naive prompt tokens with actually computed prompt suffix tokens.
  3. First-token latency: should improve when prefill is saved.
  4. Inter-token latency: should not regress from extra cache management.
  5. Effective batch size: cache reuse should allow larger batches under the same memory budget.
  6. KV memory occupancy: split active-request KV and cached reusable KV.
  7. Eviction rate: high hit rate with excessive eviction may still create instability.
  8. Tree operation overhead: CPU-side match, split, insert, ref-count, and eviction time.
  9. Fairness and tail latency: cache-aware scheduling can starve cold-prefix requests.
  10. Frontend contribution: compare full SGLang, no frontend parallelism, no frontend hints, and backend-only prefix caching.
  11. Constrained-decoding speed: separate FSM preprocessing cost from per-token decode cost.
  12. Correctness under regex: verify tokenization edge cases and probability behavior.

The workload suite should include both high-reuse and low-reuse cases. Otherwise the benchmark only proves that prefix caching helps when prefixes repeat, which is true but incomplete. The more interesting question is whether the runtime can detect reuse, exploit it without harming unrelated traffic, and keep overhead low when reuse is absent.

Limitations

SGLang is strong, but its assumptions matter.

First, RadixAttention helps most when prompts share exact prefixes. It does not help semantically similar prompts unless the token prefix is identical. The paper mentions fuzzy semantic matching as future work, but that would be a different correctness/performance tradeoff.

Second, cache-aware scheduling can conflict with fairness. A hot prefix group may keep getting priority, while cold-prefix requests wait. This is not a small issue in user-facing services. A production scheduler needs aging, SLO constraints, or admission control around the prefix-locality objective.

Third, memory pressure can erase cache benefits. Cached tokens and active requests share the pool. Under high load, cached prefixes may be evicted to admit larger active batches. That is the right behavior, but it means the speedup depends on workload shape and memory headroom.

Fourth, compressed FSM decoding is not free from modeling caveats. Regex constraints live at a string level; LLMs decode tokens. Retokenization and probability distortion are real edge cases.

Fifth, API speculative execution is heuristic. It can reduce API cost when templates are predictable, but if the model deviates from the assumed structure, the system must fall back or validate carefully.

Sixth, compiler-mode prompt rewriting is risky. Moving natural-language text can change semantics in ways a traditional compiler would not allow. The paper frames it as a case study, and I think that is the right level of confidence.

Finally, distributed prefix caching opens consistency and placement questions. The appendix discusses a weakly consistent meta-tree for data parallelism, but the full production design space includes replication, eviction propagation, worker failure, privacy isolation, and cross-node KV movement.

Takeaway

SGLang’s core contribution is the connection between a structured frontend and an optimized runtime. The frontend primitives expose where a program branches, synchronizes, reuses context, and constrains outputs. The backend uses that information to reuse KV cache, schedule for prefix locality, run branches in parallel, and skip deterministic constrained-decoding steps.

The paper’s practical message is:

  • do not submit structured LLM workflows as unrelated strings if you want the serving stack to optimize them;
  • exact prefix reuse is a runtime resource, not just an application convenience;
  • a tree-structured cache is a better fit than a flat cache for agents, self-consistency, multi-turn chat, and tree search;
  • constrained decoding should exploit deterministic spans, not only mask one token at a time;
  • frontend/runtime co-design can matter as much as a faster kernel.

For me, SGLang is the missing middle layer between prompt programming and serving infrastructure. It is above PagedAttention-style memory management and below high-level agent frameworks. That is exactly where many real LLM applications now live: not one prompt, not a full distributed service by itself, but a structured program whose execution shape is rich enough to optimize.
