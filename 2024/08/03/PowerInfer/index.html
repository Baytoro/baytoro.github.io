PowerInfer: Fast LLM Serving on a Consumer GPU

H.J. Chen
  2024-08-03 2024-08-03 Created  
  • Paper Reading 
 
  • LLM 
  • | Inference 
  • | Serving 

Song et al. PowerInfer: Fast Large Language Model Serving with a Consumer-grade GPU. SOSP 2024.

Paper: PowerInfer: Fast Large Language Model Serving with a Consumer-grade GPU

PowerInfer is a local LLM serving paper. It is not trying to beat datacenter serving systems under large batches. It asks a narrower and very practical question:

If the model is too large for a single consumer GPU, can we use CPU memory without making every token wait on CPU-GPU weight transfer?

The paper’s answer is to exploit activation locality. A small subset of MLP neurons is activated frequently across inputs. PowerInfer treats these as hot neurons and keeps them on the GPU. The remaining cold neurons stay in CPU memory and are computed on the CPU only when an online predictor says they are needed.

This is different from quantization and different from layer-level offloading. Quantization shrinks all weights. Layer offloading moves whole Transformer layers between GPU and CPU. PowerInfer instead works at neuron granularity inside layers.

The Local Serving Problem

Consumer GPUs have much less memory than datacenter GPUs. An RTX 4090 has 24 GB of VRAM. That is large for games, but not large enough for many FP16 LLMs, and still tight for some quantized large models once runtime buffers are included.

The naive offloading solution is simple: keep part of the model in CPU memory and move weights to GPU when needed. The problem is that autoregressive decoding runs the full model for every generated token. If a token step repeatedly transfers large weights over PCIe, latency becomes dominated by data movement.

PowerInfer’s key claim is that LLM inference has enough neuron-level locality to use the GPU as a hot-neuron cache and the CPU as a cold-neuron executor.

What Is A Neuron Here?

The paper defines a neuron as a row or column in a weight matrix. In an MLP block, the simplified shape is:

For ReLU-style activations, many entries of are zero or near-zero for a given token. If an intermediate activation entry is inactive, the corresponding work in the following projection can be skipped.

Figure 1 shows this at the MLP level. The activation function gates FC1 outputs, and only the activated rows or columns contribute to the FC2 computation.

The paper reports substantial MLP sparsity even outside pure ReLU models.

Table 1 is the quick motivation:

Model Activation Reported MLP sparsity
OPT-30B ReLU 97%
LLaMA2-13B SwiGLU 43%
Yi-34B SwiGLU 53%

For ReLU-based models, sparsity means zero activation. For SwiGLU-based models, the paper measures the proportion of neurons that can be dynamically pruned with less than 1% perplexity impact. That distinction matters: PowerInfer is strongest on ReLU-family models, but the authors also test lower-sparsity non-ReLU settings.

Why Existing Offloading Is Slow

The paper separates two common approaches.

GPU-centric offloading stores overflow parameters in CPU memory, then transfers needed weights to GPU at runtime. This can make a large model fit, but every token can pay PCIe transfer cost.

Hybrid CPU-GPU offloading splits layers between CPU and GPU. This reduces transfer volume, but it gives the CPU too much compute when the GPU cannot hold enough of the model.

Figure 3 shows the failure on OPT-30B with an RTX 4090. FlexGen and DejaVu with unified memory are dominated by CPU-GPU movement. The paper states that more than 99.5% of FlexGen processing time is spent transferring LLM weights from CPU to GPU. The llama.cpp-style hybrid path avoids much of that transfer, but for OPT-30B on a 24 GB 4090 only about 37% of the model is on GPU, and the CPU ends up handling most of the computation time.

PowerInfer is trying to get the best of both:

  • Keep the most frequently useful weights in GPU memory.
  • Avoid moving cold weights to GPU for each token.
  • Compute cold activated neurons directly on CPU.
  • Skip inactive neurons entirely.

Insight 1: Power-Law Activation

The central observation is not only “activations are sparse.” It is that activation frequency is highly skewed.

Figure 4 profiles about 1M tokens from Wikipedia. In one MLP block, the paper reports that 26% of OPT-30B neurons, 43% of LLaMA2-ReGLU-70B neurons, and 69% of LLaMA2-SwiGLU-70B neurons account for 80% of activations. Across the entire model, the corresponding proportions are 17%, 26%, and 75%.

This is the hot/cold split:

Group Meaning Placement intuition
Hot neurons Frequently activated across many inputs Keep on GPU
Cold neurons Input-dependent and less frequently activated Keep on CPU, compute only when predicted active

The split is useful only if it is stable across tasks. The paper checks that too.

Figure 5 shows OPT-30B activation frequency by layer and across tasks. The paper reports more than 90% overlap in the top 20% most frequently activated neurons across the profiled downstream domains. That is the key evidence behind the offline placement step. If the hot set changed completely between tasks, static placement would be fragile.

Insight 2: CPU Computation Can Beat Weight Transfer

If a cold activated neuron lives in CPU memory, there are two options:

  1. Load the neuron’s weights to GPU and compute there.
  2. Compute the neuron directly on CPU and transfer only the result.

For small local-serving batches, PowerInfer chooses the second path.

Figure 6 compares load-then-execute with direct CPU execution for OPT-30B. For batch sizes under 32, direct CPU computation is faster than transferring those weights to the RTX 4090 and computing on GPU. This is the second reason the design is neuron-level rather than layer-level: the CPU should not own whole layers, but it can handle a small set of cold activated neurons.

System Overview

PowerInfer has an offline part and an online part.

The offline part profiles activation statistics, classifies neurons as hot or cold, trains adaptive activation predictors, and solves a placement problem under GPU memory and bandwidth constraints. The online part loads the selected hot neurons on GPU, keeps cold neurons on CPU, predicts active neurons per input, and runs GPU and CPU work concurrently.

The high-level workflow is:

The model is still the same model. PowerInfer is changing the runtime path, not replacing the LLM with a smaller model.

Single-Layer Execution

The single-layer example is the easiest way to understand the runtime.

In the example, neurons 3, 5, and 7 are classified as hot offline and are stored on GPU. At runtime, the predictor says neurons 3, 4, and 5 are active. The GPU computes 3 and 5. The CPU computes 4. Neuron 7 is hot but predicted inactive, so it is skipped. After CPU computation finishes, its output is transferred to GPU and merged with the GPU result.

This is why PowerInfer needs three pieces to work together:

  • The offline hot/cold split controls memory placement.
  • The online predictor controls which neurons are computed for a particular token.
  • The hybrid executor overlaps CPU and GPU work and merges partial results.

If any piece is weak, the design loses its advantage. A bad predictor computes too much or misses useful neurons. A bad placement policy leaves hot work on CPU. A bad executor spends the saved compute on synchronization.

Adaptive Predictors

PowerInfer inherits the idea of activation predictors from DejaVu, but local deployment changes the predictor budget. Fixed-size predictors can be too large. The paper gives a concrete example: predictors for OPT-175B would require around 27 GB of GPU memory, more than an RTX 4090 has.

The paper’s solution is to size predictors according to layer sparsity and skewness. Sparse, highly skewed layers need smaller predictors because the active set is easier to identify. Dense or less skewed layers need larger predictors.

Figure 9 shows the relationship for OPT-175B at a guaranteed 95% predictor accuracy level. Higher sparsity generally permits smaller predictors, while the error bars reflect skewness differences inside layers.

Later, the evaluation reports predictor sizes for several models.

The predictor ratio is not free, but it is bounded. The paper reports that predictor parameters are about 7.09% of model weights on average, and predictor execution contributes less than 10% of total inference time.

Placement Policy

The placement policy is more subtle than “put the hottest neurons on GPU.”

The GPU has limited memory and high bandwidth. The CPU has more memory and lower compute throughput. PCIe transfer is expensive. A placement policy therefore needs to balance:

Factor Why it matters
Activation frequency Hot neurons are likely to be used often
Neuron impact Some neurons matter more to model output
GPU memory capacity The hot set cannot exceed available VRAM
CPU-GPU transfer Too much split work can create communication overhead
Layer structure Partial placement inside a layer must still be executable efficiently

The paper formulates this as an integer linear programming problem. The objective is to maximize the impact of neurons placed on GPU while satisfying memory and communication constraints. That offline solver is what turns the activation profile into an actual memory layout.

The practical reading: PowerInfer is a cache placement system for neurons, but the cache item is not only chosen by frequency. It also needs to respect layer-level execution cost.

Neuron-Aware Operators

Normal sparse kernels are not automatically a good fit here. The sparsity is dynamic, neuron-granular, and split across CPU and GPU. Converting dense matrices into generic sparse formats at runtime can erase the win.

PowerInfer implements neuron-aware operators that directly compute activated neurons and their weights. On GPU, the operator maps individual activated neurons to thread blocks. On CPU, the operator assigns activated neuron work to available CPU cores.

Figure 16 compares PowerInfer’s operators with dense computation, PyTorch sparse on CPU, and PIT on GPU. The CPU result is the most striking: PyTorch sparse does not beat dense computation until sparsity is above 87%, while PowerInfer’s CPU operator beats dense even below 10% sparsity. On GPU, PowerInfer is close to PIT, but PowerInfer’s advantage is that the same framework supports hybrid CPU-GPU execution.

Evaluation Setup

The evaluation uses two local PC configurations.

Setup CPU Host memory GPU PCIe
PC-High Intel i9-13900K, eight 5.4 GHz cores 192 GB, 67.2 GB/s RTX 4090, 24 GB PCIe 4.0, 64 GB/s
PC-Low Intel i7-12700K, eight 4.9 GHz cores 64 GB, 38.4 GB/s RTX 2080Ti, 11 GB PCIe 3.0, 32 GB/s

The tested models cover ReLU, ReGLU, SwiGLU, and dReLU variants.

Table 3 is useful because it explains the result spread. OPT and Falcon are highly sparse. LLaMA2-ReGLU is less sparse but still favorable. SwiGLU models have lower sparsity, so PowerInfer still helps but with smaller speedups.

The baselines are llama.cpp and SpecInfer. The paper also analyzes FlexGen and DejaVu earlier, but they are not the main end-to-end baselines because their latency is poor in this local, batch-small setting.

FP16 Results

The main FP16 result is batch size 1 generation speed, which matches the local interactive setting better than a throughput-oriented server benchmark.

On PC-High with RTX 4090, the paper reports an average PowerInfer generation speed of 8.32 tokens/s and a peak of 16.06 tokens/s. It reports average speedups of 7.23x over llama.cpp and 6.19x over SpecInfer, with Falcon-40B reaching up to 11.69x over llama.cpp.

On PC-Low with RTX 2080Ti, PowerInfer still improves performance, but the margin is smaller because the 11 GB GPU can host fewer hot neurons. The paper reports average speedups of 4.71x over llama.cpp and 5.97x over SpecInfer, with peaks of 7.06x and 7.47x.

This is a useful boundary condition. PowerInfer benefits from GPU memory even though it is designed for limited VRAM. If the GPU is too small relative to the model, more hot neurons spill to CPU and the CPU becomes the bottleneck.

Where The Work Runs

Figure 12 explains why PowerInfer is faster than layer-level hybrid offloading.

The paper defines neuron load as the proportion of activated neuron computations executed by each device. On PC-High, PowerInfer increases the GPU’s share from about 20% in llama.cpp to about 70%. This is the runtime effect of hot-neuron placement: the GPU gets the common work even though the whole model does not fit in VRAM.

On PC-Low, the GPU share can fall. The paper gives the example of running a roughly 60 GB model on an 11 GB RTX 2080Ti, where the GPU handles about 42% of the neuron load because it cannot hold enough hot neurons.

Long Input And INT4

Long prompts change the behavior. During prefill, many tokens are processed together, and their combined active-neuron set is less sparse. PowerInfer switches to dense GPU computation in prefill, then uses sparse hybrid execution during generation.

For 1.5K input length and 256 output length on PC-High, the paper still reports 3.47x to 5.69x speedup over llama.cpp. This is not as clean as single-token decode, but it shows that the system is not only a short-prompt trick.

The paper also evaluates INT4 models.

With INT4 quantization, PC-High reaches 13.20 tokens/s on average and 29.08 tokens/s at peak. The average speedup over llama.cpp is 2.89x, with a maximum of 4.28x. On PC-Low, the average speedup is 5.01x and the peak is 8.00x. The OPT-175B result is especially interesting: PowerInfer nearly reaches 2 tokens/s on PC-High and is 2.66x faster than llama.cpp.

Quantization and PowerInfer are complementary. Quantization reduces the memory footprint of every weight. PowerInfer changes where and whether neuron computations happen.

Batching Boundary

PowerInfer is aimed at small-batch local serving. The batch-size result makes that explicit.

On Falcon-40B with PC-High, the paper reports strong speedups when batch size is below 32, with an average 6.08x improvement over llama.cpp. At batch size 32, PowerInfer still reports 4.38x speedup, but the ratio declines as batch size grows.

The reason is joint activation. With more requests in a batch, the union of active neurons grows. Eventually the batch activates enough of the model that sparsity is less useful. This is why PowerInfer should not be read as a replacement for high-throughput datacenter batching systems. It is a local, latency-sensitive path.

Ablation

The ablation separates three ideas:

  1. +PO: add predictors and neuron-aware operators, but keep layer-wise execution.
  2. +Engine: allow GPU and CPU to process neurons from the same layer concurrently.
  3. +Policy: add the optimized placement policy from the offline solver.

The paper reports:

Variant Bamboo-7B speedup Falcon-40B speedup
+PO 1.87x 3.32x
+Engine 2.60x 7.80x
+Policy 3.62x 11.69x

The large jump from +PO to +Engine shows that neuron sparsity alone is not enough. The runtime must split work inside a layer so the GPU and CPU are both useful. The final jump from +Engine to +Policy shows that random neuron placement wastes GPU memory and creates bad communication patterns.

Predictor Overhead And Accuracy

Prediction is not free, but it is small enough in the measured setting.

Figure 17 shows predictor overhead on PC-Low. The paper reports that online predictor execution is less than 10% of total inference time on average. This matters because a perfect sparsity plan would be useless if the predictor cost were comparable to the skipped MLP work.

The paper also evaluates model accuracy after using predictors. The short version is that the reported benchmark averages remain close to the original models. This does not mean misprediction is harmless. It means the missed neurons tend to have small contribution in the evaluated tasks, and the predictors were sized to keep perplexity close to baseline.

RTX 4090 Versus A100

The headline comparison is not “4090 beats A100.” It is more careful: PowerInfer narrows the gap between a local consumer GPU setup and a server GPU that can hold the whole model.

The paper compares PowerInfer on RTX 4090 with vLLM on an 80 GB A100 for OPT-30B and Falcon-40B. With input length 1, llama.cpp on 4090 is 93% and 92% slower than vLLM on A100, while PowerInfer reduces the gap to 18% and 23%. With input length 64, PowerInfer reduces the gap to 28% and 29%.

This result is the strongest systems message in the paper. The 4090 does not magically become an A100. The CPU still becomes a bottleneck in some cases. But neuron-level locality makes the consumer-GPU setup much closer than layer offloading can.

What I Would Check In A Reproduction

For a real reproduction, I would measure these items separately:

Measurement Why it matters
Per-layer activation sparsity Decides whether PowerInfer is applicable
Hot-neuron overlap across tasks Tests whether offline placement generalizes
Predictor false negatives Missed active neurons can hurt accuracy
Predictor runtime and memory Predictor overhead can consume the saved budget
GPU/CPU neuron load split Shows whether the GPU is actually doing the common work
PCIe transfer volume Verifies that the system is not secretly transfer-bound
Prefill versus decode latency Sparsity is much cleaner during token-by-token generation
Batch size sweep Finds where joint activation destroys sparsity

The most important test is distribution shift. If a new workload activates a different hot set, an offline policy from Wikipedia may be less effective. The paper’s task-overlap result is encouraging, but a deployment should still profile on representative prompts.

Limitations

PowerInfer has clear boundaries:

  • It works best when MLP activation sparsity is high. ReLU-family models are the best fit.
  • Larger batches reduce the advantage because the union of active neurons grows.
  • Long prefill is less sparse than single-token decode, so the generation phase carries most of the win.
  • The system needs an offline profiling, predictor training, and placement step per model.
  • Predictor errors are acceptable only if missed neurons have low output impact.
  • CPU execution can become the bottleneck when the GPU cannot host enough hot neurons.
  • The design is more complex than quantization or simple layer offloading.

The paper is therefore not a universal serving recipe. It is a strong design for one important corner: large-model, low-latency, small-batch inference on a local machine with limited GPU memory and enough CPU memory.

Takeaway

PowerInfer reframes local LLM serving as a locality problem. Instead of asking only “how do I make the model smaller?”, it asks:

Which parts of the model are usually needed for the next token, and where should those parts live?

That makes the paper complementary to quantization, KV-cache paging, and speculative decoding. PowerInfer’s useful lesson is that activation sparsity is not only an arithmetic shortcut. When the hot set is stable, it becomes a memory-placement primitive.
