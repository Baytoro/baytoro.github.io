DeepSeek-AI. DeepSeek-V2: A Strong, Economical, and Efficient Mixture-of-Experts Language Model.

Paper

DeepSeek-V2 is not just a bigger MoE model. The paper is useful because it treats model architecture as an inference and training economics problem. The two central choices are Multi-head Latent Attention (MLA), which attacks the KV-cache bottleneck during decoding, and DeepSeekMoE, which keeps the activated compute small while keeping total capacity high.

The main numbers are already enough to explain why the report mattered: 236B total parameters, 21B activated parameters per token, 8.1T pre-training tokens, a context window extended to 128K, 93.3% KV-cache reduction compared with DeepSeek 67B, and up to 5.76x maximum generation throughput in the reported setup.

Figure 1 is the paper’s compact claim: DeepSeek-V2 moves the MMLU frontier among open models while reducing the training cost, KV cache, and generation bottleneck relative to DeepSeek 67B. The architecture is therefore best read from the serving path backward: what has to be cached, communicated, routed, and trained?

The dense baseline view of an LLM usually starts from parameter count. DeepSeek-V2 makes a different trade: keep only a small set of experts active, and make the attention cache much smaller. This is why the model can have 236B total parameters but still activate only 21B parameters per token.

The full architecture figure shows both pieces together. MLA changes the attention block by compressing the KV state into a latent vector. DeepSeekMoE changes the FFN block by mixing always-active shared experts with top-k routed experts.

Routing Boundaries

Fine-grained experts improve specialization, but they also make communication expensive under expert parallelism. If the top-k selected experts are spread across many devices, each token triggers more cross-device communication.

DeepSeek-V2 therefore uses device-limited routing. For each token, it first chooses at most devices whose resident experts have the highest affinity scores, then performs top-k expert selection only inside those devices. The paper uses . Results

On base model benchmarks, DeepSeek-V2 is compared against DeepSeek 67B, Qwen1.5 72B, Mixtral 8x22B, and LLaMA 3 70B. The interesting point is not that it wins every row. The interesting point is that it is an MoE model with 21B activated parameters per token competing against strong dense and MoE baselines while also reducing KV-cache cost.

The chat tables show a second axis: DeepSeek-V2-Chat and DeepSeek-V2-Chat-RL are evaluated against open-source and closed-source systems, including GPT-4 variants and Claude models. The paper’s own warning is worth remembering: some closed-source results may be underestimated due to limitations of the internal evaluation framework, so I would not over-read small differences. The broad trend is still useful: the architecture is not only a pre-training trick; the chat model is competitive after supervised fine-tuning and RL.

The appendix ablations are the most diagnostic part for MLA. The MQA/GQA/MHA comparison shows that simply reducing KV heads can hurt capability, while MLA keeps a much smaller cache and remains strong. The paper also compares small and large MoE models with MLA and MHA; the point is that MLA is not only a memory optimization but can also be accuracy-neutral or accuracy-positive in their setting.

The code evaluation plot shows DeepSeek-V2-Chat-RL near LLaMA3-70B-Chat and below stronger closed models on HumanEval and LiveCodeBench. I would read this figure as a boundary condition: V2’s architecture gives an efficient model family, but post-training and reasoning data still matter a lot for code and difficult reasoning.

Takeaways

My main takeaway from DeepSeek-V2 is that the paper puts cache design and expert communication into the model architecture itself. MLA reduces the object that must be cached during autoregressive decoding:

DeepSeekMoE reduces activated FFN compute while preserving large total capacity:

Those two choices attack different bottlenecks. MLA helps long-context and high-batch decoding by shrinking memory pressure. MoE helps scaling by separating total capacity from activated compute. Device-limited routing and balance losses then make the MoE trainable on actual hardware rather than just elegant on paper.

The limitation is that V2 still relies on auxiliary load-balancing losses, token dropping during training, and a non-trivial hand-designed routing/communication stack. DeepSeek-V3 keeps the same direction but replaces some of this with auxiliary-loss-free balancing, FP8 training, DualPipe, and MTP, which makes V2 a useful bridge between efficient MoE architecture and full-stack LLM training systems.
