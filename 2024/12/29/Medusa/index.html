Medusa: LLM Inference with Multiple Decoding Heads

H.J. Chen
  2024-12-29 2024-12-29 Created  
  • Paper Reading 
 
  • LLM 
  • | Inference 

Cai T, Li Y, Geng Z, Peng H, Lee J D, Chen D, Dao T. Medusa: Simple LLM Inference Acceleration Framework with Multiple Decoding Heads. ICML 2024.

  • Paper: arXiv PDF
  • Code: FasterDecoding/Medusa

Medusa is an inference acceleration paper that is easy to summarize incorrectly. The superficial summary is “add extra heads and decode more tokens.” The more useful reading is: Medusa replaces the separate draft model in speculative decoding with a set of cheap, target-model-attached heads, then spends one target-model forward pass on a tree of candidate continuations instead of one linear draft.

That design is aimed at a very specific bottleneck. During autoregressive decoding, a large model usually emits one token per expensive forward pass. The pass is often memory-bandwidth-bound: every step streams a large amount of model weight data, but only processes a tiny amount of new-token work. Medusa tries to make each pass advance by more than one token while keeping the serving stack simpler than a two-model speculative decoding system.

The paper is also more systems-flavored than the title suggests. The final speedup depends on three interacting quantities:

Acceleration rate is the number of accepted tokens per decoding step. Overhead is how much slower each Medusa step is than a vanilla decode step. The method wins only when the candidate tree increases accepted length more than it increases per-step work.

One-Pass Overview

Figure cropped from the paper PDF: Medusa adds several heads on top of the target LLM hidden state, produces multiple top-k future-token predictions, and verifies a candidate continuation before moving to the next decoding step.

The pipeline has three phases, similar to speculative decoding:

  1. Generate candidates.
  2. Process those candidates with the target model.
  3. Accept a prefix and append it to the sequence.

The difference is where candidates come from. Standard speculative decoding uses a small draft model. Medusa uses the target model’s own last hidden state. If the base model has hidden state at the current position, the original LM head predicts token , while Medusa head predicts token .

The paper uses a small residual MLP per head:

The initialization is practical: starts from the original LM head and starts at zero. At initialization, each Medusa head behaves like the original next-token head applied to the same hidden state. Training then specializes head 1 toward the next-next token, head 2 toward the token after that, and so on.

This is a nice engineering compromise. The heads are much cheaper than a separate draft LLM, and they live inside the same model checkpoint. There is no separate model-parallel plan, no second KV cache, and no draft model whose tokenizer or distribution needs to be aligned with the target model.

Why Separate Draft Models Are Annoying

Speculative decoding is attractive because it can be exact under the right rejection-sampling procedure. A draft model proposes several tokens, and the target model verifies them in parallel. If the draft tokens agree with the target distribution, the system can accept several tokens per target forward pass.

The deployment pain is the draft model:

Problem Why it matters
Draft quality A tiny model is fast but often rejected. A stronger draft model is slower and harder to serve.
Distribution mismatch The draft may propose text that looks reasonable but is not likely under the target model.
Serving complexity Two models mean two sets of weights, potentially two parallelism plans, and more scheduling logic.
Distributed inference Keeping a draft model synchronized with a sharded target model is not free.

Medusa’s answer is not to make a better standalone draft model. It says: use the target model’s representation as the draft source. The target model still verifies candidates, but the proposal machinery is attached to the same forward pass and can be trained with the model.

That is why the method is appealing for local or single-user serving. The paper primarily evaluates batch size 1, which matches local chat or latency-oriented serving better than high-throughput cloud batching.

Medusa Heads

Each Medusa head predicts a different future offset. With heads, one decoding position can produce distributions for:

The important limitation is that these heads are not autoregressive inside the draft. Head 3 does not first consume the token proposed by head 1 and head 2. It predicts from the same current hidden state. This makes the heads cheap and parallel, but it also means later heads face a harder, more uncertain prediction task.

The loss reflects this:

$$
\mathcal{L}{\mathrm{Medusa-1}}
= \sum{k=1}^{K} -\lambda_k \log p_t^{(k)}(y_{t+k+1}).
$$

The paper sets to a decaying weight such as because farther future positions are harder. In the shared experiment settings, they train five one-layer Medusa heads. During inference, they may only use three or four if the optimized tree does not need all of them.

My read: five heads is not a magic number. It is a reasonable ceiling for this design because independent future-token prediction gets worse as the offset grows. If the later heads are low quality, they add branches that cost verification time without improving accepted length.

Tree Attention

Tree attention mask from the paper: each candidate node can attend to the prompt and its own ancestors, but not to sibling branches that belong to incompatible continuations.

Using only one candidate chain wastes information. Each head can output several plausible tokens. If head 1 has top-2 candidates and head 2 has top-3 candidates, the Cartesian product gives six two-token continuations. Verifying those one by one would be useless, but verifying them as a tree lets shared prefixes reuse work.

new candidate nodes, excluding the virtual root. This can grow quickly, so the tree size is a real serving parameter, not a decorative detail.

Tree attention changes the attention mask. In ordinary causal decoding, token positions form one linear sequence. In Medusa, candidate nodes form multiple possible futures. A node should see:

  • the original prompt and generated prefix,
  • its own ancestors in the candidate tree,
  • not its siblings,
  • not nodes from branches that would imply a different previous token.

The paper also adjusts positional indices so the target model evaluates a branch as if it were a normal continuation. After this forward pass, the target model has logits for many candidate positions, and Medusa can choose the longest acceptable prefix.

A serving implementation has to be careful here. It is not enough to concatenate all candidates into a batch and call the model. The attention mask and position IDs encode the candidate tree, and after acceptance the runtime must collapse the verified tree back into one linear accepted sequence.

Candidate Tree Size

Tree-size ablation from the paper: larger candidate trees can increase acceleration rate, but the per-step token/s can decline once the tree becomes too large.

This figure is the most useful warning in the paper. More candidates are not automatically better. A bigger tree increases the chance of finding a longer accepted prefix, but it also increases linear-layer and attention work in the verification pass.

The left plot shows acceleration rate increasing with more candidate tokens. The right plot shows actual token/s eventually dropping as the tree grows. The optimized sparse tree at 64 nodes beats larger dense trees because it spends candidate budget on likely branches instead of expanding every combination mechanically.

The sparse tree is built from calibration statistics. For each Medusa head, the method estimates the accuracy of each top-ranked prediction. If the -th top prediction of head has accuracy , a candidate path can be scored by multiplying the per-node accuracies under an independence approximation. Nodes are then added greedily to maximize expected accepted length under a fixed tree-node budget.

This is a small but important point. Medusa is not only “attach heads.” The tree policy is part of the speedup.

Acceptance

There are two acceptance modes to keep separate.

For greedy decoding, acceptance is straightforward. The target model verifies the candidate tree, and Medusa accepts the longest prefix whose tokens match the target model’s greedy choices. If the first candidate token fails, the system can still fall back to the target model’s own next token, so decoding always advances.

For sampling, exact speculative decoding usually uses rejection sampling to preserve the target distribution. Medusa can use that too, but the paper argues that rejection sampling becomes less efficient at nonzero temperature. Even if the draft and target distributions were identical, independent sampling can reject tokens.

Medusa therefore proposes typical acceptance. Instead of insisting on exact distribution matching, it accepts a candidate token when the original model assigns it enough probability:

$$
p_{\mathrm{original}}(x_{n+k} \mid x_1,\ldots,x_{n+k-1})

\min(\epsilon,\ \delta \exp(-H(p_{\mathrm{original}}(\cdot \mid x_1,\ldots,x_{n+k-1})))).
$$

The entropy term matters. When the target model distribution is high entropy, more continuations are plausible. When it is sharp, the threshold becomes stricter. The first token is handled with greedy decoding to guarantee progress, while later tokens use the typical-acceptance criterion.

Typical acceptance ablation from the paper: raising the posterior threshold trades acceleration rate for MT-Bench score under non-greedy generation.

I would describe typical acceptance as a quality-preserving heuristic, not a lossless sampler. The paper’s Appendix A explicitly relaxes exact correspondence with the language-model distribution. That is a reasonable systems tradeoff for chat serving, but it should not be confused with exact speculative sampling when distribution preservation is required.

Medusa-1

Medusa-1 freezes the backbone LLM and trains only the added heads. The backbone hidden states are used as features, but the base model parameters do not change.

This has several good properties:

  • It is the easiest way to add Medusa to an existing model.
  • The original next-token model is not fine-tuned, so its base behavior is not damaged by training the heads.
  • Training memory can be reduced with a quantized backbone, similar in spirit to QLoRA-style setups.
  • The paper reports a few hours of training for Vicuna-7B on a single A100 PCIe GPU using 60k ShareGPT samples.

The downside is head accuracy. The frozen backbone was not trained to make future-token prediction easy from the current last hidden state. Medusa-1 can work, but the heads have to live with the representation they are given.

Medusa-2

Medusa-2 jointly trains the Medusa heads and the backbone. This gives the heads a better representation to use, but it introduces the risk of degrading the base model.

The paper’s recipe has three pieces:

  1. Add the ordinary next-token language-model loss back into training.
  2. Use a larger learning rate for the new heads than for the backbone.
  3. Warm up the heads before letting their gradients affect the backbone strongly.

The joint loss is:

$$
\mathcal{L}{\mathrm{Medusa-2}}
= \mathcal{L}{\mathrm{LM}} + \lambda_0 \mathcal{L}_{\mathrm{Medusa-1}}.
$$

The engineering reason is simple. At the beginning of training, the Medusa heads are bad, and their losses can be large. If those gradients immediately update the backbone, they can distort the model’s original next-token behavior. A two-stage or warmup recipe lets the heads become useful before co-adapting the model.

The shared settings in the appendix are also useful implementation hints: five one-layer heads, 8-bit AdamW, cosine schedule with warmup, LoRA or QLoRA for Medusa-2, head learning rate four times the backbone learning rate, LoRA rank 32, alpha 16, and dropout 0.05.

Self-Distillation

The paper assumes a training dataset aligned with the target model. For Vicuna-7B and Vicuna-13B, ShareGPT is close to the SFT data. But many released chat models do not expose their instruction-tuning data, and RLHF or DPO-style alignment can shift the output distribution away from the original SFT corpus.

Medusa’s answer is self-distillation:

  1. Start with a public seed prompt dataset from a similar domain.
  2. Ask the target model to generate responses.
  3. Train Medusa heads on that generated dataset.
  4. For Medusa-2, use the original model’s probability distribution as a teacher for the backbone loss.

The LoRA trick is neat. If the backbone is fine-tuned with an adapter, the original model can be recovered by turning the adapter off. That lets the training code get teacher probabilities without keeping a second full model in memory.

This is not free. The paper observes that using generated data alone can hurt quality when training the backbone, which is why the distillation loss is needed. In other words, Medusa-2 is not just “generate synthetic data and fine-tune.” The preservation loss is part of the method.

Main Results

Main MT-Bench result from the paper: on Vicuna-7B and Vicuna-13B, Medusa-1 gives more than 2x speedup, while Medusa-2 reaches 2.83x in this setup. The category-level plot shows higher gains on some tasks, including coding and extraction.

The headline results are clear:

Setting Reported result
Vicuna-7B, Medusa-1 2.18x speedup
Vicuna-7B, Medusa-2 2.83x speedup
Vicuna-13B, Medusa-1 2.33x speedup
Vicuna-13B, Medusa-2 2.83x speedup
Vicuna-7B Medusa-2 by MT-Bench category 2.58x to 3.62x

The category split is interesting. Coding is 3.29x and extraction is 3.62x in the figure. Those tasks often have lower-entropy next-token structure than open-ended roleplay. That matches the intuition that multi-token acceptance is easiest when the next few tokens are predictable.

Model comparison table from the paper: Medusa-2 reports acceleration rate, overhead, MT-Bench quality delta, and wall-time speedup against speculative decoding baselines.

Table 1 separates acceleration rate from overhead. For example, Vicuna-7B has an acceleration rate of 3.47 but an overhead of 1.22, giving a wall-time speedup of 2.83. That distinction is worth keeping in mind when comparing methods. A decoder can accept many tokens per step and still fail to speed up if the step becomes too expensive.

The same table reports Medusa-2 speedups of:

Model Medusa speedup
Vicuna-7B 2.83
Zephyr-7B 2.66
Vicuna-13B 2.83
Vicuna-33B 2.35

The larger and self-distilled cases are not always faster. The paper attributes weaker speedup partly to preserving quality when the true training recipe is unavailable. That is a fair warning: adding Medusa to an arbitrary model depends on how well the heads can learn the target model’s actual output distribution.

What Each Technique Adds

Technique stack from the paper: heads alone help, tree attention helps more, optimized tree construction helps again, and Medusa-2 training gives the largest reported jump in this ablation.

This table is small but useful because it gives a rough decomposition:

Step Effect
Medusa-1 heads without tree attention about 1.5x
Add tree attention about 1.9x
Use optimized tree configuration about 2.2x
Train heads with Medusa-2 about 2.8x

The message is that no single component carries the full method. The heads create future-token proposals, tree attention amortizes target-model verification, tree search spends the candidate budget better, and Medusa-2 improves head accuracy.

Sparse Tree Shape

Sparse tree visualization from the appendix: a 64-node tree with depth 4. The red path shows the accepted future tokens.

The appendix visualization helps explain why a sparse tree beats a dense tree. The tree leans toward high-probability branches instead of spreading budget uniformly. If a top-1 prediction from head 1 is much more reliable than a top-5 prediction from head 3, the tree should reflect that.

For implementation, this suggests a calibration step:

  1. Run the model and Medusa heads on a held-out calibration set.
  2. Measure how often each top-ranked candidate at each head is correct.
  3. Build a fixed sparse tree under a node budget.
  4. Use that tree shape during generation.

The tree can be static once chosen. That keeps runtime logic simple, although later work can make tree construction more dynamic.

AlpacaEval And Generalization

AlpacaEval table from the appendix: Medusa-2 keeps similar acceleration on another dataset, with reported speedups between 2.26x and 3.16x.

The AlpacaEval appendix result is useful because it checks whether MT-Bench is the only favorable case. The reported wall-time speedups are:

Model Base speed Medusa speed Speedup
Vicuna-7B 37.07 tok/s 106.76 tok/s 2.88
Vicuna-13B 29.01 tok/s 91.54 tok/s 3.16
Vicuna-33B 17.87 tok/s 40.43 tok/s 2.26
Zephyr-7B 34.21 tok/s 99.50 tok/s 2.91

These are still batch-size-1 style numbers. I would not transfer them directly to a saturated production server with continuous batching. In that setting, decode may already have better hardware utilization, and the Medusa candidate tree competes with batching for the same compute budget.

Hardware View

Roofline analysis from the appendix: adding candidate tokens moves attention matrix multiplication to higher operational intensity and higher achieved FLOP/s.

The hardware appendix is worth reading because it explains why Medusa can help at all. Vanilla decode processes one new token. Many linear layers and attention operations sit near a memory-bandwidth-bound regime. If Medusa verifies many candidate tokens in one pass, it increases the amount of arithmetic per weight movement.

The paper reports that, for Llama-33B on an A100-80GB PCIe at batch size 16 and sequence length 1024, using 64 candidate tokens gives much higher FLOP/s and operational intensity for attention matrix multiplication than regular decoding. The direction is the point: candidate verification turns a tiny decode step into a wider parallel computation.

But there is a ceiling. If the tree is too large, the step becomes compute-heavy and wall-clock speed drops. If the batch size is already large, the normal decoder may already use the GPU well, leaving less memory-bandwidth slack for Medusa to exploit. This is why the paper’s focus on batch size 1 is not a minor detail.

Implementation Notes

If I were adding Medusa to an inference engine, I would treat these as the non-negotiable pieces:

Component Implementation detail
Checkpoint format Store extra Medusa head weights next to the base model.
Head execution Run Medusa heads from the current final hidden state and collect top-k predictions per head.
Candidate tree Use a static sparse tree or a calibrated tree budget; avoid naive dense expansion unless tiny.
Attention mask Build a tree attention mask so branches cannot see incompatible sibling tokens.
Position IDs Make every branch position look like a valid continuation position to the target model.
Verification Use target-model logits on candidate nodes to decide the accepted prefix.
KV update Append only the accepted linear path to the live sequence state.
Sampling mode Choose between exact rejection sampling and typical acceptance depending on quality requirements.

Two failure modes are easy to miss:

  • If the heads are inaccurate, Medusa can waste target-model work on candidates that are mostly rejected.
  • If the tree is too large, acceleration rate can rise while actual token/s falls.

That makes Medusa more like a calibrated serving optimization than a purely architectural modification.

Comparison With EAGLE

Medusa and EAGLE are close in spirit because both try to improve speculative decoding without relying on an arbitrary small draft LM. The difference is the draft target.

Medusa predicts future tokens directly from the current target hidden state. EAGLE predicts future target-model features and then uses the target LM head to turn those features into token logits. EAGLE’s argument is that hidden features are smoother than discrete token choices, but it has to handle feature uncertainty with shifted token input.

Medusa’s advantage is simplicity. Heads are cheap, static, and easy to attach. Its weakness is that the heads are independent future-token predictors. They do not condition on each other inside the draft. That is exactly the gap later draft-head methods try to address.

My Takeaway

Medusa is a good paper because it turns speculative decoding into an attachable module:

The real insight is not only the heads. The useful system is the combination of lightweight heads, tree verification, calibrated sparse tree construction, and a training recipe that does not ruin the base model.

I would use Medusa when:

  • the workload is latency-oriented or batch size is small,
  • the target model can tolerate an added-head checkpoint format,
  • a small amount of calibration/training data is available,
  • exact sampling distribution is not mandatory, or rejection sampling is acceptable,
  • the serving engine can implement tree attention cleanly.

I would be cautious when:

  • batch size is already high,
  • output quality must match the original sampler exactly under non-greedy decoding,
  • the model’s training data or output distribution is hard to approximate,
  • the inference stack cannot efficiently build custom attention masks and position IDs.

The paper’s reported 2x to 3x range is credible in the setting it studies, but it is not a universal multiplier. The speedup lives in the balance between accepted tokens and verification overhead. Medusa works when the heads are good enough and the tree is small enough.
