AWQ: Activation-Aware Weight Quantization

H.J. Chen
  2024-01-26 2024-01-26 Created  
  • Paper Reading 
 
  • Quantization 
  • | LLM 

Reference

  • Paper: AWQ: Activation-aware Weight Quantization for LLM Compression and Acceleration
  • Code: mit-han-lab/llm-awq

I read the arXiv v6 version. The core of AWQ is not “one more 4-bit quantizer”. The useful observation is more specific: the importance of a weight cannot be decided from the weight value alone. It also depends on the activation channel multiplied by that weight.

That observation has a direct deployment consequence. If we preserve an explicit FP16 outlier path, as in mixed-precision outlier handling, the runtime kernel has to handle both a regular low-bit dense path and an exceptional high-precision path. AWQ takes a more conservative route: keep a regular dense low-bit weight format, and only use activation statistics offline to decide how to scale input channels before quantization.

The paper also ships TinyChat, which is important. AWQ is not presented only as a compression recipe; the authors also show how the resulting W4A16 models run on desktop GPUs, mobile GPUs, ARM CPUs, and edge platforms. The algorithm and the system design are coupled: AWQ is useful for deployment because it preserves a hardware-friendly dense 4-bit weight layout.

One Sentence

AWQ is activation-aware weight-only quantization:

  • activations stay in FP16/BF16 at runtime, not INT4;
  • weights are quantized group-wise to INT3/INT4;
  • calibration activations are used only offline to identify important input channels and search per-channel scales;
  • those scales are folded through equivalent transformations, so the final runtime format remains close to a regular dense W4A16 format.

What I like about the paper is that it does not overcomplicate the problem. There is no training loop, no Hessian solver, and no long layer reconstruction process. AWQ mainly trusts one robust statistic: some activation channels have much larger magnitudes, and the weight columns connected to those channels contribute more to the layer output.

Motivation: Salient Weights Depend on Activations

Figure 2 is the center of the paper. Direct RTN quantization makes OPT-6.7B INT3-g128 perplexity very poor. If 1% salient weights are kept in FP16, perplexity recovers dramatically. The problem is that a mixed FP16/INT3 format is inconvenient for hardware, because the kernel now needs to combine a regular dense low-bit path with an irregular high-precision path.

AWQ’s alternative is not to keep actual FP16 outliers. Instead, it scales up salient channels before quantization. After scaling, the weights on those channels occupy a larger range on the quantization grid, so their relative rounding error becomes smaller. The activation is scaled in the opposite direction, so the floating-point computation remains equivalent.

The key question becomes: which weights are salient?

Table 1 gives the first strong clue:

  • randomly keeping a small fraction of FP16 weights is unstable;
  • selecting weights by weight magnitude or weight norm is not enough;
  • selecting channels by activation magnitude is much more effective, and even 0.1%-1% salient channels can reduce perplexity significantly.

This means “important weights” are not simply large values in the static weight tensor. Importance is input-dependent. A weight column may not look extreme by itself, but if its corresponding activation channel is often large, its quantization error is amplified in the output.

This objective looks like reconstruction, but it is different from GPTQ in spirit. GPTQ uses calibration activations to build an approximate second-order problem, then quantizes weights sequentially with error compensation. AWQ does not run backpropagation and does not invert a Hessian. It searches over a small activation-aware scale family.

AWQ Pipeline

Putting the formulas together, the offline quantization pipeline is roughly:

  1. collect a small number of calibration sequences and run the FP16 model;
  2. cache the input activations for each linear layer;

  4. grid search and form candidate scales ;
  5. for each candidate, evaluate the output gap between and ;
  6. choose the scale with the smallest loss, then apply weight clipping to further reduce group-wise quantization MSE;
  7. store the final weights as group-wise INT3/INT4 and run W4A16 dequantization plus matrix multiplication at inference time.

Why Weight-Only Quantization Works Well for On-Device Decode

Figure 3 is the system motivation. Autoregressive generation at batch size 1 is often memory-bound rather than compute-bound. For every new token, the model reads a large amount of weight data, while the activation footprint is much smaller. W4A16 does not quantize activations, but it can reduce weight bandwidth to about one quarter of FP16, so it is especially useful in the decode stage.

This also explains why AWQ and SmoothQuant target different deployment regimes:

  • SmoothQuant targets W8A8 so both activations and weights can enter INT8 GEMM;
  • AWQ targets W4A16 so memory-bound decode reads much less weight data;
  • if the workload is large-batch prefill, W8A8 or FP8 can be more attractive;
  • if the workload is interactive edge decoding, weight bandwidth reduction is more direct.

TinyChat: Format and Kernels Matter

W4A16 is not automatically fast because most hardware does not expose a direct INT4 x FP16 matrix instruction. A real kernel has to read packed 4-bit weights, unpack and dequantize them, and multiply them with FP16 activations.

TinyChat handles several engineering details:

  • on-the-fly dequantization: do not write dequantized FP16 weights back to DRAM; unpack and dequantize inside the matmul loop;
  • platform-aware packing: reorder 4-bit weights for ARM NEON, CUDA, and other backends so unpacking uses fewer SIMD or bitwise instructions;
  • kernel fusion: reduce launches and intermediate memory traffic for operations such as LayerNorm, QKV projection, positional embedding, and KV cache update.

This part is a useful reminder: reporting a compression ratio is not the same as reporting speed. Low-bit formats only accelerate inference if the decode path accounts for unpacking, scaling, metadata loads, and memory traffic.

Language Modeling Results

Table 4 is one of the main language-modeling results. It compares RTN, GPTQ, GPTQ-R, and AWQ across LLaMA/Llama-2 model sizes. My takeaways:

  • INT4-g128 RTN is not catastrophically bad, but AWQ is consistently better;
  • INT3-g128 creates a larger gap, which means AWQ matters more when the bit-width becomes aggressive;
  • GPTQ-R’s reordering trick can help on some models, but AWQ does not depend on reordering;
  • AWQ remains close to FP16 even on 70B models, so the method is not a small-model artifact.

I see AWQ as complementary to GPTQ. GPTQ behaves more like a local second-order reconstruction solver. AWQ behaves more like an activation-statistics-guided equivalent transform. Both use calibration data, but they use it in very different ways.

Instruction-Tuned Models

Instruction-tuned models test generalization. A quantization method that reconstructs a calibration set very well does not necessarily preserve chat or instruction-following behavior. The paper uses GPT-4 pairwise evaluation on Vicuna and shows that AWQ has more quantized wins and fewer quantized losses than RTN/GPTQ under INT3-g128.

This should not be overinterpreted as “GPT-4 evaluation is the final answer”. The useful signal is narrower: AWQ avoids heavy fitting to a small calibration set, so it appears less likely to damage instruction behavior under distribution shift.

Multi-Modal Models

The OpenFlamingo result is useful because VLMs are not pure text-only language models. AWQ quantizes only the language component, yet it clearly outperforms RTN/GPTQ on COCO captioning across few-shot settings. In INT4-g128 32-shot evaluation, the degradation shrinks from RTN’s -4.57 to AWQ’s -1.17.

The VILA table is even more direct: INT4-g128 is nearly lossless across multiple visual-language benchmarks. The point is not only that the numbers are good. It suggests that activation-aware scaling is not tightly bound to one text calibration distribution; it captures a lower-level channel magnitude statistic that transfers across model families and tasks.

Code, Math, and Extreme Low-Bit Settings

The MBPP and GSM8K results show that AWQ is not merely reducing WikiText perplexity. Code and math tasks are sensitive to generation quality. Under INT4-g128, AWQ stays close to FP16, and some numbers are even slightly higher than FP16. I would not read that as “quantization makes the model smarter”; it is more likely evaluation noise, sampling variance, or a mild regularization effect. The important point is that AWQ does not visibly destroy complex generation behavior.

Table 9 is also important. AWQ can be combined with GPTQ under an extreme INT2-g64 setting and further reduce the gap. This supports a clean division of labor: AWQ is an equivalent-transform or preprocessing step, while GPTQ is a quantization solver.

Calibration Robustness

Figure 8 best shows the character of AWQ.

The left plot shows that AWQ can work with fewer calibration sequences. This makes sense because it mainly estimates average activation scale rather than fitting a complex reconstruction solution.

The right plot shows that AWQ is less sensitive to calibration distribution mismatch. When calibration and evaluation domains are swapped between PubMed and Enron, GPTQ has a much larger perplexity gap. AWQ’s degradation is only about 0.5-0.6. This matches the paper’s claim: avoiding backpropagation and heavy reconstruction reduces the chance of overfitting the calibration set.

This does not mean AWQ can ignore calibration. Activation magnitude still comes from calibration data. If the target deployment domain has unusual activation patterns, it is still better to recalibrate with representative prompts.

Speed Results

TinyChat’s speed plot connects the algorithm to actual tokens per second. Compared with HuggingFace FP16, AWQ W4A16 improves throughput on RTX 4090, Jetson Orin, and RTX 4070 laptop GPUs. Some models that run out of memory in FP16 also become runnable in W4A16.

The VILA throughput table shows the same benefit for multi-modal models. VILA-13B is OOM in FP16 on RTX 4090, while AWQ W4A16 runs with a throughput of 99.0.

Figure 10 compares AutoGPTQ, llama.cpp, exllama, and TinyChat. The comparison is not perfectly apples-to-apples because these systems support different model families, packing formats, and kernel backends. The useful message is that TinyChat is not optimized only for a single LLaMA path. It covers StarCoder, StableCode, Mistral, Falcon, and other models, and it runs on edge devices such as Jetson Orin and Raspberry Pi.

AWQ vs. GPTQ / SmoothQuant / LLM.int8 / SpQR

These methods address related LLM quantization problems, but their runtime formats are quite different:

  • LLM.int8() targets mostly INT8 computation with an FP16 outlier path. It demonstrates that LLM activation outliers are real and that naive INT8 quantization is not enough.
  • SmoothQuant targets dense W8A8 INT8. Its key signal is the activation/weight max scale, and its main idea is to migrate activation quantization difficulty into the weights.
  • GPTQ targets dense W3/W4A16 weight-only quantization. Its core signal is calibration-based Hessian/reconstruction, so it behaves like a local second-order rounding solver.
  • AWQ also targets dense W3/W4A16 weight-only quantization, but the key signal is activation magnitude plus scale search. My interpretation is that AWQ protects activation-salient weight channels through an equivalent transform while preserving a kernel-friendly dense layout.
  • SpQR targets low-bit weights plus sparse correction. It stores some sensitive/outlier weights in a sparse path, which is closer to a near-lossless compression format but gives the runtime a more complex format.

AWQ and SmoothQuant look similar at the formula level because both use diagonal scaling as an equivalent transformation. The objective is different:

  • SmoothQuant mainly wants activations to be representable in INT8;
  • AWQ wants salient weights to have lower error under INT3/INT4 group quantization;
  • SmoothQuant moves difficulty from activations into weights;
  • AWQ uses activation statistics to decide which weight columns deserve protection.

The difference between AWQ and GPTQ is more engineering-oriented:

  • GPTQ’s strength is precise local reconstruction, especially at low bit-widths;
  • AWQ’s strength is simplicity, speed, and lower risk of calibration overfitting;
  • under extremely low bit-widths, AWQ scaling can be used before GPTQ, which is exactly what Table 9 explores.

Implementation Notes

If I were implementing AWQ from scratch, I would check these details first:

  1. Attach the calibration activation hook to the right tensor. AWQ uses per-input-channel scales, so the axis for linear, attention, and MLP layers must not be flipped.
  2. Verify the floating-point equivalent transform. Before quantization, should match up to numerical error.
  3. Watch group scale inflation. If many groups have much larger than 1, the scale is too aggressive and non-salient channels will be damaged.
  4. Do not judge only by a single-layer MSE. The final model should still be checked by perplexity or task metrics because local layer error is not always aligned with full-model behavior.
  5. Account for metadata. INT4 weights still need scales, zero points, and packing padding. The real memory footprint is not just the raw bit-width.
  6. Profile the kernel path. W4A16 will not be fast if unpacking/dequantization is slow or if dequantized weights are written back to DRAM.

A practical debug plot is: for each layer, draw channel activation magnitude, selected scale , and per-channel output error before and after quantization. When AWQ works correctly, high-activation channels should receive stronger protection, while ordinary channels should not see a global error increase.

Limitations

AWQ is not a universal low-bit quantization answer.

First, it mainly reduces weight memory and weight bandwidth. It does not solve KV cache memory. In long-context serving, KV cache can become the larger bottleneck, where KIVI, KV quantization, PagedAttention-style memory management, and related methods belong to a different line of work.

Second, AWQ still uses FP16/BF16 activations at runtime, so it does not get all the benefits of W8A8 integer GEMM. Choosing AWQ depends on whether the workload is decode memory-bound or prefill compute-bound.

Third, activation magnitude is a calibration statistic. The paper shows that AWQ is less sensitive to calibration distribution mismatch than GPTQ-style reconstruction, but a very unusual deployment input distribution can still require recalibration.

Finally, AWQ depends on kernel quality. A smaller model file does not imply faster end-to-end inference unless the W4A16 kernels are actually optimized.

Takeaway

AWQ’s core contribution can be compressed into one sentence: use activation statistics to identify important weight channels, then protect those channels through equivalent scaling while keeping the final model in a regular dense low-bit weight-only format.

This paper is best read between GPTQ and SmoothQuant. GPTQ teaches that calibration activations can guide weight rounding. SmoothQuant teaches that diagonal scaling can move quantization difficulty between activations and weights. AWQ combines both ideas into a lightweight W4A16 recipe and follows the system path all the way to TinyChat.

For me, the most valuable part of AWQ is not one particular perplexity number. It is the deployment principle: if protecting outliers would make the kernel irregular, first ask whether an equivalent transform can fold that protection back into a regular dense format.
