Paper: LLMLingua: Compressing Prompts for Accelerated Inference of Large Language Models

Code: https://aka.ms/LLMLingua

LLMLingua is an inference acceleration paper, but it does not start from kernels, KV-cache layout, or batching. It starts one layer earlier: if a long prompt can be compressed before it is sent to the target LLM, then prefill latency, KV-cache memory, and API token cost all shrink together.

That makes the paper interesting for RAG and agent systems. Those prompts often contain long retrieved passages, many demonstrations, or repeated instructions. A serving stack can optimize the attention kernels perfectly and still waste most of its work on prompt tokens that are not needed for the final answer.

Motivation

The method assumes a black-box target LLM and a smaller local language model. The smaller model estimates which prompt tokens or demonstrations are more important, and the compressed prompt is then sent to the target model.

The central idea is not summarization. Summarization asks a model to rewrite the prompt into natural text. LLMLingua treats the prompt as an information source and tries to preserve the parts that keep the target model’s answer distribution close to the answer distribution under the original prompt.

Coarse-to-Fine Compression

LLMLingua splits a prompt into instruction, demonstrations, and question. These parts do not tolerate compression equally. The instruction and question usually carry task constraints, while multiple demonstrations may contain redundancy. The paper therefore uses a budget controller before token-level compression.

The budget controller first allocates different compression rates to prompt components. For demonstrations, it computes perplexity with the small LM and keeps the higher-perplexity demonstrations first. The paper’s assumption is that these examples are more informative for the target task than low-perplexity or redundant ones.

After this coarse filtering, LLMLingua applies iterative token-level prompt compression.

The iterative part matters because one-shot token removal ignores dependency between retained tokens. If a token is removed, the conditional probability of later tokens changes. LLMLingua processes segments iteratively, recomputes conditional probabilities, and selects tokens under an adjusted compression threshold. This is slower than a single scoring pass, but the ablation shows that the extra dependency modeling is not cosmetic.

The third piece is distribution alignment. The small LM is only a proxy for the target black-box model. LLMLingua tries to reduce the mismatch between the small LM distribution and the target LLM distribution, because a token that looks unimportant to a small model may still matter to GPT-style or Claude-style models.

Main Results

The first result table covers ShareGPT conversation and Arxiv-March23 summarization. Both are context-heavy settings where removing prompt tokens should help serving cost, but deleting the wrong context can damage answer quality.

On ShareGPT, LLMLingua keeps stronger ROUGE/BERTScore numbers than the baselines under the reported token budgets. On Arxiv-March23, the paper reports similar behavior: the method reaches higher compression while preserving more of the summarization quality than sentence selection and Selective-Context.

The more interesting table for me is GSM8K and BBH, because these tasks punish missing intermediate reasoning details.

On GSM8K, LLMLingua reports 79.08 EM with a 5x compression ratio under the 1-shot constraint, compared with 78.85 for the full-shot prompt. Under heavier compression, it still reports 77.41 EM at 14x and 77.33 EM at 20x. BBH drops more sharply, which is expected: it contains tasks where one deleted condition can change the answer.

This is the right way to read the paper. The method is not saying that prompts are always 20x redundant. It is showing that some prompt formats, especially demonstration-heavy ones, contain enough redundancy for aggressive compression to be useful.

Ablation

The ablation table is the part that makes the method easier to trust. It separates the effects of iterative token compression, budget control, dynamic compression ratio, perplexity-based selection, distribution alignment, and naive stop-word removal.

Removing iterative token-level compression drops GSM8K EM from 79.08 to 72.93. Removing the budget controller gives 73.62. Random selection inside the budget controller gives 72.78. These are large enough drops to show that the method is not just “delete many tokens and hope the LLM survives.”

The stop-word row is also useful. Removing stop words gives only 1.3x compression and lower EM. Prompt compression cannot be reduced to a surface-level text-cleaning trick.

Serving Cost

Prompt compression affects serving in two places:

  1. The target model receives fewer prompt tokens, so prefill compute and initial KV-cache allocation decrease.
  2. The target model may generate shorter answers because the compressed prompt often contains less redundant context.

The generation-length plot shows a downward trend as the compression ratio increases. This effect is application-dependent, but it matters for end-to-end latency because decode work is paid per generated token.

The paper also reports measured latency on GSM8K with a V100-32G GPU.

The reported end-to-end latency moves from 8.6 seconds without LLMLingua to 4.9 seconds at 2x compression, 2.3 seconds at 5x compression, and 1.3 seconds at 10x compression. The small LM compression step is not free, but in this setup it is much cheaper than running the large target model on the original prompt.

For serving systems, this makes LLMLingua complementary to KV-cache quantization, paged attention, continuous batching, and fast attention kernels. Those systems reduce the cost of serving a sequence. LLMLingua tries to reduce the sequence before those systems see it.

Failure Boundary

The limitation is semantic rather than numerical. Kernel optimization should not change the model’s input. Prompt compression does. If the compressor removes the one sentence that contains the answer, the target LLM can become confidently wrong.

The paper’s compression-ratio curve makes this visible.

Performance stays relatively strong up to moderate compression, then drops when the ratio gets too aggressive. Around very high ratios such as 25x to 30x on GSM8K, all methods degrade. LLMLingua shifts the degradation point later than the baselines, but it does not remove the tradeoff.

I would treat the compression ratio as a deployment knob, not as a fixed paper number. A RAG system should tune it against answer faithfulness, citation retention, and failure cases from its own traffic.

Practical Notes

Where I would try LLMLingua:

  • RAG prompts with long retrieved contexts and repeated boilerplate.
  • Agent traces where previous observations contain redundancy.
  • Demonstration-heavy prompts where examples can be ranked and removed.
  • API inference where prompt tokens are a direct cost center.

Where I would be careful:

  • Legal, medical, or financial prompts where one clause changes the answer.
  • Tool-use prompts where exact JSON schemas or command constraints must survive.
  • Debugging sessions where the model needs the full history, including failed attempts.
  • Any evaluation that only measures compression ratio and not evidence retention.

For production use, I would log both the original prompt and compressed prompt, then diff removed spans during debugging. Without that audit trail, a wrong answer is hard to attribute: it could come from the target LLM, the retrieved context, or the compressor deleting the necessary evidence.

Takeaway

LLMLingua is useful because it reframes part of LLM serving as input selection. The cheapest prefill token is the one never sent to the target model. The hard part is making sure that deleted tokens are actually redundant for the task, not just low-probability under a small proxy model.
