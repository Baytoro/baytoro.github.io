Paper: LLMLingua: Compressing Prompts for Accelerated Inference of Large Language Models

LLMLingua attacks inference cost before the model runs. Instead of making attention faster for a long prompt, it tries to remove tokens that the target model does not need.

Motivation

Long prompts increase TTFT, KV-cache memory, and API cost. RAG and agent prompts often contain redundant context. If unimportant tokens can be removed while preserving the answer, all downstream serving costs shrink.

The figure shows the prompt-compression pipeline: a smaller model estimates token importance and the prompt is compressed before target-model inference.

Methodology

LLMLingua uses a coarse-to-fine compression process:

  1. allocate a compression budget across prompt components;
  2. use a smaller language model to estimate token importance;
  3. remove low-importance tokens while preserving the information needed by the target LLM.

This is not KV-cache quantization. It reduces the sequence length before prefill begins.

Results

The paper reports large token reductions on reasoning and QA tasks while preserving much of the final answer quality. The serving benefit is direct: fewer tokens mean less prefill compute and less KV cache.

Takeaway

LLMLingua is useful because it reminds me that not all acceleration is a CUDA problem. Sometimes the cheapest token is the one never sent to the LLM. The risk is task dependence: compression must not delete the evidence needed for the answer.

Prompt Compression Is Not Summarization

LLMLingua is not simply asking another model to summarize the prompt. It tries to preserve the tokens that are important for the target model’s answer while deleting low-importance tokens. This is a compression problem under an answer-quality constraint.

Serving Cost Model

If a prompt shrinks from tokens to tokens, prefill compute and initial KV cache also shrink roughly with . Decode cost per generated token is less directly affected, but shorter context reduces attention over previous tokens.

This makes prompt compression especially attractive for RAG, where prompts often contain long retrieved passages with redundancy.

Risk

The failure mode is deleting the one fact needed for the answer. Unlike kernel-level acceleration, prompt compression can change model behavior semantically. It must be evaluated on the application distribution.

Source-Level Notes

LLMLingua treats prompt length as an inference cost. If a long prompt can be compressed before sending it to the target LLM, both prefill latency and KV-cache memory decrease.

The method uses a smaller language model to estimate token importance and applies budget-controlled compression. The objective is not generic summarization. It is to remove tokens that are less necessary for the downstream LLM to answer the query.

Serving Reading

The cost model is straightforward. Prefill attention cost grows with prompt length, and the produced KV cache also grows with prompt length:

Compressing prompts attacks the problem before kernels and schedulers see it.

The risk is semantic loss. Unlike quantization, prompt compression changes the input. This can remove evidence, constraints, or formatting details. I would treat it as an application-level acceleration method that needs task-specific evaluation, especially for RAG and instruction-heavy prompts.

Experiment Reading

Prompt compression needs task-level evaluation. A compressed prompt can preserve perplexity-like fluency while dropping a fact needed for the answer. For RAG, I would measure answer accuracy and citation/evidence retention, not only compression ratio.

The budget controller is important because different prompts tolerate different compression. A short instruction with precise constraints may be less compressible than a long retrieved context with redundancy.

The serving value is clearest before prefill. Reducing prompt tokens reduces prefill compute, KV cache memory, and sometimes queueing delay. It is complementary to vLLM, KIVI, and FlashInfer because it shrinks the workload those systems must serve.

Reproduction Checklist

The safe reproduction is task-specific. On QA or RAG, compare exact-match or answer faithfulness before and after compression. Also record whether the supporting evidence sentence survives compression. A high compression ratio is not useful if it deletes the fact needed for the answer.

I would test different budgets and plot quality versus prompt tokens. The curve matters more than one point: it tells whether the prompt has redundancy or whether the compressor is removing constraints too early.

Boundary / Failure Mode

The method also changes accountability. If the final answer is wrong, the error may come from the base LLM or from removed prompt evidence. For debugging, I would store the compressed prompt alongside the original prompt and highlight removed spans. That makes prompt compression auditable, which matters in RAG and tool-use workflows where missing one constraint can change the answer.
